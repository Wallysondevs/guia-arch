Arch Manutenção Periódica

O Arch não tem "versão nova" a cada dois anos: ele muda um pouco toda semana (rolling release). Em troca, pede um pouco de cuidado regular. Quinze minutos por semana evitam quase todos os problemas das aulas de recuperação. Esta aula é o checklist, com o que cada comando mostra numa máquina saudável.

Você vai aprender
  • O que conferir antes de atualizar e como atualizar com segurança.
  • Cuidar de .pacnew, órfãos e cache de pacotes.
  • Procurar serviços com falha e erros no journal.
  • Acompanhar espaço em disco, pacotes do AUR, backups e o kernel de reserva.
  • Juntar tudo num script de checagem e numa tabela semanal × mensal.

Cada linha está explicada abaixo, com a saída real da máquina do guia (que está saudável: a maioria das respostas é "nada a fazer", e é isso que você quer ver).

1. Notícias

Quando uma atualização exige ação manual, o Arch publica uma notícia antes. Ler antes de atualizar é a regra número um. Pelo navegador, em archlinux.org/news (há RSS e a lista de e-mail arch-announce), ou pelo yay:

$ yay -Pw
$ echo $?
0

-Pw (print news) mostra só as notícias mais novas que os seus pacotes. Nenhuma saída = nada novo desde a última atualização. Com -Pww, ele mostra todas as recentes; um trecho real (a lista vai da mais antiga para a mais nova):

$ yay -Pww | head -12
2025-11-05 waydroid >= 1.5.4-3 update may require manual intervention
The waydroid package prior to version 1.5.4-2 (including aur/waydroid) creates Python byte-code files (.pyc) at runtime which were untracked by pacman. This issue has been fixed in 1.5.4-3, where byte-compiling these files is now done during the packaging process.

As a result, the upgrade may conflict with the unowned files created in previous versions. If you encounter errors like the following during the update:


error: failed to commit transaction (conflicting files)

waydroid: /usr/lib/waydroid/tools/__pycache__/__init__.cpython-313.pyc exists in filesystem

waydroid: /usr/lib/waydroid/tools/actions/__pycache__/__init__.cpython-313.pyc exists in filesystem

A notícia continua com a solução exata: pacman -Syu --overwrite /usr/lib/waydroid/tools/\*__pycache__/\*. É o erro de arquivos conflitantes com a receita pronta. Os títulos mais recentes, em outubro de 2026, eram 2026-06-12 Active AUR malicious packages incident, 2026-07-21 virtualbox-ext-vnc >= 7.2.12-2 requires manual intervention e 2026-09-22 Mkinitcpio >=42 requires manual intervention for TPM2-based unlocking of LUKS devices: se você usa o que o título cita, leia antes de atualizar.

2. Atualizar

O comando é sempre o mesmo: sudo pacman -Syu (ou yay, que inclui o AUR). Tudo sobre ler a transação está em Atualizar o Sistema. Para só saber se há atualizações, sem mexer na base do sistema, use o checkupdates (pacote pacman-contrib), que baixa as bases numa pasta temporária:

$ checkupdates
$ echo $?
2                         « 2 = nenhuma atualização; 0 = há (e ele lista)
Nunca pacman -Sy sozinho

Para "ver se tem atualização", não rode pacman -Sy: ele atualiza a base sem atualizar os pacotes, e o próximo pacman -S algo vira uma atualização parcial. Use checkupdates.

Com que frequência? Uma vez por semana é um bom ritmo. Ficar meses sem atualizar é o que mais dá trabalho (chaveiro velho, várias notícias acumuladas). E não atualize logo antes de uma apresentação ou viagem: atualize quando tiver tempo de reiniciar e conferir.

Depois de atualizar: precisa reiniciar?

$ pacman -Q linux linux-lts; uname -r
linux 7.2.10.arch1-1
linux-lts 6.18.57-1
7.2.10-arch1-1           « o que roda = o instalado: não precisa

Se o uname -r mostrar uma versão diferente da do pacote linux, o kernel foi atualizado e os módulos antigos já sumiram: reinicie logo (veja o item 8 de Erros de Atualização). Atualizações de systemd, glibc e drivers de vídeo também pedem um reboot.

3. Arquivos .pacnew

$ pacdiff -o
$ echo $?
0

pacdiff -o (output) só lista os .pacnew e .pacsave pendentes; nenhuma linha = nada a fazer. Quando houver, sudo pacdiff mostra cada um e pergunta o que fazer. Como juntar as versões está em .pacnew e .pacsave.

4. Órfãos

Órfãos são pacotes que entraram como dependência de algo que você já removeu, e que ninguém mais usa:

$ pacman -Qdt
$ echo $?
1                         « 1 = nenhum órfão (o pacman não achou nada)
pacman -Q
Consulta pacotes instalados.
-d
Só os instalados como dependência.
-t
Só os que nenhum outro pacote exige (unrequired).

Quando houver órfãos, revise a lista e remova com pacman -Qdtq | sudo pacman -Rns - (-q imprime só os nomes; o - no fim lê a lista da entrada). Sem órfãos, esse comando reclama:

#> pacman -Qdtq | pacman -Rns -
erro: argumento "-" especificado com entrada padrão vazia
#> echo $?
1
Leia a lista antes de remover

Um pacote que você usa, mas que entrou como dependência (por exemplo, um programa instalado junto com outro e depois o "outro" foi removido), aparece como órfão. Se quiser mantê-lo, marque-o como explícito: sudo pacman -D --asexplicit pacote. Mais em Cache e Órfãos.

5. Cache de pacotes

Todo pacote baixado fica em /var/cache/pacman/pkg/, inclusive as versões antigas. É útil para voltar uma versão (downgrade), mas cresce sem parar:

$ du -sh /var/cache/pacman/pkg
1,3G	/var/cache/pacman/pkg
$ ls /var/cache/pacman/pkg | wc -l
820
$ paccache -d
==> no candidate packages found for pruning
$ paccache -dk1
==> no candidate packages found for pruning
$ paccache -du
==> no candidate packages found for pruning
paccache
O limpador de cache (pacote pacman-contrib).
-d
dry run: só mostra o que apagaria. Troque por -r (remove) para apagar de fato (com sudo).
-k1
keep: quantas versões manter de cada pacote (o padrão é 3).
-u
Só os pacotes que não estão mais instalados (uninstalled).

Nenhum candidato porque a máquina do guia é nova: só existe uma versão de cada pacote no cache (os 820 arquivos são os pacotes e as assinaturas .sig). Num sistema com meses de uso, o mesmo -d lista dezenas de arquivos e o espaço a liberar.

O próprio pacman-contrib traz um timer semanal que faz isso sozinho (paccache -r, mantendo 3 versões). Ele vem desligado:

$ systemctl cat paccache.timer | grep -E "^On|^Desc|^Persistent"
Description=Discard unused packages weekly
OnCalendar=weekly
Persistent=true
$ systemctl cat paccache.service | grep -E "^Exec"
ExecStart=/usr/bin/paccache -r $PACCACHE_ARGS

Para ligar: sudo systemctl enable --now paccache.timer (veja Timers e Tarefas).

6. Serviços com falha

$ systemctl --failed
  UNIT LOAD ACTIVE SUB DESCRIPTION

0 loaded units listed.             « tudo certo
$ systemctl --user --failed
  UNIT LOAD ACTIVE SUB DESCRIPTION

0 loaded units listed.

Se aparecer alguma unidade, investigue com systemctl status NOME e journalctl -u NOME -b (veja systemctl e Serviços). O --user confere os serviços da sua sessão (som, por exemplo).

7. Erros no journal

journalctl -p 3 -b mostra as mensagens de prioridade "erro" ou pior (-p 3) deste boot (-b). Na máquina do guia, as primeiras são estas:

$ journalctl -b -p 3 --no-pager | head -5
out 16 13:06:28 archlinux kernel: virt/tdx: TDX not supported by the host platform
out 16 13:06:28 archlinux kernel: ata1.00: Read log 0x00 page 0x00 failed, Emask 0x1
out 16 13:06:28 archlinux kernel: vmwgfx 0000:00:02.0: [drm] *ERROR* vmwgfx seems to be running on an unsupported hypervisor.
out 16 13:06:28 archlinux kernel: vmwgfx 0000:00:02.0: [drm] *ERROR* This configuration is likely broken.
out 16 13:06:28 archlinux kernel: vmwgfx 0000:00:02.0: [drm] *ERROR* Please switch to a supported graphics device to avoid problems.

Parecem graves, mas são normais nesta máquina: é uma máquina virtual, e o kernel reclama do processador virtual (TDX), do disco virtual e da placa de vídeo virtual. (O nome archlinux nas primeiras linhas é de antes de o sistema ler o /etc/hostname.) A manutenção não é zerar essa lista, e sim notar o que é novo: um erro de disco (I/O error, csum failed), de sistema de arquivos ou de um serviço que você usa. Mais filtros em Logs (journalctl).

O próprio journal ocupa espaço, mas é limitado sozinho (por padrão, até 10% do sistema de arquivos, no máximo 4 GiB):

#> journalctl --disk-usage
Archived and active journals take up 56M in the file system.

8. Espaço em disco

$ df -h / /boot
Sist. Arq.      Tam. Usado Disp. Uso% Montado em
/dev/sda3        25G  5,2G   19G  23% /
/dev/sda1      1022M   93M  930M  10% /boot

Fique de olho principalmente no /boot: cada kernel com o seu initramfs ocupa dezenas de MiB e, se ele encher, a próxima atualização do kernel falha no meio. A partir de ~80% em /, comece a limpar: cache (item 5), journal, ~/.cache (du -sh ~/.cache deu 11M aqui), e snapshots velhos se a raiz for Btrfs. Para achar o que ocupa espaço, du -sh pasta/* (veja lsblk, df, du).

A última linha é a mais importante: alguém marcou o paru-bin como desatualizado no site do AUR (o mantenedor ainda não publicou a versão nova). Um pacote do AUR abandonado por muito tempo pode parar de funcionar quando as bibliotecas do Arch avançam. Rotina: yay -Syu (atualiza repositórios e AUR), e de vez em quando conferir se você ainda usa cada pacote de pacman -Qm. Depois de uma atualização grande do Python ou de uma biblioteca, pacotes do AUR compilados podem precisar ser recompilados (veja AUR com Segurança).

10. Backups, snapshots e o kernel de reserva

  • Backup em outro disco (externo ou nuvem) dos seus arquivos e de /etc. Uma lista dos pacotes ajuda a reinstalar: pacman -Qqe > pacotes.txt. E, uma vez por mês, teste restaurar um arquivo: backup que nunca foi restaurado é só esperança.
  • Snapshots, se a raiz for Btrfs: sudo snapper list para ver se os automáticos estão sendo criados e limpos (Snapshots).
  • Kernel de reserva: linux-lts instalado (a saída do item 2 mostra que a máquina do guia tem) e aparecendo no GRUB (veja Recuperar o Boot).
  • Um pendrive do Arch recente na gaveta, para o resgate com chroot.

Tudo junto: um script de checagem

Um script que só consulta (não muda nada), para rodar como usuária comum antes ou depois de atualizar:

#!/usr/bin/env bash
# checagem.sh — revisão rápida do Arch (só consulta, não muda nada)
echo "== Atualizações pendentes"
checkupdates || echo "(nenhuma)"
echo "== Órfãos"
pacman -Qdtq || echo "(nenhum)"
echo "== Arquivos .pacnew"
pacdiff -o
echo "== Serviços com falha"
systemctl --failed --no-legend
echo "== Erros neste boot"
journalctl -p 3 -b --no-pager | wc -l
echo "== Espaço"
df -h / /boot
echo "== Cache do pacman"
du -sh /var/cache/pacman/pkg
echo "== Kernel"
echo "rodando: $(uname -r) | instalado: $(pacman -Q linux)"

$ ./checagem.sh
== Atualizações pendentes
(nenhuma)
== Órfãos
(nenhum)
== Arquivos .pacnew
== Serviços com falha
== Erros neste boot
112
== Espaço
Sist. Arq.      Tam. Usado Disp. Uso% Montado em
/dev/sda3        25G  5,2G   19G  23% /
/dev/sda1      1022M   93M  930M  10% /boot
== Cache do pacman
1,3G	/var/cache/pacman/pkg
== Kernel
rodando: 7.2.10-arch1-1 | instalado: linux 7.2.10.arch1-1
$ echo $?
0

O || echo "(nenhuma)" aproveita o código de saída: checkupdates e pacman -Qdtq devolvem diferente de 0 quando não acham nada. O número de erros (112) é a contagem de linhas do item 7, inflada pelos testes de outras aulas nesta máquina; o que importa é comparar com a semana anterior. Salve a saída de cada semana (./checagem.sh > checagem-$(date +%F).txt) e use diff entre duas para ver o que mudou.

Experimente

Missão: faça a checagem de serviços da semana: liste as unidades do systemd que falharam.

Missão: agora a checagem do mês: procure pacotes órfãos.

Quando não funciona

"no candidate packages found for pruning"

O que aconteceu: não é erro: o paccache não achou nada para apagar com os critérios dados (poucas versões no cache).

Como resolver: nada. Se o cache está grande mesmo assim, veja quantas versões você mantém (-k) e os pacotes desinstalados (-u). Para apagar tudo, existe o sudo pacman -Scc, mas aí o downgrade pelo cache deixa de funcionar.

"argumento "-" especificado com entrada padrão vazia"

O que aconteceu: o pacman -Qdtq | pacman -Rns - não recebeu nenhum nome: não havia órfãos.

Como resolver: nada; rode pacman -Qdt antes para ver se há algo.

"XML syntax error" no yay -Pw 
$ yay -Pww
 -> XML syntax error on line 6: element <hr> closed by </body>

O que aconteceu: o site do Arch respondeu com uma página de erro em vez da lista de notícias (sobrecarga ou manutenção). Aconteceu de verdade durante a escrita desta aula.

Como resolver: abra archlinux.org/news no navegador, ou tente mais tarde. Não pule a leitura só porque o yay falhou.

Resumo

  • Toda semana: notícias, pacman -Syu, .pacnew, systemctl --failed, reiniciar se o kernel mudou.
  • Todo mês: órfãos, cache (paccache), journalctl -p 3 -b, espaço em disco, AUR, teste de backup.
  • Sempre: kernel de reserva, pendrive do Arch, snapshots se usar Btrfs.
  • Use as ferramentas que só consultam (checkupdates, -d do paccache, pacdiff -o) antes das que mudam.

Na Arch Wiki: o checklist oficial está em System maintenance (em português); limpeza do cache e órfãos em Pacman/Tips and tricks; os .pacnew em Pacman/Pacnew and Pacsave; e o journal em Systemd/Journal.
