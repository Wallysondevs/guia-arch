Usuários e grupos

O Linux foi feito para várias pessoas usarem o mesmo computador sem mexer nas coisas umas das outras. Cada pessoa (e cada serviço) é um usuário; usuários se juntam em grupos para dividir permissões. Nesta aula você cria, muda e apaga usuários no Arch, entende os arquivos onde eles moram e descobre quais grupos ainda fazem sentido hoje.

Você vai aprender
  • O que são UID, GID, grupo principal e grupos extras.
  • Ler /etc/passwd, /etc/group e por que /etc/shadow é fechado.
  • Criar usuários com useradd (no Arch não existe adduser) e definir a senha com passwd.
  • Pôr e tirar de grupos com usermod -aG e gpasswd -d, e a armadilha do -G sem -a.
  • Apagar com userdel -r e escolher os grupos certos no Arch (wheel, systemd-journal… e por que não video/audio).

A aula sudo, root e Usuários (Nível 1) mostrou o básico de root e sudo. Aqui vamos mais fundo. Os exemplos usam um usuário de teste, teste-a6, criado e apagado na VM do guia.

Quem sou eu: id e groups

$ id
uid=1000(ana) gid=1000(ana) grupos=1000(ana),998(wheel)
$ groups
ana wheel
uid=1000(ana)
UID (user ID): o número do usuário. O sistema guarda números; o nome é só para nós. No Arch, pessoas começam em 1000.
gid=1000(ana)
Grupo principal (group ID): o grupo que os arquivos novos da ana recebem. No Arch, cada usuário ganha um grupo com o mesmo nome (user private group).
grupos=…,998(wheel)
Grupos extras (suplementares). O wheel é o dos administradores: é por ele que a ana pode usar sudo.

Com um nome depois, eles mostram outro usuário: id root, groups ana.

Missão: mostre o seu UID, o seu grupo principal e os seus grupos extras com um único comando.

Onde os usuários moram: três arquivos

/etc/passwd: a lista de usuários

Uma linha por usuário, campos separados por :. Apesar do nome, as senhas não ficam mais aqui (o x manda olhar o /etc/shadow). Algumas linhas reais:

$ grep -E '^(root|ana|http|nobody):' /etc/passwd
root:x:0:0::/root:/usr/bin/bash
http:x:33:33::/srv/http:/usr/bin/nologin
nobody:x:65534:65534:Kernel Overflow User:/:/usr/bin/nologin
ana:x:1000:1000::/home/ana:/bin/bash
CampoNa linha da anaSignificado
1anaNome de login
2xSenha: está no /etc/shadow
31000UID
41000GID do grupo principal
5(vazio)Comentário, o "nome completo" (GECOS). O do nobody é Kernel Overflow User.
6/home/anaPasta pessoal
7/bin/bashShell de login. /usr/bin/nologin = conta que não pode entrar (serviços).

O http é o usuário com que o servidor web roda: ele existe, mas não pode fazer login. Rodar serviços com usuários próprios limita o estrago se um deles for invadido.

/etc/group: a lista de grupos

$ getent group wheel
wheel:x:998:ana
$ grep -E '^(wheel|ana|video|audio):' /etc/group
wheel:x:998:ana         « nome : senha (x) : GID : membros extras, separados por vírgula
audio:x:995:            « sem membros
video:x:983:
ana:x:1000:             « o grupo principal da ana; ela não aparece listada aqui, e não precisa

getent (get entries) consulta as bases de usuários e grupos do sistema; é mais correto que o grep, porque também acha usuários que não estão nos arquivos (de rede, do systemd-homed…).

/etc/shadow: as senhas, trancadas

$ ls -l /etc/passwd /etc/group /etc/shadow /etc/gshadow
-rw-r--r-- 1 root root  825 16 out 13:39 /etc/group
-rw------- 1 root root  726 16 out 13:39 /etc/gshadow
-rw-r--r-- 1 root root 1451 16 out 13:39 /etc/passwd
-rw------- 1 root root  771 16 out 13:39 /etc/shadow
$ cat /etc/shadow
cat: /etc/shadow: Permissão negada

passwd e group são rw-r--r--: todos leem (os programas precisam saber que o UID 1000 se chama ana). shadow e gshadow são rw-------: só o root lê e escreve. Lá ficam as senhas, guardadas como hash (uma "impressão digital" da senha, que não dá para desfazer). Como ler essas permissões está em Permissões. Com sudo, a linha de um usuário recém-criado e já com senha (cortada):

$ sudo grep teste-a6 /etc/shadow | cut -c1-40
teste-a6:$y$j9T$ZL64caZUBHwNsX4UFKG9.1$Q

O $y$ no começo do hash indica o yescrypt, o ENCRYPT_METHOD do login.defs. Um ! no lugar do hash quer dizer "sem senha válida: login por senha bloqueado".

Não edite esses arquivos à mão

Um : a mais no /etc/passwd pode impedir todo mundo de entrar. Use os comandos desta aula; se precisar mesmo editar, use sudo vipw e sudo vigr, que travam o arquivo e conferem o formato. O shadow.timer do Arch confere a integridade deles todo dia (veja Timers e Tarefas).

Criar um usuário: useradd

"adduser"? Não no Arch

Quem vem do Debian ou do Ubuntu procura o adduser, um assistente que pergunta nome, senha e cria tudo. No Arch ele não existe, nem nos repositórios oficiais:

$ adduser teste
bash: adduser: comando não encontrado
$ echo $?
127
$ pacman -F /usr/bin/adduser; echo $?
1                                « nenhum pacote oficial tem esse arquivo
$ pacman -F /usr/bin/useradd
usr/bin/useradd pertence a core/shadow 4.20.0.arch1-1

O comando do Arch é o useradd, do pacote shadow (o mesmo que existe em todas as distros, por baixo do adduser). Ele não pergunta nada: faz exatamente o que as opções mandam.

As opções

sudo useradd
Cria um usuário (precisa de root).
-m
create home: cria a pasta pessoal. Sem ele, não há pasta.
-G wheel
Grupos extras, separados por vírgula (-G wheel,systemd-journal).
-s /bin/bash
O shell de login.
-c "Ana Souza"
O comentário (nome completo).
teste-a6
O nome: minúsculas, números, - e _; começa com letra.

Foi exatamente assim que a ana nasceu, na instalação da VM:

#> arch-chroot /mnt useradd -m -G wheel -s /bin/bash ana
#> arch-chroot /mnt id ana
uid=1000(ana) gid=1000(ana) groups=1000(ana),998(wheel)

(Durante a instalação o sistema ainda estava em inglês: groups em vez de grupos.) Agora, um usuário comum, só com -m:

$ id teste-a6
id: “teste-a6”: usuário inexistente
$ sudo useradd -m teste-a6
$ echo $?
0                                 « silencioso quando dá certo
$ id teste-a6
uid=1001(teste-a6) gid=1001(teste-a6) grupos=1001(teste-a6)
$ sudo ls -la /home/teste-a6
total 20
drwx------ 2 teste-a6 teste-a6 4096 16 out 13:35 .        « 700: só o dono entra (HOME_MODE)
drwxr-xr-x 4 root     root     4096 16 out 13:39 ..
-rw-r--r-- 1 teste-a6 teste-a6   21 15 set 16:47 .bash_logout
-rw-r--r-- 1 teste-a6 teste-a6   57 15 set 16:47 .bash_profile
-rw-r--r-- 1 teste-a6 teste-a6  172 15 set 16:47 .bashrc

Os três arquivos vieram de /etc/skel (skeleton, "esqueleto"): tudo o que estiver lá é copiado para a pasta de cada usuário novo. E as linhas que o useradd escreveu:

$ sudo grep teste-a6 /etc/passwd /etc/group /etc/shadow /etc/gshadow
/etc/passwd:teste-a6:x:1001:1001::/home/teste-a6:/usr/bin/bash
/etc/group:teste-a6:x:1001:
/etc/shadow:teste-a6:!:20742::::::            « "!" = ainda sem senha
/etc/gshadow:teste-a6:!::

Repare que o shell do teste-a6 é /usr/bin/bash, e o da ana, /bin/bash. No Arch, /bin é um link para /usr/bin: é o mesmo programa. O padrão vem de /etc/default/useradd, que só o root lê:

$ sudo useradd -D
GROUP=1000
GROUPS=
HOME=/home
INACTIVE=-1
EXPIRE=
SHELL=/usr/bin/bash
SKEL=/etc/skel
USRSKEL=/usr/etc/skel
CREATE_MAIL_SPOOL=yes
BTRFS_SUBVOLUME_HOME=no
BTRFS_SUBVOLUME_SYSTEM=no
LOG_INIT=yes

Definir a senha: passwd

Um usuário criado não tem senha (o !): ninguém consegue entrar como ele. O passwd define:

$ sudo passwd -S teste-a6
teste-a6 L 2026-10-16 -1 -1 -1 -1        « L = locked (sem senha utilizável)
$ sudo passwd teste-a6
Nova senha:                              « nada aparece enquanto você digita
Redigite a nova senha:
passwd: senha atualizada com sucesso
$ sudo passwd -S teste-a6
teste-a6 P 2026-10-16 -1 -1 -1 -1        « P = tem senha (password)
passwd
Sem nome: troca a sua senha (pede a atual antes). Não precisa de sudo.
sudo passwd nome
O root troca a senha de qualquer um, sem saber a antiga.
-S
status: estado da senha (P, L, NP = sem senha nenhuma), data da última troca e prazos.
-l / -u
Trava / destrava a senha (põe/tira um ! no shadow).

Os prazos (validade da senha, aviso de expiração) se veem com chage -l:

$ sudo chage -l teste-a6
Última mudança de senha					: out 16, 2026
Senha expira					: nunca
Senha inativa					: nunca
Conta expira						: nunca
Número máximo de dias entre troca de senhas		: -1
Número de dias de avisos antes da expiração da senha	: -1

Entrar como o novo usuário

su - nome (substitute user) abre um shell como outro usuário, pedindo a senha dele. O - faz um login completo (vai para a pasta dele, lê o .bash_profile):

$ su - teste-a6
Senha:
$ whoami
teste-a6
$ pwd
/home/teste-a6
$ sudo pacman -Q bash
[sudo] senha para teste-a6:
teste-a6 não está no arquivo sudoers.        « não está no wheel: sem sudo
$ echo $?
1
$ exit

O sudo recusou porque o teste-a6 não está no grupo wheel (é a linha %wheel ALL=(ALL:ALL) ALL do /etc/sudoers que libera; veja sudo, root e Usuários). A tentativa fica registrada no journal.

Grupos: usermod -aG, gpasswd -d

Pôr num grupo

sudo usermod
Modifica um usuário que já existe.
-a
append: acrescenta aos grupos que ele já tem.
-G video
O(s) grupo(s) extra(s).
teste-a6
O usuário.
$ sudo usermod -aG video teste-a6
$ id teste-a6
uid=1001(teste-a6) gid=1001(teste-a6) grupos=1001(teste-a6),983(video)

A armadilha: -G sem -a

Sem o -a, o -G substitui a lista inteira de grupos extras. Veja o video sumir:

$ sudo usermod -G audio teste-a6
$ id teste-a6
uid=1001(teste-a6) gid=1001(teste-a6) grupos=1001(teste-a6),995(audio)     « o video foi embora!
$ sudo usermod -aG video teste-a6
$ id teste-a6
uid=1001(teste-a6) gid=1001(teste-a6) grupos=1001(teste-a6),995(audio),983(video)
Nunca rode usermod -G nos seus grupos sem o -a

Se a ana rodasse sudo usermod -G video ana, sairia do wheel e perderia o sudo na hora (e não conseguiria mais rodar sudo para consertar). A saída seria entrar como root (su -, se o root tem senha) ou o resgate pelo pendrive (Resgate com chroot). Decore: -aG, sempre juntos.

Tirar de um grupo

$ sudo gpasswd -d teste-a6 audio
Removendo usuário teste-a6 do grupo audio
$ id teste-a6
uid=1001(teste-a6) gid=1001(teste-a6) grupos=1001(teste-a6),983(video)

gpasswd (group password, por razões históricas) gerencia membros de grupos: -a usuário grupo acrescenta, -d usuário grupo tira (delete). Criar e apagar grupos: sudo groupadd nome, sudo groupdel nome.

Mudou de grupo? Saia e entre de novo

Os grupos de uma sessão são lidos no login. Depois de um usermod -aG no seu próprio usuário, o id do terminal aberto ainda mostra os grupos antigos. Saia da sessão (ou reinicie) e entre de novo. Para testar na hora, num terminal só: newgrp nome-do-grupo ou su - $USER.

Quais grupos usar no Arch?

Guias antigos mandam colocar o usuário em audio, video, storage, optical… Isso era necessário antes do systemd. Hoje, o systemd-logind dá acesso ao som, ao vídeo e aos pendrives para quem está sentado no computador (a sessão ativa), automaticamente, por ACLs. A Arch Wiki (página Users and groups, seção "Pre-systemd groups") avisa que pôr usuários nesses grupos pode até quebrar coisas: o grupo audio, por exemplo, atrapalha a troca rápida de usuário.

GrupoPara quêColocar?
wheelAdministradores: sudo (depois de liberar no sudoers), ler todo o journal, polkitSim, para quem administra
systemd-journalLer todos os logs, sem outro poder (veja Logs)Para quem só precisa ler logs
admTambém lê todo o journal (tradição de outras distros)Opcional
uucpPortas seriais e USB-serial (Arduino, modems): /dev/ttyUSB0, /dev/ttyACM0Se você programa placas
kvmUsar /dev/kvm para máquinas virtuais (veja KVM)Se for usar KVM/QEMU
lpImpressoras na porta paralelaRaramente
audio, video, storage, optical, inputAcesso direto ao hardware, mesmo fora da sessãoNormalmente não: o logind já cuida. Só em casos especiais (som em sessão remota, por exemplo).

Grupos de programas específicos aparecem quando você instala o programa (por exemplo, docker; veja Docker e Podman). Para ver todos os grupos da máquina: cut -d: -f1 /etc/group.

Mudar outras coisas: usermod

Apagar: userdel

sudo userdel
Apaga o usuário dos arquivos passwd, shadow, group.
-r
remove: apaga também a pasta pessoal e a caixa de correio local. Sem ele, /home/nome fica para trás.
$ pgrep -u teste-a6; echo $?
1                                    « confira antes: nenhum processo dele rodando
$ sudo userdel -r teste-a6
userdel: teste-a6 spool de mail (/var/spool/mail/teste-a6) não foi encontrado
$ echo $?
0                                    « o aviso é inofensivo: deu certo
$ id teste-a6
id: “teste-a6”: usuário inexistente
$ ls /home
ana

O aviso aparece porque o Arch não cria caixa de correio para usuários novos (CREATE_MAIL_SPOOL=no no /etc/default/useradd), e o userdel -r tenta apagar uma que não existe. Pode ignorar.

Arquivos fora da pasta pessoal ficam órfãos

O -r apaga só a pasta pessoal. Arquivos do usuário em /tmp, /srv ou num HD externo continuam lá, com o UID antigo no lugar do dono. Se depois você criar outro usuário, ele pode receber o mesmo UID e virar dono desses arquivos sem querer (aconteceu na VM do guia: o teste-a6 recebeu o UID 1001, que antes era de outro usuário de teste, e herdou o journal dele). Procure antes com sudo find /caminho -uid 1001, numa pasta específica.

Quando não funciona

"usuário 'x' já existe" 
$ sudo useradd -m teste-a6
useradd: usuário 'teste-a6' já existe
$ echo $?
9

Como resolver: escolha outro nome, ou mude o existente com usermod. Veja quem é com id teste-a6.

"grupo 'x' não existe" 
$ sudo usermod -aG grupoinexistente teste-a6
usermod: grupo 'grupoinexistente' não existe
$ echo $?
6

O que aconteceu: erro de digitação, ou o grupo é criado por um pacote que você ainda não instalou (docker, libvirt).

Como resolver: getent group nome para conferir; instale o pacote ou crie com sudo groupadd nome.

"x não está no arquivo sudoers"

O que aconteceu: o usuário não está no wheel (ou a linha %wheel do sudoers está comentada).

Como resolver: de uma conta que tem sudo (ou como root): sudo usermod -aG wheel nome; depois, o usuário sai e entra de novo.

Coloquei no grupo, mas não funcionou

O que aconteceu: a sessão aberta ainda tem os grupos antigos.

Como confirmar: id (sessão atual) mostra sem o grupo; id nome (lido dos arquivos) mostra com.

Como resolver: saia da sessão e entre de novo.

"The account is locked due to 3 failed logins."

Mensagem real da VM, quando o polkit pediu a senha da ana logo depois de vários autores errarem a senha dela no sudo:

Info: The account is locked due to 3 failed logins.
Info: (3 minutes left to unlock)
Password:

O que aconteceu: o Arch usa o pam_faillock: 3 senhas erradas seguidas travam a conta por 10 minutos (mesmo a senha certa é recusada nesse tempo).

Como confirmar: sudo faillock --user ana lista as tentativas (hora, origem como sudo ou /dev/pts/0).

Como resolver: espere o tempo indicado, ou, como root, faillock --user ana --reset. Os limites ficam em /etc/security/faillock.conf.

Exercícios

1. Criar com pasta

Complete para criar o usuário bruno com pasta pessoal e no grupo dos administradores:

sudo useradd -G bruno

2. Acrescentar sem apagar

Complete para pôr o bruno no grupo systemd-journal sem tirá-lo dos outros:

sudo usermod systemd-journal bruno

3. Apagar tudo

Complete para apagar o bruno e a pasta pessoal dele:

sudo userdel bruno

4. No Arch, você digita adduser carla. O que acontece?

5. A ana está nos grupos ana e wheel e alguém roda sudo usermod -G video ana. Como ela fica?

6. Por que o /etc/shadow tem permissão rw------- (600)?

Resumo

  • Usuários e grupos são números (UID/GID); pessoas começam em 1000 no Arch.
  • /etc/passwd e /etc/group todos leem; /etc/shadow (as senhas) só o root.
  • No Arch: sudo useradd -m [-G wheel] nome + sudo passwd nome. Não existe adduser.
  • usermod -aG acrescenta; -G sozinho substitui. gpasswd -d tira.
  • userdel -r apaga o usuário e a pasta (o aviso do "spool de mail" é inofensivo).
  • Com o systemd-logind, quase nunca é preciso pôr alguém em audio/video; wheel e systemd-journal são os úteis.

Na Arch Wiki: a página Users and groups (em português) tem a lista completa de grupos (de usuário, de sistema, "pre-systemd" e não usados) e todos os comandos; o sudo e o grupo wheel estão em Sudo (em português); o travamento por senhas erradas, em Security.
