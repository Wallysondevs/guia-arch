Arch Servidor Web (nginx)

Um servidor web é um programa que fica esperando pedidos na rede e responde com páginas, imagens ou dados. O nginx (pronuncia-se "engine-x") é um dos mais usados no mundo: leve, rápido e configurado por um arquivo de texto. No Arch ele vem "cru", do jeito que o projeto nginx o distribui: sem as pastas e atalhos que o Debian e o Ubuntu acrescentam.

Você vai aprender
  • O que acontece quando o navegador pede uma página (porta, pedido, resposta, código de status).
  • Ligar e desligar o nginx com systemctl e testar com curl -I.
  • Ler o /etc/nginx/nginx.conf do Arch e por que ele não tem sites-enabled.
  • Publicar uma página, criar um server block, testar com nginx -t e ler os logs.
  • Os passos de HTTPS (certbot) e de firewall, e os erros reais mais comuns.
Antes desta aula

Você vai usar systemctl (veja systemctl e Serviços), journalctl (Logs) e sudo (sudo, root e Usuários). Na VM do guia o pacote nginx já está instalado e o serviço está parado e desabilitado: é assim que o Arch deixa todo serviço depois de instalado.

Como uma página chega até você

Pense numa lanchonete. O cliente (o navegador) vai até o balcão certo (o endereço e a porta), faz um pedido ("quero a página /index.html") e recebe uma resposta com um número na frente: 200 (aqui está), 404 (não temos isso), 403 (não posso te dar), 500 (a cozinha pegou fogo).

O estado inicial: instalado e parado

No Arch, instalar um serviço não o liga. Esta é uma diferença grande para o Debian, onde o apt install nginx já deixa o servidor rodando. Confira:

systemctl
O controlador de serviços do systemd.
status
Mostra o estado do serviço e as últimas linhas do log dele.
nginx
O nome da unidade (nginx.service; o .service pode ser omitido).
$ systemctl status nginx
○ nginx.service - nginx web server
     Loaded: loaded (/usr/lib/systemd/system/nginx.service; disabled; preset: disabled)   « disabled: não liga no boot
     Active: inactive (dead)                                                              « parado agora
$ echo $?
3                                        « 3 = o serviço não está rodando

O círculo vazio ○ quer dizer parado. Na linha Loaded, o primeiro disabled diz que o serviço não liga no boot e o preset: disabled diz que essa é a política padrão do Arch para ele. O código de saída 3 é o jeito do systemctl status dizer "não está ativo" (útil em scripts).

Se você tentar acessar o servidor agora, ninguém atende:

$ curl -I http://localhost
curl: (7) Failed to connect to localhost:80 after 0 ms: Could not connect to server
$ echo $?
7                                        « 7 = não conseguiu conectar

Repare em três coisas:

  • O start não imprime nada quando dá certo (código 0). Quem conta o resultado é o status.
  • O nginx roda como dois processos: o master (lê a configuração, abre a porta 80) e o worker (atende os pedidos). Quantos workers existem depende de worker_processes; o Arch deixa 1.
  • A linha [warn] could not build optimal types_hash é um aviso, não um erro: o nginx ligou. Ele aparece no nginx do Arch com a configuração de fábrica. Mais abaixo, em "Quando não funciona", você vê como calá-lo.

Quem é o dono de cada processo? E em que porta ele escuta?

$ ps -C nginx -o user,pid,cmd
USER         PID CMD
root        1385 nginx: master process /usr/bin/nginx
http        1386 nginx: worker process                    « usuário http, sem privilégios
$ sudo ss -tlnp | grep nginx
LISTEN 0      511          0.0.0.0:80        0.0.0.0:*    users:(("nginx",pid=1386,fd=4),("nginx",pid=1385,fd=4))

No Arch, o usuário sem privilégios dos servidores web se chama http (no Debian é www-data). O 0.0.0.0:80 quer dizer "porta 80 em todos os endereços da máquina". As letras de ss -tlnp: tcp, listening (escutando), números (não traduz porta em nome), processo (precisa de root para mostrar).

Cadê o sites-available e o sites-enabled?

Não existem. As pastas sites-available/, sites-enabled/ e o atalho default são uma invenção do Debian (herdada pelo Ubuntu). O Arch segue a filosofia de entregar o programa como o autor o faz (vanilla), então você recebe o nginx.conf original do projeto nginx. Se quiser o estilo Debian, você mesmo cria a pasta e uma linha include (veja "Um site novo: server block").

O arquivo é longo porque quase tudo está comentado (#). Tirando os comentários, sobra isto (o arquivo real da VM, com as linhas em branco removidas):

#user http;
worker_processes  1;

# Load all installed modules
include modules.d/*.conf;

events {
    worker_connections  1024;
}

http {
    include       mime.types;
    default_type  application/octet-stream;
    sendfile        on;
    keepalive_timeout  65;

    server {
        listen       80;
        server_name  localhost;

        location / {
            root   /usr/share/nginx/html;
            index  index.html index.htm;
        }

        error_page   500 502 503 504  /50x.html;
        location = /50x.html {
            root   /usr/share/nginx/html;
        }
    }
}
LinhaO que faz
#user http;Comentada, mas o nginx do Arch já foi compilado para usar o usuário http nos workers (o ps acima confirma).
worker_processes 1;Um processo atendente. auto usa um por núcleo de CPU.
include modules.d/*.conf;Carrega módulos instalados à parte (pacotes nginx-mod-*).
events { worker_connections 1024; }Até 1024 conexões simultâneas por worker.
http { … }Tudo o que é web fica aqui dentro.
include mime.types;Ensina ao nginx que .html é text/html, .png é image/png…
server { listen 80; … }O site padrão, na porta 80.
location / { root …; index …; }Para qualquer caminho, procure o arquivo em /usr/share/nginx/html; numa pasta, entregue index.html.
error_page 500 502 503 504 /50x.html;Página mostrada quando o servidor falha.

Regras de sintaxe que mais derrubam iniciantes: toda diretiva termina com ;, blocos usam { } e a ordem dos blocos importa (server sempre dentro de http).

Um site novo: server block

Um server block é um site. Vamos criar um segundo, na porta 8080, no estilo "uma pasta com um arquivo por site". São quatro passos.

  1. A pasta e a página 
    $ sudo mkdir -p /srv/http/meusite
$ echo '<h1>Meu site na porta 8080</h1>' | sudo tee /srv/http/meusite/index.html
<h1>Meu site na porta 8080</h1>
  2. O arquivo do site em /etc/nginx/sites-enabled/meusite.conf (crie a pasta com sudo mkdir /etc/nginx/sites-enabled e edite com sudo nano): 
    server {
    listen 8080;
    server_name localhost;
    root /srv/http/meusite;
    index index.html;
}
  3. Uma linha include dentro de http { } no nginx.conf, logo abaixo de default_type (aproveitamos para calar o aviso do types_hash): 
    http {
    include       mime.types;
    default_type  application/octet-stream;
    types_hash_max_size 4096;
    include sites-enabled/*.conf;
  4. Testar, recarregar e conferir 
    $ sudo nginx -t
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
$ sudo systemctl reload nginx
$ curl http://localhost:8080
<h1>Meu site na porta 8080</h1>
$ sudo ss -tlnp | grep nginx
LISTEN 0      511          0.0.0.0:8080      0.0.0.0:*    users:(("nginx",pid=2299,fd=8),("nginx",pid=1385,fd=8))
LISTEN 0      511          0.0.0.0:80        0.0.0.0:*    users:(("nginx",pid=2299,fd=4),("nginx",pid=1385,fd=4))

Agora o nginx atende nas duas portas. Repare que o aviso do types_hash sumiu do nginx -t.

Vários sites na mesma porta

Em vez de portas diferentes, servidores de verdade usam o nome: dois blocos com listen 80; e server_name blog.exemplo.com; / server_name loja.exemplo.com;. O nginx olha o cabeçalho Host do pedido para escolher o bloco. Para testar sem DNS: curl -H 'Host: blog.exemplo.com' http://localhost.

O que nginx -t faz com um erro

Tire o ; do fim de listen 8080 e teste:

$ sudo nginx -t
2026/10/16 13:21:48 [emerg] 2123#2123: invalid parameter "server_name" in /etc/nginx/sites-enabled/meusite.conf:3
nginx: configuration file /etc/nginx/nginx.conf test failed
$ echo $?
1
$ sudo systemctl reload nginx
Job for nginx.service failed.
See "systemctl status nginx.service" and "journalctl -xeu nginx.service" for details.
$ systemctl status nginx | head -3
● nginx.service - nginx web server
     Loaded: loaded (/usr/lib/systemd/system/nginx.service; disabled; preset: disabled)
     Active: active (running) since Fri 2026-10-16 13:21:18 -03; 29s ago      « continua no ar!

A mensagem aponta a linha 3, mas o erro está na linha 2: sem o ;, o nginx leu listen 8080 server_name localhost como uma diretiva só e estranhou o "parâmetro" server_name. Procure o erro na linha indicada e na anterior. E repare na boa notícia: um reload que falha deixa a configuração antiga funcionando. Um restart com o arquivo quebrado, ao contrário, deixaria o site fora do ar. Por isso: nginx -t antes, sempre.

HTTPS com certbot (ilustrativo)

HTTPS é o HTTP com criptografia (o cadeado do navegador). Para isso o servidor precisa de um certificado assinado por uma autoridade. A Let's Encrypt dá certificados de graça, e o certbot é o programa que os pede e renova.

Por que esta parte é ilustrativa

A Let's Encrypt só entrega certificado para um domínio de verdade (como meusite.com.br) que aponta para o seu servidor e responde na porta 80 pela internet. A VM do guia não tem nada disso. Por isso aqui só a instalação é real (vista com o previa, sem instalar); o resto mostra os comandos e o que eles fazem.

O certbot é escrito em Python, por isso vêm 14 bibliotecas python-* junto. O certbot-nginx é o plugin que sabe editar o nginx.conf. Com um domínio de verdade, o caminho seria:

sudo pacman -S certbot certbot-nginx
sudo certbot --nginx -d meusite.com.br          # pede o certificado e edita o server block
sudo systemctl enable --now certbot-renew.timer # renovação automática (se o seu pacote trouxer o timer)
sudo certbot renew --dry-run                    # testa a renovação sem mudar nada

O certificado fica em /etc/letsencrypt/live/meusite.com.br/, e o server block ganha listen 443 ssl;, ssl_certificate e ssl_certificate_key, parecido com o bloco "HTTPS server" comentado no fim do nginx.conf do Arch. Os certificados valem 90 dias; por isso a renovação precisa ser automática. Se o seu certbot não trouxer um timer, crie um (veja Timers e Tarefas).

Firewall: abrir só o necessário

O Arch vem sem firewall ativo. Se você ativar um (nftables ou ufw), lembre de liberar as portas do servidor web, senão ninguém de fora acessa. Com o ufw, a ideia é:

sudo ufw allow 22/tcp     # o SSH primeiro, para não se trancar fora!
sudo ufw allow 80/tcp     # http
sudo ufw allow 443/tcp    # https

Não ative o firewall sem ler a aula Firewall (nftables e ufw): num servidor remoto, ativá-lo sem liberar a porta 22 corta o seu próprio acesso por SSH.

Quando não funciona

"Could not connect to server" 
$ curl -I http://localhost
curl: (7) Failed to connect to localhost:80 after 0 ms: Could not connect to server

O que aconteceu: ninguém está escutando na porta 80. No Arch, a causa número 1 é o serviço nunca ter sido ligado (instalar não liga).

Como confirmar: systemctl is-active nginx responde inactive; sudo ss -tlnp | grep :80 não mostra nada.

Como resolver: sudo systemctl start nginx (ou enable --now).

"bind() … failed (98: Address already in use)" 
#> nginx
2026/10/16 13:22:06 [emerg] 2459#2459: bind() to 0.0.0.0:80 failed (98: Address already in use)
…                                                 « o nginx tenta 5 vezes
2026/10/16 13:22:06 [emerg] 2459#2459: still could not bind()
#> echo $?
1

O que aconteceu: outro programa já ocupa a porta. Acima, foi um nginx rodado à mão com o serviço já ligado; também acontece com Apache e nginx instalados juntos, ou um container publicando a porta 80.

Como confirmar: sudo ss -tlnp | grep ':80 ' mostra quem está na porta.

Como resolver: pare o outro programa ou mude o listen. Não rode nginx à mão: use sempre systemctl.

Erro 403 Forbidden 
$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080
403
$ journalctl -u nginx -n 1 --no-pager
out 16 13:21:59 notebook nginx[2299]: 2026/10/16 13:21:59 [error] 2299#2299: *10 open() "/srv/http/meusite/index.html" failed (13: Permission denied), client: 127.0.0.1, server: localhost, request: "GET / HTTP/1.1", host: "localhost:8080"

O que aconteceu: o worker roda como http e não consegue ler o arquivo (aqui ele estava com modo 600, só o dono lê). Outra causa clássica: o site dentro de /home/ana, que no Arch tem modo 700, e o http não entra lá.

Como resolver: deixe os arquivos legíveis por todos (chmod 644 nos arquivos, 755 nas pastas) e prefira /srv/http a /home. Veja Permissões.

O que aconteceu: só um aviso ([warn]): a tabela de tipos do mime.types é maior que o tamanho padrão.

Como resolver: acrescente types_hash_max_size 4096; dentro de http { }, como fizemos no server block.

"Job for nginx.service failed"

O que aconteceu: erro de sintaxe ou porta ocupada no start/reload.

Como confirmar: sudo nginx -t aponta arquivo e linha; journalctl -xeu nginx mostra a mensagem completa ([emerg] …).

Como resolver: corrija a linha indicada (ou a anterior: ; esquecido) e repita.

"Access denied as the requested operation requires interactive authentication" 
$ systemctl start nginx
Failed to start nginx.service: Access denied as the requested operation requires interactive authentication. However, interactive authentication has not been enabled by the calling program.
See system logs and 'systemctl status nginx.service' for details.

O que aconteceu: faltou o sudo (a mensagem acima é de uma sessão sem terminal; num terminal gráfico o systemd pode abrir uma janela pedindo senha).

Como resolver: sudo systemctl start nginx.

Resumo

  • No Arch, instalar não liga: sudo systemctl enable --now nginx.
  • Teste com curl -I http://localhost; 200 é sucesso.
  • A configuração é um só arquivo, /etc/nginx/nginx.conf; sites-enabled só existe se você criar.
  • sudo nginx -t antes de reload; um reload que falha mantém a configuração antiga.
  • Acessos em /var/log/nginx/access.log; erros em journalctl -u nginx.
  • Workers rodam como http: use /srv/http e permissões de leitura.
