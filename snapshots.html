Arch Snapshots

Um snapshot é uma "foto" de um subvolume Btrfs num instante. Ele é criado em menos de um segundo, quase não ocupa espaço e deixa você ver, comparar e recuperar arquivos como eram. O snapper organiza essas fotos: cria automaticamente, numera, compara, desfaz alterações e apaga as velhas. Com o snap-pac, cada pacman -Syu ganha uma foto de "antes" e outra de "depois".

Você vai aprender
  • Criar snapshots com btrfs subvolume snapshot e entender por que eles são "de graça".
  • Configurar o snapper e usar list, create, status, diff e undochange.
  • Os pares pre/post e o que o snap-pac e o grub-btrfs fazem.
  • Timeshift × snapper: qual usar.
  • As três formas de restaurar: um arquivo, uma alteração, o sistema inteiro.
Snapshot não é backup

O snapshot fica no mesmo disco. Se o disco morrer, for roubado ou criptografado por um vírus, os snapshots vão junto. Eles protegem contra erros (uma atualização ruim, um rm errado); contra perda do disco, só um backup em outro lugar.

O laboratório

A raiz da máquina do guia é ext4, então tudo aqui acontece num Btrfs dentro de um arquivo-imagem, montado em /mnt/a8 com os subvolumes @, @home (em /mnt/a8/home) e @snapshots (em /mnt/a8/.snapshots). A montagem desse laboratório está passo a passo em Btrfs e Subvolumes.

Snapshot "na mão": btrfs subvolume snapshot

btrfs subvolume snapshot
Cria um snapshot (um subvolume novo que compartilha tudo com a origem).
-r
read-only: o snapshot fica só de leitura. É o certo para "fotos" de segurança.
/mnt/a8/home
A origem: precisa ser um subvolume (aqui, o @home montado).
/mnt/a8/.snapshots/home-antes
Onde o snapshot vai aparecer (como uma pasta).

#> cp /mnt/a8/.snapshots/home-antes/ana/notas.txt /mnt/a8/home/ana/

Ligar para o João

Por que o snapshot é "de graça"

Com um arquivo de 20 MiB na home, veja o espaço antes e depois do snapshot, e depois de apagar o arquivo original:

#> btrfs filesystem df /mnt/a8 | head -1
Data, single: total=328.00MiB, used=20.03MiB
#> btrfs subvolume snapshot -r /mnt/a8/home /mnt/a8/.snapshots/home-2
Create readonly snapshot of '/mnt/a8/home' in '/mnt/a8/.snapshots/home-2'
#> sync
#> btrfs filesystem df /mnt/a8 | head -1
Data, single: total=328.00MiB, used=20.03MiB        « o snapshot não gastou nada
#> btrfs filesystem du -s /mnt/a8/home /mnt/a8/.snapshots/home-2
     Total   Exclusive  Set shared  Filename
  20.00MiB       0.00B    20.00MiB  /mnt/a8/home              « os mesmos blocos...
  20.00MiB       0.00B    20.00MiB  /mnt/a8/.snapshots/home-2  « ...nos dois
#> rm /mnt/a8/home/ana/fotos.bin
#> sync
#> btrfs filesystem df /mnt/a8 | head -1
Data, single: total=328.00MiB, used=20.03MiB        « apagar não liberou espaço!
#> btrfs filesystem du -s /mnt/a8/home /mnt/a8/.snapshots/home-2
     Total   Exclusive  Set shared  Filename
     0.00B       0.00B       0.00B  /mnt/a8/home
  20.00MiB    20.00MiB       0.00B  /mnt/a8/.snapshots/home-2  « agora só o snapshot segura o arquivo
#> btrfs subvolume delete /mnt/a8/.snapshots/home-2
Delete subvolume 262 (no-commit): '/mnt/a8/.snapshots/home-2'
#> btrfs subvolume sync /mnt/a8
Waiting for 1 subvolume
Subvolume id 262 is gone (1/1)
#> btrfs filesystem sync /mnt/a8
#> btrfs filesystem df /mnt/a8 | head -1
Data, single: total=328.00MiB, used=32.00KiB        « agora sim o espaço voltou

Essa é a pegadinha dos snapshots: apagar arquivos não libera espaço enquanto algum snapshot ainda os guarda. Quando o disco enche "do nada", quase sempre são snapshots velhos. A limpeza automática do snapper existe exatamente para isso. O delete diz no-commit porque a liberação acontece em segundo plano; o subvolume sync espera ela terminar.

Snapshot gravável

Sem o -r, o snapshot nasce gravável: btrfs subvolume snapshot /mnt/a8/.snapshots/home-antes /mnt/a8/.snapshots/home-gravavel respondeu Create snapshot of …. É assim que se "promove" uma foto a sistema ativo numa restauração (veja o projeto).

snapper: snapshots organizados

O snapper nasceu no openSUSE e está no repositório oficial do Arch (pacote snapper). Ele trabalha com configurações: cada configuração cuida de um subvolume, guarda os snapshots numerados em .snapshots/ dentro dele e tem regras de limpeza. Num sistema real, a configuração se chama root e aponta para /; no laboratório, criamos a teste, apontando para o @home da imagem.

Criar a configuração: create-config

snapper
O programa.
-c teste
Nome da configuração (config). Sem -c, o snapper usa root.
create-config
Cria a configuração.
/mnt/a8/home
O subvolume que ela vai fotografar.
#> snapper -c teste create-config /mnt/a8/home
#> echo $?

#> snapper list-configs

Criar e listar snapshots

-d "antes da faxina"

--userdata important=yes
Etiqueta livre; important=yes faz a limpeza usar o limite dos importantes.
-p
--print-number: imprime o número do snapshot criado.

O que mudou: status e diff

snapper -c teste status
Lista os arquivos diferentes entre dois snapshots.
1..3
Do snapshot 1 até o 3. Use 0 para "agora" (ex.: 1..0).
#> snapper -c teste status 1..3
+..... /mnt/a8/home/ana/ideias.txt     « + criado
-..... /mnt/a8/home/ana/notas.txt      « - apagado
+..... /mnt/a8/home/ana/projetos
#> snapper -c teste diff 1..3 /mnt/a8/home/ana/notas.txt
--- /mnt/a8/home/.snapshots/1/snapshot/ana/notas.txt	2026-10-16 13:23:43.512750324 -0300
+++ /mnt/a8/home/.snapshots/3/snapshot/ana/notas.txt	1969-12-31 21:00:00.000000000 -0300
@@ -1,3 +0,0 @@
-Comprar café
-Ligar para o João
-Estudar Btrfs

Cada linha do status começa com seis posições. A primeira é o tipo de mudança: + criado, - apagado, c conteúdo alterado, t tipo mudou. As outras cinco marcam mudanças de permissão, dono (user), grupo, atributos estendidos (x) e ACL (a); um ponto quer dizer "não mudou". O diff mostra o conteúdo, no formato do diff -u (a data de 1969 é o "arquivo inexistente").

Desfazer: undochange

undochange A..B desfaz no estado atual as mudanças que aconteceram entre A e B. Pode ser um arquivo só ou tudo:

#> snapper -c teste undochange 1..3 /mnt/a8/home/ana/notas.txt
criar:1 modificar:0 remover:0              « recriou só o notas.txt
#> cat /mnt/a8/home/ana/notas.txt
Comprar café
Ligar para o João
Estudar Btrfs
#> ls /mnt/a8/home/ana
ideias.txt
notas.txt
projetos
#> snapper -c teste undochange 1..3
criar:1 modificar:0 remover:2              « tudo: apagou ideias.txt e projetos
#> ls /mnt/a8/home/ana
notas.txt
undochange apaga o que foi criado depois

Desfazer 1..3 inteiro remove os arquivos criados no meio (o ideias.txt sumiu). Antes de um undochange grande, rode o status e, na dúvida, crie um snapshot novo do estado atual: assim dá para desfazer o desfazer.

Pares pre/post

Para mudanças planejadas, o snapper usa pares: um snapshot pre antes e um post depois, ligados pelo número. É exatamente o que o snap-pac faz em cada transação do pacman:

#> snapper -c teste create -t pre -p -d "antes de editar"
4
#> echo "Estudar snapper" >> /mnt/a8/home/ana/notas.txt
#> snapper -c teste create -t post --pre-number 4 -d "depois de editar"
#> snapper -c teste status 4..5
c..... /mnt/a8/home/ana/notas.txt           « c = conteúdo mudou
#> snapper -c teste diff 4..5
--- /mnt/a8/home/.snapshots/4/snapshot/ana/notas.txt	2026-10-16 13:24:53.729885577 -0300
+++ /mnt/a8/home/.snapshots/5/snapshot/ana/notas.txt	2026-10-16 13:25:05.368750324 -0300
@@ -1,3 +1,4 @@
 Comprar café
 Ligar para o João
 Estudar Btrfs
+Estudar snapper

O atalho --command cria o pre, roda o comando e cria o post:

#> snapper -c teste create --command "rm /mnt/a8/home/ana/notas.txt" -d "comando rm"
#> snapper -c teste list --type pre-post
Pre # │ Post # │ Data anterior            │ Data posterior           │ Descrição       │ Dados de usuário
──────┼────────┼──────────────────────────┼──────────────────────────┼─────────────────┼─────────────────
    4 │      5 │ sex 16 out 2026 13:25:03 │ sex 16 out 2026 13:25:05 │ antes de editar │
    6 │      7 │ sex 16 out 2026 13:25:06 │ sex 16 out 2026 13:25:07 │ comando rm      │
#> snapper -c teste status 6..7
-..... /mnt/a8/home/ana/notas.txt
#> snapper -c teste undochange 6..7
criar:1 modificar:0 remover:0
#> cat /mnt/a8/home/ana/notas.txt
Comprar café
Ligar para o João
Estudar Btrfs
Estudar snapper

Apagar e limpar

#> snapper -c teste delete 2
#> snapper -c teste delete 6-7                « uma faixa
#> snapper -c teste list
# │ Tipo   │ Pre # │ Data                     │ Usuário │ Limpeza │ Descrição        │ Dados de usuário
──┼────────┼───────┼──────────────────────────┼─────────┼─────────┼──────────────────┼─────────────────
0 │ single │       │                          │ root    │         │ current          │
1 │ single │       │ sex 16 out 2026 13:24:49 │ root    │         │ antes da faxina  │
3 │ single │       │ sex 16 out 2026 13:24:52 │ root    │         │ depois da faxina │
4 │ pre    │       │ sex 16 out 2026 13:25:03 │ root    │         │ antes de editar  │
5 │ post   │     4 │ sex 16 out 2026 13:25:05 │ root    │         │ depois de editar │
#> snapper -c teste cleanup number
#> echo $?
0

cleanup number aplica a regra NUMBER_LIMIT agora; não apagou nada porque nenhum snapshot com limpeza number passava do limite (e todos tinham menos de 1 hora). No sistema real, quem roda as limpezas é o timer snapper-cleanup.timer (de hora em hora), e quem cria as fotos de hora em hora é o snapper-timeline.timer. Ligar os dois está no projeto.

Para desfazer o laboratório, apague a configuração (isso apaga os snapshots dela e o subvolume .snapshots):

#> snapper -c teste delete-config
#> snapper list-configs
Configuração │ Subvolume
─────────────┼──────────
#> grep SNAPPER_CONFIGS /etc/conf.d/snapper
SNAPPER_CONFIGS=""

snap-pac: snapshots a cada pacman

O snap-pac é um conjunto de hooks do pacman: antes de cada instalação, atualização ou remoção, ele chama snapper create -t pre; depois, snapper create -t post. A descrição é o comando do pacman. Se uma atualização quebrar algo, você tem o "antes" pronto. A instalação é pequena (resumo real, respondido com "não"):

#> pacman -S snap-pac
resolvendo dependências...
procurando pacotes conflitantes...

Pacotes (1) snap-pac-3.0.1-3

Tamanho total download:   0,02 MiB
Tamanho total instalado:  0,04 MiB

:: Continuar a instalação? [S/n] n

O pacote é só isso:

$ pacman -Fl snap-pac | grep -v '/$'
snap-pac etc/snap-pac.ini
snap-pac usr/share/doc/snap-pac/README.md
snap-pac usr/share/libalpm/hooks/05-snap-pac-pre.hook      « roda antes
snap-pac usr/share/libalpm/hooks/10-snap-pac-removal.hook
snap-pac usr/share/libalpm/hooks/zz-snap-pac-post.hook     « roda por último
snap-pac usr/share/libalpm/scripts/snap-pac
snap-pac usr/share/licenses/snap-pac/LICENSE
snap-pac usr/share/man/man8/snap-pac.8.gz

O hook de "antes", tirado do pacote (sem o cabeçalho de licença):

[Trigger]
Operation = Upgrade
Operation = Install
Operation = Remove
Type = Package
Target = *

[Action]
Description = Performing snapper pre snapshots for the following configurations...
Depends = snap-pac
When = PreTransaction
Exec = /usr/share/libalpm/scripts/snap-pac pre
NeedsTargets
AbortOnFail

Target = *: qualquer pacote. When = PreTransaction: antes de mexer em qualquer arquivo. AbortOnFail: se o snapshot falhar, o pacman não continua (melhor parar do que atualizar sem rede de proteção). Os números 05- e zz- no nome garantem a ordem: o "antes" roda primeiro, o "depois" por último. Por padrão, só a configuração root é fotografada; para incluir outras, edite /etc/snap-pac.ini (seção [nome] com snapshot = True).

Num sistema com snap-pac, cada atualização deixa um par na lista, com descrições como pacman -Syu no pre e a lista de pacotes no post (ilustrativo: a máquina do guia não tem raiz Btrfs).

grub-btrfs: dar boot num snapshot

Se a atualização quebrou o boot, de nada adianta um snapshot que você não consegue alcançar. O grub-btrfs acrescenta ao menu do GRUB um submenu com os snapshots, para iniciar o sistema como ele era. Ele traz (lista real dos arquivos):

$ pacman -Fl grub-btrfs | grep -v "/$"
grub-btrfs etc/default/grub-btrfs/config
grub-btrfs etc/grub.d/41_snapshots-btrfs                   « script que o grub-mkconfig roda
grub-btrfs usr/bin/grub-btrfsd                            « o vigia
grub-btrfs usr/lib/initcpio/hooks/grub-btrfs-overlayfs
grub-btrfs usr/lib/initcpio/install/grub-btrfs-overlayfs  « hook do mkinitcpio
grub-btrfs usr/lib/systemd/system/grub-btrfsd.service
grub-btrfs usr/share/doc/grub-btrfs/README.md
grub-btrfs usr/share/doc/grub-btrfs/initramfs-overlayfs.md
grub-btrfs usr/share/licenses/grub-btrfs/LICENSE
grub-btrfs usr/share/man/man8/grub-btrfs.8.gz
grub-btrfs usr/share/man/man8/grub-btrfsd.8.gz
$ pacman -Si grub-btrfs | grep -E "^(Depende|Dependências opc)" -A3
Depende de           : btrfs-progs  grub
Depend. opcionais    : snapper: For snapper support
                       inotify-tools: For grub-btrfsd daemon
Conflita com         : Nenhum
  • 41_snapshots-btrfs: o grub-mkconfig passa a gerar o submenu "Arch Linux snapshots".
  • grub-btrfsd.service: vigia /.snapshots (precisa do inotify-tools) e regenera o submenu sozinho a cada snapshot novo: ExecStart=/usr/bin/grub-btrfsd --syslog /.snapshots. Ligue com systemctl enable --now grub-btrfsd.
  • grub-btrfs-overlayfs: os snapshots do snapper são só de leitura, e muitos serviços não sobem num / só de leitura. Esse hook, acrescentado ao fim do HOOKS= do mkinitcpio.conf, monta uma camada gravável temporária por cima.

Tudo isso é ilustrativo aqui: a máquina do guia usa ext4 e não mexemos no GRUB dela. O fluxo de socorro fica assim: atualização quebrou → no menu do GRUB, "Arch Linux snapshots" → escolha o pre da atualização → o sistema liga como era → você decide restaurar de vez (veja abaixo).

Timeshift

O Timeshift (pacote timeshift, repositório extra) é a alternativa com interface gráfica, popular no Linux Mint. Ele tem dois modos: Btrfs (snapshots de verdade, mas exige o layout com subvolumes chamados exatamente @ e @home) e rsync (cópias de arquivos, funciona em ext4, mas ocupa espaço de verdade). A instalação puxa a pilha GTK (resumo real, respondido com "não"; a lista de 41 pacotes foi encurtada com …):

#> pacman -S timeshift
resolvendo dependências...
procurando pacotes conflitantes...

Pacotes (41) adwaita-cursors-51.0-1  adwaita-fonts-51.0-2
             …
             xorg-xkbcomp-1.5.0-1  xorg-xprop-1.2.8-1  timeshift-26.09.0-1

Tamanho total download:    21,59 MiB
Tamanho total instalado:  122,39 MiB

:: Continuar a instalação? [S/n] n

O uso é pela janela (ilustrativo aqui): escolher o tipo, o disco e a agenda. Pelo terminal, timeshift --create --comments "antes" e timeshift --list. Com o grub-btrfs, o vigia usa grub-btrfsd --timeshift-auto.

Restaurar: três tamanhos de problema

ProblemaComo restaurar
Apaguei/estraguei um arquivoCopie de /.snapshots/N/snapshot/caminho, ou snapper undochange N..0 /caminho/arquivo.
Uma atualização estragou algo, mas o sistema ligasnapper status PRE..POST para ver o que mudou e snapper undochange PRE..POST. Cuidado: a base de dados do pacman também volta; confira com pacman -Qkk.
O sistema não ligaBoot no snapshot pelo grub-btrfs e snapper rollback; ou, do pendrive, troque o subvolume @ por um snapshot (passo a passo no projeto).

O snapper rollback só existe para a configuração da raiz: ele cria um snapshot gravável do escolhido e o torna o subvolume padrão do próximo boot. Na configuração de teste, ele se recusa (veja abaixo).

Quando não funciona

"Sem permissões." 
$ snapper -c teste list
Sem permissões.
$ echo $?
1

O que aconteceu: você rodou como usuário comum e a configuração não libera ninguém além do root.

Como resolver: use sudo snapper …, ou libere seu grupo: sudo snapper -c root set-config ALLOW_GROUPS=wheel SYNC_ACL=yes.

A configuração "root" não existe 
$ snapper list
A configuração "root" não existe. Provavelmente, o snapper não está configurado.
Consulte "man snapper" para obter mais instruções.

O que aconteceu: sem -c, o snapper procura a configuração root, que ainda não foi criada.

Como resolver: snapper list-configs mostra as que existem; use -c nome, ou crie a da raiz com snapper -c root create-config /. Um nome que não existe dá Configuração desconhecida.

"subvolume is not a btrfs subvolume" 
#> snapper -c log create-config /mnt/a8/etc
Erro de E/S (subvolume is not a btrfs subvolume).

O que aconteceu: o caminho é uma pasta comum, não um subvolume. O snapper só fotografa subvolumes Btrfs (ou volumes LVM finos).

Como resolver: confira com btrfs subvolume show caminho; crie um subvolume para esses dados. Recriar uma configuração com o mesmo nome dá Falha ao criar a configuração (config already exists).

"Instantâneo inválido." 
#> snapper -c teste undochange 0..1
Instantâneo inválido.

O que aconteceu: a ordem ou o número está errado. Para voltar ao estado do snapshot 1, a forma é undochange 1..0 ("desfaça o que mudou de 1 até agora").

rollback num subvolume que não é a raiz 
#> snapper -c projeto rollback 2
O comando 'rollback' não pode ser usado num subvolume não-root /mnt/a8.

O que aconteceu: o rollback só funciona na configuração de /. Para outros subvolumes, use undochange ou troque o subvolume à mão (no projeto).

Disco cheio sem motivo aparente

O que aconteceu: snapshots antigos seguram blocos de arquivos que você já apagou (como visto acima).

Como confirmar: sudo snapper list (muitos snapshots? sem algoritmo de limpeza?) e sudo btrfs filesystem usage /.

Como resolver: apague faixas antigas (snapper delete 10-40), confira se o snapper-cleanup.timer está ativo e reduza os *_LIMIT.

Resumo

  • Snapshot = foto instantânea de um subvolume; começa sem ocupar espaço e cresce conforme o original muda.
  • Apagar arquivos não libera espaço enquanto um snapshot os guarda.
  • snapper: create-config, create -d, list, status, diff, undochange, delete; o 0 é "agora".
  • snap-pac = par pre/post a cada pacman; grub-btrfs = boot nos snapshots.
  • Timeshift é a opção gráfica; snapper é a mais flexível. Nenhum dos dois é backup.
