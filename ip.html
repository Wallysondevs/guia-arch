Arch ip, ping, ss

Três ferramentas respondem quase todas as perguntas sobre a rede: ip mostra as placas, os endereços e as rotas; ping testa se um destino responde; ss lista as conexões e as portas abertas. No Arch, as três vêm no meta-pacote base, ou seja, existem em qualquer instalação, até na mais mínima.

Você vai aprender
  • Ler a saída completa do ip a linha por linha, e a versão resumida ip -br a.
  • Ver as placas com ip link, o gateway com ip route e os vizinhos com ip neigh.
  • Usar o ping com -c, entender cada linha (que no Arch sai em português) e os códigos de saída 0, 1 e 2.
  • Ver o caminho até um site com tracepath (e por que o traceroute não vem instalado).
  • Descobrir quais portas estão abertas, e qual programa usa cada uma, com ss -tulpn.

Esta aula é a continuação de NetworkManager e iwd: lá você viu quem configura a rede; aqui você aprende a conferir o resultado. Os exemplos são reais, da VM do guia: a máquina notebook, ligada por cabo (placa enp0s3), dentro do VirtualBox. Por isso os endereços são 10.0.2.x; no seu computador, provavelmente serão 192.168.0.x ou 192.168.1.x.

De onde vêm esses comandos

No Arch, cada comando vem de um pacote. Saber qual ajuda a entender o que existe numa instalação nova:

$ pacman -Qo /usr/bin/ip /usr/bin/ss /usr/bin/ping /usr/bin/tracepath
/usr/bin/ip pertence a iproute2 7.2.0-1
/usr/bin/ss pertence a iproute2 7.2.0-1
/usr/bin/ping pertence a iputils 20250605-1
/usr/bin/tracepath pertence a iputils 20250605-1
PacoteTrazVem no base?
iproute2ip, ss, bridge, tcSim
iputilsping, tracepath, arpingSim
inetutilshostname, telnet, ftpNão (a VM tem porque as aulas usam)

E o ifconfig e o netstat?

Tutoriais antigos usam ifconfig e netstat, do pacote net-tools, parado há anos. O Arch não os instala:

$ ifconfig
bash: ifconfig: comando não encontrado
$ netstat -tulpn
bash: netstat: comando não encontrado

Use os equivalentes modernos: ip a no lugar do ifconfig e ss no lugar do netstat. As opções do ss foram feitas parecidas com as do netstat de propósito.

O comando ip

O ip é a ferramenta oficial de rede do kernel Linux. Ele mostra o que o kernel sabe agora, não importa quem configurou (NetworkManager, systemd-networkd, você à mão). Ele trabalha com objetos, e cada objeto é uma parte da rede:

ObjetoAbreviaçãoMostra
ip addressip aOs endereços IP de cada placa
ip linkip lAs placas em si: ligadas ou não, endereço físico (MAC)
ip routeip rAs rotas: por onde sai cada destino (e o gateway)
ip neighbourip n ou ip neighOs vizinhos: aparelhos da rede local que o computador já encontrou

Qualquer abreviação sem ambiguidade funciona: ip a, ip addr e ip address são o mesmo comando. Ver a rede não precisa de root; só mudar precisa (veja mais abaixo).

Ver os endereços: ip -br a

Comece pela versão resumida, uma linha por placa:

ip
A ferramenta de rede.
-br
De brief, "resumido": uma linha por placa. Vem antes do objeto.
a
O objeto address: os endereços.
$ ip -br a
lo               UNKNOWN        127.0.0.1/8 ::1/128
enp0s3           UP             10.0.2.15/24 fd17:625c:f037:2:3074:376a:4fe9:621c/64 fe80::9c83:cf89:6133:11ca/64

São três colunas: o nome da placa, o estado e os endereços. O endereço que quase sempre interessa é o primeiro, o IPv4 da placa que está UP: 10.0.2.15/24. O /24 diz o tamanho da rede (os três primeiros números, 10.0.2, identificam a rede; o último, a máquina).

NomeO que é
loLoopback: a placa virtual que o computador usa para falar consigo mesmo (127.0.0.1). Sempre existe e sempre aparece como UNKNOWN, o que é normal.
enp0s3, eno1, enp2s0Placa de cabo (Ethernet). en = Ethernet; p0s3 = a posição dela no barramento PCI (barramento 0, slot 3). O nome é fixo: não muda se você colocar outra placa.
wlan0, wlp3s0Placa Wi-Fi. wl = wireless, "sem fio".
docker0, podman0, virbr0, wg0Placas virtuais criadas por containers, máquinas virtuais ou VPN.

Na coluna de estado, UP quer dizer ligada e com conexão; DOWN, desligada ou sem cabo.

Com cores e só o que está ligado

Acrescente -c (de color): ip -br -c a pinta o estado de verde ou vermelho e os endereços IPv4 e IPv6 em cores diferentes. E ip -br a show up esconde as placas desligadas, útil num notebook com várias placas virtuais.

Os endereços IPv6

Ao lado do IPv4 aparecem endereços longos, com :. O que começa com fe80:: é de enlace local: toda placa tem um, e ele só vale dentro da rede local. O que começa com fd17:… foi dado pelo roteador (aqui, o roteador virtual do VirtualBox). Para o dia a dia você pode ignorá-los; para ver só um tipo, use -4 ou -6: ip -4 a.

Cada placa é um bloco que começa com um número. Dentro do bloco da enp0s3, linha por linha:

PedaçoSignificado
2: enp0s3:Número interno da placa e o nome dela.
<BROADCAST,MULTICAST,UP,LOWER_UP>As "bandeiras" da placa. UP: ela foi ligada. LOWER_UP: há sinal físico (cabo conectado ou Wi-Fi associado). Sem LOWER_UP, o cabo está solto.
mtu 1500Tamanho máximo de cada pacote, em bytes. 1500 é o padrão das redes com cabo.
qdisc fq_codelA "fila" que organiza os pacotes que saem. Pode ignorar.
state UPO estado do enlace (a mesma coluna do -br).
link/ether 08:00:27:74:b2:03O endereço físico (MAC) da placa, gravado de fábrica. brd ff:ff:… é o endereço "para todos".
altname enx08002774b203Um nome alternativo da mesma placa, montado a partir do MAC. Os dois nomes funcionam.
inet 10.0.2.15/24O endereço IPv4 e o tamanho da rede (/24 = máscara 255.255.255.0).
brd 10.0.2.255Endereço de broadcast: falar com todos da rede local de uma vez.
scope globalVale fora da máquina (o 127.0.0.1 é scope host: só dentro dela).
dynamicO endereço veio por DHCP: foi "emprestado" pelo roteador. Um IP fixo não tem essa palavra.
noprefixrouteQuem criou a rota para essa rede foi o NetworkManager, não o kernel sozinho.
valid_lft 86267secPor quanto tempo o empréstimo ainda vale: 86267 segundos, quase 24 horas. O NetworkManager renova antes de acabar.

Para ver uma placa só, diga qual: ip a show enp0s3 (ou ip a show dev enp0s3). Juntando com -4, sobra só o IPv4:

$ ip -4 a show enp0s3
2: enp0s3: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP group default qlen 1000
    altname enx08002774b203
    inet 10.0.2.15/24 brd 10.0.2.255 scope global dynamic noprefixroute enp0s3
       valid_lft 85726sec preferred_lft 85726sec

Se a placa não existe, o ip avisa (em inglês) e devolve código 1:

$ ip a show dev nada
Device "nada" does not exist.
$ echo $?
1

As placas: ip link

O ip link mostra as placas sem os endereços IP: só o nome, as bandeiras e o MAC. É o comando para responder "a placa existe? o cabo está ligado?".

$ ip link
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 qdisc noqueue state UNKNOWN mode DEFAULT group default qlen 1000
    link/loopback 00:00:00:00:00:00 brd 00:00:00:00:00:00
2: enp0s3: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP mode DEFAULT group default qlen 1000
    link/ether 08:00:27:74:b2:03 brd ff:ff:ff:ff:ff:ff
    altname enx08002774b203
$ ip -br link
lo               UNKNOWN        00:00:00:00:00:00 <LOOPBACK,UP,LOWER_UP>
enp0s3           UP             08:00:27:74:b2:03 <BROADCAST,MULTICAST,UP,LOWER_UP>      « nome, estado, MAC, bandeiras

Num notebook, se a placa Wi-Fi não aparece no ip link, o kernel não a reconheceu (falta driver ou firmware). Se aparece mas está DOWN, ela existe e só não está conectada.

Estatísticas: ip -s link

Com -s (statistics), o ip conta o tráfego que passou pela placa desde o boot:

$ ip -s link show enp0s3
2: enp0s3: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP mode DEFAULT group default qlen 1000
    link/ether 08:00:27:74:b2:03 brd ff:ff:ff:ff:ff:ff
    RX:  bytes packets errors dropped  missed   mcast
         81168     544      0       0       0       1     « recebidos
    TX:  bytes packets errors dropped carrier collsns
        118642     486      0       0       0       0     « enviados
    altname enx08002774b203

RX (de receive) é o que chegou e TX (de transmit), o que saiu. Números crescendo em errors ou dropped indicam cabo ruim, placa com defeito ou Wi-Fi fraco.

Rotas e gateway: ip route

A tabela de rotas diz por onde sai cada destino. A linha mais importante é a rota padrão (default): tudo o que não é da rede local vai para o gateway, que normalmente é o roteador.

$ ip route
default via 10.0.2.2 dev enp0s3 proto dhcp src 10.0.2.15 metric 100                   « o gateway
10.0.2.0/24 dev enp0s3 proto kernel scope link src 10.0.2.15 metric 100                « a rede local
default
Qualquer destino que não tenha uma rota mais específica (a internet inteira).
via 10.0.2.2
Mande para este endereço: o gateway. Na VM é o roteador virtual do VirtualBox; em casa, o seu roteador.
dev enp0s3
Saindo por esta placa.
proto dhcp
A rota foi recebida por DHCP (quem a instalou foi o NetworkManager).
src 10.0.2.15
O endereço de origem que os pacotes vão usar.
metric 100
Prioridade: com duas rotas iguais (cabo e Wi-Fi juntos), vence a de número menor. O NetworkManager dá 100 ao cabo e 600 ao Wi-Fi, por isso o cabo ganha.

A segunda linha diz que os endereços 10.0.2.0 a 10.0.2.255 (/24) estão "ali do lado" (scope link): são alcançados direto, sem passar pelo roteador.

Quer saber por qual caminho um endereço específico vai sair? Pergunte direto com ip route get:

$ ip route get 1.1.1.1
1.1.1.1 via 10.0.2.2 dev enp0s3 src 10.0.2.15 uid 1000
    cache

O IPv6 tem a sua própria tabela, vista com ip -6 route (na VM, o gateway IPv6 é fe80::2):

$ ip -6 r
fd17:625c:f037:2::/64 dev enp0s3 proto ra metric 100 pref medium
fe80::/64 dev enp0s3 proto kernel metric 1024 pref medium
default via fe80::2 dev enp0s3 proto ra metric 100 pref medium
Sem linha default, sem internet

Se o ip route não mostra nenhuma linha começando com default, o computador não sabe como sair da rede local: nenhum site abre, mesmo com IP na placa. Quase sempre o DHCP falhou ou o gerenciador de rede não está rodando; veja NetworkManager e iwd.

Vizinhos: ip neigh

Para falar com um aparelho da rede local, o computador precisa do MAC dele. O ip neigh mostra a "agenda" de vizinhos que ele já descobriu:

$ ip neigh
10.0.2.2 dev enp0s3 lladdr 52:54:00:12:35:00 REACHABLE          « o gateway respondeu há pouco
10.0.2.3 dev enp0s3 lladdr 52:54:00:12:35:00 STALE              « o DNS: conhecido, mas faz tempo
fe80::2 dev enp0s3 lladdr 52:54:00:12:35:00 router STALE

lladdr é o MAC do vizinho. REACHABLE quer dizer "respondeu recentemente"; STALE, "conheço, mas faz tempo que não confirmo"; FAILED, "tentei e ninguém respondeu" (aparelho desligado ou IP errado). Na VM, os três vizinhos têm o mesmo MAC porque são todos o mesmo roteador virtual do VirtualBox.

Mudar a rede com ip: precisa de root, e é temporário

O ip também liga e desliga placas, põe endereços e cria rotas (ip link set, ip addr add, ip route add). Como usuária comum, o kernel recusa:

$ ip link set enp0s3 down
RTNETLINK answers: Operation not permitted
$ echo $?
2

Com sudo funcionaria, mas há dois motivos para quase nunca fazer isso no dia a dia:

  • Tudo some no próximo boot (e às vezes antes: o NetworkManager pode desfazer a mudança). Configuração permanente se faz no gerenciador de rede, com nmcli (veja NetworkManager e iwd).
  • Por SSH, derrubar a placa corta o seu próprio acesso. Por isso o comando acima não foi repetido com sudo na VM do guia.

ping: o destino responde?

O ping manda pequenos pacotes de teste (do protocolo ICMP, o "de serviço" da internet) e mede quanto tempo a resposta demora. No Linux ele não para sozinho: sem limite, continua até você apertar Ctrl+C. Por isso quase sempre se usa -c.

ping
O programa (o nome imita o "ping" do sonar).
-c 3
De count: envia 3 pacotes e para.
archlinux.org
O destino: um nome ou um IP.
$ ping -c 3 archlinux.org
PING archlinux.org (209.126.35.79) 56(84) bytes de dados.                 « o nome virou este IP
64 bytes de 209.126.35.79: icmp_seq=1 ttl=64 tempo=41.6 ms                « resposta 1, em 41,6 ms
64 bytes de 209.126.35.79: icmp_seq=2 ttl=64 tempo=40.9 ms
64 bytes de 209.126.35.79: icmp_seq=3 ttl=64 tempo=41.7 ms

--- archlinux.org estatísticas de ping ---
3 pacotes transmitidos, 3 recebidos, 0% packet loss, time 2384ms           « nenhum perdido
rtt min/avg/max/mdev = 40.864/41.369/41.660/0.358 ms                        « mínimo/médio/máximo/variação
$ echo $?
0

Repare: no Arch o ping fala português ("bytes de dados", "tempo=", "estatísticas de ping"), porque o pacote iputils traz a tradução. Só algumas partes ficam em inglês (packet loss, time, rtt). Os números usam ponto (41.6), não vírgula.

ParteSignificado
PING archlinux.org (209.126.35.79)O DNS funcionou: o nome foi traduzido para este IP. Se o erro aparecer aqui, o problema é de nome (veja curl, wget, dig).
56(84) bytes de dadosCada pacote leva 56 bytes de dados (84 com os cabeçalhos).
icmp_seq=1Número do pacote. Se aparecer 1, 2, 4, o 3 se perdeu.
ttl=64"Tempo de vida": quantos roteadores o pacote ainda poderia atravessar.
tempo=41.6 msIda e volta, em milissegundos. Até uns 50 ms é rápido; acima de 200 ms dá para sentir num jogo ou numa chamada.
0% packet lossPorcentagem de pacotes sem resposta. O ideal é 0%.
rtt min/avg/max/mdevTempos mínimo, médio, máximo e a variação (mdev). Variação alta = conexão instável.

O tempo depende do momento. Rodado de novo, minutos depois, o mesmo comando na VM deu tempo=166 ms, 829 ms e 745 ms: a rede estava ocupada. Por isso vale mandar vários pacotes e olhar a média.

Sem -c: parar com Ctrl+C

Sem limite, o ping continua. Ao apertar Ctrl+C, ele para e mostra o resumo do que mandou até ali (na VM: 3 pacotes em cerca de 3 segundos):

$ ping archlinux.org
PING archlinux.org (209.126.35.79) 56(84) bytes de dados.
64 bytes de 209.126.35.79: icmp_seq=1 ttl=64 tempo=42.8 ms
64 bytes de 209.126.35.79: icmp_seq=2 ttl=64 tempo=44.7 ms
64 bytes de 209.126.35.79: icmp_seq=3 ttl=64 tempo=41.5 ms
^C                                                                   « aqui a ana apertou Ctrl+C
--- archlinux.org estatísticas de ping ---
3 pacotes transmitidos, 3 recebidos, 0% packet loss, time 2927ms
rtt min/avg/max/mdev = 41.539/43.004/44.683/1.292 ms

O que o ping devolve: códigos 0, 1 e 2

Em scripts, o que importa é o código de saída (echo $?). O ping usa três valores, e cada um aponta para um problema diferente:

$ ping -c 2 -W 1 10.0.2.99
PING 10.0.2.99 (10.0.2.99) 56(84) bytes de dados.

--- 10.0.2.99 estatísticas de ping ---
2 pacotes transmitidos, 0 recebidos, 100% packet loss, time 1613ms

$ echo $?
1                                                    « enviou, mas ninguém respondeu
$ ping -c 1 nao-existe.invalid
ping: nao-existe.invalid: Nome ou serviço desconhecido
$ echo $?
2                                                    « erro antes de enviar: o nome não existe
$ ping -c 1 127.0.0.1 > /dev/null; echo $?
0                                                    « respondeu
CódigoQuer dizerCausa típica
0Pelo menos uma resposta chegouTudo certo
1Os pacotes saíram, mas nenhum voltouMáquina desligada, IP errado ou ping bloqueado
2Erro antes de enviarNome inexistente (DNS), sem rede, opção errada (ping sozinho: ping: usage error: Endereço de destino requerido)

O -W 1 (de wait) espera no máximo 1 segundo por resposta. Com isso dá para escrever, por exemplo: ping -c 1 -W 2 10.0.2.2 > /dev/null && echo "roteador ok".

Ping sem resposta nem sempre é problema

Muitos servidores e firewalls bloqueiam o ping de propósito. Se o site abre no navegador mas o ping dá 100% de perda, a sua rede está bem. Para testar um site de verdade, use o curl (veja curl, wget, dig).

O roteiro de diagnóstico

Quando "a internet não funciona", teste nesta ordem. O primeiro passo que falhar mostra onde está o problema:

Teste, nesta ordemSe falhar, o problema é…
ip -br a mostra um IPv4 na placa?Cabo, Wi-Fi ou DHCP (veja NetworkManager e iwd)
ip route tem a linha default via?DHCP ou configuração do gerenciador
ping -c 3 IP-do-gateway (o via; na VM, 10.0.2.2)A rede local ou o roteador
ping -c 3 1.1.1.1A saída do roteador para a internet (o provedor)
ping -c 3 archlinux.orgO DNS, se o passo anterior funcionou

O caminho até o destino: tracepath

Entre você e um site há vários roteadores; cada um é um salto (hop). O tracepath, que vem no iputils junto com o ping, mostra os saltos um a um, para descobrir onde a conexão para.

tracepath
O programa (não precisa de root).
-n
Mostra só os IPs, sem tentar descobrir o nome de cada roteador (mais rápido).
-m 6
No máximo 6 saltos (o padrão é 30).
archlinux.org
O destino.
$ tracepath -n -m 6 archlinux.org
 1?: [LOCALHOST]                      pmtu 1500                  « a própria máquina
 1:  10.0.2.2                                              0.416ms        « salto 1: o roteador do VirtualBox
 1:  10.0.2.2                                              0.357ms
 2:  192.168.0.1                                          81.732ms asymm  1     « salto 2: o roteador da casa
 3:  192.168.0.1                                           7.363ms pmtu 0
 3:  falha no envio
     Resumir: pmtu 0

Cada linha numerada é um salto, com o tempo até ele. pmtu é o maior pacote que passa pelo caminho. asymm quer dizer que a resposta voltou por um caminho diferente da ida. Sem o -n, os nomes aparecem no lugar dos números (na VM, _gateway para o 10.0.2.2, nome que o systemd dá ao gateway).

Por que a VM não passa do salto 3

A rede da VM é a "NAT" do VirtualBox, que não repassa as respostas que o tracepath precisa ouvir dos roteadores da internet; por isso ela para no roteador de casa com falha no envio ("Resumir" é a tradução, um pouco estranha, de Resume). Num computador ligado direto no roteador, a lista continua até o destino. Saltos que não respondem aparecem como no reply, e isso é comum: muitos roteadores não respondem de propósito.

E o traceroute?

O clássico traceroute não vem no Arch:

$ traceroute archlinux.org
bash: traceroute: comando não encontrado

Ele é um pacote à parte, pequeno. A transação real (respondida com n, então nada foi instalado na VM):

#> pacman -S traceroute
resolvendo dependências...
procurando pacotes conflitantes...

Pacotes (1) traceroute-2.1.6-1

Tamanho total download:   0,04 MiB
Tamanho total instalado:  0,08 MiB

:: Continuar a instalação? [S/n] n

Para o dia a dia, o tracepath basta. O traceroute tem mais opções (usar TCP na porta 443, por exemplo: traceroute -T -p 443, como root), úteis quando o caminho bloqueia os pacotes comuns. Outra opção popular é o mtr (pacote mtr), que junta ping e traceroute numa tela que se atualiza sozinha.

ss: conexões e portas abertas

O ss (de socket statistics) lista as conexões de rede. Um socket é a "tomada" que um programa abre para conversar pela rede, numa porta (um número de 1 a 65535: 22 é o SSH, 80 o HTTP, 443 o HTTPS). A combinação mais usada é ss -tulpn, que responde "quais portas estão esperando conexões nesta máquina?". Você vai usá-la antes de mexer no firewall.

ss
O programa.
-t
Conexões TCP (a maioria: web, SSH, e-mail).
-u
Conexões UDP (DNS, DHCP, jogos, vídeo).
-l
Só as que estão listening, "escutando", à espera de alguém.
-p
Mostra o programa (process) dono de cada porta.
-n
Números em vez de nomes: 22 em vez de ssh.

Como usuária comum:

$ ss -tulpn
Netid State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
tcp   LISTEN 0      128          0.0.0.0:22        0.0.0.0:*                   « alguém escuta na porta 22
tcp   LISTEN 0      128             [::]:22           [::]:*

A coluna Process veio vazia. Não é erro: o sshd pertence ao root, e o Linux não deixa uma usuária comum ver os detalhes dos processos de outro usuário. Com sudo, o nome aparece:

$ sudo ss -tulpn
Netid State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
tcp   LISTEN 0      128          0.0.0.0:22        0.0.0.0:*    users:(("sshd",pid=310,fd=6))     « o servidor SSH
tcp   LISTEN 0      128             [::]:22           [::]:*    users:(("sshd",pid=310,fd=7))
ColunaSignificado
NetidO protocolo: tcp ou udp.
StateLISTEN: esperando conexões. UNCONN: porta UDP aberta (UDP não tem "conexão"). ESTAB: conexão estabelecida.
Recv-Q / Send-QFilas de dados. Numa porta LISTEN, o Send-Q (128) é quantas conexões podem esperar na fila.
Local Address:PortEm qual endereço e porta o programa escuta. 0.0.0.0 = todas as placas IPv4; [::] = todas IPv6; 127.0.0.1 = só a própria máquina (ninguém de fora alcança).
Peer Address:PortO outro lado. * quando ainda não há ninguém.
ProcessPrograma, PID e número do descritor. Completo só com sudo.

Essa lista curta é típica de um Arch: no Arch, nenhum serviço vem ligado, então só aparece o que você habilitou. Na VM, só o SSH. Quando outro autor do guia estava com o nginx ligado, apareceram também as portas 80 e 8080. Num desktop, é comum ver a impressora (631) e a descoberta de rede do avahi (5353, UDP).

Conexões ativas: ss -tn

Sem o -l, o ss mostra as conexões já estabelecidas. Na VM, são as sessões SSH dos autores do guia, vindas do roteador do VirtualBox (10.0.2.2):

$ ss -tn
State Recv-Q Send-Q Local Address:Port Peer Address:Port
ESTAB 0      0          10.0.2.15:22       10.0.2.2:49668      « alguém conectado no SSH
ESTAB 0      0          10.0.2.15:22       10.0.2.2:34228
$ sudo ss -tnp
State Recv-Q Send-Q Local Address:Port Peer Address:Port Process
ESTAB 0      0          10.0.2.15:22       10.0.2.2:47354 users:(("sshd-session",pid=1088,fd=7),("sshd-session",pid=1066,fd=7))

A porta do outro lado (49668) é sorteada pelo cliente a cada conexão. Cada sessão SSH aparece como um processo sshd-session.

Filtrar uma porta

O ss aceita filtros no fim. sport é a porta de origem (a sua), dport, a de destino:

$ ss -tln sport = :22
State  Recv-Q Send-Q Local Address:Port Peer Address:Port
LISTEN 0      128          0.0.0.0:22        0.0.0.0:*
LISTEN 0      128             [::]:22           [::]:*

O jeito "de pipe" também funciona e é mais fácil de lembrar: sudo ss -tlnp | grep 22 (veja grep).

E o resolvectl?

Muitos tutoriais mostram o DNS com resolvectl status. O comando existe no Arch (vem no systemd), mas depende do serviço systemd-resolved, que vem desligado. Na VM, quem cuida do DNS é o NetworkManager, escrevendo o /etc/resolv.conf. Resultado:

$ resolvectl status
Failed to connect to service /run/systemd/resolve/io.systemd.Resolve: Arquivo ou diretório inexistente
$ echo $?
1
$ cat /etc/resolv.conf
# Generated by NetworkManager
search lan
nameserver 10.0.2.3                    « o servidor de DNS em uso
nameserver fd17:625c:f037:2::3

Não é defeito: é o padrão do Arch. Para ligar o resolved, veja a seção de DNS de NetworkManager e iwd; para perguntar ao DNS, use as ferramentas de curl, wget, dig.

Experimente

O terminal simulado tem a rede da VM: as placas, os endereços e as rotas são os reais. (ping, ss e tracepath não funcionam nele: para esses, use as saídas desta aula ou o seu Arch.)

Missão 1: mostre os endereços de todas as placas, uma linha por placa. Qual é o IPv4 da placa com cabo?

Missão 2: descubra o gateway da máquina: mostre a tabela de rotas e encontre a linha default.

Missão 3: qual é o endereço físico (MAC) da placa enp0s3? Use o objeto do ip que mostra as placas sem os IPs.

Quando não funciona

"Nome ou serviço desconhecido" 
$ ping -c 1 nao-existe.invalid
ping: nao-existe.invalid: Nome ou serviço desconhecido

O que aconteceu: o computador não conseguiu transformar o nome em IP: erro de digitação, DNS sem resposta ou nenhuma rede.

Como confirmar: teste um IP direto, sem nome: ping -c 3 1.1.1.1. Se o IP responde e o nome não, o problema é o DNS. Veja os servidores em cat /etc/resolv.conf.

Como resolver: confira a grafia; depois, o DNS do perfil no NetworkManager (NetworkManager e iwd).

100% de perda de pacotes 
$ ping -c 2 -W 1 10.0.2.99
PING 10.0.2.99 (10.0.2.99) 56(84) bytes de dados.

--- 10.0.2.99 estatísticas de ping ---
2 pacotes transmitidos, 0 recebidos, 100% packet loss, time 1613ms

O que aconteceu: o destino não respondeu (código 1). Pode estar desligado, num IP diferente ou bloqueando ping.

Como confirmar: faça ping no seu gateway (o via do ip route). Se nem o gateway responde, o problema é a sua própria conexão.

A placa aparece DOWN, sem IP ou sem default

O que aconteceu: no ip -br a, a placa está DOWN ou sem endereço IPv4; ou o ip route não tem a linha default.

Como confirmar: ip a show enp0s3: sem LOWER_UP, o cabo está solto ou o Wi-Fi não está associado. Com LOWER_UP mas sem inet, o DHCP falhou. Veja também systemctl is-active NetworkManager.

Como resolver: confira o cabo; reconecte com nmcli connection up NOME; se o gerenciador estiver parado, sudo systemctl enable --now NetworkManager (veja NetworkManager e iwd).

"RTNETLINK answers: Operation not permitted" 
$ ip link set enp0s3 down
RTNETLINK answers: Operation not permitted

O que aconteceu: você tentou mudar a rede como usuária comum (código 2).

Como resolver: mudanças pedem sudo, e são temporárias. Para algo permanente, use o nmcli. Nunca derrube a placa pela qual você está conectado por SSH.

"ifconfig: comando não encontrado" / "netstat: comando não encontrado"

O que aconteceu: são do pacote antigo net-tools, que o Arch não instala.

Como resolver: use ip a no lugar do ifconfig e ss -tulpn no lugar do netstat -tulpn. Não há necessidade de instalar o net-tools.

"hostname: invalid option -- 'I'"

O que aconteceu: o hostname -I é do Debian e do Ubuntu. O hostname do Arch vem do inetutils e não tem essa opção (e, numa instalação nova, nem o hostname existe: bash: hostname: comando não encontrado).

Como resolver: hostname -i, ou melhor, ip -br a. Para o nome da máquina sem instalar nada: cat /etc/hostname ou hostnamectl.

O ss não mostra o programa

O que aconteceu: sem root, a coluna Process fica vazia para portas de outros usuários (quase todos os serviços são do root).

Como resolver: sudo ss -tulpn (veja sudo, root e Usuários).

Resumo

  • ip e ss (pacote iproute2) e ping e tracepath (iputils) vêm no base; ifconfig, netstat e traceroute, não.
  • ip -br a mostra o IP de cada placa; ip a, todos os detalhes (LOWER_UP = cabo/sinal; dynamic = DHCP).
  • ip route mostra o gateway na linha default via; sem ela não há internet.
  • ping -c N testa resposta, em português no Arch; código 0 = respondeu, 1 = sem resposta, 2 = erro (nome inexistente).
  • tracepath mostra os saltos até o destino.
  • ss -tulpn lista as portas abertas; o nome do programa só aparece com sudo.
  • resolvectl falha porque o systemd-resolved vem desligado: o DNS está no /etc/resolv.conf.

Na Arch Wiki: a página Network configuration (em português) explica o ip, os nomes das placas, a verificação da conexão com ping e a lista de portas com ss; os detalhes da placa com cabo estão em Network configuration/Ethernet; o DNS (e por que o resolvectl depende de um serviço) em Domain name resolution e systemd-resolved.
