Arch Estrutura de Diretórios

No Windows existem o C:, o D:, e cada disco tem a sua árvore. No Linux existe uma árvore só, que começa numa pasta chamada / (a "raiz"). Tudo fica pendurado nela: seus arquivos, os programas, as configurações, o kernel, os pacotes baixados pelo pacman e até os pendrives. Nesta aula você conhece cada galho dessa árvore num Arch real.

Você vai aprender
  • O que é a raiz / e como ver o que existe nela.
  • Para que serve cada pasta principal, com uma tabela completa.
  • Por que no Arch /bin, /sbin e /lib são só atalhos para dentro de /usr.
  • O que fica em /boot (uma partição FAT32 à parte) e em /var (o cache e a base do pacman, os logs).
  • Por que o /tmp some ao reiniciar e por que ninguém além de você abre a sua pasta pessoal.

Os exemplos acontecem na máquina notebook, com a usuária ana, instalada à mão seguindo a Arch Wiki. As saídas foram copiadas dessa máquina.

A raiz: /

A barra sozinha, /, é a pasta de cima de todas. Para ver o que há nela, liste-a com ls:

ls
O programa que lista o conteúdo de uma pasta (de list).
/
O argumento: a pasta a listar. Aqui, a raiz.
$ ls /
bin   dev  home  lib64       mnt  proc  run   srv  tmp  var
boot  etc  lib   lost+found  opt  root  sbin  sys  usr

São 19 itens, menos que em outras distribuições: o Arch não cria /media nem os atalhos vmlinuz na raiz que o Debian cria. Você não precisa decorar todos: no dia a dia você vai usar /home, /etc, /var e /tmp. Os outros aparecem quando você for administrar a máquina.

O tree (pacote tree, instalado na máquina do guia) desenha a mesma coisa como árvore, e já mostra quais itens são atalhos:

$ tree -L 1 /
/
├── bin -> usr/bin
├── boot
├── dev
├── etc
├── home
├── lib -> usr/lib
├── lib64 -> usr/lib
├── lost+found
├── mnt
├── opt
├── proc
├── root
├── run
├── sbin -> usr/bin
├── srv
├── sys
├── tmp
├── usr
└── var

20 directories, 0 files

O -L 1 limita a um nível (level): sem ele, o tree desceria por todas as pastas do sistema, o que leva muito tempo. O "20 directories" conta a própria raiz.

Árvore de cabeça para baixo

Pense numa árvore genealógica: a raiz / fica em cima e as pastas se ramificam para baixo. /home/ana/Documentos se lê "a pasta Documentos, dentro de ana, dentro de home, dentro da raiz". A aula Caminhos ensina a escrever esses endereços.

O mapa das pastas

Essa organização segue um padrão chamado FHS (Filesystem Hierarchy Standard, "padrão da hierarquia do sistema de arquivos"), por isso é quase igual em qualquer Linux. No Arch, o próprio padrão tem página de manual: man file-hierarchy (veja Obtendo Ajuda). As pastas vêm do pacote filesystem, o primeiro que o pacstrap instala.

/usr: tudo mora aqui (e /bin é só um atalho)

Na listagem da raiz aparecem bin, sbin, lib e lib64. No Arch, nenhum deles é pasta de verdade: são links simbólicos, atalhos para pastas dentro de /usr. O -l do ls mostra para onde cada um aponta, e o -d mostra o próprio item, não o conteúdo dele:

ls
Lista.
-l
Formato longo: a primeira letra l indica um link, e a seta -> mostra o destino.
-d
Mostra o item em si (de directory), sem entrar nele.
/bin /sbin /lib /lib64 /usr/sbin /usr/lib64
Seis argumentos: os seis atalhos.
$ ls -ld /bin /sbin /lib /lib64 /usr/sbin /usr/lib64
lrwxrwxrwx 1 root root 7 12 out  2025 /bin -> usr/bin        « l = link; a seta mostra o destino
lrwxrwxrwx 1 root root 7 12 out  2025 /lib -> usr/lib
lrwxrwxrwx 1 root root 7 12 out  2025 /lib64 -> usr/lib       « no Arch, lib64 e lib são a mesma pasta
lrwxrwxrwx 1 root root 7 12 out  2025 /sbin -> usr/bin       « sbin também vai para usr/bin!
lrwxrwxrwx 1 root root 3 12 out  2025 /usr/lib64 -> lib
lrwxrwxrwx 1 root root 3 12 out  2025 /usr/sbin -> bin

A data 12 out 2025 é a do pacote filesystem, que criou esses atalhos. Antigamente, os programas básicos ficavam em /bin, os de administrador em /sbin e o resto em /usr/bin. O Arch juntou tudo num lugar só, /usr/bin, e foi mais longe que o Debian: até o /sbin e o /usr/sbin apontam para /usr/bin. Os atalhos só existem para que scripts antigos, que chamam /bin/bash ou /sbin/fdisk, sigam funcionando.

Você pode confirmar com o pwd: o -P mostra o caminho físico, já resolvido.

$ cd /bin
$ pwd
/bin
$ pwd -P
/usr/bin                       « o lugar de verdade

Consequência: os comandos de administrador estão no seu PATH

O PATH é a lista de pastas onde o shell procura os comandos. No Arch, a da Ana já inclui /usr/bin, e portanto tudo:

$ echo $PATH
/usr/local/sbin:/usr/local/bin:/usr/bin:/usr/bin/site_perl:/usr/bin/vendor_perl:/usr/bin/core_perl
$ type fdisk
fdisk é /usr/bin/fdisk
$ fdisk -l
fdisk: não foi possível abrir /dev/sda: Permissão negada
fdisk: não foi possível abrir /dev/sr0: Permissão negada

Diferente do Debian, onde um usuário comum recebe "comando não encontrado" para fdisk, no Arch o comando é encontrado, mas o disco recusa: ler discos é coisa de administrador. Com sudo fdisk -l funciona (veja sudo, root e Usuários).

Missão: você está em /bin. Descubra em que pasta você está de verdade, resolvendo o atalho.

/etc: as configurações

Quase toda configuração do sistema é um arquivo de texto em /etc (na máquina do guia, 147 itens). Como são textos, dá para descobrir muita coisa só lendo:

$ cat /etc/hostname
notebook
$ ls -l /etc/localtime
lrwxrwxrwx 1 root root 37 16 out 12:09 /etc/localtime -> /usr/share/zoneinfo/America/Sao_Paulo
$ grep -v '^#' /etc/pacman.conf | grep -v '^$' | head -12
[options]
HoldPkg     = pacman glibc
Architecture = auto
CheckSpace
ParallelDownloads = 5
DownloadUser = alpm
SigLevel    = Required DatabaseOptional
LocalFileSigLevel = Optional
[core]
Include = /etc/pacman.d/mirrorlist
[extra]
Include = /etc/pacman.d/mirrorlist

O /etc/pacman.conf configura o pacman e lista os repositórios ([core], [extra]); cada repositório usa os servidores de /etc/pacman.d/mirrorlist. Os dois grep só escondem os comentários e as linhas vazias (veja grep). Você vai editar arquivos de /etc muitas vezes, sempre com sudo, e o pacman tem um cuidado especial com eles (veja .pacnew e .pacsave).

/home e /root: as casas, trancadas

Cada usuário tem uma pasta dentro de /home. A da Ana é /home/ana, e o til (~) é um apelido para ela. Veja as permissões:

$ ls /home
ana
$ ls -ld /home/ana
drwx------ 15 ana ana 4096 15 out 08:47 /home/ana

O drwx------ quer dizer que só a dona (ana) pode ler, escrever e entrar. Outros usuários da mesma máquina não conseguem nem listar o que há lá dentro. No Arch, o useradd -m cria a pasta pessoal com permissão 700. Você vai ler essas letras com calma em Entendendo Permissões.

A pasta do administrador, /root, fica fora de /home (para continuar acessível mesmo se /home estiver em outro disco que não montou) e também é fechada:

$ ls -ld /root
drwxr-x--- 3 root root 4096 16 out 13:05 /root
$ ls /root
ls: não foi possível abrir o diretório '/root': Permissão negada
$ cd /root
bash: cd: /root: Permissão negada
$ echo $?
1

Missão: confira as permissões da sua própria pasta pessoal com ls -ld ~ e depois tente entrar em /root com cd /root para ver a resposta.

/boot: a partição EFI, em FAT32

Em /boot fica o que o computador precisa para ligar: o kernel, o initramfs e o carregador de boot. Num Arch instalado como manda a Wiki em UEFI, /boot não é uma pasta comum: é uma partição separada, a partição de sistema EFI (ESP), formatada em FAT32, porque é o único formato que o firmware do computador sabe ler. O findmnt mostra de onde vem cada pasta montada:

$ findmnt /boot
TARGET SOURCE    FSTYPE OPTIONS
/boot  /dev/sda1 vfat   rw,relatime,fmask=0022,dmask=0022,codepage=437,iocharset=ascii,shortname=mixed,utf8,errors=remount-ro
$ findmnt /
TARGET SOURCE    FSTYPE OPTIONS
/      /dev/sda3 ext4   rw,relatime

vfat é o nome que o Linux dá à família FAT. Agora veja o conteúdo:

$ ls -la /boot
total 78268
drwxr-xr-x  4 root root     4096 31 dez  1969 .                         « FAT não guarda data da raiz
dr-xr-xr-x 17 root root     4096 16 out 12:08 ..
drwxr-xr-x  3 root root     4096 16 out 12:10 EFI                       « o GRUB para o firmware UEFI
drwxr-xr-x  6 root root     4096 16 out 13:03 grub                      « configuração do GRUB
-rwxr-xr-x  1 root root 15555951 16 out 12:58 initramfs-linux.img
-rwxr-xr-x  1 root root 15554295 16 out 12:58 initramfs-linux-lts.img
-rwxr-xr-x  1 root root 15265792 25 set 19:53 intel-ucode.img             « microcódigo do processador
-rwxr-xr-x  1 root root 17240576 16 out 12:09 vmlinuz-linux               « o kernel linux
-rwxr-xr-x  1 root root 16503296 16 out 12:58 vmlinuz-linux-lts           « o kernel linux-lts
ItemO que é
vmlinuz-linuxO kernel do pacote linux. No Arch o nome não tem a versão; o arquivo é substituído a cada atualização.
initramfs-linux.imgUm mini-sistema que o kernel usa para achar e montar a raiz, gerado pelo mkinitcpio.
*-ltsO segundo kernel instalado na máquina do guia (linux-lts), de reserva.
intel-ucode.imgCorreções do processador Intel, carregadas antes do kernel.
grub/, EFI/O carregador de boot GRUB (veja Bootloader).

Dois detalhes vêm do FAT32, que não conhece dono nem permissões do Linux: todos os arquivos aparecem como root com -rwxr-xr-x (quem decide isso são as opções fmask=0022,dmask=0022 da montagem), e a pasta raiz da partição não tem data, por isso aparece o "dia zero" do Unix (1º de janeiro de 1970 em UTC, que no fuso de Brasília vira 31 dez 1969).

Não mexa em /boot à mão

Apagar ou renomear algo aqui pode deixar o computador sem ligar. Quem cuida desses arquivos são o pacman (ao atualizar o kernel), o mkinitcpio e o grub-mkconfig. Se a partição encher ou não montar, o próximo pacman -Syu falha ao copiar o kernel; veja Atualizar o Sistema.

/var: o que muda (pacman e logs)

Em /var (de variable) fica tudo o que cresce e muda enquanto o sistema roda:

$ ls /var
cache  db  empty  games  lib  local  lock  log  mail  opt  run  spool  tmp

/var/cache/pacman/pkg: os pacotes baixados

Todo pacote que o pacman instala é baixado primeiro para cá, e fica aqui depois de instalado:

$ ls /var/cache/pacman/pkg | head -5
aardvark-dns-2.1.0-3-x86_64.pkg.tar.zst
aardvark-dns-2.1.0-3-x86_64.pkg.tar.zst.sig            « a assinatura digital do pacote
abseil-cpp-20260817.0-2-x86_64.pkg.tar.zst
abseil-cpp-20260817.0-2-x86_64.pkg.tar.zst.sig
accountsservice-26.27.3-1-x86_64.pkg.tar.zst
$ ls /var/cache/pacman/pkg/*.pkg.tar.zst | wc -l
404
$ du -sh /var/cache/pacman/pkg 2>/dev/null
1,3G	/var/cache/pacman/pkg

404 pacotes ocupam 1,3 GB. Guardá-los permite voltar a uma versão anterior sem internet, mas o cache cresce a cada atualização e é o motivo número 1 de disco cheio no Arch. O 2>/dev/null esconde avisos de "Permissão negada" de subpastas temporárias do pacman. A limpeza é assunto de Cache e Órfãos.

/var/log: o journal e o pacman.log

$ ls /var/log
audit  btmp  journal  lastlog  nginx  old  pacman.log  private  wtmp
$ ls /var/log/journal
42634ff99dd3440394e6cd711c974f65              « o "machine ID" desta máquina
$ head -2 /var/log/pacman.log
[2026-10-16T15:02:24+0000] [PACMAN] Running 'pacman -b /mnt//var/lib/pacman/ -r /mnt -Sy --config=/tmp/pacman.conf.2ZHS --disable-sandbox --noconfirm --cachedir=/mnt//var/cache/pacman/pkg/ base linux linux-firmware intel-ucode networkmanager sudo nano vim man-db man-pages texinfo grub efibootmgr openssh'
[2026-10-16T15:02:24+0000] [PACMAN] synchronizing package lists

O Arch não tem o arquivo /var/log/syslog dos tutoriais antigos: os registros do sistema ficam no journal do systemd, em formato binário, e se leem com journalctl (veja journalctl). Já o pacman.log é texto puro e conta toda a história dos pacotes: a primeira linha é o próprio pacstrap da instalação (com a hora em UTC, +0000, porque o pendrive de instalação não sabia o fuso).

Missão: mostre as 3 últimas linhas do registro do pacman, em /var/log. Dica: tail -3 mostra o fim de um arquivo.

/tmp: o que está lá some ao reiniciar

No Arch, a pasta /tmp fica na memória RAM, não no disco:

$ findmnt /tmp
TARGET SOURCE FSTYPE OPTIONS
/tmp   tmpfs  tmpfs  rw,nosuid,nodev,nr_inodes=1048576,inode64,huge=advise,usrquota      « tmpfs = na memória
$ findmnt /var/tmp
$ echo $?
1                                « nada: /var/tmp não é montagem própria, fica no disco da raiz

Isso deixa o /tmp rápido, mas tem uma consequência: tudo o que estiver lá desaparece quando o computador reinicia. O tamanho máximo é metade da RAM (no df -h, tmpfs 1,9G … /tmp numa máquina de 4 GB).

Atenção

Nunca guarde em /tmp nada que você queira manter. Baixou um arquivo para lá? Mova para a sua pasta pessoal antes de desligar. Temporários que precisam sobreviver a um reinício vão em /var/tmp.

/run, /dev, /proc e /sys: pastas que não estão no disco

Quatro pastas da raiz são criadas pelo kernel e pelo systemd a cada boot e não ocupam disco. Repare no tamanho 0 do /proc e do /sys no ls -l /:

$ ls -l / | grep -E ' (dev|proc|run|sys)$'

dr-xr-xr-x 121 root root     0 16 out 14:50 proc
drwxr-xr-x  25 root root   600 16 out 14:51 run
dr-xr-xr-x  13 root root     0 16 out 14:50 sys

/opt, /srv e /mnt: as pastas vazias

$ ls /opt /mnt
/mnt:

/opt:
$ ls /srv
ftp  http

As três começam vazias (o /srv só com duas subpastas vazias criadas pelo pacote filesystem). O /opt recebe programas grandes que vêm "inteiros" de fora, como alguns pacotes do AUR (veja O que é o AUR). O /mnt serviu, durante a instalação, para montar o sistema novo antes do arch-chroot.

O /srv/http existe, mas o servidor web nginx do Arch não usa essa pasta: a página padrão dele fica dentro do próprio pacote, em /usr/share/nginx/html:

$ ls /usr/share/nginx/html
50x.html  index.html
$ pacman -Qo /usr/share/nginx/html/index.html
/usr/share/nginx/html/index.html pertence a nginx 1.30.5-1

Quando você publicar um site de verdade, a recomendação é colocá-lo em /srv/http e apontar o nginx para lá (veja Servidor Web).

Quando não funciona

"Permissão negada" ao entrar numa pasta 
$ cd /root
bash: cd: /root: Permissão negada

O que aconteceu: a pasta pertence a outro usuário e está fechada para você.

Como resolver: se for mesmo necessário, use sudo (por exemplo, sudo ls /root). Para a pasta pessoal de outra pessoa, peça a ela que compartilhe o arquivo.

Salvei um arquivo em /tmp e ele sumiu

O que aconteceu: no Arch o /tmp fica na memória (tmpfs) e é esvaziado a cada reinício.

Como resolver: guarde arquivos que importam em ~/. Para temporários que precisam sobreviver a um reinício, use /var/tmp.

"Arquivo ou diretório inexistente" no /var/log/syslog ou no /media 
$ ls /media
ls: não foi possível acessar '/media': Arquivo ou diretório inexistente

O que aconteceu: o tutorial era de outra distribuição. O Arch não tem /var/log/syslog (os logs estão no journal) nem /media (os pendrives aparecem em /run/media/SEU_USUÁRIO).

Como resolver: use journalctl para os logs e lsblk ou findmnt para achar onde o pendrive foi montado.

"Permissão negada" num comando de administrador que foi encontrado 
$ fdisk -l
fdisk: não foi possível abrir /dev/sda: Permissão negada

O que aconteceu: no Arch, /usr/sbin é o mesmo que /usr/bin, então o comando existe para você, mas o dispositivo (/dev/sda) só abre para o root.

Como resolver: sudo fdisk -l.

O disco encheu e eu não sei onde

O que aconteceu: no Arch, o suspeito número 1 é o cache do pacman; o segundo, o journal.

Como confirmar: du -sh /var/cache/pacman/pkg e journalctl --disk-usage. Use du sempre numa pasta específica, nunca em / inteiro: ler o disco todo é muito lento.

Como resolver: veja Cache e Órfãos.

Resumo

  • Há uma árvore só, que começa em /; o padrão se chama FHS (man file-hierarchy).
  • Programas em /usr/bin; /bin, /sbin, /usr/sbin, /lib e /lib64 são atalhos para dentro de /usr.
  • Configurações em /etc; seus arquivos em /home/ana (o ~, modo 700); o root em /root.
  • /boot é a partição EFI em FAT32, com vmlinuz-linux e o initramfs.
  • /var/cache/pacman/pkg guarda os pacotes baixados; /var/lib/pacman, a base do pacman; os logs estão no journal e no pacman.log.
  • /tmp fica na memória e é esvaziado ao reiniciar; /run, /dev, /proc e /sys também não estão no disco.

Na Arch Wiki: a árvore do Arch está em Arch filesystem hierarchy; a partição de /boot, em EFI system partition (em português); o /tmp na memória, em tmpfs; o cache e a base do pacman, em pacman — Cleaning the package cache (pacman em português); e as montagens, em fstab (em português).
