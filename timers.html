Timers e tarefas agendadas

Fazer backup toda noite, limpar uma pasta toda semana, lembrar de beber água a cada hora: são tarefas agendadas. Em muitas distros quem faz isso é o velho cron. No Arch, o jeito nativo são os timers do systemd, e o próprio sistema já usa vários. O cron continua disponível (pacote cronie), mas não vem ligado.

Você vai aprender
  • Ver os timers que o Arch já usa, com systemctl list-timers.
  • Criar o seu par .service + .timer em ~/.config/systemd/user/, sem sudo.
  • Escrever horários com OnCalendar= e conferir com systemd-analyze calendar.
  • Usar o cronie e o crontab, e o que fazer se você procura o at.
  • Escolher entre timer e cron.

A ideia: um despertador e uma tarefa

Um timer do systemd são dois arquivos que trabalham juntos:

ArquivoPapelComparação
nome.serviceO quê: o comando a rodarA tarefa escrita no bilhete
nome.timerQuando: o horário ou intervaloO despertador que manda fazer a tarefa

Por padrão, o nome.timer dispara o nome.service de mesmo nome. Quem fica ligado (enable) é o timer; o serviço só roda quando o timer manda. Como é tudo systemd, você ganha de graça o log no journal, o systemctl status e a chance de rodar tarefas perdidas enquanto o computador estava desligado. Se ainda não leu, veja systemctl e Serviços.

Por dentro de um timer do sistema

$ systemctl cat shadow.timer
# /usr/lib/systemd/system/shadow.timer
[Unit]
Description=Daily verification of password and group files

[Timer]
OnCalendar=daily
AccuracySec=12h
Persistent=true
[Timer]
A seção que só os timers têm.
OnCalendar=daily
Quando: todo dia à meia-noite (detalhes abaixo).
AccuracySec=12h
Margem de atraso permitida: o systemd pode rodar até 12 horas depois, para juntar tarefas e economizar energia. O padrão é 1 minuto.
Persistent=true
Se o computador estava desligado na hora marcada, roda assim que ligar. É o que o cron não faz sozinho.

O shadow.timer não tem seção [Install] e ninguém rodou enable nele: o próprio pacote já traz o link que o liga, numa pasta de /usr/lib. Já o do snapper foi habilitado à mão, e o link dele fica em /etc:

$ ls /usr/lib/systemd/system/timers.target.wants/ /etc/systemd/system/timers.target.wants/

snapper-timeline.timer               « habilitado pelo administrador

archlinux-keyring-wkd-sync.timer     « ligados pelos pacotes
man-db.timer
shadow.timer

Os seus timers terão [Install] com WantedBy=timers.target, para o enable saber onde criar o link.

Criar o seu timer (como usuário, sem sudo)

Vamos criar um lembrete que escreve "Hora de beber água!" no journal a cada minuto (curto de propósito, para ver funcionando; na vida real seria a cada hora). Tudo como a ana, com systemctl --user, na pasta das unidades do usuário.

  1. Crie a pasta (ela não existe numa conta nova):

    $ mkdir -p ~/.config/systemd/user
$ cd ~/.config/systemd/user

  2. O serviço (o quê). Crie a6-lembrete.service com o editor que preferir:

    [Unit]
Description=Lembrete de beber água (a6)

[Service]
Type=oneshot
ExecStart=/usr/bin/logger -t lembrete "Hora de beber água!"
    Type=oneshot
    Roda uma vez e termina (não é um programa que fica rodando). É o tipo certo para tarefas agendadas.
    ExecStart=
    O comando, com o caminho completo do programa. Aqui, o logger escreve uma linha no journal com a etiqueta lembrete. Para um script seu: ExecStart=%h/bin/backup.sh (%h = a sua pasta pessoal).
    Sem [Install]
    O serviço não precisa ser habilitado: quem o chama é o timer.

  3. O timer (quando). Crie a6-lembrete.timer, com o mesmo nome:

    [Unit]
Description=Lembrete a cada minuto (a6)

[Timer]
OnCalendar=minutely
Persistent=true

[Install]
WantedBy=timers.target
    OnCalendar=minutely
    A cada minuto, no segundo 00. Para cada hora: hourly.
    Persistent=true
    Recupera execuções perdidas com a máquina desligada.
    WantedBy=timers.target
    O enable liga este timer junto com os outros timers, no login.

  4. Avise o systemd e ligue o timer (não o serviço):

    $ systemctl --user daemon-reload
$ systemctl --user enable --now a6-lembrete.timer
Created symlink '/home/ana/.config/systemd/user/timers.target.wants/a6-lembrete.timer' → '/home/ana/.config/systemd/user/a6-lembrete.timer'.
$ echo $?
0

  5. Confira. Real, na VM:

Timer de usuário só roda com você logado

O systemd do usuário nasce no seu login e morre quando a última sessão fecha. Para que os seus timers rodem com você deslogado (num servidor, por exemplo), ative o lingering: sudo loginctl enable-linger ana. Tarefas do sistema inteiro (backup de /etc, por exemplo) vão em /etc/systemd/system/, com sudo systemctl, e rodam como root.

Missão: crie o arquivo ~/.config/systemd/user/backup.timer com uma seção [Timer] que dispare todo dia (OnCalendar=daily). Dica: mkdir -p e printf '…\n…\n' > arquivo.

OnCalendar: como escrever o horário

O formato completo é DiaDaSemana Ano-Mês-Dia Hora:Minuto:Segundo. O * quer dizer "qualquer"; partes omitidas viram o padrão (data = qualquer dia; segundos = 00). Os dias da semana são em inglês (Mon, Tue, Wed, Thu, Fri, Sat, Sun).

Em vez de horário, intervalo

Além do relógio, um timer pode contar tempo a partir de um evento (os monotonic timers):

OpçãoDispara…
OnBootSec=15min15 minutos depois do boot
OnStartupSec=5min5 minutos depois que o systemd (do usuário, no --user) começou: depois do login
OnUnitActiveSec=1h1 hora depois da última vez que o serviço rodou (repete)
OnActiveSec=10s10 segundos depois que o timer foi ligado

Uma vez só: systemd-run

Para "rode isto daqui a 10 segundos (ou 2 horas), uma vez", não precisa criar arquivos. O systemd-run cria um timer temporário, que some depois de disparar:

$ systemd-run --user --on-active=10s logger -t lembrete 'Uma vez só, daqui a 10 s'
Running timer as unit: run-p93154-i91943.timer
Will run service as unit: run-p93154-i91943.service
$ systemctl --user list-timers --no-pager
NEXT                        LEFT LAST PASSED UNIT                    ACTIVATES
Fri 2026-10-16 13:41:13 -03   9s -         - run-p93154-i91943.timer run-p93154-i91943.service

1 timers listed.
Pass --all to see loaded but inactive timers, too.

Ele rodou às 13:41:23 (de novo, o minuto de tolerância) e o timer desapareceu da lista. Também aceita horário: systemd-run --user --on-calendar='18:00' comando.

O cron no Arch: cronie

O cron (de chronos, "tempo" em grego) é o agendador clássico do Unix: uma tabela, a crontab, com uma linha por tarefa. No Arch, a implementação oficial é o pacote cronie. Na VM ele está instalado, mas, como todo serviço no Arch, não vem ligado:

$ pacman -Qo /usr/bin/crontab
/usr/bin/crontab pertence a cronie 1.7.2-2
$ systemctl is-active cronie; systemctl is-enabled cronie
inactive
disabled

Num Arch novo, você instala com sudo pacman -S cronie. Ligar:

$ sudo systemctl enable --now cronie
Created symlink '/etc/systemd/system/multi-user.target.wants/cronie.service' → '/usr/lib/systemd/system/cronie.service'.
$ systemctl status cronie --no-pager | head -10

O cron roda com um ambiente mínimo

Na crontab, o PATH é curto e o seu .bashrc não é lido. Um comando que funciona no terminal pode falhar no cron por "comando não encontrado". Use caminhos completos (/usr/bin/rsync) e redirecione a saída para um arquivo para poder ver os erros (… >> ~/cron.log 2>&1). Nos timers o problema é parecido, mas os erros vão sozinhos para o journal.

As pastas do sistema: /etc/cron.*

O cronie também traz um esquema de pastas: scripts colocados em /etc/cron.hourly/ rodam a cada hora, por causa desta linha do pacote:

$ cat /etc/cron.d/0hourly
# Run the hourly jobs
SHELL=/bin/bash
PATH=/sbin:/bin:/usr/sbin:/usr/bin
MAILTO=root
01 * * * * root run-parts /etc/cron.hourly
$ ls /etc/cron.d /etc/cron.daily /etc/cron.hourly
/etc/cron.d:
0hourly

/etc/cron.daily:

/etc/cron.hourly:
0anacron
snapper

Repare na sexta coluna: nas tabelas do sistema (/etc/cron.d/), há um campo a mais, o usuário (root). O 0anacron roda o anacron, que executa as tarefas diárias/semanais perdidas com a máquina desligada. /etc/cron.daily está vazio: os pacotes do Arch usam timers, não cron.

E o at?

O at é o agendador "uma vez só" clássico (echo comando | at 18:00). Ele não vem no Arch e não estava na VM:

$ at
bash: at: comando não encontrado
$ pacman -Si at | head -4
Repositório          : extra
Nome                 : at
Versão               : 3.2.5-5
Descrição            : AT and batch delayed command scheduling utility and daemon

Se quiser, instale com sudo pacman -S at e ligue o serviço dele com sudo systemctl enable --now atd. Mas o systemd-run --on-active= / --on-calendar=, que você viu acima, faz o mesmo sem pacote extra.

Quando não funciona

O timer está na lista, mas a tarefa falha

O que aconteceu: o timer disparou, mas o .service deu erro (caminho errado no ExecStart, script sem permissão de execução).

Como confirmar: systemctl --user status nome.service e journalctl --user -u nome.service. Rode o serviço à mão: systemctl --user start nome.service.

Como resolver: use caminhos completos; chmod +x no script (veja Permissões); depois de editar, systemctl --user daemon-reload.

"Failed to parse calendar specification" 
$ systemd-analyze calendar 'segunda 08:00'
Failed to parse calendar specification 'segunda 08:00': Argumento inválido
$ echo $?
1

O que aconteceu: os nomes dos dias são em inglês (Mon). A mesma expressão num .timer faz o timer não carregar.

Como resolver: Mon 08:00. Teste sempre com systemd-analyze calendar antes de colocar no arquivo.

Escrevi a crontab, mas nada acontece

O que aconteceu: no Arch, o cronie não vem ligado (e às vezes nem instalado). A crontab é aceita, mas ninguém a lê.

Como confirmar: systemctl is-active cronie responde inactive; journalctl -u cronie não mostra linhas CMD.

Como resolver: sudo systemctl enable --now cronie. Se ainda falhar, é o ambiente: caminhos completos e >> arquivo 2>&1.

"no crontab for ana"

O que aconteceu: não é erro: você ainda não tem crontab (código de saída 1). Crie com crontab -e.

Meu timer de usuário não rodou à noite

O que aconteceu: você estava deslogado: o systemd do usuário só existe com uma sessão aberta.

Como resolver: sudo loginctl enable-linger ana, ou transforme-o em timer do sistema (/etc/systemd/system/, User=ana no .service). Com Persistent=true, ele roda no próximo login.

6. Qual comando mostra quando os timers do sistema vão disparar?

Resumo

  • No Arch, o jeito nativo de agendar é o timer do systemd: um .service (o quê) + um .timer (quando).
  • Os seus vão em ~/.config/systemd/user/ e se ligam com systemctl --user enable --now nome.timer.
  • OnCalendar= usa dias em inglês; teste com systemd-analyze calendar.
  • Persistent=true recupera execuções perdidas; o atraso de até 1 minuto é o AccuracySec.
  • O cron existe (cronie), mas precisa de enable --now; o at não vem instalado (use systemd-run).

Na Arch Wiki: os timers estão em systemd/Timers (em português), com a seção "As a cron replacement" comparando com o cron; o cron e o cronie, em Cron; os serviços de usuário e o lingering, em systemd/User. O formato completo de horários está em man systemd.time.
