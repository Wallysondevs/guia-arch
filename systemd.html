systemctl e serviços

Um serviço é um programa que roda em segundo plano, sem janela: o servidor SSH, o gerenciador de rede, um servidor web. No Arch, quem liga, desliga e vigia esses programas é o systemd, e você conversa com ele pelo comando systemctl (system control). É uma das ferramentas mais usadas na administração do Arch.

Você vai aprender
  • O que são o systemd, as unidades e os estados active e enabled.
  • Ler o systemctl status linha por linha.
  • Ligar, desligar, reiniciar e habilitar no boot (start, stop, restart, reload, enable, disable, --now).
  • Listar serviços, achar os que falharam e ler um arquivo .service.
  • Personalizar um serviço com systemctl edit e usar serviços do seu usuário com systemctl --user.

systemd, unidades e o PID 1

Quando o kernel termina de carregar, ele inicia um programa, o de PID 1. No Arch, esse programa é o systemd: ele monta os discos, sobe a rede, abre o login: e inicia os serviços (você viu a árvore em Processos e kill). Cada coisa que o systemd gerencia é uma unidade (unit), descrita num arquivo de texto. O tipo vem no fim do nome:

TipoO que éExemplo na VM
.serviceUm programa (serviço)sshd.service, NetworkManager.service
.socketUma porta ou socket que liga o serviço quando alguém conectapodman.socket
.timerUm agendamento (o "cron" do systemd)snapper-timeline.timer (veja Timers e Tarefas)
.targetUm grupo de unidades, um "ponto" do bootmulti-user.target
.mountUm ponto de montagemboot.mount

Quando o tipo é .service, pode omitir: systemctl status sshd é o mesmo que systemctl status sshd.service.

Dois estados que não se misturam

PerguntaEstadoMuda com
Está rodando agora?active / inactive / failedstart, stop
Vai ligar no próximo boot?enabled / disabledenable, disable

Um serviço pode estar ativo e desabilitado (você ligou à mão; no próximo boot não volta) ou habilitado e inativo (vai ligar no boot, mas agora está parado). Essa é a confusão número 1 de quem chega ao systemd.

No Arch, instalar não liga nada

No Debian e no Ubuntu, instalar o nginx já deixa o serviço rodando. No Arch, não: o pacote só traz os arquivos, e você decide o que ligar. Por isso a instalação manual termina com systemctl enable NetworkManager sshd (foi exatamente o que a VM do guia recebeu). Os presets do Arch são quase todos disabled, como você verá abaixo.

Ligar e desligar: start, stop, restart, reload

Precisa de sudo

Mudar o estado de um serviço do sistema é tarefa de administrador. Sem sudo, depende de onde você está. Num terminal de verdade, o polkit (o porteiro das permissões do systemd) pede a senha. Na VM havia dois administradores no momento, então ele perguntou primeiro quem ia se autenticar:

$ systemctl start nginx
==== AUTHENTICATING FOR org.freedesktop.systemd1.manage-units ====
É necessária autenticação para iniciar “nginx.service”.
Multiple identities can be used for authentication:
 1.  ana
 2.  teste-a1
Choose identity to authenticate as (1-2):

Com um só administrador, ele vai direto ao Password:. Já num script, por SSH sem terminal ou com --no-ask-password, não há como perguntar, e vem a recusa:

$ systemctl --no-ask-password start nginx
Failed to start nginx.service: Access denied as the requested operation requires interactive authentication. However, interactive authentication has not been enabled by the calling program.
See system logs and 'systemctl status nginx.service' for details.
$ echo $?
1

O caminho de sempre é o sudo (veja sudo, root e Usuários). Nas sessões abaixo, o [sudo] senha para ana: aparece só no primeiro comando; o sudo lembra a senha por alguns minutos.

As quatro ações

stopDesliga agora (manda TERM a todos os processos do cgroup)Não quer mais ele rodando
restartstop + start. Se estava parado, só liga.Depois de mudar a configuração; quando ele "se perdeu"

Ligar no boot: enable, disable e --now

enable
Faz a unidade ligar nos próximos boots. Não liga agora.
disable
Desfaz. Não desliga agora.
--now
Junto com enable, também faz start; junto com disable, também faz stop.
$ sudo systemctl enable nginx
Created symlink '/etc/systemd/system/multi-user.target.wants/nginx.service' → '/usr/lib/systemd/system/nginx.service'.
$ systemctl is-enabled nginx
enabled
$ sudo systemctl disable nginx
Removed '/etc/systemd/system/multi-user.target.wants/nginx.service'.
$ sudo systemctl enable --now nginx
Created symlink '/etc/systemd/system/multi-user.target.wants/nginx.service' → '/usr/lib/systemd/system/nginx.service'.
$ systemctl is-active nginx; systemctl is-enabled nginx
active
enabled
$ sudo systemctl disable --now nginx
Removed '/etc/systemd/system/multi-user.target.wants/nginx.service'.
$ systemctl is-active nginx; systemctl is-enabled nginx
inactive
disabled                         « de volta ao estado original

Repare no que o enable realmente faz: cria um link simbólico numa pasta multi-user.target.wants. "Wants" = "quer": quando o boot chega ao multi-user.target (o sistema pronto para uso), ele "quer" o nginx junto. Por que esse alvo? Porque o arquivo da unidade diz, na seção [Install]: WantedBy=multi-user.target (você verá abaixo).

Missão: com um único comando, habilite o nginx para o boot e ligue-o agora. (A senha da ana no simulador é ana.)

start × enable: qual usar?

Você quer…Comando
Testar um serviço só hojesudo systemctl start nome
Que ele ligue sempre, a partir de agorasudo systemctl enable --now nome
Que ligue a partir do próximo boot (não agora)sudo systemctl enable nome
Desligar agora e para sempresudo systemctl disable --now nome

Por dentro: o arquivo .service

Uma unidade é um arquivo de texto no formato "seções e chaves" (parecido com um .ini). systemctl cat mostra o arquivo e de onde ele vem. O do sshd no Arch:

$ systemctl cat sshd
# /usr/lib/systemd/system/sshd.service
[Unit]
After=network.target sshdgenkeys.service
Before=ssh-access.target
Description=OpenSSH Daemon
Documentation=man:sshd(8) man:sshd_config(5)
Wants=sshdgenkeys.service ssh-access.target

[Service]
Type=notify-reload
ExecStart=/usr/bin/sshd -D
KillMode=process
Restart=always

[Install]
WantedBy=multi-user.target
LinhaO que faz
[Unit]: quem é e com quem se relaciona
Description= / Documentation=O nome bonito (aparece no status) e onde ler mais
After=network.target sshdgenkeys.serviceOrdem: só começa depois da rede e do serviço que gera as chaves do servidor
Wants=sshdgenkeys.service …Dependência fraca: liga essas unidades junto (se falharem, o sshd sobe mesmo assim)
Before=ssh-access.targetTermina antes desse alvo
[Service]: como rodar
Type=notify-reloadO programa avisa o systemd quando está pronto e sabe recarregar a configuração (por isso o reload funciona)
ExecStart=/usr/bin/sshd -DO comando. -D = não ir para segundo plano sozinho: quem cuida disso é o systemd.
KillMode=processNo stop, mata só o processo principal: as conexões SSH abertas sobrevivem a um restart do sshd
Restart=alwaysSe o sshd morrer, o systemd o liga de novo
[Install]: o que o enable faz
WantedBy=multi-user.targetO enable cria o link em multi-user.target.wants/

daemon-reload: avisar que um arquivo mudou

O systemd lê os arquivos de unidade uma vez e guarda na memória. Se você cria ou muda um arquivo à mão, ele avisa que está usando a versão velha. Real, com uma unidade de teste do usuário ana:

$ systemctl --user status a6-ok --no-pager | head -4
Warning: The unit file, source configuration file or drop-ins of a6-ok.service changed on disk. Run 'systemctl --user daemon-reload' to reload units.
● a6-ok.service
     Loaded: loaded (/home/ana/.config/systemd/user/a6-ok.service; static)
     Active: active (running) since Fri 2026-10-16 13:31:54 -03; 24ms ago
$ systemctl --user daemon-reload       « relê todos os arquivos; não reinicia nenhum serviço

Para unidades do sistema: sudo systemctl daemon-reload. Ele não escreve nada quando dá certo.

Personalizar sem estragar: systemctl edit

Quer mudar um detalhe de um serviço do pacote (por exemplo, fazer o nginx reiniciar sozinho se cair)? Não edite o arquivo em /usr/lib. Crie um drop-in: um arquivo pequeno, só com as linhas que mudam, numa pasta NOME.service.d/. O systemd junta os dois.

Os próprios pacotes usam isso. Na VM, o snapper acrescenta uma linha ao timer dele, e o systemctl cat mostra o arquivo principal e o drop-in, um depois do outro:

$ systemctl cat snapper-timeline.timer
# /usr/lib/systemd/system/snapper-timeline.timer
[Unit]
Description=Timeline of Snapper Snapshots
Documentation=man:snapper(8) man:snapper-configs(5)

[Timer]
OnCalendar=hourly

[Install]
WantedBy=timers.target

# /usr/lib/systemd/system/snapper-timeline.timer.d/10-snapper-sync-override.conf     « o drop-in
[Unit]
After=snapper-sync.service

Para criar o seu, systemctl edit abre um editor, e ao salvar ele grava o drop-in e já faz o daemon-reload. Ilustrativo (não aplicado na VM compartilhada):

$ sudo systemctl edit nginx
[Service]
Restart=on-failure
RestartSec=5
systemctl edit nginx
Abre o editor com um arquivo vazio (e o original comentado, para consulta). Ao salvar, cria /etc/systemd/system/nginx.service.d/override.conf.
[Service]
A seção que você quer mudar precisa aparecer de novo.
Restart=on-failure
Reinicia o nginx se ele sair com erro. RestartSec=5: espera 5 segundos antes.
systemctl edit --full nginx
Copia o arquivo inteiro para /etc/systemd/system/ e edita a cópia. Funciona, mas você deixa de receber as mudanças que o pacote fizer no original.
systemctl revert nginx
Apaga os seus drop-ins e volta ao arquivo do pacote.
Qual editor ele abre?

O da variável SYSTEMD_EDITOR, ou EDITOR, ou VISUAL; se nenhuma existir, tenta editor, nano, vim e vi, nessa ordem. Lembre que o pacote base do Arch não traz editor nenhum: sem nano ou vim instalados, o systemctl edit não tem o que abrir. Para escolher: sudo SYSTEMD_EDITOR=vim systemctl edit nginx. Para ver todas as personalizações do sistema: systemd-delta.

Quando não funciona

"Unit … not found" 
$ sudo systemctl start nginx-teste
Failed to start nginx-teste.service: Unit nginx-teste.service not found.
$ echo $?
5

O que aconteceu: não existe unidade com esse nome. Erro de digitação, pacote não instalado, ou o nome é outro (no Arch é sshd, não ssh como no Debian; é cronie, não cron).

Como resolver: systemctl list-unit-files | grep parte-do-nome e, se não aparecer, pacman -Ql pacote | grep '\.service' para ver o nome que o pacote instalou.

"Access denied … requires interactive authentication"

O que aconteceu: você mandou mudar um serviço do sistema sem sudo, num lugar onde o polkit não pode perguntar a senha (script, SSH sem terminal). Num terminal normal, aparece ==== AUTHENTICATING FOR … ==== pedindo a senha.

Como resolver: repita com sudo. Se for um serviço seu, use systemctl --user.

"Job for X.service failed because the control process exited with error code"

O que aconteceu: o systemd tentou ligar e o programa saiu com erro (configuração errada, porta já em uso, arquivo faltando).

Como confirmar: exatamente o que a mensagem manda: systemctl status X (veja a linha Process: … status=) e journalctl -xeu X (as últimas mensagens dele, com explicações).

Como resolver: corrija o que o log apontar. Muitos programas testam a própria configuração: sudo nginx -t, sudo sshd -t. Depois, sudo systemctl restart X.

Liguei, mas depois do reboot estava desligado

O que aconteceu: você usou start, que vale só até desligar.

Como confirmar: systemctl is-enabled nome responde disabled.

Como resolver: sudo systemctl enable nome (ou enable --now).

"Warning: The unit file … changed on disk"

O que aconteceu: você editou o arquivo da unidade à mão e o systemd ainda usa a versão antiga.

Como resolver: sudo systemctl daemon-reload (ou systemctl --user daemon-reload) e depois restart no serviço.

Referência

ComandoO que faz
systemctl status nomeEstado e últimos logs
sudo systemctl start|stop|restart|reload nomeLiga, desliga, reinicia, relê a configuração
sudo systemctl enable|disable nomeLiga/não liga no boot (--now também liga/desliga agora)
sudo systemctl mask|unmask nomeBloqueia/desbloqueia de vez

Exercícios

1. Para sempre, a partir de agora

Complete para habilitar o cronie no boot e ligá-lo já:

sudo systemctl cronie

2. O arquivo da unidade

Qual subcomando mostra o conteúdo de sshd.service, com os drop-ins?

systemctl sshd

3. Depois de editar à mão

Você mudou um arquivo em /etc/systemd/system/. Complete o comando que faz o systemd reler:

sudo systemctl

4. systemctl status nginx mostra Loaded: … disabled e Active: active (running). O que acontece no próximo boot?

5. Onde você deve guardar uma personalização de um serviço que veio de um pacote?

6. Você instalou o nginx com o pacman. Ele já está rodando?

Resumo

  • O systemd é o PID 1; o systemctl é o controle remoto dele.
  • active = rodando agora (start/stop); enabled = liga no boot (enable/disable); --now faz os dois.
  • Mudar serviços do sistema exige sudo; ver o status, não.
  • No Arch, instalar um pacote não liga o serviço.
  • systemctl --failed depois de atualizar; status e journalctl -u quando algo falha.
  • Personalize com systemctl edit (drop-in em /etc), nunca editando /usr/lib.
