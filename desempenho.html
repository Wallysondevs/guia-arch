Arch Desempenho

O Arch já é enxuto: só roda o que você instalou e ligou. Por isso a maior parte das "dicas para deixar o Linux mais rápido" que circulam na internet não muda nada, ou piora. Esta aula ensina o método de quem ajusta sistemas de verdade: medir antes, mudar uma coisa, medir depois.

Você vai aprender
  • Ler memória (free), processos (top/htop) e tempo de boot (systemd-analyze) com as saídas reais da VM.
  • O governor da CPU e o cpupower.
  • Recuperar disco com paccache e limitar o journal.
  • Acelerar downloads do pacman (ParallelDownloads, espelhos).
  • Separar o que vale a pena dos mitos (preload, irqbalance, "limpar a RAM").

O método: medir, mudar uma coisa, medir de novo

Imagine um médico que receita remédio sem examinar. Pode acertar, mas também pode tratar a doença errada. Com computador é igual: se o sistema "está lento", primeiro descubra o quê está lento (CPU? memória? disco? rede? o boot?) e só então mexa, uma coisa por vez, para saber o que funcionou.

Memória: free -h

free
Mostra a memória RAM e a swap.
-h
human: em Gi/Mi em vez de kibibytes.
$ free -h
               total       usada       livre    compart.  buff/cache  disponível
Mem.:          3,8Gi       1,6Gi       1,5Gi        53Mi       1,1Gi       2,2Gi
Swap:          4,0Gi          0B       4,0Gi
ColunaO que é
totalA RAM da máquina (a VM tem 4 GB; o kernel reserva um pouco)
usadaUsada pelos programas
livreSem uso nenhum. Não é o número que importa
compart.Memória compartilhada (tmpfs, gráficos)
buff/cacheCache de disco: arquivos lidos recentemente, guardados na RAM "de graça"
disponívelO que importa: quanto os programas ainda podem usar (livre + cache que pode ser descartado)
"Linux comeu minha RAM!"

Memória livre é memória desperdiçada. O kernel usa a sobra como cache de disco e a devolve na hora em que um programa pede. Por isso "livre" pequeno é normal; preocupe-se quando disponível fica perto de zero e a coluna usada da Swap cresce. Comandos que "limpam a RAM" (echo 3 > /proc/sys/vm/drop_caches) só jogam o cache fora e deixam o sistema mais lento logo depois.

Missão: descubra quanta memória a máquina ainda tem disponível para programas, em unidades fáceis de ler.

Processos: top e htop

O htop é a versão colorida e interativa do top (instale com sudo pacman -S htop; a VM já tem). A tela dele é explicada, com captura real, em Processos e kill. Aqui usamos o top em modo "foto" (-b = batch, -n1 = uma vez, -o %MEM = ordenar por memória), que dá para copiar:

Como ler a linha %CPU(s):

us
user: programas comuns.
sy
system: o kernel trabalhando para eles.
id
idle: ocioso. 0,0 = CPU totalmente ocupada naquele instante.
wa
I/O wait: esperando o disco. Alto = o gargalo é o disco, não a CPU.
st
steal: tempo "roubado" pelo hipervisor (só em VMs).

A carga (load average) é quantos processos, em média, querem rodar ao mesmo tempo. Compare com o número de núcleos: a VM tem nproc = 2, então carga 3,34 quer dizer "mais trabalho do que núcleos" naquele momento (vários autores usavam a VM ao mesmo tempo). Num PC de 8 núcleos, 3,34 seria tranquilo.

Leia de baixo para cima: o boot esperou a partição EFI aparecer (a .device), checou-a (systemd-fsck), montou /boot, e assim por diante até graphical.target. @ é "quando ficou pronto" e + é "quanto demorou". Conclusão real para esta VM: o gargalo é o disco virtual lento (o initrd-switch-root e a espera pelos dispositivos), não um serviço. Desligar serviços aqui ganharia pouco.

Vale a pena mexer no boot?

Desabilite só o que você sabe que não usa (sudo systemctl disable --now SERVIÇO; veja systemctl e Serviços). Exemplo da VM: lvm2-monitor.service custa 1,4 s e não há LVM; mas se um dia você usar LVM, ele faz falta. systemd-analyze plot > boot.svg gera um gráfico do boot inteiro para abrir no navegador.

CPU: o governor

O processador muda de frequência o tempo todo. Quem decide como é o governor (o "governador"): powersave (economiza, sobe quando precisa), performance (sempre no máximo), schedutil (segue a carga do agendador)… Nos processadores atuais, o driver (intel_pstate, amd-pstate) já faz um bom trabalho sozinho.

$ cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor
cat: /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor: Arquivo ou diretório inexistente

Na VM do guia não existe a pasta cpufreq: a frequência de uma CPU virtual é controlada pelo computador de fora. Num notebook ou desktop físico, o arquivo existe e mostra, por exemplo, powersave. O cpupower é a ferramenta do Arch para ver e trocar o governor:

#> previa -S cpupower
resolvendo dependências...
procurando pacotes conflitantes...

Pacotes (1) cpupower-7.2.10-1                     « mesma versão do kernel: vem do código do Linux

Tamanho total download:   0,21 MiB
Tamanho total instalado:  0,62 MiB

:: Continuar a instalação? [S/n] n
cpupower frequency-info                     # driver, governors disponíveis, faixa de frequência
sudo cpupower frequency-set -g performance  # troca até o próximo boot
# para fixar: edite /etc/default/cpupower (governor='performance')
sudo systemctl enable --now cpupower.service
FerramentaPara quem
cpupowerDesktop: fixar um governor
power-profiles-daemonDesktop GNOME/KDE: os três perfis (economia, equilibrado, desempenho) no menu do sistema
tlpNotebook: bateria (não use junto com o power-profiles-daemon)

Memória extra: zram

O zram cria uma swap comprimida dentro da RAM: em vez de mandar páginas para o disco (lento), o kernel as comprime na memória. Em máquinas com pouca RAM e disco lento, é o ajuste que mais se sente. A VM usa uma partição de swap comum e nenhum zram:

$ swapon --show
NAME      TYPE      SIZE USED PRIO
/dev/sda2 partition   4G   0B   -1
$ zramctl
$ cat /proc/sys/vm/swappiness
60

O zramctl sem saída quer dizer "nenhum dispositivo zram". Como configurar (zram-generator) e o que é swappiness estão em Swap e zram.

Disco: cache do pacman e journal

O cache do pacman

Todo pacote baixado fica em /var/cache/pacman/pkg/, e o pacman nunca apaga sozinho. Na VM, depois de uma instalação e das aulas:

$ sudo du -sh /var/cache/pacman/pkg
1,3G	/var/cache/pacman/pkg
$ paccache -d
==> no candidate packages found for pruning
$ paccache -dk0 | tail -1
==> finished dry run: 404 candidates (disk space saved: 1.26 GiB)
paccache
Limpador do cache (pacote pacman-contrib). Mensagens em inglês.
-d
dry run: só mostra o que faria. Pode rodar como usuário comum.
-k0
keep 0: não guardar nenhuma versão. O padrão é -k3 (guarda as 3 mais novas de cada pacote).
-r
(sem -d) remove de verdade: sudo paccache -r.

O primeiro paccache -d não achou nada porque o sistema é novo: só existe uma versão de cada pacote, e o padrão guarda 3. Com o tempo, a cada atualização, o cache cresce. A solução automática é o timer que já vem no pacman-contrib (desligado):

$ systemctl list-unit-files | grep -E 'paccache|fstrim'
fstrim.service                                                            static          -
paccache.service                                                          static          -
fstrim.timer                                                              disabled        disabled
paccache.timer                                                            disabled        disabled

sudo systemctl enable --now paccache.timer roda paccache -r toda semana. Detalhes, pacman -Sc e órfãos: Cache e Órfãos. Guardar algumas versões antigas é o que permite voltar um pacote sem internet; não use -k0 no dia a dia.

fstrim.timer: para SSD

Também desligado de fábrica. Num SSD, sudo systemctl enable --now fstrim.timer avisa o disco, uma vez por semana, quais blocos estão livres. Mantém o SSD rápido e é um dos poucos ajustes que a Arch Wiki recomenda para quase todos.

O journal

$ journalctl --disk-usage
Archived and active journals take up 56M in the file system.
$ grep -v '^#' /etc/systemd/journald.conf | grep -v '^$'
[Journal]                                          « tudo no padrão

Por padrão o journal pode ocupar até 10% do sistema de arquivos (com teto de 4 GiB). Para limitar, crie um arquivo em /etc/systemd/journald.conf.d/ (a pasta não existe de fábrica) com [Journal] e SystemMaxUse=200M, e reinicie o systemd-journald. Para limpar agora: sudo journalctl --vacuum-size=200M. Veja Logs (journalctl).

Downloads mais rápidos: ParallelDownloads e espelhos

$ grep -E '^#?ParallelDownloads' /etc/pacman.conf
ParallelDownloads = 5

O pacman baixa até 5 pacotes ao mesmo tempo (o padrão atual; em pacman antigos a linha vinha comentada). Subir para 10 ajuda pouco numa conexão doméstica; o que mais pesa é usar espelhos próximos e rápidos, escolhidos com o reflector. Veja Espelhos (reflector).

Mitos e meias-verdades

"Instale o preload para abrir programas mais rápido" 
$ pacman -Si preload
erro: o pacote "preload" não foi encontrado

O preload não está nos repositórios oficiais (só no AUR) e não recebe desenvolvimento há mais de uma década. Com SSD e o cache de disco do kernel, o ganho é nulo; com HD e pouca RAM, ele ocupa a memória que faltava. Não vale a pena.

"irqbalance deixa tudo mais rápido" 
#> previa -S irqbalance
…
Pacotes (1) irqbalance-1.9.5-3

Tamanho total download:   0,05 MiB
Tamanho total instalado:  0,12 MiB

Ele distribui as interrupções de hardware entre os núcleos. Faz diferença em servidores com muitas placas de rede e muitos núcleos; num desktop ou notebook, o kernel já espalha bem. Só instale se medir interrupções concentradas num núcleo (cat /proc/interrupts).

"Use swappiness=10 / 1 / 0"

Valores baixos fazem o kernel evitar a swap até o último momento; aí, quando a RAM acaba, o sistema trava de uma vez em vez de ir desacelerando. Com zram, a recomendação é até o contrário (valores altos). Mude só depois de entender Swap e zram.

"Troque o agendador de disco / o kernel para ficar rápido" 
$ cat /sys/block/sda/queue/scheduler
none [mq-deadline] kyber bfq

O kernel escolhe um bom agendador por tipo de disco (entre colchetes, o atual). linux-zen pode melhorar a sensação de resposta em desktops sob carga, mas não faz programas rodarem mais rápido; veja Kernels.

Resumo

  • Meça antes, mude uma coisa, meça depois.
  • RAM: olhe "disponível"; cache não é desperdício.
  • Boot: systemd-analyze, blame (sem .device) e critical-chain.
  • Disco: paccache.timer, limite do journal, fstrim.timer em SSD.
  • zram e espelhos rápidos ajudam de verdade; preload, "limpar RAM" e swappiness 0 são mitos.
