Firewall: nftables e ufw

Um firewall ("parede corta-fogo") decide quais conexões de rede podem entrar e sair da máquina. O Linux tem o firewall dentro do kernel (o netfilter); o que muda é a ferramenta para escrever as regras: nft (nftables), ufw ou firewalld. No Arch, como quase tudo, nenhum vem ligado: você escolhe se quer e qual.

Você vai aprender
  • Conferir que o seu Arch está sem firewall (nft list ruleset, ufw status).
  • Ler, linha por linha, o /etc/nftables.conf que vem no pacote.
  • Usar o ufw: allow, deny, enable, status.
  • Conhecer o firewalld e escolher entre os três.
  • A regra de ouro: libere o SSH antes de ligar qualquer firewall numa máquina remota.
Sobre os exemplos desta aula

A VM do guia é acessada por SSH por vários autores ao mesmo tempo. Ligar um firewall nela, com uma regra errada, cortaria o acesso de todos. Por isso, aqui, só os comandos de leitura foram rodados de verdade (estado, arquivos, testes de sintaxe). Todo comando que liga, carrega ou muda regras está marcado como ilustrativo. Esse cuidado é exatamente o que você deve ter num servidor.

Como funciona

Cada pacote de rede que chega passa por uma série de regras, de cima para baixo. A primeira que "casa" decide: aceitar (accept), descartar calado (drop) ou recusar avisando (reject). Se nenhuma casar, vale a política padrão (policy).

TermoO que é
inputO que chega à máquina (alguém tentando acessar o seu SSH, o seu servidor web)
outputO que sai (você navegando). Quase sempre liberado.
forwardO que passa pela máquina indo para outra (roteadores, VMs, containers)
portaO "ramal" de cada serviço: 22 = SSH, 80 = HTTP, 443 = HTTPS
estado (conntrack)O kernel lembra das conexões: a resposta de um site que você abriu é established e pode entrar

A configuração mais comum num computador pessoal: bloquear tudo o que chega, exceto respostas ao que você pediu e os serviços que você quer oferecer (o SSH, por exemplo).

Sem firewall é perigoso?

Num computador pessoal atrás do roteador de casa, sem serviços ligados, o risco é pequeno: uma porta só "existe" se algum programa estiver escutando nela. O primeiro passo de segurança é sempre ver o que está escutando (sudo ss -tulpn; veja NetworkManager e iwd) e desligar o que não precisa. O firewall é a segunda camada, e fica importante em notebooks que usam Wi-Fi público e em servidores.

nftables: o firewall do kernel

O pacote nftables traz um serviço (nftables.service) que, ao ligar, carrega as regras do arquivo /etc/nftables.conf. O arquivo que vem no pacote já é um bom firewall de computador pessoal. Real:

#!/usr/bin/nft -f
# vim:set ts=2 sw=2 et:

# IPv4/IPv6 Simple & Safe firewall ruleset.
# More examples in /usr/share/nftables/ and /usr/share/doc/nftables/examples/.

destroy table inet filter
table inet filter {
  chain input {
    type filter hook input priority filter
    policy drop

    ct state invalid drop comment "early drop of invalid connections"
    ct state {established, related} accept comment "allow tracked connections"
    iif lo accept comment "allow from loopback"
    meta l4proto { icmp, icmpv6 } accept comment "allow icmp"
    tcp dport ssh accept comment "allow sshd"
    pkttype host limit rate 5/second counter reject with icmpx type admin-prohibited
    counter
  }
  chain forward {
    type filter hook forward priority filter
    policy drop
  }
}
LinhaO que faz
destroy table inet filterApaga a tabela antiga com esse nome, se existir, para recarregar do zero sem duplicar regras
table inet filter { … }Uma tabela chamada filter, da família inet (vale para IPv4 e IPv6 de uma vez)
chain input { type filter hook input priority filterUma corrente de regras pendurada (hook) na entrada: olha tudo o que chega
policy dropO que não for liberado abaixo é descartado
ct state invalid dropDescarta pacotes que não fazem sentido (ct = conntrack)
ct state {established, related} acceptAceita respostas a conexões que você abriu. Sem esta linha, você não navegaria.
iif lo acceptAceita tudo da interface lo (a própria máquina falando com ela mesma)
meta l4proto { icmp, icmpv6 } acceptAceita ICMP (o ping e mensagens de controle; o IPv6 precisa delas para funcionar)
tcp dport ssh acceptLibera a porta 22 (SSH). É isso que deixa este arquivo "seguro" de ligar numa máquina acessada por SSH.
pkttype host limit rate 5/second counter reject with icmpx type admin-prohibitedPara o resto que era endereçado a esta máquina: recusa avisando (em vez de silêncio), no máximo 5 por segundo, e conta
counterConta o que chegou até o fim (e vai cair na política drop)
chain forward { … policy drop }Não deixa a máquina repassar pacotes para outras (ela não é um roteador)

O nft pode conferir um arquivo sem carregar nada, com -c (check). Isso foi rodado na VM (sem efeito nenhum):

$ sudo nft -c -f /etc/nftables.conf
$ echo $?
0                                « sintaxe correta; nada foi carregado

Ligar o nftables

Ilustrativo (não rodado na VM). Com o arquivo acima (que libera o SSH), ligar é um comando:

$ sudo systemctl enable --now nftables
$ sudo nft list ruleset          « agora mostra a tabela inet filter carregada

Para liberar outro serviço, acrescente uma linha na chain input, logo depois da do SSH, e recarregue:

    tcp dport ssh accept comment "allow sshd"
    tcp dport { http, https } accept comment "servidor web"

$ sudo nft -c -f /etc/nftables.conf      « confira antes
$ sudo systemctl reload nftables          « recarrega o arquivo

Exemplos prontos para outras situações ficam em /usr/share/nftables/ (inet-filter.nft, inet-nat.nft, all-in-one.nft…).

ufw: o firewall "descomplicado"

O ufw (Uncomplicated Firewall, vindo do Ubuntu) escreve as regras para você a partir de comandos simples. Na VM ele está instalado e inativo:

$ sudo ufw status verbose
Status: inactive
$ grep -v '^#' /etc/ufw/ufw.conf | grep -v '^$'
ENABLED=no                       « não liga no boot
LOGLEVEL=low
$ grep -v '^#' /etc/default/ufw | grep -v '^$' | head -4
IPV6=yes
DEFAULT_INPUT_POLICY="DROP"      « quando ligado: bloqueia o que chega…
DEFAULT_OUTPUT_POLICY="ACCEPT"   « …e libera o que sai
DEFAULT_FORWARD_POLICY="DROP"

Repare na consequência: ao ligar o ufw sem nenhuma regra, a entrada fica toda bloqueada, inclusive o SSH. Ao contrário do nftables.conf do Arch, o ufw não libera a porta 22 sozinho.

A sequência certa: primeiro o SSH, depois o enable

Ilustrativo: os comandos abaixo não foram rodados na VM, e as saídas foram omitidas (não puderam ser conferidas). Num computador seu:

  1. Libere o SSH (se você acessa a máquina por SSH, ou vai acessar):

    $ sudo ufw allow ssh
    allow
    Libera a entrada.
    ssh
    O serviço, pelo nome (de /etc/services: porta 22/tcp). Valem também 22/tcp, SSH (o perfil) ou from 192.168.0.0/24 to any port 22 (só da rede de casa).

    Com o ufw desligado, a regra fica guardada e entra em vigor quando ele ligar.

  2. Confira o que vai valer (ufw show added agora lista ufw allow 22/tcp).

  3. Ligue. O ufw avisa que pode derrubar conexões SSH e pergunta (y/n):

    $ sudo ufw enable
$ sudo systemctl enable ufw          « para o serviço carregar as regras no boot

  4. Veja as regras ativas:

    $ sudo ufw status numbered

    A saída lista cada regra com um número, a porta (22/tcp), a ação (ALLOW IN) e a origem (Anywhere), em duas versões: IPv4 e (v6).

firewalld

O firewalld (do Fedora e do Red Hat) organiza a rede em zonas (public, home, work…), cada uma com seus serviços liberados, e integra com o NetworkManager: o Wi-Fi do café pode estar na zona public e o de casa na home. Não está instalado na VM (erro: o pacote "firewalld" não foi encontrado). Ilustrativo:

$ sudo pacman -S firewalld
$ sudo systemctl enable --now firewalld
$ sudo firewall-cmd --get-active-zones
$ sudo firewall-cmd --zone=public --add-service=ssh --permanent
$ sudo firewall-cmd --reload
$ sudo firewall-cmd --list-all
--add-service=ssh
Libera um serviço conhecido na zona.
--permanent
Grava na configuração. Sem ele, a regra vale só até o próximo reload/boot (útil para testar).
--reload
Aplica a configuração gravada.

Desktops KDE oferecem uma tela de firewall que funciona com o ufw ou com o firewalld.

Use um só

Ligar dois deles ao mesmo tempo (ufw e firewalld, ou nftables.service e ufw) cria regras sobrepostas e comportamentos difíceis de entender. Escolha um, e desabilite os outros. Containers (Docker, Podman) e máquinas virtuais também criam regras próprias (veja Docker e Podman).

Quando não funciona

Liguei o firewall e o SSH caiu

O que aconteceu: a política de entrada passou a ser drop e não havia regra para a porta 22 (o caso clássico do ufw enable sem ufw allow ssh).

Como resolver: só pelo console da máquina (teclado e monitor, ou o console web da VPS): sudo ufw allow ssh ou sudo ufw disable; no nftables, sudo systemctl stop nftables (ou sudo nft flush ruleset, que apaga todas as regras carregadas). Prevenção: libere o SSH primeiro e mantenha uma sessão aberta enquanto testa.

"Operation not permitted (perhaps you must be root?)" / "You need to be root"

O que aconteceu: ver e mudar o firewall é coisa de root.

Como resolver: sudo nft list ruleset, sudo ufw status.

O serviço está rodando, mas ninguém de fora consegue acessar

Como confirmar, em ordem: o serviço escuta em 0.0.0.0 e não só em 127.0.0.1? (sudo ss -tulpn); a porta está liberada? (sudo nft list ruleset ou sudo ufw status); o roteador encaminha a porta (para acesso de fora de casa)?

Como resolver: libere a porta (ufw allow 8080/tcp ou uma linha tcp dport 8080 accept) e confira a configuração do serviço.

Erro de sintaxe no nftables.conf

O que aconteceu: o nft recusa o arquivo inteiro (nada é carregado) e mostra a linha do erro com um ^^^^ embaixo.

Como resolver: sempre sudo nft -c -f /etc/nftables.conf antes do reload; o systemctl status nftables e o journalctl -u nftables mostram a mensagem.

Resumo

  • O firewall é do kernel (netfilter/nftables); nft, ufw e firewalld são formas de escrever as regras.
  • No Arch, nenhum vem ligado: sudo nft list ruleset vazio, ufw status → inactive.
  • O /etc/nftables.conf do pacote bloqueia a entrada, mas libera respostas, loopback, ICMP e o SSH.
  • O ufw bloqueia a entrada ao ligar e não libera o SSH sozinho: ufw allow ssh antes do ufw enable.
  • Teste sem aplicar (nft -c), mantenha uma sessão aberta e use um firewall só.
