Logs com journalctl

Tudo o que acontece no sistema vira uma linha de log (registro): um login, um serviço que falhou, um pendrive conectado, um erro do driver de vídeo. No Arch, quem guarda essas linhas é o systemd-journald, num banco de dados chamado journal ("diário"). Você lê com o journalctl. Saber filtrar o journal é o que separa "deu um erro" de "já sei o que foi".

Você vai aprender
  • Ler o journal e o formato de cada linha.
  • Filtrar por boot (-b), serviço (-u), prioridade (-p), tempo (--since), kernel (-k) e texto (-g).
  • Acompanhar ao vivo com -f e escolher o formato com -o.
  • Quem pode ler os logs no Arch (e a mensagem "Hint" de quem não pode).
  • Ver o tamanho, limpar (--vacuum-size) e configurar o journald.conf.

O journal no Arch

Em sistemas antigos, cada programa escrevia o seu arquivo de texto em /var/log/ (syslog, auth.log, messages…). O Arch não instala um syslog por padrão: tudo vai para o journal, que é binário (não dá para ler com cat) e indexado (filtrar é rápido). Os arquivos ficam aqui:

$ ls -la /var/log/journal/*/ | head -8
total 57380
drwxr-sr-x+ 2 root systemd-journal     4096 16 out 13:32 .
drwxr-sr-x+ 3 root systemd-journal     4096 16 out 12:11 ..
-rw-r-----+ 1 root systemd-journal  8388608 16 out 12:41 system@00065df727493845-e1d117b6ede35394.journal~
-rw-r-----+ 1 root systemd-journal 16777216 16 out 13:35 system.journal          « mensagens do sistema
-rw-r-----+ 1 root systemd-journal  8388608 16 out 13:35 user-1000.journal       « mensagens dos programas da ana (UID 1000)
-rw-r-----+ 1 root systemd-journal  8388608 16 out 13:35 user-1001.journal
-rw-r-----+ 1 root systemd-journal  8388608 16 out 13:35 user-1002.journal

O ~ no fim do primeiro arquivo marca um journal que foi fechado "sujo" (a VM foi desligada à força naquele boot; veja Quando o Sistema Trava). O + nas permissões indica uma ACL, permissões extras que você verá na seção "Quem pode ler".

Persistente: os logs sobrevivem ao reboot

O journal pode guardar os logs só na memória (/run/log/journal, somem ao desligar) ou no disco (/var/log/journal). No Arch, o padrão é no disco: o pacote systemd cria a pasta e a configuração padrão diz persistent:

$ pacman -Qo /var/log/journal
/var/log/journal/ pertence a systemd 262-1
$ grep -n 'Storage' /etc/systemd/journald.conf
20:#Storage=persistent         « comentado = é o valor padrão

journalctl sem nada

Sem argumentos, o journalctl mostra tudo, do mais antigo ao mais novo, dentro do less (setas e PgDn rolam, / procura, G vai para o fim, q sai). As primeiras linhas são do primeiro boot da VM, com o kernel se apresentando:

Os filtros do dia a dia

-n: as últimas linhas

$ journalctl -n 5 --no-pager
out 16 13:35:21 notebook systemd-logind[290]: Removed session 406.
out 16 13:35:29 notebook sshd-session[87513]: Accepted publickey for ana from 10.0.2.2 port 58622 ssh2: ED25519 SHA256:6M/mVNpF+bW06tP4uvsWog9MyDbccU3itKRoSUIIgls
out 16 13:35:29 notebook sshd-session[87513]: pam_unix(sshd:session): session opened for user ana(uid=1000) by ana(uid=0)
out 16 13:35:30 notebook systemd-logind[290]: New session '407' of user 'ana' with class 'user' and type 'tty'.
out 16 13:35:30 notebook systemd[1]: Started Session 407 of User ana.

-n (number) sem número = 10. -e (end) abre o less já no fim; -r (reverse) põe as mais novas primeiro.

-b: por boot

-b
Só o boot atual.
-b -1
O boot anterior (-2 o de antes, e assim por diante). A lista sai com journalctl --list-boots.
$ journalctl -b --no-pager | head -2
out 16 13:06:28 archlinux kernel: Linux version 7.2.10-arch1-1 (linux@archlinux) (gcc (GCC) 16.2.1 20260810, GNU ld (GNU Binutils) 2.47) #1 SMP PREEMPT_DYNAMIC Mon, 12 Oct 2026 06:58:10 +0000
out 16 13:06:28 archlinux kernel: Command line: BOOT_IMAGE=/vmlinuz-linux root=UUID=75d167c8-1dad-4d0a-a0ae-b063058a18e9 rw loglevel=3 quiet
$ journalctl -b -1 -u sshd -n 2 --no-pager
out 16 13:06:09 notebook systemd[1]: sshd.service: Deactivated successfully.
out 16 13:06:09 notebook systemd[1]: Stopped OpenSSH Daemon.        « o fim do sshd no boot anterior

-u: por serviço

-u (unit) mostra só as mensagens de uma unidade do systemd. É o filtro mais útil quando um serviço falha (veja systemctl e Serviços):

$ journalctl -u sshd -n 4 --no-pager
out 16 13:35:20 notebook sshd-session[87407]: Accepted publickey for root from 10.0.2.2 port 53228 ssh2: ED25519 SHA256:6M/mVNpF+bW06tP4uvsWog9MyDbccU3itKRoSUIIgls
out 16 13:35:20 notebook sshd-session[87407]: pam_unix(sshd:session): session opened for user root(uid=0) by root(uid=0)
out 16 13:35:29 notebook sshd-session[87513]: Accepted publickey for ana from 10.0.2.2 port 58622 ssh2: ED25519 SHA256:6M/mVNpF+bW06tP4uvsWog9MyDbccU3itKRoSUIIgls
out 16 13:35:29 notebook sshd-session[87513]: pam_unix(sshd:session): session opened for user ana(uid=1000) by ana(uid=0)

Dá para repetir: -u sshd -u nginx mostra os dois, misturados na ordem do tempo. Para os serviços do seu usuário, journalctl --user -u nome.

Missão: mostre só as mensagens do serviço sshd (se quiser, só as 5 últimas).

-p: por prioridade

Cada mensagem tem uma prioridade, de 0 (o sistema vai cair) a 7 (detalhes para programadores). -p mostra a escolhida e todas as mais graves:

NúmeroNomeQuando aparece
0emergO sistema está inutilizável
1alertAção imediata necessária
2critCrítico (hardware falhando)
3errErro: algo não funcionou
4warningAviso: funcionou, mas preste atenção
5noticeNormal, mas digno de nota
6infoInformação (a maioria)
7debugDepuração

Os erros do boot atual da VM (trecho; a VM é usada por vários autores e tinha dezenas de linhas):

$ journalctl -p err -b --no-pager
out 16 13:06:28 archlinux kernel: virt/tdx: TDX not supported by the host platform
out 16 13:06:28 archlinux kernel: ata1.00: Read log 0x00 page 0x00 failed, Emask 0x1
out 16 13:06:28 archlinux kernel: vmwgfx 0000:00:02.0: [drm] *ERROR* vmwgfx seems to be running on an unsupported hypervisor.
…
out 16 13:21:48 notebook nginx[2126]: 2026/10/16 13:21:48 [emerg] 2126#2126: invalid parameter "server_name" in /etc/nginx/sites-enabled/meusite.conf:3
out 16 13:21:48 notebook systemd[1]: Reload failed for nginx web server.
…
out 16 13:26:19 notebook sudo[15509]:      ana : 1 incorrect password attempt ; TTY=pts/0 ; PWD=/home/ana ; USER=root ; COMMAND=/usr/bin/pacman -Q bash
…
out 16 13:31:38 notebook systemd[2032]: Failed to start Teste que falha (a6).
$ journalctl -p warning -b --no-pager | wc -l

Como ler isso: as primeiras linhas são do kernel reclamando do hardware virtual (normais numa VM e inofensivas); depois aparecem coisas de verdade, como um erro de configuração do nginx (invalid parameter "server_name" … meusite.conf:3: arquivo e linha!), uma senha errada no sudo e a unidade de teste que falhou. Nem todo "erro" no log é problema: procure os que se repetem ou que coincidem com a hora do defeito. No terminal, err aparece em vermelho e warning em amarelo.

Uma faixa de prioridades

-p warning..err mostra só de 4 a 3, sem os críticos. Também vale o número: -p 3 = -p err.

-k: só o kernel

-k (kernel) mostra as mensagens do kernel, como o antigo comando dmesg, mas com horário de verdade e de qualquer boot (-k -b -1). Use para problemas de hardware, discos, pendrives e drivers:

$ journalctl -k -n 4 --no-pager
out 16 13:32:03 notebook kernel: EXT4-fs (dm-0): unmounting filesystem 7be8e846-aa8b-4287-9b1b-91221d984fa2.
out 16 13:34:07 notebook zram_generator::config[86670]: No configuration found.
out 16 13:34:08 notebook zram_generator::config[86723]: No configuration found.
out 16 13:34:39 notebook kernel: loop0: detected capacity change from 0 to 62914560

As linhas do zram_generator aparecem porque esse programa, que roda no começo do boot, escreve direto no canal de mensagens do kernel.

--since e --until: por tempo

--since
A partir de quando. Aceita "2026-10-16 13:00", "13:30" (hoje), today, yesterday, "10 min ago", "-1h".
--until
Até quando. Mesmos formatos.
$ journalctl --since today -u NetworkManager --no-pager | head -3
out 16 12:12:00 notebook systemd[1]: Starting Network Manager...
out 16 12:12:01 notebook NetworkManager[285]: <info>  [1792163521.2466] NetworkManager (version 1.58.1-2) is starting... (boot:d89c67be-cb28-4e04-b530-80f044b99d6c)
out 16 12:12:01 notebook NetworkManager[285]: <info>  [1792163521.2618] Read config: /etc/NetworkManager/NetworkManager.conf, /usr/lib/NetworkManager/conf.d/20-connectivity.conf
$ journalctl --since '2026-10-16 13:00' --until '2026-10-16 13:05' --no-pager | tail -2
out 16 13:04:54 notebook systemd-logind[292]: New session '4' of user 'ana' with class 'user' and type 'tty'.
out 16 13:04:54 notebook systemd[1]: Started Session 4 of User ana.
$ journalctl --since '10 min ago' --no-pager | wc -l
2826                       « 10 minutos de uma VM com vários autores trabalhando

As palavras são em inglês, mesmo com o sistema em português:

$ journalctl --since ontem
Failed to parse timestamp: ontem

-t e -g: por programa e por texto

-t (tag, o identificador) filtra pelo nome que aparece antes do [PID], mesmo quando não é um serviço (como o sudo). -g (grep) procura um texto (expressão regular) na mensagem:

$ journalctl -t sudo -n 2 --no-pager
out 16 13:33:40 notebook sudo[81448]: pam_unix(sudo:auth): conversation failed
out 16 13:33:40 notebook sudo[81448]: pam_unix(sudo:auth): auth could not identify password for [teste-a1c]
$ journalctl -g 'Failed to start' -n 2 --no-pager
out 16 13:31:38 notebook systemd[2032]: Failed to start Teste que falha (a6).
out 16 13:31:38 notebook systemd[2032]: Failed to start Teste que falha (a6).

Combinar filtros

Os filtros se somam ("e"). Uma pergunta comum, "quais erros o NetworkManager deu desde o boot?", fica:

$ journalctl -b -u NetworkManager -p err

Missão: mostre só as mensagens de erro (ou mais graves) do boot atual.

Ao vivo: -f

-f (follow, "seguir") mostra as últimas linhas e fica esperando as novas, como o tail -f. Saia com Ctrl+C. Ótimo para deixar aberto num terminal enquanto você reproduz o problema em outro.

Na VM, o -f ficou escutando o identificador guia enquanto o comando logger (que escreve no journal) mandava duas mensagens, uma delas com prioridade de erro:

$ journalctl -f -n 0 -t guia            « -n 0: não mostra o passado, só o que chegar
out 16 13:36:05 notebook guia[87970]: Olá do Guia Arch
out 16 13:36:05 notebook guia[87971]: Algo deu errado (teste)
^C

As mensagens foram escritas, em outro terminal, com:

$ logger -t guia "Olá do Guia Arch"
$ logger -t guia -p user.err "Algo deu errado (teste)"
$ journalctl -t guia -p err --no-pager
out 16 13:36:05 notebook guia[87971]: Algo deu errado (teste)      « só a de erro passa pelo -p err

O logger é útil nos seus scripts: em vez de um arquivo de log seu, escreva no journal e leia com journalctl -t meuscript.

Quem pode ler os logs

O log do sistema tem informação sensível (quem entrou, de onde, que comandos o sudo rodou). No Arch, os arquivos são do grupo systemd-journal e têm uma ACL que libera a leitura também para os grupos wheel e adm:

$ getfacl /var/log/journal/42634ff99dd3440394e6cd711c974f65
getfacl: Removing leading '/' from absolute path names
# file: var/log/journal/42634ff99dd3440394e6cd711c974f65
# owner: root
# group: systemd-journal
# flags: -s-
user::rwx
group::r-x
group:wheel:r-x           « quem está no wheel lê tudo
group:adm:r-x
mask::r-x

A ana está no wheel (é a administradora; veja Usuários e Grupos), então lê tudo sem sudo. Um usuário comum, como o teste-a6 criado para esta aula, só vê as mensagens dos próprios programas, e o journalctl avisa:

$ journalctl -u sshd -n 2 --no-pager
Hint: You are currently not seeing messages from other users and the system.
      Users in groups 'adm', 'systemd-journal', 'wheel' can see all messages.
      Pass -q to turn off this notice.
-- No entries --
Para ler tudoComoObservação
Usar sudosudo journalctl …Funciona sempre; pede senha
Grupo wheelJá vem para o administradorTambém dá poder de sudo
Grupo systemd-journalsudo usermod -aG systemd-journal nomeSó leitura de logs, sem nenhum outro poder: o certo para quem só precisa ler
Grupo admsudo usermod -aG adm nomeTradição de outras distros; no Arch, o efeito é o mesmo para o journal

Depois de entrar num grupo, é preciso sair e entrar de novo na sessão para valer.

Tamanho e limpeza

Quanto ocupa

$ journalctl --disk-usage
Archived and active journals take up 56M in the file system.

O journal se limita sozinho: por padrão usa no máximo 10% do sistema de arquivos, com teto de 4 GiB, e apaga os arquivos mais antigos quando chega lá. Num disco de 25 GiB como o da VM, isso dá uns 2,5 GiB. Normalmente você não precisa fazer nada.

Limpar à mão: --vacuum

--vacuum-size=500M
Apaga arquivos arquivados (os antigos, não o atual) até o total ficar abaixo de 500 MiB.
--vacuum-time=2weeks
Apaga os arquivados com mais de duas semanas.
--vacuum-files=5
Mantém no máximo 5 arquivos arquivados.
$ sudo journalctl --vacuum-size=500M
Vacuuming done, freed 0B of archived journals from /var/log/journal.
Vacuuming done, freed 0B of archived journals from /var/log/journal/42634ff99dd3440394e6cd711c974f65.
Vacuuming done, freed 0B of archived journals from /run/log/journal.
$ sudo journalctl --vacuum-time=2weeks
Vacuuming done, freed 0B of archived journals from /var/log/journal.
Vacuuming done, freed 0B of archived journals from /run/log/journal.
Vacuuming done, freed 0B of archived journals from /var/log/journal/42634ff99dd3440394e6cd711c974f65.

freed 0B: nada foi apagado, porque o journal da VM (56 MiB, de um dia) já está abaixo do limite e é mais novo que duas semanas. Num sistema de meses, aparecem as linhas Deleted archived journal … e o total liberado.

Não apague os arquivos com rm

Apagar arquivos de /var/log/journal à mão, com o journald rodando, pode corromper o journal atual. Use sempre o --vacuum. E lembre: limpar o log apaga as pistas de problemas antigos.

journald.conf: mudar os limites

A configuração fica em /etc/systemd/journald.conf. No Arch ela vem toda comentada: cada linha mostra o padrão de fábrica (trecho do arquivo real):

[Journal]
#Storage=persistent
#Compress=yes
#Seal=yes
#SplitMode=uid
#SyncIntervalSec=5m
#RateLimitIntervalSec=30s
#RateLimitBurst=10000
#SystemMaxUse=
#SystemKeepFree=
#SystemMaxFileSize=
#SystemMaxFiles=100
…
#MaxRetentionSec=0
#MaxFileSec=1month
#ForwardToSyslog=no
…
OpçãoO que controla
Storage=persistent (disco), volatile (só memória), auto (disco se a pasta existir), none
SystemMaxUse=Tamanho máximo no disco (vazio = 10% do sistema de arquivos, até 4G)
SystemKeepFree=Quanto espaço livre deixar no disco (padrão: 15%)
MaxRetentionSec=Idade máxima das mensagens (0 = sem limite)
ForwardToSyslog=Mandar também para um syslog tradicional, se você instalar um

O próprio arquivo recomenda não editá-lo, e sim criar um drop-in em /etc/systemd/journald.conf.d/ (pasta que não existe na instalação padrão). Ilustrativo (não aplicado na VM):

[Journal]
SystemMaxUse=500M

$ sudo mkdir -p /etc/systemd/journald.conf.d
$ sudo nano /etc/systemd/journald.conf.d/tamanho.conf
$ sudo systemctl restart systemd-journald

Quando não funciona

"Hint: You are currently not seeing messages from other users and the system."

O que aconteceu: o seu usuário não está nos grupos wheel, adm ou systemd-journal, então só vê os próprios logs.

Como confirmar: id mostra os seus grupos.

Como resolver: use sudo journalctl … ou peça para entrar no grupo systemd-journal (sudo usermod -aG systemd-journal nome, depois saia e entre de novo).

"-- No entries --" 
$ journalctl -u nada
-- No entries --
$ echo $?
0

O que aconteceu: o filtro não casou com nada. Repare que o código de saída é 0: para o journalctl, "nenhuma linha" não é erro. Causas comuns: nome de unidade errado (ssh em vez de sshd), --since num período sem mensagens, ou falta de permissão (veja o cenário acima).

Como resolver: confira o nome com systemctl list-units | grep parte; afrouxe o filtro (tire o -p, aumente o --since).

"Failed to parse timestamp"

O que aconteceu: o --since/--until recebeu algo que ele não entende (palavras em português, data no formato 16/10/2026).

Como resolver: use AAAA-MM-DD HH:MM entre aspas, ou today, yesterday, "2 hours ago".

"No journal boot entry found" ou só existe o boot 0

O que aconteceu: o boot pedido é mais antigo que os logs guardados, ou o journal não está persistente (alguém mudou Storage=volatile ou apagou /var/log/journal).

Como resolver: journalctl --list-boots; para voltar à persistência, sudo mkdir -p /var/log/journal, confira o Storage= e sudo systemctl restart systemd-journald.

Exercícios

1. Só os erros

Complete para ver as mensagens de erro (e mais graves) do boot atual:

journalctl -b -p

2. Ao vivo, de um serviço

Complete para acompanhar ao vivo só as mensagens do NetworkManager:

journalctl -u

3. Limpar

Complete para deixar os logs arquivados com no máximo 200 MiB:

sudo journalctl

4. Um usuário fora dos grupos wheel, adm e systemd-journal roda journalctl -u sshd. O que acontece?

5. No Arch, os logs sobrevivem ao reboot?

6. journalctl -p warning mostra quais mensagens?

Resumo

  • O journal guarda os logs de tudo; no Arch, no disco (/var/log/journal).
  • Filtros principais: -b (boot), -u (serviço), -p (prioridade), --since (tempo), -k (kernel), -g (texto); eles se somam.
  • -f acompanha ao vivo; -n limita; -o short-iso dá a data completa.
  • Quem está em wheel, adm ou systemd-journal lê tudo; os outros veem o "Hint" ou usam sudo.
  • O tamanho se controla sozinho (10%, até 4G); para limpar, --vacuum-size/--vacuum-time, nunca rm.
