Compilar do AUR: makepkg

O makepkg (de make package, "fazer pacote") é o programa que transforma uma receita do AUR num pacote de verdade. Ele lê o PKGBUILD, baixa o programa, confere se o download não foi adulterado, compila, e embala tudo num arquivo .pkg.tar.zst que o pacman sabe instalar. Os ajudantes como o yay fazem exatamente isso por baixo; aprender o jeito manual é o que permite entender (e consertar) quando algo dá errado.

Você vai aprender
  • O caminho completo: git clone → ler o PKGBUILD → makepkg → pacman -U.
  • Ler um PKGBUILD real (o do yay-bin) linha por linha.
  • As opções -s, -i, -si, -c, -f e a saída do makepkg fase por fase.
  • Os erros reais: Dependências faltando, Um pacote já foi compilado, assinatura PGP desconhecida.
  • Ajustar o /etc/makepkg.conf e atualizar um pacote do AUR à mão.

O caminho de uma receita até o sistema

  1. Baixar a receita com git clone (vem só o PKGBUILD e o .SRCINFO).
  2. Ler o PKGBUILD. Não é burocracia: é a única revisão que essa receita vai ter.
  3. Rodar makepkg como usuário comum. Ele baixa o programa, confere, compila e cria o .pkg.tar.zst.
  4. Instalar o pacote com sudo pacman -U arquivo.pkg.tar.zst (ou deixar o makepkg -i chamar isso por você).

Antes de começar: git e base-devel

O makepkg vem com o pacman, mas para compilar você precisa do grupo de ferramentas base-devel (gcc, make, fakeroot, patch, sudo…) e do git. Na VM eles já estão instalados, e o --needed faz o pacman pular o que já existe:

$ sudo pacman -S --needed git base-devel
atenção: git-2.56.0-1 está atualizado -- ignorando
atenção: base-devel-1-2 está atualizado -- ignorando
nada para fazer
--needed
"Só se precisar": não reinstala o que já está na versão mais nova. Sem ele, o pacman reinstalaria os dois.
base-devel
Um metapacote: não tem arquivos, só dependências (gcc make fakeroot binutils patch sudo…). O makepkg supõe que ele está instalado: as receitas não listam essas ferramentas.

1. Baixar a receita

Crie uma pasta para as suas receitas (a ana usa ~/aur) e clone o endereço que aparece em "Git Clone URL" na página do pacote. Este é o comando real da instalação do yay na VM do guia:

$ mkdir -p ~/aur && cd ~/aur && git clone https://aur.archlinux.org/yay-bin.git
Clonando em 'yay-bin'...
$ cd yay-bin
$ ls
PKGBUILD

O ls mostra só o PKGBUILD porque os outros arquivos (.SRCINFO, .gitignore, .git) começam com ponto. Se você clonar um nome que não existe, o AUR não dá erro: o git clona um repositório vazio, avisa aviso: Parece que você clonou um repositório vazio. (seguido de várias linhas hint: sobre o nome do branch) e termina com código 0, como se tudo tivesse dado certo. A pasta criada só tem .git. Confira o nome na página do pacote.

2. Ler o PKGBUILD antes

Esta é a receita real do yay-bin 13.0.1, que a ana usou para instalar o yay:

# Maintainer: Jguer <pkgbuilds at jguer.space>
pkgname=yay-bin
pkgver=13.0.1
pkgrel=1
pkgdesc="Yet another yogurt. Pacman wrapper and AUR helper written in go. Pre-compiled."
arch=('x86_64' 'aarch64' 'armv7h')
url="https://github.com/Jguer/yay"
license=('GPL-3.0-or-later')
depends=(
  'pacman>6.1'
  'git'
)
optdepends=(
  'sudo: privilege elevation'
  'doas: privilege elevation'
)
provides=('yay')
conflicts=('yay')

source_x86_64=("https://github.com/Jguer/yay/releases/download/v${pkgver}/${pkgname/-bin/}_${pkgver}_x86_64.tar.gz")
source_aarch64=("https://github.com/Jguer/yay/releases/download/v${pkgver}/${pkgname/-bin/}_${pkgver}_aarch64.tar.gz")
source_armv7h=("https://github.com/Jguer/yay/releases/download/v${pkgver}/${pkgname/-bin/}_${pkgver}_armv7h.tar.gz")

sha256sums_x86_64=('1fdfcb5f7f387bc858d3a5754bdf4e4575bfbddac9560535a716d0ed7189c057')
sha256sums_aarch64=('75bc500c8677d6760f51117ae0a61689e9cf165bea3c4800825a5c879d030726')
sha256sums_armv7h=('9fe24f478ff6b80252fd6591061d478f0579e9118bc2522efe5328550870502f')

package() {
  _output="${srcdir}/${pkgname/-bin/}_${pkgver}_${CARCH}"
  install -Dm755 "${_output}/${pkgname/-bin/}" "${pkgdir}/usr/bin/${pkgname/-bin/}"
  install -Dm644 "${_output}/yay.8" "${pkgdir}/usr/share/man/man8/yay.8"

  # Shell autocompletion script
  install -Dm644 "${_output}/bash" "${pkgdir}/usr/share/bash-completion/completions/yay"
  install -Dm644 "${_output}/zsh" "${pkgdir}/usr/share/zsh/site-functions/_yay"
  install -Dm644 "${_output}/fish" "${pkgdir}/usr/share/fish/vendor_completions.d/yay.fish"

  LANGS="ca cs de en es eu fr_FR he id it_IT ja ko pl_PL pt_BR pt ru_RU ru sv tr uk zh_CN zh_TW"
  for lang in ${LANGS}; do
    install -Dm644 "${_output}/${lang}.mo" "${pkgdir}/usr/share/locale/${lang}/LC_MESSAGES/yay.mo"
  done
}

Esta receita é das mais simples: um -bin não compila nada, só baixa o programa pronto do autor e o coloca nos lugares certos. Receitas de fonte têm também build() (compilar); todas as partes estão explicadas em Escrever um PKGBUILD. O que procurar numa receita suspeita está em AUR com Segurança.

3. makepkg: as opções

Rode o makepkg dentro da pasta da receita e como usuário comum. As opções mais usadas:

OpçãoNome longoO que faz
(nenhuma)Baixa, confere, compila e cria o .pkg.tar.zst. Não instala nada. Se faltar dependência, para.
-s--syncdepsInstala as dependências que faltam dos repositórios oficiais, com sudo pacman (pede a senha).
-i--installNo final, instala o pacote criado com sudo pacman -U.
-siAs duas: o jeito mais comum de "instalar do AUR".
-r--rmdepsRemove, no final, as dependências que o -s instalou só para compilar.
-c--cleanApaga as pastas de trabalho src/ e pkg/ no final.
-C--cleanbuildApaga a src/ antes de começar (compilação do zero).
-f--forceRecria o pacote mesmo que ele já exista na pasta.
-o--nobuildSó baixa e extrai (para você olhar o código antes de compilar).
-g--genintegCalcula e mostra as somas sha256sums dos arquivos.
--noconfirmNão pergunta nada ao pacman (scripts). Evite no dia a dia.

O que o -c e o -f mudam

Rodar de novo, sem mudar nada, dá erro:

$ makepkg
==> ERRO: Um pacote já foi compilado. (use -f para sobrescrever)
$ echo $?
13

Com -f ele recria; com -c, limpa no final (só as linhas ==>, filtradas com grep):

$ makepkg -fc 2>&1 | grep "^==>"

Instalar como dependência

Se você compilou um pacote do AUR só porque outro precisava dele, instale com sudo pacman -U --asdeps arquivo. Assim ele aparece como órfão (pacman -Qdt) quando ninguém mais precisar dele. Veja Cache e Órfãos.

"Dependências faltando" e por que o -s precisa de sudo

Na instalação da VM, o terceiro pacote, downgrade, não compilou. O log real:

$ git clone -q https://aur.archlinux.org/downgrade.git && cd downgrade && makepkg -s --noconfirm 2>&1 | tail -3
==> Dependências faltando:
  -> fzf
==> ERRO: Não foi possível resolver todas as dependências.

A receita pede depends=('pacman-contrib' 'fzf'), e o fzf não estava instalado. Para ver o que acontece em cada caso, uma receita de teste que depende do cowsay (que não está instalado):

$ makepkg
==> Criando o pacote: teste-dep 1-1 (sex 16 out 2026 13:22:42)
==> Verificando as dependências de tempo de execução...
==> Dependências faltando:
  -> cowsay
==> ERRO: Não foi possível resolver todas as dependências.
$ echo $?
8

Sem -s, o makepkg só reclama. Com -s, ele tenta instalar o que falta chamando sudo pacman -S --asdeps cowsay. Instalar é coisa de root, por isso a senha:

$ makepkg -s
==> Criando o pacote: teste-dep 1-1 (sex 16 out 2026 13:23:15)
==> Verificando as dependências de tempo de execução...
==> Instalando dependências não encontradas...
[sudo] senha para ana:

Daí em diante aparece o resumo normal do pacman. Se o sudo não consegue pedir a senha (num script, sem terminal), o erro é este, e foi o que aconteceu no log da VM, escondido pelo | tail -3:

$ makepkg -s </dev/null
==> Criando o pacote: teste-dep 1-1 (sex 16 out 2026 13:22:43)
==> Verificando as dependências de tempo de execução...
==> Instalando dependências não encontradas...
sudo: a terminal is required to read the password; either use ssh's -t option or configure an askpass helper
sudo: uma senha é necessária
==> ERRO: "pacman" falhou em instalar dependências não encontradas.
==> Dependências faltando:
  -> cowsay
==> ERRO: Não foi possível resolver todas as dependências.
O -s só acha dependências dos repositórios oficiais

Se a dependência que falta também é do AUR, o makepkg -s não sabe buscá-la: o pacman responde alvo não encontrado. Você precisa compilar e instalar essa dependência antes (com o mesmo processo). Fazer isso sozinho, na ordem certa, é justamente o trabalho de um ajudante.

Nunca como root

#> makepkg
==> ERRO: Executar makepkg como root não é permitido, pois isso pode
causar danos catastróficos e permanentes ao seu sistema.
#> echo $?
10

Um erro no package() (um caminho sem $pkgdir, por exemplo) como usuário comum só consegue estragar a sua pasta; como root, estragaria o sistema. Por isso o makepkg roda como você e só o pacman -U usa root.

Assinaturas PGP das fontes

Muitos programas publicam, junto do arquivo, uma assinatura (.sig) feita com a chave pessoal do autor. A receita lista essa assinatura em source e diz em validpgpkeys qual chave pode tê-la feito. Exemplo real, a receita do ncurses5-compat-libs:

$ grep -n -E "^(source|validpgpkeys)" -A3 PKGBUILD
18:source=(https://ftp.gnu.org/pub/gnu/ncurses/ncurses-$pkgver.tar.gz{,.sig})
19-sha256sums=('355b4cbbed880b0381a04c46617b7656e362585d52e9cf84a67e2009b749ff11'
20-            'SKIP')                                   « a .sig não precisa de soma
21:validpgpkeys=('19882D92DDA4C400C22C0D56CC2AF4472167BE03')  # Thomas Dickey
…

O {,.sig} é expansão de chaves do Bash: vira dois itens, o .tar.gz e o .tar.gz.sig. Na primeira tentativa, o makepkg não conhece a chave:

$ makepkg -o
…
==> Validando source arquivos com sha256sums...
    ncurses-6.6.tar.gz ... Passou
    ncurses-6.6.tar.gz.sig ... Ignorada
==> Verificando assinatura de arquivo fonte com gpg...
    ncurses-6.6.tar.gz ... FALHOU (chave pública desconhecida CC2AF4472167BE03)
==> ERRO: Uma ou mais assinaturas PGP não puderam ser verificadas!
$ echo $?
1

A solução é importar a chave pública para o seu chaveiro (o do seu usuário, em ~/.gnupg; não é o chaveiro do pacman). Use o número completo (a impressão digital) que está em validpgpkeys:

$ gpg --recv-keys 19882D92DDA4C400C22C0D56CC2AF4472167BE03
gpg: /home/ana/.gnupg/trustdb.gpg: trustdb criada
gpg: chave CC2AF4472167BE03: chave pública "Thomas E. Dickey (self-signed w/o SHA1) <dickey@invisible-island.net>" importada
gpg:          Número total processado: 1
gpg:                       importadas: 1
$ makepkg -o
…
==> Verificando assinatura de arquivo fonte com gpg...
    ncurses-6.6.tar.gz ... Passou                 « agora confere
==> Extraindo fontes...
  -> Extraindo ncurses-6.6.tar.gz com bsdtar
==> Iniciando prepare()...
==> Os fontes estão prontos.
gpg
O GnuPG, programa de criptografia.
--recv-keys
"Receber chaves": baixa a chave de um servidor de chaves (no Arch, por padrão, keyserver.ubuntu.com).
1988…BE03
A impressão digital completa. Os últimos 16 dígitos (CC2AF4472167BE03) são o "ID longo" que aparece no erro.
Importar a chave não é "confiar cegamente"

A assinatura prova que o arquivo foi assinado por quem tem aquela chave. Quem garante que a chave é mesmo do autor? A receita (que você leu) e, melhor ainda, o site oficial do projeto, que costuma publicar a impressão digital. Nunca contorne o erro com makepkg --skippgpcheck sem saber por que a chave mudou.

/etc/makepkg.conf: o jeito que o makepkg trabalha

As configurações globais do makepkg ficam em /etc/makepkg.conf (e em /etc/makepkg.conf.d/, com ajustes para Rust e Fortran). As linhas que mais importam, na VM:

$ grep -n -E "MAKEFLAGS|^BUILDENV|BUILDDIR|^OPTIONS|PKGDEST|SRCDEST|PACKAGER" /etc/makepkg.conf

72:BUILDENV=(!distcc color !ccache check !sign)

129:#PKGDEST=/home/packages

VariávelO que controlaSugestão

BUILDDIROnde ficam src/ e pkg/. Padrão: a pasta da receita/tmp/makepkg compila na RAM (rápido, mas precisa de RAM sobrando)

Não edite o arquivo do sistema: crie o seu, que tem prioridade. O makepkg lê ~/.makepkg.conf (ou ~/.config/pacman/makepkg.conf) depois do global:

MAKEFLAGS="-j$(nproc)"
PACKAGER="Ana <ana@exemplo.com>"
OPTIONS=(strip docs !libtool !staticlibs emptydirs zipman purge !debug lto)

O mistério do yay-bin-debug

Na instalação do yay apareceram dois pacotes: yay-bin e yay-bin-debug. O motivo é o debug nas OPTIONS padrão: para todo programa compilado (binário ELF), o makepkg separa os símbolos de depuração num pacote NOME-debug, usado para investigar travamentos com o gdb. Com um binário pronto como o do yay, que não tem esses símbolos, o makepkg reclamou e criou um pacote quase vazio (6,6 KiB):

$ makepkg -s --noconfirm
…
  -> Removendo símbolos desnecessários dos executáveis e bibliotecas...
Error while writing index for `/home/ana/aur/yay-bin/pkg/yay-bin/usr/bin/yay': No debugging symbols
gdb-add-index: No index was created for ./usr/bin/yay
gdb-add-index: [Was there no debuginfo? Was there already an index?]
…
==> Criando o pacote "yay-bin"...
…
==> Criando o pacote "yay-bin-debug"...
…
$ ls
pkg       src                       yay-bin-13.0.1-1-x86_64.pkg.tar.zst
PKGBUILD  yay_13.0.1_x86_64.tar.gz  yay-bin-debug-13.0.1-1-x86_64.pkg.tar.zst

As mensagens No debugging symbols são inofensivas. Você não precisa instalar o -debug: para quem não depura programas, o normal é pôr !debug no seu makepkg.conf, como no exemplo acima. Pacotes any (scripts, como o downgrade) nunca geram -debug. Para tirar o que já foi instalado: sudo pacman -R yay-bin-debug.

Missão: mostre só a linha OPTIONS ativa (a que não começa com #) do /etc/makepkg.conf e confira se o debug está ligado.

Atualizar um pacote do AUR à mão

O pacman -Syu não atualiza nada que veio do AUR. Para saber o que você precisa acompanhar:

$ pacman -Qm
downgrade 12.0.4-1
paru-bin 2.1.0-1
yay-bin 13.0.1-1
yay-bin-debug 13.0.1-1

Para cada um, entre na pasta da receita e traga as mudanças com git pull:

$ git pull
Já está atualizado.            « nada novo: a sua versão é a última
$ echo $?
0

Quando houver novidade, o git pull lista os arquivos alterados. Leia o que mudou antes de compilar: git log -p -1 mostra a última mudança, linha por linha (+ = acrescentada, - = removida). Depois:

$ git log --oneline -3
6a212a7 Release 12.0.4
683636e Release 12.0.3
a7c5e87 Release 12.0.2
$ makepkg -si          « compila a versão nova e instala por cima

Fazer isso pacote por pacote cansa. É exatamente o que yay e paru automatizam (veja Ajudantes: yay e paru), mostrando as diferenças para você revisar.

Quando não funciona

"Um pacote já foi compilado. (use -f para sobrescrever)"

O que aconteceu: o .pkg.tar.zst daquela versão já existe na pasta (código de saída 13).

Como resolver: se é só para instalar, sudo pacman -U nome-*.pkg.tar.zst; se quer recompilar, makepkg -f.

"Dependências faltando: … Não foi possível resolver todas as dependências."

O que aconteceu: falta um pacote de depends ou makedepends (código 8).

Como resolver: rode com -s (e digite a senha). Se o pacman disser alvo não encontrado, a dependência é do AUR: compile-a primeiro.

"FALHOU" na validação das somas 
==> Validando source arquivos com sha256sums...
    ola.in ... FALHOU
==> ERRO: Um ou mais arquivos não passaram na verificação de validade!

O que aconteceu: o arquivo baixado é diferente do que o mantenedor conferiu. Pode ser um download corrompido, o autor ter trocado o arquivo sem mudar a versão, ou alguém ter adulterado.

Como resolver: apague o arquivo e baixe de novo (makepkg -C). Se continuar, leia os comentários do pacote e avise o mantenedor. Não "conserte" trocando a soma por SKIP.

"FALHOU (chave pública desconhecida …)"

O que aconteceu: a fonte é assinada e a chave do autor não está no seu chaveiro.

Como resolver: gpg --recv-keys IMPRESSÃO-DIGITAL com o número de validpgpkeys. Se o servidor de chaves não responder, tente gpg --keyserver hkps://keys.openpgp.org --recv-keys ….

"Executar makepkg como root não é permitido"

O que aconteceu: você estava como root (ou usou sudo makepkg).

Como resolver: saia do root e rode como seu usuário. O makepkg pede o sudo sozinho quando precisa.

Resumo

  • Caminho manual: git clone → ler o PKGBUILD → makepkg -si.
  • O makepkg roda como usuário comum; só o pacman -U usa root (via sudo).
  • -s instala dependências dos repositórios oficiais; dependências do AUR você compila antes.
  • Passou/FALHOU nas somas e nas assinaturas protegem você: não desligue essas verificações.
  • Ajuste MAKEFLAGS, PACKAGER e !debug no seu ~/.config/pacman/makepkg.conf.
  • Atualizar à mão: git pull, ler o git log -p, makepkg -si.
