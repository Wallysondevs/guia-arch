Kernels: linux, lts, zen

O kernel é o núcleo do sistema: o programa que conversa com o processador, a memória, o disco e a placa de rede, e reparte tudo isso entre os outros programas. No Arch, ele é um pacote como outro qualquer, atualizado quase toda semana, e você pode ter mais de um instalado. A ana tem dois, e isso rendeu uma pegadinha real com o GRUB, que você vai ver nesta aula.

Você vai aprender
  • Descobrir qual kernel está rodando e quais estão instalados.
  • Os quatro kernels oficiais (linux, linux-lts, linux-zen, linux-hardened) e para quem serve cada um.
  • Por que manter um segundo kernel de reserva, e como escolher no GRUB.
  • A pegadinha: depois de instalar o LTS, o GRUB passou a iniciar o LTS. E a correção com GRUB_TOP_LEVEL.
  • Headers, DKMS e módulos (lsmod, modinfo, modprobe).

Onde o kernel mora

O pacote linux instala duas coisas principais:

  • O kernel propriamente dito, um arquivo chamado vmlinuz (o "z" é de comprimido). O pacote o coloca em /usr/lib/modules/VERSÃO/vmlinuz, e um hook do mkinitcpio o copia para /boot/vmlinuz-linux, onde o bootloader o encontra.
  • Os módulos: milhares de drivers em /usr/lib/modules/VERSÃO/kernel/, carregados só quando um aparelho precisa deles.

No boot, o bootloader (o GRUB, na ana) carrega o vmlinuz e o initramfs, um mini-sistema que monta o disco de verdade (assunto de mkinitcpio e initramfs).

Instalar outro kernel

É um pacman -S comum. Resumo real da instalação do zen (respondendo "n" no fim, nada foi instalado):

$ sudo pacman -S linux-zen
resolvendo dependências...
procurando pacotes conflitantes...

Pacotes (1) linux-zen-7.2.10.zen1-1

Tamanho total download:   166,81 MiB
Tamanho total instalado:  167,35 MiB

:: Continuar a instalação? [S/n] n

Se você confirmar, o fim da instalação roda o mkinitcpio para gerar o initramfs do kernel novo (você vê isso no log real da instalação do LTS, logo abaixo). Mas falta um passo que o pacman não faz: avisar o GRUB.

Por que ter um kernel de reserva

No Arch, o kernel é atualizado com o resto do sistema. Quase sempre dá tudo certo. Mas, de vez em quando, uma versão nova tem um defeito com algum hardware específico: a tela fica preta, o Wi-Fi some, o boot para. Se você tem só um kernel, sobra o pendrive de resgate (Resgate com chroot). Se tem dois, basta escolher o outro no menu do GRUB e corrigir com calma.

O linux-lts é o reserva ideal: é uma série diferente, então dificilmente quebra junto com o linux. O custo é espaço em /boot (uns 31 MiB a mais: kernel + initramfs) e a instalação dos headers de cada um, se você usa DKMS.

$ ls -lh /boot
total 77M
drwxr-xr-x 3 root root 4,0K 16 out 12:10 EFI
drwxr-xr-x 6 root root 4,0K 16 out 13:03 grub
-rwxr-xr-x 1 root root  15M 16 out 12:58 initramfs-linux.img
-rwxr-xr-x 1 root root  15M 16 out 12:58 initramfs-linux-lts.img
-rwxr-xr-x 1 root root  15M 25 set 19:53 intel-ucode.img
-rwxr-xr-x 1 root root  17M 16 out 12:09 vmlinuz-linux
-rwxr-xr-x 1 root root  16M 16 out 12:58 vmlinuz-linux-lts

Com a partição EFI de 1 GiB da ana, espaço não é problema. Com uma de 300 MiB, três kernels já apertam.

3. Reiniciou… no LTS

$ grep -n "^GRUB_DEFAULT" /etc/default/grub
3:GRUB_DEFAULT=0
$ uname -r
6.18.57-1-lts

GRUB_DEFAULT=0 quer dizer "inicie a primeira entrada do menu". E o grub-mkconfig põe os kernels em ordem pelo nome do arquivo, do "maior" para o "menor": vmlinuz-linux-lts vem antes de vmlinuz-linux. A primeira entrada passou a ser o LTS. Nada quebrou, mas a ana estava rodando o kernel reserva sem saber. O registro do sistema confirma (cada boot, com -b negativo para os anteriores; veja Logs):

$ sudo journalctl -k -b -3 -o cat | head -1
Linux version 6.18.57-1-lts (linux-lts@archlinux) (gcc (GCC) 16.2.1 20260810, GNU ld (GNU Binutils) 2.47) #1 SMP PREEMPT_DYNAMIC Thu, 15 Oct 2026 13:43:34 +0000

4. A correção: GRUB_TOP_LEVEL

A opção GRUB_TOP_LEVEL, em /etc/default/grub, diz qual kernel fica no topo do menu, não importa a ordem dos nomes:

GRUB_TOP_LEVEL=
A opção do GRUB.
"/boot/vmlinuz-linux"
O caminho do kernel que deve ser a primeira entrada (e, portanto, o padrão com GRUB_DEFAULT=0).
$ echo 'GRUB_TOP_LEVEL="/boot/vmlinuz-linux"' | sudo tee -a /etc/default/grub
GRUB_TOP_LEVEL="/boot/vmlinuz-linux"
$ sudo grub-mkconfig -o /boot/grub/grub.cfg

O pacman não roda o grub-mkconfig

Headers e DKMS

Alguns drivers não vêm com o kernel: o do VirtualBox (para rodar máquinas virtuais), drivers de placas Wi-Fi raras, o da NVIDIA em certas versões. Eles são compilados na sua máquina, para o kernel que você tem. Para isso, precisam dos headers do kernel: os arquivos de cabeçalho e scripts de compilação daquela versão exata (o pacote linux-headers, linux-lts-headers…).

O DKMS (Dynamic Kernel Module Support) automatiza isso: a cada atualização de kernel, ele recompila esses drivers sozinho. Os pacotes que usam DKMS têm o nome terminado em -dkms.

A ana tem headers só do LTS

$ pacman -Q dkms linux-headers linux-lts-headers
erro: o pacote "dkms" não foi encontrado
erro: o pacote "linux-headers" não foi encontrado
linux-lts-headers 6.18.57-1

Na instalação, a ana pediu linux-lts linux-lts-headers, mas nunca os headers do kernel principal. Se um dia ela instalar um pacote -dkms, o driver será compilado só para o LTS, e no linux ele não vai existir. A regra: um pacote de headers para cada kernel instalado.

$ sudo pacman -S linux-headers
resolvendo dependências...
procurando pacotes conflitantes...

Pacotes (1) linux-headers-7.2.10.arch1-1

Tamanho total download:    68,75 MiB
Tamanho total instalado:  321,41 MiB

:: Continuar a instalação? [S/n] n
$ sudo pacman -S dkms
resolvendo dependências...
procurando pacotes conflitantes...

Pacotes (1) dkms-3.4.4-1

Tamanho total download:   0,05 MiB
Tamanho total instalado:  0,16 MiB

:: Continuar a instalação? [S/n] n

(Resumos reais, respondidos com "n".) Os headers ficam em /usr/lib/modules/VERSÃO/build. Você não precisa instalar o dkms à mão: os pacotes -dkms o puxam como dependência. Se você não usa nenhum driver de fora, não precisa de headers.

Módulos: lsmod, modinfo e modprobe

A maior parte dos drivers é módulo: um pedaço do kernel que entra e sai com ele rodando. O udev carrega sozinho o módulo certo quando um aparelho aparece; você só mexe à mão para investigar ou para casos especiais.

lsmod: o que está carregado

$ lsmod | head -8
Module                  Size  Used by
loop                   45056  3
tcp_diag               20480  0
inet_diag              20480  1 tcp_diag
rfkill                 45056  1
vfat                   28672  1
fat                   114688  1 vfat
intel_rapl_msr         24576  0
$ lsmod | wc -l
39

Size é o tamanho na memória; Used by, quantos usam o módulo e quais. O vfat (FAT32 da /boot) usa o fat. São só 38 módulos (a primeira linha é o título) porque os drivers mais comuns, como o do ext4, vêm embutidos no kernel do Arch e não aparecem aqui.

modprobe: carregar e descarregar

#> modprobe -v zram
insmod /lib/modules/7.2.10-arch1-1/kernel/lib/lz4/lz4hc_compress.ko.zst
insmod /lib/modules/7.2.10-arch1-1/kernel/lib/842/842_compress.ko.zst

zram                   73728  0
842_decompress         20480  1 zram
842_compress           24576  1 zram

rmmod lz4hc_compress
rmmod 842_compress

O modprobe (como root) resolve as dependências: para carregar o zram, carregou antes três módulos de compressão (-v mostra cada insmod). Com -r (remove), tira o módulo e as dependências que ficaram sem uso. Um módulo que está sendo usado (o Used by do lsmod maior que 0) não pode ser retirado.

Na ana, as duas pastas em /etc estão vazias: nada foi personalizado. Se o módulo precisa estar no initramfs (driver do disco, por exemplo), mude também o mkinitcpio.

Quando não funciona

Depois de instalar um segundo kernel, o sistema iniciou com ele 
$ uname -r
6.18.57-1-lts

O que aconteceu: com GRUB_DEFAULT=0, vale a primeira entrada, e o grub-mkconfig colocou o linux-lts antes do linux.

Como resolver: acrescente GRUB_TOP_LEVEL="/boot/vmlinuz-linux" a /etc/default/grub, rode sudo grub-mkconfig -o /boot/grub/grub.cfg e reinicie (detalhes acima).

"Module … not found in directory /lib/modules/…" 
#> modprobe naoexiste
modprobe: FATAL: Module naoexiste not found in directory /lib/modules/7.2.10-arch1-1
#> echo $?
1

O que aconteceu: aqui, o nome está errado. Mas a mesma mensagem aparece numa situação típica do Arch: você atualizou o kernel e ainda não reiniciou. O pacman apagou a pasta de módulos da versão antiga, que é a que está rodando; um pendrive ou outro aparelho ligado agora não acha o driver.

Como confirmar: compare uname -r com ls /usr/lib/modules. Se a versão em uso não estiver na lista, é isso.

Como resolver: reinicie depois de toda atualização do kernel. Veja Atualizar o Sistema.

Um driver -dkms não funciona num dos kernels

O que aconteceu: faltam os headers daquele kernel, e o DKMS não conseguiu compilar o módulo para ele.

Como confirmar: pacman -Q linux linux-headers linux-lts linux-lts-headers e, com o dkms instalado, dkms status.

Como resolver: instale o pacote de headers que falta. A reinstalação do pacote -dkms recompila para todos os kernels.

"Não há espaço disponível no dispositivo" ao atualizar o kernel

O que aconteceu: a /boot (partição EFI) encheu, e o mkinitcpio não conseguiu gravar o initramfs.

Como confirmar: df -h /boot e ls -lh /boot.

Como resolver: remova um kernel que você não usa (sudo pacman -Rns linux-zen, depois grub-mkconfig) e rode sudo mkinitcpio -P. Não reinicie antes de o initramfs ser gerado sem erros.

Resumo

  • uname -r mostra o kernel em uso; pacman -Q e ls /boot, os instalados.

  • Instalar ou remover kernel → grub-mkconfig. Com dois kernels, o GRUB pode escolher o LTS: GRUB_TOP_LEVEL resolve.
  • Drivers -dkms precisam dos headers de cada kernel.
  • Módulos: lsmod, modinfo, modprobe/modprobe -r. Reinicie depois de atualizar o kernel.

Na Arch Wiki: os kernels oficiais e não oficiais estão em Kernel (em português); módulos, modprobe.d e blacklist, em Kernel module (em português); o DKMS, em Dynamic Kernel Module Support (em português); e o menu, o GRUB_TOP_LEVEL e o GRUB_SAVEDEFAULT, em GRUB (em português). O caminho do boot inteiro está em Arch boot process (em português).
