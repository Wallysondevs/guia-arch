Arch Docker e Podman

Um container é um programa rodando numa "caixa" isolada, com o próprio sistema de arquivos, a própria lista de processos e a própria rede, mas usando o mesmo kernel da máquina. Com containers você roda um Alpine, um Debian ou um banco de dados dentro do seu Arch sem instalar nada no sistema. No Arch, as duas ferramentas mais usadas são o Podman e o Docker.

Você vai aprender
  • A diferença entre imagem, container e registro (e entre container e máquina virtual).
  • Rodar containers com o Podman como usuário comum, sem daemon e sem root.
  • Listar, entrar, parar e apagar containers e imagens.
  • Como o Docker é instalado no Arch (serviço, grupo docker) e quando escolher cada um.
  • O que é "compose" e os erros reais mais comuns.

Imagem, container e registro

Pense numa receita de bolo e no bolo pronto:

TermoAnalogiaNa prática

ContainerO bolo feito com a receitaUma execução da imagem, com uma camada gravável por cima. Dá para fazer vários a partir da mesma imagem.
Registro (registry)A livraria de receitasO servidor de onde as imagens são baixadas: docker.io (Docker Hub), quay.io, ghcr.io…

O nome completo de uma imagem tem quatro partes:

docker.io
O registro (o Docker Hub).
/library
A conta dona da imagem (library = imagens oficiais).
/alpine
O nome da imagem.
:latest
A tag (versão). Sem tag, vale latest.

Container × máquina virtual

Uma máquina virtual simula um computador inteiro e roda outro kernel; um container só isola processos no mesmo kernel. Por isso o container liga em segundos e ocupa megabytes, mas não roda Windows nem outro kernel. Dentro de um container Alpine no seu Arch, uname -r mostra o kernel do Arch.

Podman: sem daemon, sem root

O Docker clássico funciona com um daemon (o serviço dockerd) rodando como root o tempo todo; o comando docker só manda pedidos para ele. O Podman (de Pod Manager) não tem daemon: cada podman run cria o container direto, como um processo seu. E ele foi feito para rodar rootless, como usuário comum. Na VM do guia, o pacote já está instalado:

$ podman --version
podman version 6.1.4
$ pacman -Qi podman | grep -E '^(Versão|Depende de)'
Versão               : 6.1.4-1
Depende de           : catatonit  conmon  containers-common  oci-runtime  glibc  nftables  gpgme  libgpgme.so=45-64  libgcc  libseccomp  libseccomp.so=2-64  passt  shadow  sqlite

Algumas dependências contam a história de como ele funciona: conmon vigia cada container, oci-runtime é "quem cria a caixa" (no Arch, o crun), passt dá rede aos containers sem root e shadow traz as ferramentas de faixas de IDs.

Como "root no container" não é root de verdade

Para rodar sem root, o Podman usa namespaces de usuário: dentro do container, o processo acha que é o usuário 0 (root), mas, para o kernel, ele é a ana. Os outros usuários do container (1, 2, 3…) são emprestados de uma faixa de números reservada para a ana em /etc/subuid e /etc/subgid:

$ grep ana /etc/subuid /etc/subgid
/etc/subuid:ana:100000:65536          « a ana pode usar os UIDs 100000 a 165535
/etc/subgid:ana:100000:65536

Essas linhas foram criadas pelo useradd quando a ana foi criada. Se um usuário não as tiver, o Podman rootless reclama (veja "Quando não funciona").

Cada usuário tem os seus containers

As imagens e containers da ana ficam em ~/.local/share/containers. O root (com sudo podman) tem outro depósito, em /var/lib/containers. Um sudo podman images não mostra as imagens da ana, e vice-versa.

Na primeira vez, o Podman baixa a imagem (cerca de 3 MB comprimidos). A linha Resolved "alpine" as an alias explica como ele soube que alpine quer dizer docker.io/library/alpine: o pacote containers-common traz uma lista de apelidos conhecidos.

  "alpine" = "docker.io/library/alpine"

Da segunda vez, a imagem já está no disco e nada é baixado. Com o nome completo, nenhuma resolução é necessária:

$ time podman run --rm docker.io/library/alpine echo oi
oi

user	0m0,205s

$ podman images

docker.io/library/alpine  latest      320994c3b997  4 weeks ago  8.72 MB

O tempo varia muito: na VM do guia (lenta, com disco virtual), ligar a rede rootless pela primeira vez demorou 13 segundos; num computador comum, um container Alpine liga em menos de um segundo. Na tabela do images, CREATED é quando a imagem foi gerada pelo Alpine, não quando você a baixou, e o SIZE (8,72 MB) é o tamanho descomprimido.

Use sempre o nome completo

Em scripts e tutoriais, escreva docker.io/library/alpine em vez de alpine. Fica claro de onde vem a imagem e evita que um nome curto aponte para um registro inesperado.

Rodar um comando dentro de um container que já está ligado é com exec:

$ podman exec dorminhoco ps
PID   USER     TIME  COMMAND
    1 root      0:00 sleep 600                       « lá dentro, o sleep é o processo 1
    2 root      0:00 ps
$ ps -o user,pid,cmd -C sleep
USER         PID CMD
ana        29389 sleep 600                           « no Arch, é um processo comum da ana
$ podman top dorminhoco user huser pid args
USER        HUSER       PID         COMMAND
root        1000        1           sleep 600        « USER no container, HUSER no host (uid 1000 = ana)

Esta é a prova do rootless: o "root" do container é a ana (uid 1000) para o kernel. Se alguém escapar do container, cai com os poderes da ana, não do root. Para um terminal interativo lá dentro, use podman exec -it dorminhoco sh (-i mantém a entrada aberta, -t cria um terminal; saia com exit).

Parar e apagar

$ podman stop -t 1 dorminhoco
time="2026-10-16T13:27:52-03:00" level=warning msg="StopSignal SIGTERM failed to stop container dorminhoco in 1 seconds, resorting to SIGKILL"
dorminhoco
$ podman ps -a
CONTAINER ID  IMAGE                            COMMAND     CREATED         STATUS                      PORTS       NAMES
b9ca1f960c50  docker.io/library/alpine:latest  sleep 600   25 seconds ago  Exited (137) 8 seconds ago              dorminhoco
$ podman rm dorminhoco
dorminhoco
$ podman ps -a
CONTAINER ID  IMAGE       COMMAND     CREATED     STATUS      PORTS       NAMES

O stop manda primeiro um SIGTERM (pedido educado) e, depois do prazo (-t 1 = 1 segundo; o padrão é 10), um SIGKILL. O aviso apareceu porque o sleep, sendo o processo 1 do container, ignora o SIGTERM. O código 137 é 128 + 9 (morto pelo sinal 9, SIGKILL); veja Processos e kill. Sem -a, o podman ps só lista os ligados; com -a (all), também os parados. Um container parado ainda ocupa espaço até o rm.

$ podman rmi docker.io/library/alpine

rmi = remove image. Ele recusa apagar uma imagem usada por algum container (mesmo parado): apague o container antes, ou use podman rmi -f. Para limpar tudo o que não está em uso de uma vez: podman system prune -a (pergunta antes).

Publicar uma porta

Um container tem rede própria. Para o mundo acessar um serviço dele, publique uma porta com -p PORTA_DO_HOST:PORTA_DO_CONTAINER. Sem root, há uma regra: portas abaixo de 1024 são reservadas.

$ podman run --rm -p 80:80 docker.io/library/alpine true
Error: pasta failed with exit code 1:
Listen failed for HOST TCP port */80: Permission denied
Couldn't listen on requested ports

$ echo $?
126
$ podman run --rm -p 8081:80 docker.io/library/alpine true
$ echo $?
0

Use uma porta alta (8080, 8081…) e, se precisar mesmo da 80, ponha um nginx do sistema na frente como proxy, ou rode aquele container com sudo podman.

Docker no Arch (ilustrativo)

A VM do guia não tem Docker (o comando nem existe: bash: docker: comando não encontrado). O tamanho real da instalação, visto com o previa (nada foi instalado):

#> previa -S docker
resolvendo dependências...
procurando pacotes conflitantes...

Pacotes (4) containerd-2.4.2-1  libpathrs-0.2.6-1  runc-1.5.2-1
            docker-1:29.9.1-1

Tamanho total download:    54,27 MiB
Tamanho total instalado:  221,65 MiB

:: Continuar a instalação? [S/n] n

O 1: antes da versão é a época do pacote (veja pacman Avançado). O containerd e o runc são as peças que o daemon usa para criar containers. Depois de instalar, no Arch você precisa de dois passos que no Ubuntu vêm prontos:

  1. Ligar o daemon (instalar não liga, como sempre no Arch): 
    sudo systemctl enable --now docker.service
# ou só o socket: o daemon sobe na primeira vez que alguém usar o docker
sudo systemctl enable --now docker.socket
  2. Usar sem sudo (opcional): entrar no grupo docker e fazer logout/login. 
    sudo usermod -aG docker ana
# saia da sessão e entre de novo; confira com:
groups
O grupo docker vale o mesmo que root

Quem está no grupo docker pode mandar o daemon (que roda como root) montar a raiz do sistema dentro de um container: docker run -v /:/host … e editar qualquer arquivo. Na prática, entrar no grupo docker é ganhar root sem senha. Em máquinas compartilhadas, prefira o Podman rootless (ou o Docker em modo rootless, que a Arch Wiki explica). Veja Usuários e Grupos.

"Quero digitar docker, mas usar o Podman"

Os comandos do Podman são quase idênticos aos do Docker (run, ps, images, exec, rm, rmi, build…). O pacote podman-docker cria um comando docker que chama o Podman (previa -S podman-docker: 0,02 MiB). Não instale docker e podman-docker juntos.

Compose: vários containers de uma vez (ilustrativo)

Um site costuma ter várias peças (servidor web, banco de dados). O compose descreve todas num arquivo YAML e liga tudo com um comando.

services:
  web:
    image: docker.io/library/nginx:alpine
    ports:
      - "8080:80"
    volumes:
      - ./site:/usr/share/nginx/html:ro
  banco:
    image: docker.io/library/postgres:17
    environment:
      POSTGRES_PASSWORD: troque-esta-senha

O socket do Podman

Alguns programas (o Podman Desktop, ferramentas feitas para Docker) conversam com um socket da API em vez de chamar o comando. O Podman traz o podman.socket, desligado de fábrica: o serviço só sobe quando alguém conecta.

$ systemctl status podman.socket
○ podman.socket - Podman API Socket
     Loaded: loaded (/usr/lib/systemd/system/podman.socket; disabled; preset: disabled)
     Active: inactive (dead)
$ systemctl --user is-active podman.socket
inactive

Há duas versões: a do sistema (sudo systemctl enable --now podman.socket, para o Podman do root) e a do usuário (systemctl --user enable --now podman.socket, para os containers da ana). Só ligue se algum programa pedir.

Missão: um programa pediu a API do Podman do sistema. Ligue o podman.socket agora (sem habilitar no boot; senha ana) e confira com systemctl is-active podman.socket.

Quando não funciona

"short-name … did not resolve to an alias" 
$ podman pull meuapp
Error: short-name "meuapp" did not resolve to an alias and no containers-registries.conf(5) was found
$ echo $?
125

O que aconteceu: o nome curto não está na lista de apelidos, e o Arch não traz um /etc/containers/registries.conf dizendo em quais registros procurar (de propósito: procurar um nome curto em vários registros é um risco de segurança).

Como resolver: use o nome completo (docker.io/usuario/meuapp, quay.io/…). Se quiser mesmo nomes curtos, crie /etc/containers/registries.conf com unqualified-search-registries = ["docker.io"].

"Listen failed for HOST TCP port */80: Permission denied"

O que aconteceu: sem root, portas abaixo de 1024 são proibidas.

Como resolver: use -p 8080:80. Alternativas: sudo podman, ou baixar o limite com sysctl net.ipv4.ip_unprivileged_port_start=80 (vale para todos os programas da máquina; pense antes).

"cannot find UID/GID for user" / "not enough IDs available"

O que aconteceu: o usuário não tem faixa em /etc/subuid e /etc/subgid (acontece com usuários criados por ferramentas antigas).

Como resolver: sudo usermod --add-subuids 100000-165535 --add-subgids 100000-165535 USUARIO (sem sobrepor a faixa de outro usuário) e depois podman system migrate.

"Cannot connect to the Docker daemon at unix:///var/run/docker.sock"

O que aconteceu: o Docker foi instalado, mas o serviço não foi ligado (padrão do Arch), ou você não está no grupo docker/não fez logout depois de entrar nele.

Como resolver: sudo systemctl enable --now docker.service; confira groups; use sudo docker enquanto isso.

"image is in use by a container"

O que aconteceu: podman rmi numa imagem que ainda tem container (mesmo parado).

Como resolver: podman ps -a, podman rm NOME e repita o rmi.

Resumo

  • Imagem = receita; container = execução dela; registro = de onde vem a imagem.
  • O Podman não tem daemon e roda sem root: cada usuário tem suas imagens em ~/.local/share/containers.
  • run --rm, ps -a, exec, stop, rm, images, rmi: os mesmos nomes no Docker.
  • Sem root, publique portas altas (-p 8080:80).
  • Docker no Arch: pacman -S docker + systemctl enable --now docker; o grupo docker equivale a root.
  • Use nomes completos de imagem: docker.io/library/alpine.
