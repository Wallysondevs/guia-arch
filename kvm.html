Arch Máquinas Virtuais (KVM)

Uma máquina virtual (VM) é um computador inteiro simulado dentro do seu: com BIOS/UEFI, disco, placa de rede e o seu próprio kernel. Com ela você testa outra distribuição, o Windows ou a própria instalação do Arch sem arriscar a máquina de verdade. Todo este guia foi conferido numa VM. No Linux, o caminho mais rápido é o KVM, que já vem dentro do kernel.

Você vai aprender
  • As peças: KVM, QEMU, libvirt e virt-manager, e quem faz o quê.
  • Conferir se o seu processador tem virtualização (e o que aparece dentro de uma VM).
  • Instalar o conjunto no Arch, com o tamanho real, e pôr o usuário no grupo libvirt.
  • Os comandos básicos do virsh.
  • O VirtualBox no Arch: módulos do kernel e DKMS.

As peças do quebra-cabeça

Pense numa locadora de carros. Alguém fabrica o motor, alguém monta o carro, alguém administra a frota e alguém atende no balcão:

PeçaO que fazAnalogiaPacote no Arch
KVMMódulo do kernel (kvm_intel ou kvm_amd) que usa a virtualização do processador para a VM rodar quase na velocidade realO motorJá vem no linux
QEMUO programa que simula o resto do computador (disco, rede, vídeo, USB) e usa o KVM como motorO carroqemu-desktop (ou qemu-base, sem interface gráfica)
libvirtUm serviço que guarda e administra as VMs (rede, discos, ligar no boot), com o comando virshA administração da frotalibvirt

Você pode usar o QEMU sozinho (linha de comando longa), mas o conjunto libvirt + virt-manager é o mais confortável, parecido com o VirtualBox.

O processador tem virtualização?

O KVM precisa de uma extensão do processador: VT-x na Intel (a opção vmx) ou AMD-V na AMD (a opção svm). Quase todo processador desde 2010 tem, mas ela pode estar desligada no firmware (BIOS/UEFI), com nomes como "Intel Virtualization Technology", "SVM Mode" ou "Virtualization".

lscpu
Mostra as informações do processador (em pt_BR no Arch configurado).
| grep -i virt
Filtra as linhas com "virt", sem diferenciar maiúsculas (-i).

Num computador de verdade com Intel e VT-x ligado, a linha que interessa é Virtualização: VT-x (na AMD, AMD-V). Na VM do guia, que roda dentro do VirtualBox, a saída real é outra:

$ lscpu | grep -i virt
Tamanhos de endereço:                      46 bits physical, 48 bits virtual   « nada a ver: só tem "virtual" no nome
Tipo de virtualização:                     completo                            « ESTE processador é virtual
$ lscpu | grep -E 'Nome do modelo|hipervisor'
Nome do modelo:                            Intel(R) Xeon(R) CPU E5-2630 v4 @ 2.20GHz
Fabricante do hipervisor:                  KVM

Leia com atenção: não existe a linha Virtualização: VT-x. As linhas Fabricante do hipervisor e Tipo de virtualização: completo dizem o contrário do que procuramos: este Arch está dentro de uma VM (o VirtualBox se apresenta ao convidado pela interface "KVM" de paravirtualização), e não pode criar VMs aceleradas. O VirtualBox não repassa o VT-x para o convidado se a virtualização aninhada (nested) não estiver ligada nas configurações da VM.

Outras três formas de conferir, com as saídas reais da VM:

$ grep -c -E 'vmx|svm' /proc/cpuinfo
0                                                « nenhum núcleo com vmx/svm
$ echo $?
1                                                « grep não achou nada
$ ls -l /dev/kvm
ls: não foi possível acessar '/dev/kvm': Arquivo ou diretório inexistente
$ systemd-detect-virt
oracle                                           « estou dentro do VirtualBox (Oracle)

Qual usar? ls -l /dev/kvm é o teste definitivo: se o arquivo existe, o KVM está pronto. Os outros dizem por que não está.

O que o kernel diz quando falta VT-x

O módulo do KVM é carregado sozinho no boot quando o processador tem suporte. Forçando o carregamento na VM do guia:

#> modprobe kvm_intel
modprobe: ERROR: could not insert 'kvm_intel': Operation not supported
#> echo $?
1
#> dmesg | grep kvm_intel
[ 1474.053519] kvm_intel: VMX not supported by CPU 1

Num PC físico, a mesma mensagem quer dizer: ligue a virtualização no firmware. (O teste carregou o módulo genérico kvm como dependência; ele foi descarregado depois com modprobe -r kvm irqbypass.)

Três coisas para entender nesta saída:

  • A pergunta de provedor. Algum pacote precisa de "um JACK" (servidor de áudio profissional), e dois pacotes oferecem isso. Se o seu Arch usa PipeWire para o som (o padrão nos desktops atuais), escolha 2) pipewire-jack; o padrão 1) jack2 instala um servidor de áudio à parte. Veja pacman Avançado.
  • 167 pacotes, 467 MiB. Numa instalação mínima (sem desktop), o virt-manager traz GTK, ícones e bibliotecas de vídeo e áudio. Num desktop GNOME ou KDE, boa parte já estaria instalada e a conta seria bem menor.
  • qemu-desktop é um meta-pacote que puxa dezenas de qemu-* pequenos (áudio, vídeo, USB, interfaces). Para um servidor sem tela, qemu-base basta: 22 pacotes, 23,21 MiB de download e 124,04 MiB instalados (também conferido com o previa).

Depois de instalar (ilustrativo)

Como sempre no Arch, instalar não liga o serviço, nem dá permissão ao seu usuário:

  1. Ligar o libvirt. O libvirt moderno é dividido em vários daemons pequenos, ativados por socket; o atalho clássico ainda funciona: 
    sudo systemctl enable --now libvirtd.service
  2. Entrar no grupo libvirt para criar e controlar VMs do sistema sem digitar senha a cada vez. O grupo é criado pelo próprio pacote: 
    sudo usermod -aG libvirt ana
# saia da sessão e entre de novo, depois confira:
groups
  3. Ligar a rede padrão (NAT, 192.168.122.0/24), que vem desligada: 
    sudo virsh net-start default
sudo virsh net-autostart default
  4. Abrir o virt-manager pelo menu ("Gerenciador de máquinas virtuais") e criar a VM: escolher a ISO, memória, CPUs, disco. Marque "Personalizar configuração antes de instalar" e, em Visão geral → Firmware, escolha UEFI (vem do pacote edk2-ovmf, que está na lista acima) para treinar a instalação UEFI do Arch.
Sessão do sistema × sessão do usuário

O libvirt tem duas "conexões": qemu:///system (VMs do sistema, com rede NAT completa; é a padrão do virt-manager e a que precisa do grupo libvirt) e qemu:///session (VMs só do seu usuário, sem root, com rede mais limitada). Para começar, use a do sistema.

O grupo libvirt é poderoso

Quem controla o libvirt do sistema pode criar uma VM com acesso aos discos da máquina. Como o grupo docker (veja Docker e Podman), ponha nele só quem já poderia ser administrador. Grupos em Usuários e Grupos.

virsh: o libvirt pelo terminal (ilustrativo)

O virsh faz tudo o que o virt-manager faz, e é o jeito de administrar VMs num servidor sem tela. Os comandos mais usados (a VM do guia não tem VT-x, então eles não foram rodados aqui):

ComandoO que faz
virsh list --allLista as VMs (ligadas e desligadas), com estado executando/desligado
virsh start arch-testeLiga a VM
virsh shutdown arch-testePede para a VM desligar (como apertar o botão)
virsh destroy arch-testeDesliga à força (como tirar da tomada). Não apaga nada, apesar do nome
virsh autostart arch-testeLiga a VM junto com o computador
virsh dominfo arch-testeMemória, CPUs, estado
virsh snapshot-create-as arch-teste antes-updateTira um snapshot (disco qcow2)
virsh undefine arch-teste --remove-all-storageApaga a VM e os discos (cuidado)
virsh net-list --allLista as redes virtuais

No libvirt, uma VM se chama domínio (domain), por isso dominfo. A configuração de cada VM é um arquivo XML (virsh dumpxml arch-teste mostra; virsh edit arch-teste edita).

O disco da VM: qemu-img

Os discos ficam em /var/lib/libvirt/images/, no formato qcow2 (QEMU copy-on-write): o arquivo cresce conforme a VM grava e aceita snapshots.

qemu-img create -f qcow2 arch-teste.qcow2 20G   # 20 GiB "prometidos", quase nada ocupado
qemu-img info arch-teste.qcow2                    # tamanho virtual × tamanho real no disco
Btrfs e discos de VM

Se a sua raiz é Btrfs, desligue o copy-on-write na pasta das imagens antes de criar os discos (chattr +C /var/lib/libvirt/images): Btrfs com CoW em cima de qcow2 (que também é CoW) fica lento e fragmentado. Veja Btrfs e Subvolumes.

VirtualBox no Arch

O VirtualBox (da Oracle) é o que roda a VM deste guia. Ele não usa o KVM: traz seus próprios módulos de kernel (vboxdrv e companhia). E aqui mora a pegadinha do Arch: módulos de kernel precisam ser compilados para cada versão de kernel, e o kernel do Arch muda quase toda semana.

DKMS (Dynamic Kernel Module Support) é um sistema que, por um hook do pacman, recompila módulos de terceiros sempre que um kernel é instalado ou atualizado. Por isso a atualização do kernel fica alguns minutos mais lenta. Se esquecer os headers, o VirtualBox não liga as VMs ("Kernel driver not installed (rc=-1908)"). Veja Kernels.

sudo pacman -S virtualbox linux-headers     # + linux-lts-headers se usar o LTS
sudo modprobe vboxdrv                        # ou reinicie
sudo usermod -aG vboxusers ana               # só para usar USB nas VMs
Arch como convidado

Se o Arch é a VM (como no guia), o pacote é outro: virtualbox-guest-utils (redimensionar a tela, área de transferência, pastas compartilhadas), com o serviço vboxservice. No QEMU/KVM, o equivalente é qemu-guest-agent e, para a tela, spice-vdagent.

Containers (Docker e Podman) são outra coisa: mais leves, mas sempre com o mesmo kernel. Para testar outra distribuição Linux só pela linha de comando, um container basta; para testar uma instalação, um bootloader ou outro kernel, só uma VM serve.

Quando não funciona

"KVM is not available" / "KVM não disponível"

O que aconteceu: o virt-manager não achou /dev/kvm. A VM até roda, mas emulada, dezenas de vezes mais lenta.

Como confirmar: ls -l /dev/kvm; lscpu | grep -i virt; dmesg | grep -i kvm (ex.: kvm_intel: VMX not supported by CPU 1).

Como resolver: ligue VT-x/AMD-V (às vezes "SVM") no firmware. Se o Arch é ele mesmo uma VM, ligue a virtualização aninhada no programa de fora (no VirtualBox: Configurações → Sistema → Processador → "Habilitar VT-x/AMD-V aninhado").

"modprobe: ERROR: could not insert 'kvm_intel': Operation not supported"

O que aconteceu: o processador não oferece VMX (desligado no firmware ou VM sem aninhamento). Saída real na VM do guia, acima.

Como resolver: o mesmo do anterior. Não adianta instalar nada.

"authentication unavailable: no polkit agent available" / "Permission denied" no virt-manager

O que aconteceu: seu usuário não está no grupo libvirt, ou entrou mas não fez logout.

Como resolver: sudo usermod -aG libvirt $USER, saia e entre de novo, confira com groups.

"Network 'default' is not active"

O que aconteceu: a rede NAT padrão vem desligada (ou falta o dnsmasq).

Como resolver: sudo virsh net-start default e sudo virsh net-autostart default; confira pacman -Q dnsmasq.

VirtualBox: "Kernel driver not installed (rc=-1908)"

O que aconteceu: o módulo vboxdrv não foi compilado para o kernel atual: faltam os headers ou você atualizou o kernel e não reiniciou.

Como resolver: sudo pacman -S linux-headers (o DKMS compila na hora), depois sudo modprobe vboxdrv ou reinicie.

Resumo

  • KVM (kernel) é o motor, QEMU simula o computador, libvirt administra, virt-manager é a janela.
  • Sem VT-x/AMD-V não há KVM: ls -l /dev/kvm é o teste; ligue no firmware.
  • Dentro de uma VM, lscpu mostra o hipervisor, não "VT-x"; só com virtualização aninhada dá para criar VMs.
  • qemu-desktop libvirt virt-manager dnsmasq, systemctl enable --now libvirtd, grupo libvirt.
  • VirtualBox no Arch: módulos via virtualbox-host-dkms + linux-headers.
