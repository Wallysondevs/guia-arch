Arch Resgate com chroot

O computador não liga mais no Arch: o GRUB sumiu, o kernel não acha a raiz, uma atualização foi interrompida. Quase sempre o sistema está inteiro no disco, só não consegue iniciar. O resgate é o mesmo truque da instalação: ligar pelo pendrive do Arch, montar o sistema quebrado e "entrar" nele com arch-chroot para consertá-lo por dentro, com o pacman, o mkinitcpio e o GRUB dele.

Você vai aprender
  • O que o chroot e o arch-chroot fazem.
  • O roteiro completo: pendrive → identificar partições → montar raiz e EFI → arch-chroot → consertar → sair.
  • O que dá para consertar lá dentro: kernel, initramfs, GRUB, senha esquecida, pacman interrompido.
  • Os erros mais comuns do próprio resgate (esquecer a EFI, montar a partição errada).

O diagnóstico de cada tela de erro está em Recuperar o Boot; esta aula é a ferramenta que quase todos eles usam.

O que é chroot

chroot (de change root, mudar a raiz) roda um programa achando que uma pasta qualquer é o /. Se você montou o disco do Arch quebrado em /mnt e roda chroot /mnt, o /etc/fstab que o shell enxerga é o do sistema quebrado, o pacman que roda é o dele e instala no disco dele. É como "teletransportar" o terminal para dentro do sistema que não liga.

Um chroot puro não basta: programas como o pacman, o mkinitcpio e o grub-install precisam de /proc, /sys, /dev, das variáveis EFI e da internet. O arch-chroot (pacote arch-install-scripts, que já vem no pendrive) monta tudo isso antes e desmonta na saída. Foi ele que você usou na instalação.

O roteiro do resgate

Os comandos do ambiente live abaixo são os da instalação real da máquina do guia (o live fala inglês e usa o zsh, com o prompt root@archiso ~ #). As saídas vêm dos registros dessa instalação.

  1. Dê boot pelo pendrive do Arch (o mesmo da instalação; baixe a ISO mais nova se o seu for antigo: veja Baixar e Verificar a ISO). No menu do firmware, escolha o pendrive no modo UEFI. Confira, ajuste o teclado e a rede (detalhes em O Ambiente Live): 
    #> cat /sys/firmware/efi/fw_platform_size
64                                 « 64 = boot em UEFI (precisa ser o mesmo modo do sistema)
#> loadkeys br-abnt2
#> ping -c 3 archlinux.org

64 bytes from 209.126.35.79: icmp_seq=2 ttl=64 time=42.5 ms
64 bytes from 209.126.35.79: icmp_seq=3 ttl=64 time=55.2 ms

3 packets transmitted, 3 received, 0% packet loss, time 5616ms
rtt min/avg/max/mdev = 42.522/47.247/55.200/5.656 ms
  2. Descubra qual partição é qual. Não confie em lembranças: os nomes (sda, nvme0n1) podem mudar com outro pendrive conectado. Olhe tipo e tamanho: 
    #> lsblk -f /dev/sda
NAME   FSTYPE FSVER LABEL UUID                                 FSAVAIL FSUSE% MOUNTPOINTS
sda
├─sda1 vfat   FAT32       C509-6CB1                             929,2M     9% /boot
├─sda2 swap   1           02576132-0458-4975-916f-94e08af9a31c                [SWAP]
└─sda3 ext4   1.0         75d167c8-1dad-4d0a-a0ae-b063058a18e9   18,1G    21% /

    Essa saída é da máquina do guia ligada, para você ver os tipos. No pendrive, a coluna MOUNTPOINTS vem vazia e aparecem também o loop0 (o sistema do live) e o próprio pendrive. A pista: vfat de ~1 GiB é a EFI; swap é a swap; a ext4 (ou btrfs, ou crypto_LUKS) grande é a raiz.

  3. Monte a raiz em /mnt e a EFI em /mnt/boot (onde ela fica no sistema; confira no fstab dele, em /mnt/etc/fstab, se tiver dúvida): 
    #> mount /dev/sda3 /mnt
#> mount --mkdir /dev/sda1 /mnt/boot
#> lsblk -f
NAME   FSTYPE   FSVER            LABEL       UUID                                 FSAVAIL FSUSE% MOUNTPOINTS
loop0  squashfs 4.0                                                                     0   100% /run/archiso/airootfs
sda
|-sda1 vfat     FAT32                        C509-6CB1                              1022M     0% /mnt/boot
|-sda2 swap     1                            02576132-0458-4975-916f-94e08af9a31c                [SWAP]
`-sda3 ext4     1.0                          75d167c8-1dad-4d0a-a0ae-b063058a18e9   23.2G     0% /mnt
sr0    iso9660  Joliet Extension ARCH_202606 2026-06-01-15-21-12-00                     0   100% /run/archiso/bootmnt

    Se o seu disco for diferente, monte antes as camadas de baixo:

    A raiz é…Antes do mountO mount da raiz
    ext4 simples—mount /dev/sda3 /mnt
    Btrfs com subvolumes—mount -o subvol=@ /dev/sda3 /mnt (e @home etc., se for mexer neles)
    LUKScryptsetup open /dev/sda3 cryptrootmount /dev/mapper/cryptroot /mnt
    LVM (on LUKS)cryptsetup open … e vgchange -aymount /dev/VG/raiz /mnt
  4. Entre no sistema: arch-chroot /mnt. O prompt muda para o do Bash do seu Arch, na pasta /: 
    #> arch-chroot /mnt
    #> cat /etc/hostname
notebook                       « é o sistema do disco, não o do pendrive

    (O conteúdo do /etc/hostname é o do treino real mais abaixo.) Dentro do chroot, o nome da máquina no prompt continua archiso (o kernel em execução é o do pendrive), mas todos os arquivos são os do seu sistema.

  5. Conserte (veja abaixo o que dá para fazer).
  6. Saia, desmonte e reinicie. exit (ou Ctrl+D) volta ao live; umount -R /mnt desmonta tudo, na ordem certa, gravando o que estava pendente: 
    #> umount -R /mnt; swapoff /dev/sda2; echo ok
ok
#> reboot

    Tire o pendrive quando a tela apagar. Desmontar antes de reiniciar evita o aviso de "volume não foi desmontado corretamente" na EFI (veja Recuperar o Boot).

Treino de verdade, sem pendrive

Dá para treinar o arch-chroot na própria máquina, com segurança, montando o disco dela de novo, só para leitura, num "espaço de montagens" separado (unshare -m): nada do que se monta ali aparece para o resto do sistema, e tudo some quando o shell termina. Foi assim que as saídas abaixo foram tiradas (cada comando do chroot foi rodado como arch-chroot /mnt comando, que dá o mesmo resultado que digitar lá dentro).

#> unshare -m --propagation private bash
#> mount /dev/sda3 /mnt
#> mount -o remount,ro,bind /mnt                « só leitura: nenhum risco
#> ls /mnt

#> arch-chroot /mnt

O ls /mnt/boot veio vazio: a EFI ainda não foi montada. Lá dentro, o /boot também está vazio, mas o pacman funciona normalmente:

#> ls /boot
#> cat /etc/hostname; pacman -Q linux linux-lts
notebook
linux 7.2.10.arch1-1
linux-lts 6.18.57-1
O erro clássico: esquecer a EFI

Nesse estado, um mkinitcpio -P ou a reinstalação do kernel gravariam os arquivos novos na pasta /boot da raiz, escondida embaixo da EFI. O comando dá "certo", você reinicia e o boot continua usando os arquivos velhos da EFI. Sempre confira com ls /mnt/boot (deve mostrar vmlinuz-linux, initramfs-linux.img, EFI, grub) antes de entrar.

O findmnt mostra tudo o que o arch-chroot montou sozinho. O touch falhou porque o treino é só leitura; num resgate de verdade, a raiz está gravável. Repare no uname -r: dentro do chroot, ele mostra o kernel que está rodando (no pendrive, seria o do live), não o instalado. Por isso o mkinitcpio -P usa os presets (/etc/mkinitcpio.d/*.preset) e não o uname. Para encerrar o treino: umount -R /mnt e exit (o unshare termina e as montagens somem).

O que consertar lá dentro

Refazer o initramfs

Initramfs quebrado ou desatualizado (atualização interrompida, hook novo de LUKS/LVM): mkinitcpio -P refaz as imagens de todos os kernels (-P = todos os presets). A saída real, rodada do live durante a instalação:

#> arch-chroot /mnt mkinitcpio -P

==> Using default configuration file: '/etc/mkinitcpio.conf'
  -> -k /boot/vmlinuz-linux -g /boot/initramfs-linux.img
==> Starting build: '7.2.10-arch1-1'

  -> Running build hook: [systemd]

Reinstalar o kernel

Se o /boot ficou sem o vmlinuz-linux, ou os módulos em /usr/lib/modules estão incompletos: pacman -S linux dentro do chroot. A reinstalação regrava o kernel e roda os hooks que refazem o initramfs. Assim ficou o fim da instalação real do linux-lts na máquina do guia (trecho de uma transação maior, com vários pacotes):

Reinstalar o GRUB

Entrada sumiu do firmware, grub rescue>, ou o Windows sobrescreveu o boot: reinstale e regere o menu. Saídas reais da instalação:

As opções têm que ser as da sua instalação (a EFI em /boot ou em /efi?). Se o firmware "esquece" a entrada a cada boot, acrescente --removable. Explicações completas em Bootloader e Recuperar o Boot.

Senha esquecida

Como root dentro do chroot, o passwd troca a senha de qualquer usuário sem pedir a antiga. Saída real (com um usuário de teste):

#> passwd teste-a8
Nova senha:
Redigite a nova senha:
passwd: senha atualizada com sucesso
#> passwd -S teste-a8
teste-a8 P 2026-10-16 -1 -1 -1 -1          « P = tem senha (usable Password)

No seu caso: passwd ana e/ou passwd (sozinho = root). Se a conta ficou bloqueada por tentativas erradas, faillock --user ana --reset (veja Segurança). E repare: qualquer um com um pendrive faz isso no seu computador. Só a criptografia de disco impede.

pacman quebrado ou atualização interrompida

Faltou energia no meio do pacman -Syu: pacotes ficaram pela metade e às vezes sobra a trava /var/lib/pacman/db.lck. Dentro do chroot:

  1. Confirme que nenhum pacman está rodando e apague a trava (rm /var/lib/pacman/db.lck).
  2. Complete a atualização: pacman -Syu.
  3. Procure arquivos estragados: pacman -Qkk 2>&1 | grep -v ' 0 arquivo alterado' e reinstale os pacotes citados com pacman -S pacote.
  4. Refaça o initramfs (mkinitcpio -P), por garantia.

Cada mensagem desse caminho, com a saída real, está em Erros de Atualização. Se o próprio pacman do sistema não roda mais (biblioteca quebrada), use o pacman do pendrive apontando para o disco: pacman --sysroot /mnt -Syu (sem chroot).

fstab errado

Um UUID errado ou uma opção inválida no /etc/fstab derruba o boot. Edite /mnt/etc/fstab (nem precisa de chroot) e compare com genfstab -U /mnt. Veja mount e fstab e o caso do emergency mode em Recuperar o Boot.

Experimente

Missão: num resgate, o /mnt/etc/fstab diz qual partição é a raiz. Na máquina do guia, descubra o UUID da raiz (/) olhando o /etc/fstab.

Quando não funciona

"mount point does not exist" 
#> mount /dev/sda1 /mnt/boot
mount: /mnt/boot: mount point does not exist.
       dmesg(1) may have more information after failed mount system call.

O que aconteceu: a pasta /mnt/boot não existe. Quase sempre porque a raiz ainda não foi montada em /mnt (a pasta boot está dentro dela), ou porque você montou a partição errada como raiz. (Saída real da máquina do guia com LANG=C, igual à do live; em pt_BR: o ponto de montagem não existe.)

Como resolver: monte a raiz primeiro; confira com ls /mnt (deve ter bin boot etc home usr var…). Se a pasta realmente não existe, mount --mkdir cria.

"is not a mountpoint" / "failed to setup chroot" 
#> arch-chroot /tmp/a8/vazio2
==> WARNING: /tmp/a8/vazio2 is not a mountpoint. This may have undesirable side effects.
mount: /tmp/a8/vazio2/proc: o ponto de montagem não existe.
       dmesg(1) pode ter mais informação após uma chamada a montar o sistema falhada.
==> ERROR: failed to setup chroot /tmp/a8/vazio2

O que aconteceu: a pasta não é um sistema montado (você esqueceu o mount, ou digitou o caminho errado) e não tem proc, sys… dentro.

Como resolver: monte a raiz em /mnt e rode arch-chroot /mnt.

"não parece ser uma partição EFI" 
#> grub-install --target=x86_64-efi --efi-directory=/var/tmp/a8 --bootloader-id=TESTE --no-nvram
Instalando para a plataforma x86_64-efi.
grub-install: erro: /var/tmp/a8 não parece ser uma partição EFI.

O que aconteceu: o --efi-directory aponta para uma pasta que não é a partição FAT da EFI. No resgate, é o sintoma de ter esquecido de montar a EFI em /mnt/boot antes do arch-chroot (aí a mensagem fala de /boot).

Como resolver: exit, mount /dev/sda1 /mnt/boot, arch-chroot /mnt e repita.

O conserto "funcionou", mas nada mudou no boot

O que aconteceu: o mkinitcpio ou o pacman -S linux rodaram sem a EFI montada e gravaram no /boot errado (veja o aviso acima). Ou você consertou outro sistema (outra partição, outro disco).

Como confirmar: no live, ls -l /mnt/boot: as datas de initramfs-linux.img devem ser de agora.

Como resolver: monte a EFI e repita o conserto.

Sem internet dentro do chroot

O que aconteceu: a rede é a do live. Se o ping falha no live, falha no chroot também.

Como resolver: saia, conecte no live (cabo, ou iwctl para Wi-Fi; veja O Ambiente Live) e entre de novo. O arch-chroot copia o DNS do live (a linha /etc/resolv.conf do findmnt).

Resumo

  • Pendrive (UEFI) → lsblk -f → montar raiz em /mnt e EFI em /mnt/boot → arch-chroot /mnt.
  • LUKS, LVM e Btrfs têm um passo antes do mount (cryptsetup open, vgchange -ay, -o subvol=@).
  • Lá dentro: mkinitcpio -P, pacman -S linux, grub-install + grub-mkconfig, passwd, pacman -Syu/-Qkk.
  • Confira ls /mnt/boot antes de entrar: esquecer a EFI é o erro mais comum.
  • Saia com exit e umount -R /mnt antes do reboot.
