Arch Erros de Atualização

Quase todo problema de atualização no Arch começa com uma mensagem do pacman que diz exatamente o que está errado, mas em linguagem de máquina. Esta aula é um dicionário: para cada erro clássico, a mensagem real, a causa, como confirmar e como resolver sem piorar as coisas.

Você vai aprender
  • A ler a mensagem antes de procurar a solução (e onde procurar: as notícias do Arch).
  • Destravar a base de dados com segurança (db.lck).
  • Resolver chaves e assinaturas (archlinux-keyring primeiro).
  • Tratar arquivos conflitantes, dependências, espelho fora do ar e disco cheio.
  • O que fazer depois de uma atualização interrompida e quando o kernel novo "some" com os módulos.
De onde vêm estas saídas

A máquina do guia é compartilhada e não pode ser estragada de verdade. Por isso, cada erro foi provocado num ambiente de teste: o pacman de verdade, mas apontando para pastas descartáveis em /tmp/a8 (com --root, --dbpath, --cachedir, --gpgdir e --config). As mensagens são as mesmas que você veria no sistema; só os caminhos mudam (onde aparece /tmp/a8/…, no seu computador seria /var/lib/pacman/…, /usr/bin/… etc.). O primeiro erro é da instalação real da máquina. Nos testes, o … substitui opções repetidas e linhas sem importância, e foram omitidos os avisos database file for 'core' does not exist, que só existem no ambiente de teste (lá, a raiz de mentira não tem as bases dos repositórios; por isso também se usou -dd, para pular dependências).

Antes de tudo: três regras

  1. Leia as notícias em archlinux.org/news antes de atualizar. Quando uma atualização exige intervenção manual (um --overwrite, um pacote trocado), a receita está lá.
  2. Sempre pacman -Syu completo. Nunca pacman -Sy pacote (atualização parcial: um pacote novo com bibliotecas velhas é a receita do "não liga mais"). Veja Atualizar o Sistema.
  3. Leia a mensagem inteira, principalmente a linha que começa com erro: e as que vêm logo depois. Copie-a exatamente se for pesquisar.

1. "não foi possível travar a base de dados"

Este aconteceu de verdade na máquina do guia, logo depois de ela ser desligada à força no meio de um uso do pacman:

#> pacman -Syu --noconfirm --needed base-devel git … linux-lts linux-lts-headers
:: Sincronizando a base de dados de pacotes...
erro: falha ao sincronizar todas as bases de dados (não foi possível travar a base de dados)
#> pgrep -a pacman; ls -l /var/lib/pacman/db.lck
---------- 1 root root 0 16 out 12:40 /var/lib/pacman/db.lck
#> rm /var/lib/pacman/db.lck
#> pacman -Syu --noconfirm --needed base-devel git … linux-lts linux-lts-headers
:: Sincronizando a base de dados de pacotes...
 core sendo baixado...
 extra sendo baixado...
:: Iniciando atualização completa do sistema...

Num -S ou -R, a mensagem é mais explicativa (ambiente de teste):

#> pacman --dbpath /tmp/a8/db -S htop
erro: falha ao iniciar a transação (não foi possível travar a base de dados)
erro: não foi possível travar a base de dados: Arquivo existe
  se tiver certeza de que um gerenciador de pacotes não esteja
  em execução, você pode remover /tmp/a8/db/db.lck
#> echo $?
1

Causa: enquanto trabalha, o pacman cria o arquivo vazio /var/lib/pacman/db.lck (a trava) para que dois pacman não mexam nos pacotes ao mesmo tempo. Se ele é interrompido (desligamento forçado, terminal fechado, kill -9), a trava fica para trás.

Como confirmar: pgrep -a pacman não deve mostrar nada (código de saída 1). Lembre também do yay/paru, de um "Discover"/"GNOME Software" aberto e de outro terminal.

Como resolver: se nada está rodando, sudo rm /var/lib/pacman/db.lck e repita.

Nunca apague a trava com outro pacman rodando

Dois pacman ao mesmo tempo podem corromper a base de dados local. Se o pgrep mostrar um pacman, espere ele terminar. E se a trava sobrou de uma atualização interrompida, depois de apagá-la siga o item 7.

2. Chaves e assinaturas

Cada pacote é assinado pelo empacotador, e o pacman confere a assinatura com o chaveiro do Arch (pacote archlinux-keyring). Se o seu chaveiro está velho (máquina meses sem atualizar) e um empacotador novo assinou o pacote, aparece (ambiente de teste com um chaveiro que conhece a chave mas não confia nela):

#> pacman … --gpgdir /tmp/a8/gnupg -Sdd nano
procurando pacotes conflitantes...

Pacotes (1) nano-9.2-1

Tamanho total instalado:  2,71 MiB

:: Continuar a instalação? [S/n]
:: Obtendo pacotes...
 nano-9.2-1-x86_64 sendo baixado...
verificando chaveiro...
verificando integridade de pacotes...
erro: nano: a assinatura de "Andreas Radke <andyrtr@archlinux.org>" tem confiança desconhecida
:: Arquivo /tmp/a8/cache/nano-9.2-1-x86_64.pkg.tar.zst está corrompido (pacote inválido ou corrompido (assinatura PGP)).
Deseja apagá-lo? [S/n] erro: falha ao efetuar a transação (pacote inválido ou corrompido (assinatura PGP))

Ocorreram erros e, portanto, nenhum pacote foi atualizado.

Outras formas da mesma doença: assinatura … é inválida, chave "…" é desconhecida seguida de :: Importar a chave PGP …? [S/n], e pacote inválido ou corrompido (assinatura PGP).

Causa: quase sempre o chaveiro desatualizado. Mais raramente, o download veio estragado de um espelho ruim, ou o relógio do computador está muito errado (assinaturas "do futuro").

Como resolver: atualize primeiro o chaveiro e depois o resto:

#> pacman -Sy archlinux-keyring && pacman -Su

É a única exceção aceita à regra do "nunca -Sy pacote": o -Su vem logo em seguida, no mesmo comando. Responder S para apagar o arquivo "corrompido" é seguro: ele é baixado de novo. O archlinux-keyring também se atualiza sozinho pela internet, pelo timer archlinux-keyring-wkd-sync.timer (ativo na máquina do guia: o próximo disparo aparecia em systemctl list-timers como Tue 2026-10-20 10:34:32 -03). Se ainda assim falhar, confira o relógio (timedatectl) e veja Chaves e Assinaturas para pacman-key --populate.

Reinstalar o chaveiro do jeito certo mostra o aviso de "reinstalando" (resumo real, respondido com "não"):

#> pacman -S archlinux-keyring
atenção: archlinux-keyring-20260909-1 está atualizado -- reinstalando
resolvendo dependências...
procurando pacotes conflitantes...

Pacotes (1) archlinux-keyring-20260909-1

Tamanho total instalado:  1,73 MiB
Alteração no tamanho:     0,00 MiB

:: Continuar a instalação? [S/n] n
Não desligue a verificação

Trocar SigLevel para Never no /etc/pacman.conf "resolve" a mensagem tirando a única proteção contra pacotes adulterados. Nunca faça isso.

3. "existe no sistema de arquivos" (arquivos conflitantes)

#> pacman --root /tmp/a8/raiz … -Udd htop-3.5.3-1-x86_64.pkg.tar.zst
…
:: Continuar a instalação? [S/n]
verificando chaveiro...
verificando integridade de pacotes...
carregando arquivos do pacote...
verificando conflitos de arquivos...
erro: falha ao efetuar a transação (arquivos conflitantes)
htop: /tmp/a8/raiz/usr/bin/htop existe no sistema de arquivos
Ocorreram erros e, portanto, nenhum pacote foi atualizado.
#> echo $?
1

Causa: o pacote quer instalar um arquivo que já existe e que não pertence a nenhum pacote (no teste, um htop "feito à mão"). Na vida real: algo instalado com make install, pip install como root, um script de instalação de fora, ou um arquivo que mudou de pacote numa atualização (aí as notícias avisam). O pacman se recusa a sobrescrever o que não é dele, e não instala nada.

Como confirmar: pergunte de quem é o arquivo:

#> pacman -Qo /usr/bin/htop
/usr/bin/htop pertence a htop 3.5.3-1          « no sistema: pertence a um pacote, tudo certo

Se a resposta for erro: Nenhum pacote possui /caminho, o arquivo é "órfão" e é ele que atrapalha.

Como resolver: se o arquivo é lixo de uma instalação manual, apague-o (ou desinstale o que o criou) e repita. Se as notícias do Arch mandarem sobrescrever, use --overwrite com o caminho exato ou um padrão:

#> pacman --root /tmp/a8/raiz … -Udd --overwrite /tmp/a8/raiz/usr/bin/htop htop-3.5.3-1-x86_64.pkg.tar.zst
…
verificando conflitos de arquivos...
verificando espaço em disco disponível...
:: Processando alterações do pacote...
instalando htop...
#> echo $?
0

No sistema normal, seria pacman -Syu --overwrite /usr/bin/htop (no teste, o caminho inclui a raiz de mentira). Para vários arquivos de uma vez, um padrão. Um exemplo real das notícias do Arch (05/11/2025): versões antigas do pacote waydroid criavam arquivos .pyc que o pacman não conhecia, e a atualização parava com waydroid: /usr/lib/waydroid/tools/__pycache__/__init__.cpython-313.pyc exists in filesystem. A própria notícia trazia a receita: pacman -Syu --overwrite /usr/lib/waydroid/tools/\*__pycache__/\* (as barras protegem os * do shell, para que o padrão chegue inteiro ao pacman). Veja como ler as notícias em Manutenção Periódica.

Nunca --overwrite '*'

Isso sobrescreve qualquer arquivo de qualquer pacote sem perguntar e pode esconder o problema de verdade (dois pacotes brigando pelo mesmo arquivo). Use só o caminho que a mensagem citou, e só quando entender de onde ele veio.

4. "não foi possível satisfazer as dependências"

#> pacman --root /tmp/a8/raiz … -U htop-3.5.3-1-x86_64.pkg.tar.zst
carregando pacotes...
resolvendo dependências...
atenção: não é possível resolver "libcap", uma dependência de "htop"
atenção: não é possível resolver "libcap.so=2-64", uma dependência de "htop"
atenção: não é possível resolver "libnl", uma dependência de "htop"
atenção: não é possível resolver "ncurses", uma dependência de "htop"
atenção: não é possível resolver "libncursesw.so=6-64", uma dependência de "htop"
:: O seguinte pacote não pode ser atualizado devido a dependências não resolvidas:
      htop

:: Deseja ignorar o pacote acima para esta atualização? [s/N] erro: falha ao preparar a transação (não foi possível satisfazer as dependências)

:: não foi possível satisfazer a dependência "libcap" necessária por htop
:: não foi possível satisfazer a dependência "libcap.so=2-64" necessária por htop
:: não foi possível satisfazer a dependência "libnl" necessária por htop
:: não foi possível satisfazer a dependência "ncurses" necessária por htop
:: não foi possível satisfazer a dependência "libncursesw.so=6-64" necessária por htop

Causa: o pacote precisa de algo que não existe nos repositórios configurados, ou numa versão que não existe. No teste, a raiz estava vazia e sem repositórios. Na vida real, os culpados mais comuns são:

  • um pacote do AUR que exige a versão antiga de uma biblioteca (ex.: libfoo.so=1 quando o Arch já está na 2);
  • um pacote travado em IgnorePkg no pacman.conf ou "segurado" com downgrade;
  • uma atualização parcial anterior, ou espelho atrasado (parte dos pacotes novos ainda não chegou).

Como confirmar: a linha necessária por PACOTE diz quem está pedindo. pacman -Qi PACOTE mostra se ele é do AUR (pacman -Qm lista os de fora).

Como resolver: faça um pacman -Syu completo; se o culpado é do AUR, atualize-o ou recompile (yay -Syu, ou yay -S pacote --rebuild), ou remova-o temporariamente. Nunca use -d/-dd (pular dependências) para "passar": o pacote instala, mas não funciona.

5. Espelho fora do ar ou com 404

Um espelho que respondeu "não existe" (ambiente de teste com um endereço de propósito errado):

#> pacman --config /tmp/a8/pacman-404.conf --dbpath /tmp/a8/db404 -Sy
:: Sincronizando a base de dados de pacotes...
 core sendo baixado...
erro: falha ao obter o arquivo "core.db" de geo.mirror.pkgbuild.com : The requested URL returned error: 404
erro: falha ao sincronizar todas as bases de dados (falha ao obter alguns arquivos)
#> echo $?
1

E um espelho cujo nome não existe (ou sem internet/DNS):

#> pacman --config /tmp/a8/pacman-404.conf --dbpath /tmp/a8/db404 -Sy
:: Sincronizando a base de dados de pacotes...
erro: falha ao obter o arquivo "extra.db" de espelho.exemplo.invalid : Could not resolve host: espelho.exemplo.invalid
 extra sendo baixado...
atenção: erro fatal de espelho.exemplo.invalid, ignorando o restante desta transação
erro: falha ao sincronizar todas as bases de dados (url inválida para o servidor)

Causa: o primeiro espelho da lista está fora do ar, atrasado, ou foi desativado. Um 404 ao baixar um pacote (não a base) costuma ser outra coisa: a sua base de dados está velha e pede uma versão que o espelho já apagou.

Como confirmar: ping -c 3 archlinux.org (internet), e olhe a primeira linha Server = de /etc/pacman.d/mirrorlist. Quando há vários servidores, o pacman tenta o próximo sozinho; o erro só aparece se todos falharem.

Como resolver: para o 404 de pacote, pacman -Syu (base nova). Para espelho ruim, gere uma lista nova com o reflector (veja Espelhos) e force o download das bases com pacman -Syyu (dois y = baixa mesmo que pareçam atualizadas).

6. Disco cheio

Antes de mexer em qualquer arquivo, o pacman confere se cabe (CheckSpace no pacman.conf). Ambiente de teste com uma "partição" de 20 MiB e o pacote linux-lts (156 MiB instalado):

#> pacman --root /tmp/a8/mini … -Udd linux-lts-6.18.57-1-x86_64.pkg.tar.zst
…
Tamanho total instalado:  155,84 MiB

:: Continuar a instalação? [S/n]
verificando chaveiro...
verificando integridade de pacotes...
carregando arquivos do pacote...
verificando conflitos de arquivos...
verificando espaço em disco disponível...
erro: Partição /tmp/a8/mini cheia demais: 43377 blocos necessários, 5119 blocos livres
erro: espaço livre em disco insuficiente
erro: falha ao efetuar a transação (não há espaço livre suficiente em disco)
Ocorreram erros e, portanto, nenhum pacote foi atualizado.

Ainda bem: nada foi instalado pela metade. Se o disco enche durante o download, o erro aparece ao gravar o arquivo no cache.

Como confirmar: df -h / /boot. O cache de pacotes costuma ser o maior culpado:

#> df -h / /boot
Sist. Arq.      Tam. Usado Disp. Uso% Montado em
/dev/sda3        25G  5,2G   19G  23% /
/dev/sda1      1022M   93M  930M  10% /boot
#> du -sh /var/cache/pacman/pkg
1,3G	/var/cache/pacman/pkg

Como resolver: limpe versões antigas do cache com paccache -rk1 (mantém só a última de cada pacote) ou paccache -ruk0 (apaga as de pacotes desinstalados); o pacman -Sc também serve (veja Cache e Órfãos). Depois, logs (journalctl --vacuum-size=200M) e, com Btrfs, snapshots velhos. A partição /boot pequena (de 300 MiB, em instalações antigas) enche com dois kernels e seus initramfs: aí só ajuda remover um kernel ou aumentar a partição.

7. Atualização interrompida (falta de energia)

Se o computador desligou no meio do pacman -Syu, alguns pacotes ficaram com arquivos novos, outros com velhos, e a trava ficou para trás. O sistema pode nem ligar (aí, faça os passos de dentro do resgate com chroot).

  1. Destrave e complete a atualização: rm /var/lib/pacman/db.lck (item 1) e pacman -Syu. O pacman reinstala o que estava pendente.
  2. Procure arquivos que sumiram com pacman -Qk (check). Num sistema saudável: 
    #> pacman -Qk pacman bash
pacman: total de 426 arquivos,  0 arquivo em falta
bash: total de 269 arquivos,  0 arquivo em falta
    Num ambiente de teste, com um arquivo do pacote tree apagado: 
    #> pacman $R -Qk tree
atenção: tree: /tmp/a8/raiz/usr/share/man/man1/tree.1.gz (Arquivo ou diretório inexistente)
tree: total de 7 arquivos,  1 arquivo em falta
#> echo $?
1
  3. Procure arquivos estragados com -Qkk (dois k: confere tamanho, data e soma SHA256 de cada arquivo). No teste, o executável foi "cortado" para 100 bytes, como numa gravação interrompida: 
    #> pacman $R -Qkk tree
atenção: tree: /tmp/a8/raiz/usr/bin/tree (Última modificação incorreta)
atenção: tree: /tmp/a8/raiz/usr/bin/tree (Tamanho incorreto)
atenção: tree: /tmp/a8/raiz/usr/bin/tree (soma de verificação SHA256 incorreta)
atenção: tree: /tmp/a8/raiz/usr/share/man/man1/tree.1.gz (Arquivo ou diretório inexistente)
tree: total de 7 arquivos, 2 arquivos alterados
    ($R guardava as opções --root/--dbpath do teste.) Para o sistema inteiro: pacman -Qkk 2>&1 | grep -v ' 0 arquivo alterado'. Demora (lê todos os arquivos), e arquivos de configuração que você editou também aparecem; o que importa são os de /usr.
  4. Reinstale os pacotes atingidos: pacman -S tree. No teste: 
    #> pacman $P --noconfirm -Udd tree-2.3.2-1-x86_64.pkg.tar.zst 2>&1 | tail -3
atenção: não foi possível obter informações do arquivo usr/share/man/man1/tree.1.gz
:: Processando alterações do pacote...
reinstalando tree...
#> pacman $R -Qkk tree
tree: total de 7 arquivos, 0 arquivo alterado          « consertado
  5. Refaça o initramfs (mkinitcpio -P) se o kernel estava na transação, e confira o GRUB.

8. Atualizei o kernel e os módulos não carregam

Depois de uma atualização do linux, sem reiniciar, um pendrive não monta, a rede de uma placa USB não sobe, ou o modprobe reclama assim (simulado com -S, que faz o modprobe agir como se outro kernel estivesse rodando):

#> modprobe -n -v -S 7.2.11-arch1-1 vfat
modprobe: FATAL: Module vfat not found in directory /lib/modules/7.2.11-arch1-1
#> echo $?
1
#> uname -r
7.2.10-arch1-1
#> ls /usr/lib/modules
6.18.57-1-lts
7.2.10-arch1-1

Causa: o pacman troca os módulos: a pasta do kernel antigo (o que está rodando) é apagada e entra a do novo. Até reiniciar, o kernel em memória procura os módulos numa pasta que não existe mais.

Como confirmar: compare uname -r (o que roda) com pacman -Q linux e ls /usr/lib/modules (o que está instalado). Repare que o pacote mostra 7.2.10.arch1-1 (com ponto) e o uname, 7.2.10-arch1-1 (com hífen): é a mesma versão.

Como resolver: reinicie. É por isso que atualizações do kernel pedem reboot logo. Ter o linux-lts instalado também ajuda: se o kernel novo não ligar, o LTS liga (veja Kernels).

9. Arquivos .pacnew

Não é erro, mas aparece na atualização: atenção: /etc/pacman.conf instalado como /etc/pacman.conf.pacnew. O pacman não sobrescreve um arquivo de configuração que você editou; ele deixa a versão nova ao lado, com .pacnew, para você comparar e juntar. Para listar os pendentes:

#> pacdiff -o
#> echo $?
0                     « nada pendente na máquina do guia

Como comparar e juntar está em .pacnew e .pacsave. Ignorar um .pacnew por meses é uma causa comum de "atualizei e quebrou".

Exercícios

1. Quem é o dono?

Antes de usar --overwrite, descubra a qual pacote pertence /usr/lib/libfoo.so:

pacman /usr/lib/libfoo.so

2. Chaveiro primeiro

Complete o comando que resolve erros de assinatura:

pacman -Sy && pacman

3. Aparece "não foi possível travar a base de dados". Qual é o primeiro passo?

4. Depois de atualizar o kernel, o pendrive não monta e o modprobe diz "Module vfat not found in directory /lib/modules/…". O que fazer?

5. Faltou energia no meio do pacman -Syu. Qual comando encontra arquivos de pacotes que ficaram estragados?

Resumo

  • Leia as notícias, use sempre -Syu completo e leia a linha erro: inteira.
  • Trava: confirme que nada roda, apague db.lck. Assinatura: archlinux-keyring primeiro.
  • Conflito de arquivos: pacman -Qo, notícias, --overwrite só no caminho citado.
  • Dependências: quase sempre um pacote do AUR ou uma atualização parcial.
  • Interrupção: destravar, -Syu, -Qkk, reinstalar os citados, mkinitcpio -P. Kernel novo sem módulos: reinicie.
