pacman Avançado

Em pacman: o Básico você aprendeu a procurar, instalar e remover. Esta aula é sobre perguntar: o que eu instalei de propósito? De que pacote é este arquivo? Que pacote tem o comando que me falta? Algum arquivo do sistema foi alterado? E também sobre os ajustes que deixam o pacman mais confortável.

Você vai aprender
  • Filtrar os instalados: -Qe, -Qet, -Qd, -Qm, -Qs, e a opção -q para scripts.
  • Descobrir o dono de um arquivo (-Qo) e qual pacote tem um comando que você não tem (-F).
  • Conferir a integridade dos arquivos (-Qk, -Qkk).
  • Grupos, motivo da instalação (-D), pactree e expac.
  • --needed, --overwrite e as opções do /etc/pacman.conf.

Filtros de consulta: o que tem instalado?

Lembre-se: o pacman anota em cada pacote por que ele foi instalado. "Explicitamente" é o que você pediu; "como dependência" é o que veio junto. Os filtros de -Q usam essa anotação:

-Qe
explicit: só os instalados explicitamente.
-Qd
deps: só os instalados como dependência.
-Qt
unrequired: só os que nenhum outro pacote exige (nem como dependência opcional; -Qtt ignora as opcionais).
-Qm
foreign ("estrangeiros"): os que não existem em nenhum repositório ligado, quase sempre do AUR.
-Qn
native: o contrário, os que vêm dos repositórios.
$ pacman -Q | wc -l
408                         « todos
$ pacman -Qe | wc -l
45                          « os que alguém pediu
$ pacman -Qd | wc -l
363                         « os que vieram como dependência (45 + 363 = 408)
$ pacman -Qn | wc -l
404                         « dos repositórios oficiais
$ pacman -Qm
downgrade 12.0.4-1          « os 4 que não estão nos repositórios: vieram do AUR
paru-bin 2.1.0-1
yay-bin 13.0.1-1
yay-bin-debug 13.0.1-1      « símbolos de depuração que o makepkg gerou junto (veja makepkg)

Os filtros se combinam. -Qet (explícitos e que ninguém exige) é a "lista do que eu escolhi": o retrato do seu sistema, sem os pacotes que outros já puxam. Atenção a um detalhe: um t esconde também o que é dependência opcional de alguém. Por isso o linux e o base-devel (opcional do pacman) não aparecem abaixo; com -Qett (dois t, ignorando as opcionais), a lista da VM sobe de 24 para 35:

Guardar a lista para reinstalar em outra máquina

A opção -q (quiet) tira as versões e deixa só os nomes, perfeito para scripts: pacman -Qqen > pacotes.txt guarda os explícitos dos repositórios. Numa instalação nova, sudo pacman -S --needed - < pacotes.txt instala todos (o - diz "leia os nomes da entrada").

$ pacman -Qmq
downgrade
paru-bin
yay-bin
yay-bin-debug

De quem é este arquivo? -Qo

-Qo
query owns: qual pacote instalado é dono do arquivo.
/usr/bin/ls
Um caminho. Também aceita só o nome de um comando que esteja no PATH.
$ pacman -Qo /usr/bin/ls
/usr/bin/ls pertence a coreutils 9.12-2
$ pacman -Qo ls
/usr/bin/ls pertence a coreutils 9.12-2           « achou o comando no PATH
$ pacman -Qo /etc/pacman.conf
/etc/pacman.conf pertence a pacman 7.1.0.r9.g54d9411-3
$ pacman -Qo /home/ana/frutas.txt
erro: Nenhum pacote possui /home/ana/frutas.txt   « criado por você, não por um pacote
$ echo $?
1

Use para saber de onde veio um programa, quem é dono de uma configuração em /etc, ou se um arquivo esquecido em /usr é "órfão" (não pertence a ninguém).

Qual pacote tem o comando que me falta? -F

O -Qo só conhece o que está instalado. Para procurar arquivos em todos os pacotes dos repositórios, use -F (files). Ele precisa de um catálogo de arquivos à parte, que você baixa uma vez (e de vez em quando) com -Fy. Saída real na VM:

$ sudo pacman -Fy
:: Sincronizando a base de dados de pacotes...
 core sendo baixado...
 extra sendo baixado...

Esse catálogo é bem maior que o normal: na VM, extra.files tem 50 MiB, contra 8,5 MiB do extra.db. Agora, o caso clássico: você digita hostname num Arch novo e recebe bash: hostname: comando não encontrado. Quem tem esse arquivo?

$ pacman -F hostname
core/gettext 1.0-2 [instalado]
    usr/lib/gettext/hostname                       « um arquivo com esse nome, mas não é o comando
core/inetutils 2.8-1 [instalado]
    usr/bin/hostname                               « este é o comando (está em usr/bin)
extra/archiso 91-1
    usr/share/archiso/configs/releng/airootfs/etc/hostname
extra/gstreamer-docs 1.28.8-1
    usr/share/doc/gstreamer/html/assets/js/search/hostname
extra/reproducible-faketools-hostname 0.5.5-3
    usr/lib/reproducible-faketools/bin/hostname
extra/smolvm 1.28.1-1
    usr/lib/smolvm/agent-rootfs/bin/hostname
    usr/lib/smolvm/agent-rootfs/etc/hostname

Com o nome sozinho, aparecem todos os arquivos chamados hostname. Os comandos ficam em usr/bin: a resposta é o pacote inetutils (na VM ele já está instalado, por isso o [instalado]). Para ir direto, passe o caminho completo, ou use -Fx com uma expressão regular:

$ pacman -F /usr/bin/hostname
usr/bin/hostname pertence a core/inetutils 2.8-1
$ pacman -Fx 'bin/(neo|fast)fetch$'
usr/bin/fastfetch pertence a extra/fastfetch 2.70.0-1     « o neofetch não existe mais nos repositórios
$ pacman -F xyzabc
$ echo $?
1                                                         « nada encontrado: sem mensagem, código 1

Conferir a integridade: -Qk e -Qkk

-Qk
check: confere se todos os arquivos do pacote existem.
-Qkk
Confere também as propriedades de cada arquivo: tamanho, data, permissões e a soma SHA-256 registrada no mtree.
$ pacman -Qk bash
bash: total de 269 arquivos,  0 arquivo em falta
$ pacman -Qkk bash
bash: total de 270 arquivos, 0 arquivo alterado
$ echo $?
0

Para o sistema inteiro, pacman -Qk sem nome confere todos os pacotes. Mostrar só os que têm problema: pacman -Qk 2>/dev/null | grep -v ' 0 arquivo em falta' (na VM, nada apareceu). O -Qkk no sistema inteiro lê todos os arquivos e demora; prefira por pacote.

Rode -Qkk como root

Como usuário comum, o pacman não consegue ler alguns arquivos protegidos e acusa um "alterado" falso:

$ pacman -Qkk sudo
atenção: sudo: /etc/sudoers (falha ao calcular a soma de verificação SHA256)    « sem permissão para ler
arquivo backup: sudo: /etc/sudoers (Última modificação incorreta)
arquivo backup: sudo: /etc/sudoers (Tamanho incorreto)
sudo: total de 244 arquivos, 1 arquivo alterado
$ echo $?
1
$ sudo pacman -Qkk sudo
arquivo backup: sudo: /etc/sudoers (Última modificação incorreta)
arquivo backup: sudo: /etc/sudoers (Tamanho incorreto)
arquivo backup: sudo: /etc/sudoers (soma de verificação SHA256 incorreta)
sudo: total de 244 arquivos, 0 arquivo alterado                         « como root: nada de errado

E as linhas arquivo backup? São arquivos de configuração que o pacote marcou como "do usuário" (a lista backup do pacote). É esperado que você os edite: o /etc/sudoers foi alterado com visudo na instalação. Por isso eles não contam no total de alterados. Veja quais arquivos de um pacote são desse tipo com pacman -Qii (dois i):

$ pacman -Qii sudo | tail -6
Validado por         : Assinatura
Arquivos backup      : /etc/pam.d/sudo [unmodified]
                       /etc/sudo.conf [unmodified]
                       /etc/sudo_logsrvd.conf [unmodified]
                       /etc/sudoers [modified]                « você mexeu
Extended Data   : pkgtype=pkg

Se um arquivo que não é de configuração aparecer alterado (um /usr/bin/…), algo está errado: disco com defeito, um make install por cima, ou coisa pior. A solução costuma ser reinstalar o pacote (sudo pacman -S pacote).

Grupos de pacotes

Um grupo é um apelido para vários pacotes, útil para instalar um ambiente inteiro de uma vez. -Sg lista grupos do repositório; -Qg, os grupos de pacotes instalados:

$ pacman -Sg | wc -l
107                              « 107 grupos nos repositórios
$ pacman -Sg xfce4
xfce4 exo
xfce4 garcon
xfce4 thunar
…                                « (14 membros)
xfce4 xfwm4
$ pacman -Qg
vulkan-devel spirv-tools         « o único pacote da VM que pertence a um grupo

Ao instalar um grupo, o pacman deixa escolher os membros (Enter = todos):

$ sudo pacman -S xfce4
:: Há 14 membros no grupo xfce4:
:: Repositório extra
   1) exo  2) garcon  3) thunar  4) thunar-volman  5) tumbler
   6) xfce4-appfinder  7) xfce4-panel  8) xfce4-power-manager  9) xfce4-session
   10) xfce4-settings  11) xfce4-terminal  12) xfconf  13) xfdesktop  14) xfwm4

Digite uma seleção (padrão=todos):          « ex.: "1-5 11" ou "^4" (todos menos o 4)
resolvendo dependências...

base-devel não é mais grupo

Guias antigos mandam fazer pacman -S base-devel "escolhendo o grupo". Desde 2023, base-devel é um metapacote: um pacote vazio que só depende dos outros. Por isso:

$ pacman -Sg base-devel
erro: grupo de pacotes "base-devel" não foi encontrado
$ pacman -Si base-devel | grep -E "^(Nome|Grupos|Depende)"
Nome                 : base-devel
Grupos               : Nenhum
Depende de           : archlinux-keyring  autoconf  automake  binutils  bison  debugedit  fakeroot  file  findutils  flex  gawk  gcc  gettext  grep  groff  gzip  libtool  m4  make  pacman  patch  pkgconf  sed  sudo  texinfo  which

Na prática, sudo pacman -S base-devel continua funcionando (e é o que a aula makepkg usa). A diferença: grupo deixa escolher membros; metapacote instala todos e marca cada um como dependência.

Motivo da instalação: -D --asdeps e --asexplicit

Às vezes o "motivo" fica errado: você instalou à mão uma biblioteca que, na verdade, só serve a outro programa. Corrigir faz o -Rs e a busca de órfãos funcionarem direito. Como isso muda o banco de dados, o teste abaixo foi feito numa cópia do banco da VM (--dbpath), sem tocar no sistema:

-D
database: mexer só no banco de dados, sem instalar nem remover.
--asdeps
Marcar como "instalado como dependência".
--asexplicit
Marcar como "instalado explicitamente".
#> pacman -D --asdeps htop
htop: motivo da instalação foi definido como "instalado como dependência"
#> pacman -Qdt
htop 3.5.3-1                     « agora o htop é um órfão: dependência que ninguém usa
#> pacman -D --asexplicit htop
htop: motivo da instalação foi definido como "instalado explicitamente"
#> pacman -Qdt
#> echo $?
1                                « voltou a ser explícito: nenhum órfão

Também dá para escolher o motivo na hora de instalar: sudo pacman -S --asdeps pacote. Um nome errado dá erro: não foi possível definir o motivo da instalação do pacote xyz (não foi possível ler ou escrever o pacote).

A árvore de dependências: pactree

O pactree (do pacote pacman-contrib) desenha as dependências como uma árvore. A árvore completa do htop tem 147 linhas (o pactree -u htop, sem repetições, lista 51 pacotes); limite a profundidade com -d:

$ pactree -d1 htop
htop
├─libcap
├─libcap provides libcap.so=2-64          « o libcap "fornece" a biblioteca que o htop pede
├─libnl
├─ncurses
└─ncurses provides libncursesw.so=6-64

Com -r (reverse), a pergunta inversa: quem depende deste pacote?

$ pactree -r htop
htop                                      « ninguém depende do htop
$ pactree -r ncurses | head -8
ncurses
├─bash
│ ├─arch-install-scripts
│ │ └─devtools
│ ├─audit
│ │ ├─dbus
│ │ │ ├─avahi
│ │ │ │ └─ostree

Útil antes de remover algo: pactree -r mostra o que seria afetado. As palavras provides são do próprio pactree (ele não é traduzido).

Consultas sob medida: expac

O expac (pacote expac) imprime os campos que você escolher, num formato parecido com o printf. Cada %letra é um campo:

CódigoCampoCódigoCampo
%nnome%mtamanho instalado
%vversão%ktamanho do download
%ddescrição%wmotivo (explicit/dependency)
%rrepositório%Nquem depende dele

O uso mais famoso: os 10 maiores pacotes instalados. -H M mostra os tamanhos em MiB; o sort -h entende "MiB":

$ expac -H M '%m\t%n' | sort -h | tail -10
70.34 MiB	perl
73.79 MiB	python
82.66 MiB	podman
103.55 MiB	linux-firmware-nvidia
137.97 MiB	linux-firmware-intel
155.84 MiB	linux-lts
161.60 MiB	linux
164.87 MiB	llvm-libs
220.89 MiB	gcc
273.49 MiB	linux-lts-headers             « o maior: os cabeçalhos do kernel LTS
$ expac '%n %v' htop pacman
htop 3.5.3-1
pacman 7.1.0.r9.g54d9411-3
$ expac -Q '%n: %w' htop jq
htop: explicit
jq: dependency
$ expac -S '%r/%n %v %k' fastfetch
extra/fastfetch 2.70.0-1 680713            « -S = do repositório; %k em bytes sem o -H

Sem -S, o expac consulta os instalados (o mesmo que -Q). Repare que o expac usa ponto como separador decimal (70.34), enquanto o pacman usa vírgula (70,34).

--needed e --overwrite

--needed: não reinstalar

$ sudo pacman -S --needed htop
atenção: htop-3.5.3-1 está atualizado -- ignorando
nada para fazer
$ echo $?
0

Use em listas e scripts (pacman -S --needed git base-devel): instala só o que falta, sem reinstalar o resto.

--overwrite: quando um arquivo "existe no sistema de arquivos"

O pacman se recusa a instalar um arquivo que já existe e não pertence a nenhum pacote. Para reproduzir sem risco, criamos um pacote de teste (a4-ola, que instala /usr/bin/a4-ola) e o instalamos numa raiz falsa em /tmp/a4/raiz2 (opção --root), onde antes colocamos um arquivo com o mesmo nome. A saída é real:

#> pacman -U a4-ola-1.0-1-any.pkg.tar.zst
…
verificando conflitos de arquivos...
erro: falha ao efetuar a transação (arquivos conflitantes)
a4-ola: /tmp/a4/raiz2/usr/bin/a4-ola existe no sistema de arquivos
Ocorreram erros e, portanto, nenhum pacote foi atualizado.
#> echo $?
1

Nada foi instalado: o pacman parou antes de mexer em qualquer coisa. A opção --overwrite recebe um caminho (ou um padrão com *) que ele pode sobrescrever. Num sistema normal, seria sudo pacman -U --overwrite /usr/bin/a4-ola a4-ola-1.0-1-any.pkg.tar.zst (ou sudo pacman -S --overwrite /caminho pacote, para um pacote do repositório). Na raiz falsa usamos o padrão '*/a4-ola': a instalação passou e o arquivo antigo foi substituído pelo do pacote.

--overwrite não é botão de "resolver"

Antes de usar, descubra de onde veio o arquivo: pacman -Qo /caminho. Se ele pertence a outro pacote, o problema é outro (conflito entre pacotes). Se não pertence a ninguém, foi instalado à mão (sudo make install, pip como root, um instalador .sh) e você pode estar apagando algo que usa. Use o caminho exato, nunca --overwrite '*'. Quando uma notícia do Arch manda usar --overwrite, ela diz exatamente qual caminho.

Quando não funciona

pacman -F avisa "database file … does not exist" 
$ pacman -F hostname
atenção: database file for 'core' does not exist (use '-Fy' to download)
atenção: database file for 'extra' does not exist (use '-Fy' to download)

O que aconteceu: o catálogo de arquivos nunca foi baixado (esse aviso ainda não tem tradução).

Como resolver: sudo pacman -Fy e repita. Atualize-o de vez em quando, junto com o sistema.

"grupo de pacotes … não foi encontrado" 
$ pacman -Sg base-devel
erro: grupo de pacotes "base-devel" não foi encontrado

O que aconteceu: não existe grupo com esse nome. Às vezes é um metapacote (como o base-devel), às vezes erro de digitação.

Como resolver: pacman -Si nome para ver se é um pacote; pacman -Sg para listar os grupos.

-Qkk diz "1 arquivo alterado" e "falha ao calcular a soma de verificação"

O que aconteceu: você rodou como usuário comum e o pacman não pôde ler um arquivo protegido.

Como resolver: repita com sudo. As linhas arquivo backup são configurações que você editou: normais.

"existe no sistema de arquivos"

O que aconteceu: um arquivo do pacote já está no disco sem pertencer a nenhum pacote (ou pertence a outro).

Como confirmar: pacman -Qo /caminho/do/arquivo.

Como resolver: se é sobra de instalação manual e você não precisa dele, --overwrite /caminho/exato. Se é de outro pacote, leia as notícias e Erros de Atualização.

Resumo

  • -Qe, -Qd, -Qt, -Qm filtram os instalados pelo motivo e pela origem; -q deixa só os nomes.
  • -Qo diz o dono de um arquivo instalado; -F procura em todos os pacotes (depois de -Fy).
  • -Qkk confere a integridade; rode como root; arquivo backup = configuração editada, normal.
  • base-devel é metapacote, não grupo. -D --asdeps corrige o motivo da instalação.
  • pactree -r mostra quem depende; expac monta consultas sob medida.
  • --overwrite só com caminho exato e depois de pacman -Qo.
