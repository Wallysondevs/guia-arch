Arch Recuperar o Boot

Entre apertar o botão e ver a tela de login, o computador passa por uma corrida de revezamento: firmware, GRUB, kernel, initramfs, systemd. Quando o boot falha, a tela onde ele parou diz qual corredor derrubou o bastão. Esta aula ensina a reconhecer cada tela e a consertar a camada certa, sem reinstalar nada.

Você vai aprender
  • As camadas do boot e como saber em qual delas o problema está.
  • Recriar a entrada UEFI com grub-install (e o --removable) e ler o efibootmgr.
  • Sair do grub rescue> e dar boot "na mão" pelo GRUB.
  • Kernel panic, Failed to mount /sysroot, initramfs quebrado e o kernel LTS de reserva.
  • O emergency mode por fstab errado e o fsck.fat na partição EFI.

As camadas do boot

#CamadaO que fazSe ela falha, você vê…
1Firmware UEFILê as entradas de boot (NVRAM) e carrega o grubx64.efi da partição EFIA tela de configuração do firmware, "No bootable device", ou outro sistema (Windows) ligando direto
2GRUBLê o /boot/grub/grub.cfg, mostra o menu, carrega kernel e initramfsgrub rescue>, um prompt grub> sem menu, error: file not found
3Kernel + initramfsO initramfs carrega drivers, abre LUKS/LVM e monta a raizKernel panic, Failed to mount /sysroot, Timed out waiting for device, um shell de emergência do initramfs
4systemdMonta o resto do fstab, sobe serviços, mostra o loginYou are in emergency mode, serviços em vermelho ([FAILED])

As camadas 1 e 2 quase sempre se consertam com o resgate com chroot; a 3, com o kernel LTS ou o chroot; a 4, de dentro do próprio emergency mode. Nesta aula, o que não dá para provocar na máquina do guia sem desligá-la é marcado como ilustrativo; o resto tem saída real.

Camada 1: o firmware não acha o GRUB

O firmware UEFI guarda na NVRAM da placa-mãe uma lista de entradas, cada uma apontando para um arquivo .efi numa partição EFI. O efibootmgr mostra essa lista (na máquina do guia, hoje):

Boot0003* GRUB	HD(1,GPT,42528876-2401-45ed-aa76-555fea61a03e,0x800,0x200000)/\EFI\GRUB\grubx64.efi

O arquivo, com barras do Windows: é o /boot/EFI/GRUB/grubx64.efi.

A entrada some quando: uma atualização do firmware (BIOS) zera a NVRAM, o Windows "toma" o boot, a bateria da placa acaba, ou a partição EFI foi recriada. O arquivo ainda está lá; só o ponteiro sumiu.

Conserto: grub-install de novo

Do resgate com chroot, com a EFI montada em /mnt/boot, repita o grub-install da instalação: ele copia o grubx64.efi e recria a entrada. Saída real da instalação:

#> arch-chroot /mnt grub-install --target=x86_64-efi --efi-directory=/boot --bootloader-id=GRUB
Installing for x86_64-efi platform.
Installation finished. No error reported.

O caminho de reserva: --removable

Alguns firmwares "esquecem" entradas novas ou só procuram o caminho padrão \EFI\BOOT\BOOTX64.EFI (o mesmo que os pendrives usam). O --removable instala o GRUB nesse caminho, que funciona mesmo sem entrada na NVRAM. Para mostrar sem tocar a EFI da máquina, instalamos numa partição FAT de teste (um arquivo-imagem), com --no-nvram para não criar entrada:

#> mkfs.fat -F 32 -n EFITESTE /dev/loop0
mkfs.fat 4.2 (2021-01-31)
#> mount --mkdir /dev/loop0 /tmp/a8/efi
#> grub-install --target=x86_64-efi --efi-directory=/tmp/a8/efi --boot-directory=/tmp/a8/efi --removable --no-nvram
Instalando para a plataforma x86_64-efi.
Instalação terminada. Sem erros reportados.
#> echo $?
0
#> ls -R /tmp/a8/efi/EFI
/tmp/a8/efi/EFI:
BOOT

/tmp/a8/efi/EFI/BOOT:
BOOTX64.EFI                    « o nome que todo firmware UEFI procura
#> ls /tmp/a8/efi/grub
fonts
grubenv
locale
themes
x86_64-efi

No resgate de verdade: arch-chroot /mnt grub-install --target=x86_64-efi --efi-directory=/boot --removable. Pode ter as duas instalações ao mesmo tempo (a normal e a removível). Depois de qualquer grub-install, rode também grub-mkconfig -o /boot/grub/grub.cfg.

Mexer na lista à mão (ilustrativo)

ComandoO que faz
efibootmgr -o 0003,0000Muda a ordem de boot (BootOrder)
efibootmgr -n 0002Só no próximo boot, usa a 0002 (BootNext)

Modo do pendrive

O efibootmgr e o grub-install UEFI só funcionam se o pendrive deu boot em UEFI. Confira no live: cat /sys/firmware/efi/fw_platform_size deve responder 64. Se o arquivo não existe, o pendrive ligou no modo antigo (BIOS/CSM): reinicie e escolha a opção "UEFI: …" no menu do firmware.

Camada 2: o GRUB não acha os arquivos

grub rescue> (ilustrativo)

O grubx64.efi carregou, mas não achou a pasta /boot/grub (com os módulos e o grub.cfg): a partição mudou de número, foi formatada ou o UUID mudou. Ele cai num modo mínimo, que só entende ls, set, insmod e pouco mais. Uma sessão típica:

error: no such partition.
Entering rescue mode...
grub rescue> ls
(hd0) (hd0,gpt3) (hd0,gpt2) (hd0,gpt1)
grub rescue> ls (hd0,gpt1)/
EFI/ grub/ initramfs-linux.img vmlinuz-linux …
grub rescue> set prefix=(hd0,gpt1)/grub
grub rescue> set root=(hd0,gpt1)
grub rescue> insmod normal
grub rescue> normal
ls
Lista discos e partições como o GRUB os vê: (hd0,gpt1) = disco 0, partição GPT 1.
ls (hd0,gpt1)/
Olha dentro de uma partição: procure a que tem grub/ (na máquina do guia, a EFI, porque o /boot é a EFI).
set prefix=…
Onde está a pasta grub com os módulos.
set root=…
A partição padrão para os caminhos seguintes.
insmod normal
Carrega o módulo do modo normal (menu, comandos completos).
normal
Entra no modo normal: o menu aparece.

Isso é só para ligar uma vez. Já dentro do Arch (ou do chroot), conserte de vez com grub-install … e grub-mkconfig -o /boot/grub/grub.cfg.

grub> sem menu: boot à mão (ilustrativo)

Se aparece só grub> (modo normal, mas sem grub.cfg), dá para digitar o que o menu faria. Os valores abaixo são os reais da entrada do LTS no grub.cfg da máquina do guia:

#> sed -n '147,163p' /boot/grub/grub.cfg
	menuentry 'Arch Linux, with Linux linux-lts' --class arch --class gnu-linux --class gnu --class os $menuentry_id_option 'gnulinux-linux-lts-advanced-75d167c8-1dad-4d0a-a0ae-b063058a18e9' {
		load_video
		set gfxpayload=keep
		insmod gzio
		insmod part_gpt
		insmod fat
		set root='hd0,gpt1'
		if [ x$feature_platform_search_hint = xy ]; then
		  search --no-floppy --fs-uuid --set=root --hint-bios=hd0,gpt1 --hint-efi=hd0,gpt1 --hint-baremetal=ahci0,gpt1  C509-6CB1
		else
		  search --no-floppy --fs-uuid --set=root C509-6CB1
		fi
		echo	'Carregando o Linux linux-lts...'
		linux	/vmlinuz-linux-lts root=UUID=75d167c8-1dad-4d0a-a0ae-b063058a18e9 rw  loglevel=3 quiet
		echo	'Carregando o ramdisk inicial...'
		initrd	/intel-ucode.img /initramfs-linux-lts.img
	}

No grub>, as três linhas essenciais seriam set root=(hd0,gpt1), linux /vmlinuz-linux root=UUID=75d167c8-1dad-4d0a-a0ae-b063058a18e9 rw, initrd /intel-ucode.img /initramfs-linux.img e, por fim, boot. A tecla Tab completa nomes de arquivos ali. Repare: root= do kernel é a raiz (sda3, ext4), enquanto o root do GRUB é onde estão kernel e initramfs (sda1, a EFI).

Ligado no LTS, uname -r mostra 6.18.57-1-lts (como no registro real da instalação), e você conserta o kernel principal de dentro do sistema, sem pendrive: pacman -S linux e mkinitcpio -P. Para que o padrão do menu seja o kernel principal e não o LTS, a máquina do guia usa GRUB_TOP_LEVEL="/boot/vmlinuz-linux" no /etc/default/grub (detalhes em Kernels). Ter um segundo kernel instalado é o seguro mais barato do Arch.

O UUID que o kernel recebe tem que ser o da raiz:

├─sda1 vfat   FAT32       C509-6CB1                             929,2M     9% /boot

Initramfs quebrado

O initramfs fica incompleto quando o mkinitcpio falha no meio (falta de espaço no /boot, hook com nome errado, atualização interrompida). Um mkinitcpio com problema avisa, com código de saída diferente de 0. Exemplo real, com um hook de nome errado numa configuração de teste:

#> mkinitcpio -c /tmp/a8/mkinitcpio-errado.conf -g /tmp/a8/initramfs-errado.img
…
==> ERROR: Hook 'lvm' cannot be found
  -> Running build hook: [filesystems]
  -> Running build hook: [fsck]
==> Generating module dependencies
==> Creating zstd-compressed initcpio image: '/tmp/a8/initramfs-errado.img'
==> WARNING: errors were encountered during the build. The image may not be complete.
#> echo $?
1

Conserto: corrigir o /etc/mkinitcpio.conf e rodar mkinitcpio -P até terminar com Initcpio image generation successful para todos os kernels (do LTS, se ele liga; senão, do chroot). Mais em mkinitcpio e initramfs.

Camada 4: emergency mode por fstab errado

A raiz montou, mas uma linha do /etc/fstab aponta para algo que não existe (um HD externo removido, um UUID digitado errado). O systemd espera 90 segundos pelo dispositivo e desiste, caindo no modo de emergência. A tela (ilustrativa; o texto do systemd é em inglês) termina assim:

[ TIME ] Timed out waiting for device /dev/disk/by-uuid/1234abcd-0000-4000-8000-000000000000.
[DEPEND] Dependency failed for /mnt/dados.
[DEPEND] Dependency failed for Local File Systems.
You are in emergency mode. After logging in, type "journalctl -xb" to view
system logs, "systemctl reboot" to reboot, or "exit" to continue bootup.
Give root password for maintenance
(or press Control-D to continue):

Dá para reproduzir o diagnóstico com segurança numa cópia do fstab, com uma linha de propósito errada:

#> cp /etc/fstab /tmp/a8/fstab
#> echo 'UUID=1234abcd-0000-4000-8000-000000000000  /tmp/a8/dados  ext4  defaults  0 2' >> /tmp/a8/fstab
#> findmnt --verify --tab-file /tmp/a8/fstab

0 erro de análise, 2 erros, 0 aviso
/tmp/a8/dados
   [E] alvo não alcançável na inicialização: Arquivo ou diretório inexistente
   [E] fonte não alcançável na inicialização: UUID=1234abcd-0000-4000-8000-000000000000   « o culpado
#> echo $?
1
#> mount --mkdir --fstab /tmp/a8/fstab /tmp/a8/dados
mount: /tmp/a8/dados: não foi possível localizar UUID=1234abcd-0000-4000-8000-000000000000.
#> echo $?
1

findmnt --verify confere cada linha do fstab (por padrão, o /etc/fstab; aqui, a cópia com --tab-file). Rode-o sempre depois de editar o fstab, antes de reiniciar.

Consertar de dentro do emergency mode

  1. Digite a senha de root. (Sem senha de root definida, o systemd não deixa entrar: use o resgate.)
  2. Veja o motivo: journalctl -xb -p 3 mostra os erros deste boot (veja Logs).
  3. Libere a escrita, se precisar: se a raiz estiver só leitura, mount -o remount,rw /.
  4. Corrija o fstab: nano /etc/fstab (ou vim): conserte o UUID, comente a linha com #, ou acrescente nofail.
  5. Confira e continue: findmnt --verify, systemctl daemon-reload e exit (continua o boot) ou systemctl reboot.

Para discos que nem sempre estão ligados, use nofail (o boot não espera por ele) e, de preferência, um tempo curto:

#> tail -1 /tmp/a8/fstab
UUID=1234abcd-0000-4000-8000-000000000000  /tmp/a8/dados  ext4  defaults,nofail,x-systemd.device-timeout=5s  0 2

O findmnt --verify continua apontando o UUID inexistente (ele confere, não perdoa), mas o boot não para mais por causa dele. Mais opções em mount e fstab.

A partição EFI "suja": fsck.fat

Depois de um desligamento forçado, a partição EFI (FAT32) fica marcada como "não desmontada corretamente". O kernel avisa ao montá-la. Reproduzimos isso copiando uma partição FAT de teste enquanto ela estava montada (a cópia fica igual a um disco de um computador que desligou da tomada) e montando a cópia:

#> sync
#> cp --sparse=always /var/tmp/a8/efi.img /var/tmp/a8/efi-desligada.img   « cópia "com o computador ligado"
#> umount /tmp/a8/efi
#> losetup -d /dev/loop0
#> losetup -f --show /var/tmp/a8/efi-desligada.img
/dev/loop0
#> mount /dev/loop0 /tmp/a8/efi
#> journalctl -k -n 2 --no-pager -o short
out 16 13:39:27 notebook kernel: loop0: detected capacity change from 0 to 614400
out 16 13:39:34 notebook kernel: FAT-fs (loop0): Volume was not properly unmounted. Some data may be corrupt. Please run fsck.

#> fsck.fat -n /dev/loop0

  65:01/00

A "diferença entre o setor de boot e a cópia" (65:01/00) é o próprio indicador de sujeira: o byte 65 vale 1 no original e 0 na cópia de segurança. Depois do -a, ela some junto. Na máquina do guia, isso aconteceu de verdade na EFI depois de um desligamento forçado; o conserto foi:

#> umount /boot && fsck.fat -a -w /dev/sda1; mount /boot; echo montado
fsck.fat 4.2 (2021-01-31)
There are differences between boot sector and its backup.
This is mostly harmless. Differences: (offset:original/backup)
  65:01/00
  Not automatically fixing this.
Dirty bit is set. Fs was not properly unmounted and some data may be corrupt.

/dev/sda1: 410 files, 23743/261627 clusters
montado

-w grava as mudanças na hora. O umount /boot antes é obrigatório: nunca rode fsck num sistema de arquivos montado. É um problema leve (os arquivos estavam intactos), mas vale consertar: um FAT sujo pode, com o tempo, perder arquivos como o initramfs.

Quando não funciona

"EFI variables are not supported on this system"

O que aconteceu (ilustrativo): o grub-install ou o efibootmgr não acharam as variáveis UEFI. O pendrive deu boot em modo BIOS, ou você usou chroot puro (sem o efivarfs que o arch-chroot monta).

Como resolver: confira /sys/firmware/efi/fw_platform_size no live, reinicie o pendrive em UEFI, use arch-chroot. Se ainda assim não der, grub-install --removable não depende da NVRAM.

O GRUB liga, mas o menu não tem o Arch (ou tem kernel velho)

O que aconteceu: o grub.cfg não foi regerado. O pacman não roda grub-mkconfig sozinho.

Como resolver: grub-mkconfig -o /boot/grub/grub.cfg e confira as linhas Imagem Linux encontrada (veja Bootloader).

O fsck.fat diz "comando não encontrado"

O que aconteceu: o fsck.fat vem no pacote dosfstools, que não faz parte do base. No pendrive do Arch ele já existe.

Como resolver: pacman -S dosfstools, ou rode o conserto pelo live.

Resumo

  • Identifique a camada pela tela: firmware, GRUB, kernel/initramfs ou systemd.
  • Entrada UEFI sumida: grub-install de novo (e --removable como reserva); confira com efibootmgr.
  • grub rescue>: set prefix, set root, insmod normal, normal; depois conserte de vez.
  • Kernel/initramfs: kernel LTS primeiro; depois pacman -S linux e mkinitcpio -P; confira o root=UUID.
  • Emergency mode: senha de root, journalctl -xb, corrigir o fstab, findmnt --verify. EFI suja: fsck.fat -a desmontada.
