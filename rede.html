NetworkManager e iwd

No Arch, a rede não "simplesmente funciona" sozinha: alguém precisa pedir um endereço ao roteador, escolher o Wi-Fi e configurar o DNS. Esse "alguém" é um gerenciador de rede, e você escolhe qual na instalação. O mais comum, e o da VM do guia, é o NetworkManager, controlado pelo comando nmcli. Nesta aula você aprende a usá-lo, a conferir a rede com ip, ping e ss, e conhece as alternativas.

Você vai aprender
  • Ver o estado da rede com nmcli general, nmcli device e nmcli connection.
  • Conectar a um Wi-Fi com nmcli e com o nmtui.
  • Configurar IP fixo e DNS (e de onde vem o /etc/resolv.conf).
  • Diagnosticar com ip a, ip route, ping e ss -tulpn.
  • Quando usar iwd ou systemd-networkd em vez do NetworkManager.

Quem cuida da rede no Arch

Conectar à rede envolve várias tarefas: ligar a placa, se associar ao Wi-Fi (com a senha), pedir um endereço IP por DHCP (Dynamic Host Configuration Protocol: o roteador "empresta" um endereço), definir a rota para a internet e os servidores de DNS (que traduzem archlinux.org em números). O Arch não vem com nada disso ligado; na instalação você instala e habilita um gerenciador. A VM do guia recebeu o NetworkManager, como mostra o log da instalação:

#> arch-chroot /mnt systemctl enable NetworkManager sshd
$ pacman -Q networkmanager wpa_supplicant
networkmanager 1.58.1-2
wpa_supplicant 2:2.12-1
$ systemctl is-active NetworkManager systemd-networkd systemd-resolved
active                 « o NetworkManager
inactive               « o systemd-networkd (vem no pacote systemd, desligado)
inactive               « o systemd-resolved (idem)
Um gerenciador por vez

Nunca deixe dois gerenciadores ligados ao mesmo tempo (NetworkManager + systemd-networkd, ou NetworkManager + dhcpcd): eles brigam pela placa e a conexão cai e volta. Se trocar de um para outro, faça disable --now no antigo antes de ligar o novo.

nmcli: o estado da rede

nmcli = NetworkManager command-line interface. Ele fala português quando o sistema está em português.

nmcli general

$ nmcli general
STATE      CONNECTIVITY  WIFI-HW   WIFI        WWAN-HW   WWAN        METERED
conectado  completa      faltando  habilitado  faltando  habilitado  não (adivinhado)

STATEconectadoHá uma conexão ativa

nmcli device: as placas

$ nmcli device
DEVICE  TYPE      STATE                     CONNECTION
enp0s3  ethernet  conectado                 Conexão cabeada 1
lo      loopback  conectado (externamente)  lo

Um dispositivo é uma placa de rede. enp0s3 é o nome da placa com fio da VM: en = ethernet, p0s3 = a posição dela no barramento PCI (barramento 0, slot 3). Placas Wi-Fi costumam se chamar wlan0 ou wlp2s0. O lo (loopback) é a rede interna do próprio computador (127.0.0.1).

nmcli connection: os perfis

Uma conexão (perfil) é um conjunto de configurações: "esta rede Wi-Fi, com esta senha, IP automático". Um dispositivo usa um perfil por vez. Você pode ter vários perfis (casa, trabalho) para a mesma placa.

$ nmcli connection show
NAME               UUID                                  TYPE      DEVICE
Conexão cabeada 1  5c85cc50-5b40-34c6-9635-e7b2db0c9e02  ethernet  enp0s3
lo                 baf8cb5c-c5ea-4179-aecc-b7ff5ef1e7c2  loopback  lo

O perfil "Conexão cabeada 1" foi criado sozinho pelo NetworkManager quando viu o cabo. Os detalhes (com -f você escolhe os campos; sem ele, são mais de 100 linhas):

$ nmcli -f connection.id,connection.type,connection.interface-name,connection.autoconnect,ipv4.method,ipv4.addresses,ipv4.gateway,ipv4.dns,ipv6.method connection show 'Conexão cabeada 1'
connection.id:                          Conexão cabeada 1
connection.type:                        802-3-ethernet        « 802.3 = o padrão do cabo de rede
connection.interface-name:              enp0s3
connection.autoconnect:                 sim                   « conecta sozinho no boot
ipv4.method:                            auto                  « auto = DHCP
ipv4.addresses:                         --                    « nenhum endereço fixo
ipv4.gateway:                           --
ipv4.dns:                               --
ipv6.method:                            auto

E o que o DHCP entregou de fato, visto pelo dispositivo:

$ nmcli -f GENERAL.DEVICE,GENERAL.TYPE,GENERAL.HWADDR,GENERAL.STATE,IP4.ADDRESS,IP4.GATEWAY,IP4.DNS,IP6.ADDRESS device show enp0s3
GENERAL.DEVICE:                         enp0s3
GENERAL.TYPE:                           ethernet
GENERAL.HWADDR:                         08:00:27:74:B2:03         « endereço físico (MAC) da placa
GENERAL.STATE:                          100 (conectado)
IP4.ADDRESS[1]:                         10.0.2.15/24              « o IP da máquina
IP4.GATEWAY:                            10.0.2.2                  « o "roteador"
IP4.DNS[1]:                             10.0.2.3                  « o servidor de DNS
IP6.ADDRESS[1]:                         fd17:625c:f037:2:3074:376a:4fe9:621c/64
IP6.ADDRESS[2]:                         fe80::9c83:cf89:6133:11ca/64

Os endereços 10.0.2.x são da rede virtual do VirtualBox; no seu computador, provavelmente serão 192.168.0.x ou 192.168.1.x.

Onde os perfis ficam

Perfis que você cria ou modifica são gravados em /etc/NetworkManager/system-connections/ (só o root lê: guardam senhas de Wi-Fi). O perfil automático do cabo, enquanto ninguém mexe nele, existe só na memória, em /run:

$ sudo nmcli -f NAME,FILENAME connection show
NAME               FILENAME
Conexão cabeada 1  /run/NetworkManager/system-connections/Conexão cabeada 1.nmconnection
lo                 /run/NetworkManager/system-connections/lo.nmconnection
$ sudo ls -l /etc/NetworkManager/system-connections/
total 0

Wi-Fi com nmcli

A VM do guia não tem placa Wi-Fi, então a lista de redes volta vazia (e com código 0, sem erro):

$ nmcli radio
WIFI-HW   WIFI        WWAN-HW   WWAN
faltando  habilitado  faltando  habilitado
$ nmcli device wifi list
$ echo $?
0

Num notebook, os comandos são estes. Ilustrativo (sem Wi-Fi na VM, as saídas não puderam ser conferidas; a rede "CasaDaAna" é inventada):

$ nmcli device wifi list                          « redes visíveis: SSID, sinal, segurança
$ nmcli device wifi rescan                        « procura de novo
$ nmcli device wifi connect CasaDaAna --ask       « pergunta a senha sem deixá-la no histórico
$ nmcli device wifi connect CasaDaAna password 'minha senha'
$ nmcli connection show                           « o perfil "CasaDaAna" foi criado e fica salvo
$ nmcli connection down CasaDaAna                 « desconectar
$ nmcli connection up CasaDaAna                   « reconectar
$ nmcli connection delete CasaDaAna               « esquecer a rede
$ nmcli radio wifi off                            « desligar o Wi-Fi (modo avião)
nmcli device wifi connect
Procura a rede, cria um perfil com o nome dela e conecta.
CasaDaAna
O SSID (nome da rede). Com espaços, entre aspas: 'Casa da Ana'.
password '…'
A senha. Ela fica no histórico do Bash; o --ask evita isso.

Na primeira conexão, por ser uma mudança no sistema, o polkit pode pedir a senha de administrador (usuários do wheel numa sessão local costumam ser liberados). Depois, o perfil reconecta sozinho sempre que a rede estiver ao alcance.

nmtui: menus no terminal

Se você prefere menus, o nmtui (text user interface, instalado junto com o NetworkManager) abre uma tela azul com três opções: Editar uma conexão, Ativar uma conexão (lista as redes Wi-Fi; Enter conecta e pede a senha) e Definir nome de máquina do sistema. Use as setas, Tab e Enter; Esc volta. É o jeito mais fácil de conectar ao Wi-Fi logo depois da instalação, num TTY sem interface gráfica. (Descrição ilustrativa; na VM o nmtui está em /usr/bin/nmtui, mas a tela não foi capturada.)

Com um desktop instalado, o ícone de rede do GNOME ou do KDE conversa com o mesmo NetworkManager: perfis criados no nmcli aparecem lá, e vice-versa.

IP fixo

Um servidor em casa (veja Servidor Caseiro) costuma precisar de um endereço que não muda. Com o NetworkManager, você muda o perfil: método manual, o endereço, o gateway e o DNS.

Ilustrativo: não foi aplicado na VM

Mudar o IP da VM derrubaria o SSH de todos os autores. Os comandos abaixo são os corretos, mas a sessão não foi rodada. Faça isso no seu computador com acesso físico (ou um segundo caminho de acesso), nunca por SSH na única conexão.

$ sudo nmcli connection modify 'Conexão cabeada 1' \
>     ipv4.method manual \
>     ipv4.addresses 192.168.0.50/24 \
>     ipv4.gateway 192.168.0.1 \
>     ipv4.dns '1.1.1.1 9.9.9.9'
$ sudo nmcli connection up 'Conexão cabeada 1'      « aplica (reconecta)
connection modify 'Conexão cabeada 1'
Muda o perfil (depois disso ele passa a ser gravado em /etc/NetworkManager/system-connections/).
ipv4.method manual
Sem DHCP: você informa tudo. auto volta ao DHCP.
ipv4.addresses 192.168.0.50/24
O IP e o tamanho da rede (/24 = os 3 primeiros números identificam a rede, a máscara 255.255.255.0). Escolha um endereço fora da faixa que o roteador distribui.
ipv4.gateway
O roteador.
ipv4.dns
Os servidores de DNS, separados por espaço.

Para voltar ao automático:

$ sudo nmcli connection modify 'Conexão cabeada 1' ipv4.method auto ipv4.addresses '' ipv4.gateway '' ipv4.dns ''
$ sudo nmcli connection up 'Conexão cabeada 1'
Alternativa: reserva no roteador

Muitas vezes é mais simples deixar o Arch em DHCP e configurar no roteador uma "reserva de DHCP" para o MAC da placa (o GENERAL.HWADDR): o roteador sempre entrega o mesmo IP, e nada muda no Linux.

DNS: quem traduz os nomes

Os programas descobrem qual servidor de DNS usar lendo o /etc/resolv.conf. Na VM, quem escreve esse arquivo é o próprio NetworkManager, com o que recebeu do DHCP:

$ ls -l /etc/resolv.conf
-rw-r--r-- 1 root root 92 16 out 13:06 /etc/resolv.conf     « arquivo comum, não um link
$ cat /etc/resolv.conf
# Generated by NetworkManager
search lan
nameserver 10.0.2.3
nameserver fd17:625c:f037:2::3
$ getent hosts archlinux.org
2604:cac0:a104:d::3 archlinux.org             « a tradução funcionando

Não edite esse arquivo à mão: o NetworkManager o reescreve a cada conexão. Para escolher o DNS, use ipv4.dns no perfil (como no IP fixo) e, para ignorar o DNS do roteador, ipv4.ignore-auto-dns yes.

E o resolvectl?

Em muitos tutoriais aparece o resolvectl, do systemd-resolved (um serviço de DNS com cache). No Arch ele vem no pacote systemd, mas desligado, e por isso o comando falha:

$ resolvectl status
Failed to connect to service /run/systemd/resolve/io.systemd.Resolve: Arquivo ou diretório inexistente
$ echo $?
1

Para usá-lo com o NetworkManager (ilustrativo; não foi feito na VM): sudo systemctl enable --now systemd-resolved e trocar o arquivo por um link, sudo ln -sf ../run/systemd/resolve/stub-resolv.conf /etc/resolv.conf. O NetworkManager percebe o link e passa a entregar o DNS ao resolved. Vantagens: cache, DNS por conexão (útil com VPN), DNS-over-TLS. Para uso doméstico, o padrão (sem resolved) funciona bem.

O nome da máquina

$ cat /etc/hostname /etc/hosts
notebook

O /etc/hosts é uma "agenda" consultada antes do DNS: uma linha 192.168.0.50 servidor faz ping servidor funcionar na sua rede. Mudar o nome da máquina: sudo hostnamectl hostname novo-nome (ou pelo nmtui).

ip route: o caminho

$ ip route
default via 10.0.2.2 dev enp0s3 proto dhcp src 10.0.2.15 metric 100
10.0.2.0/24 dev enp0s3 proto kernel scope link src 10.0.2.15 metric 100
default via 10.0.2.2
A rota padrão: tudo que não é da rede local vai para o roteador 10.0.2.2. Sem essa linha, não há internet.
dev enp0s3 proto dhcp
Pela placa enp0s3; a rota veio do DHCP.
10.0.2.0/24 … scope link
A rede local: endereços 10.0.2.x são alcançados direto, sem roteador.
metric 100
Prioridade (menor ganha), quando há duas rotas (cabo e Wi-Fi juntos).

ss -tulpn: quem está escutando

ss (socket statistics) mostra as portas abertas. É o que você confere antes de mexer no firewall (veja Firewall).

-t / -u
TCP / UDP.
-l
Só quem está listening (esperando conexões).
-p
Mostra o processo (precisa de sudo para os de outros usuários).
-n
Números (porta 22) em vez de nomes (ssh).
$ sudo ss -tulpn
Netid State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
tcp   LISTEN 0      511          0.0.0.0:8080      0.0.0.0:*    users:(("nginx",pid=97069,fd=5),("nginx",pid=97068,fd=5))
tcp   LISTEN 0      511          0.0.0.0:80        0.0.0.0:*    users:(("nginx",pid=97069,fd=6),("nginx",pid=97068,fd=6))
tcp   LISTEN 0      128          0.0.0.0:22        0.0.0.0:*    users:(("sshd",pid=310,fd=6))
tcp   LISTEN 0      128             [::]:22           [::]:*    users:(("sshd",pid=310,fd=7))

Leia assim: o sshd espera conexões na porta 22, em todos os endereços IPv4 (0.0.0.0) e IPv6 ([::]); naquele momento outro autor estava com o nginx ligado, nas portas 80 e 8080. Um endereço 127.0.0.1:porta quer dizer "só aceita conexões da própria máquina". Sem sudo, a coluna Process sai vazia para serviços do root.

Quando não funciona

Depois da instalação, nada de rede

O que aconteceu: o gerenciador não foi instalado ou habilitado no chroot (o pacstrap básico não traz nenhum).

Como confirmar: systemctl is-active NetworkManager → inactive, ou Unit NetworkManager.service not found.

Como resolver: se estiver instalado, sudo systemctl enable --now NetworkManager. Se não estiver, volte ao pendrive, monte e entre no sistema com arch-chroot, instale com pacman -S networkmanager e habilite (veja Resgate com chroot).

"Nome ou serviço desconhecido" 
$ ping -c 1 nao-existe.invalid
ping: nao-existe.invalid: Nome ou serviço desconhecido

O que aconteceu: o nome não foi traduzido: erro de digitação, ou o DNS não está funcionando.

Como confirmar: ping -c 3 1.1.1.1 funciona? Então a internet está ok e o problema é DNS. Veja cat /etc/resolv.conf.

Como resolver: sudo nmcli connection modify NOME ipv4.dns '1.1.1.1' e nmcli connection up NOME.

"Failed to connect to service /run/systemd/resolve/…"

O que aconteceu: você usou resolvectl, mas o systemd-resolved não está ligado (o padrão do Arch).

Como resolver: use cat /etc/resolv.conf e nmcli device show para ver o DNS, ou habilite o resolved (seção DNS).

A conexão cai e volta sozinha

O que aconteceu: quase sempre, dois gerenciadores ligados ao mesmo tempo.

Como confirmar: systemctl is-active NetworkManager systemd-networkd dhcpcd iwd: mais de um active (o iwd ativo é normal só se você o configurou como motor do NetworkManager e ele foi iniciado por ele).

Como resolver: sudo systemctl disable --now nos que sobram. Para ver o que o NetworkManager diz: journalctl -u NetworkManager -b.

O Wi-Fi não aparece

O que aconteceu: a placa está bloqueada (botão de modo avião), sem driver/firmware, ou o rádio está desligado.

Como confirmar: nmcli radio (WIFI-HW deve ser habilitado), rfkill list (bloqueios), ip link (a placa existe?), journalctl -k | grep -i firmware.

Como resolver: nmcli radio wifi on; rfkill unblock wifi; instale o firmware (pacote linux-firmware, que no Arch é dividido em partes: confira se a da sua placa está instalada).

Resumo

  • No Arch você escolhe e habilita o gerenciador de rede; um só por vez.
  • nmcli general, device e connection mostram o estado; nmcli device wifi connect e nmtui conectam.
  • IP fixo e DNS se mudam no perfil (nmcli connection modify), não editando arquivos.
  • O /etc/resolv.conf é escrito pelo NetworkManager; o systemd-resolved vem desligado.
  • Diagnóstico: ip -br a → ip route → ping (gateway, IP, nome) → ss -tulpn.
  • Alternativas: iwd (Wi-Fi leve) e systemd-networkd (servidores).

Na Arch Wiki: NetworkManager (em português) tem todos os comandos do nmcli, o motor iwd e a integração com o resolved; o iwd (em português) e o systemd-networkd têm páginas próprias; o diagnóstico geral e os comandos ip estão em Network configuration (em português); o DNS, em Domain name resolution e systemd-resolved.
