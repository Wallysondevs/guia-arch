Projeto: Btrfs com Snapshots Automáticos

Neste laboratório você monta, do zero, o esquema que transforma o Arch num sistema que "volta no tempo": um Btrfs com o layout de subvolumes da Arch Wiki, o snapper tirando fotos de hora em hora e limpando as velhas, e dois jeitos de desfazer um estrago: arquivo por arquivo e trocando o sistema inteiro por um snapshot. Tudo num disco de mentira (um arquivo-imagem), com saídas reais. No fim, o mapa para fazer o mesmo no seu sistema de verdade.

Você vai praticar
  • mkfs.btrfs, subvolumes @, @home, @snapshots e montagem com subvol= (aula Btrfs).
  • snapper com o @snapshots separado, set-config, timers de timeline e limpeza (aula Snapshots).
  • status, diff, undochange e o rollback "à mão" do subvolume @.
  • Desmontar tudo sem deixar lixo.

Precisa de: root, os pacotes btrfs-progs e snapper, uns 3 GiB livres em /var/tmp (o arquivo é esparso: ocupa bem menos). Tempo: 30 a 40 minutos, mais uma espera de até uma hora se quiser ver a foto automática.

Antes de começar

Confira o número do loop que o losetup devolver e use esse em todos os comandos. Errar o dispositivo num mkfs apaga um disco de verdade. Aqui foi /dev/loop0; no seu computador pode ser outro.

Parte 1: o disco e os subvolumes

  1. Crie a imagem e ligue-a a um loop: 
    #> mkdir -p /var/tmp/a8 /mnt/a8
#> truncate -s 3G /var/tmp/a8/projeto.img
#> losetup -f --show /var/tmp/a8/projeto.img
/dev/loop0
  2. Formate e crie os três subvolumes no topo. O -q deixa o mkfs.btrfs calado; o subvolume create aceita vários caminhos de uma vez: 
    #> mkfs.btrfs -q -L projeto /dev/loop0
#> mount /dev/loop0 /mnt/a8
#> btrfs subvolume create /mnt/a8/@ /mnt/a8/@home /mnt/a8/@snapshots
Create subvolume '/mnt/a8/@'
Create subvolume '/mnt/a8/@home'
Create subvolume '/mnt/a8/@snapshots'
#> umount /mnt/a8
  3. Monte como se fosse uma instalação: @ na "raiz" (/mnt/a8) e @home na home. A variável D evita repetir o dispositivo: 
    #> D=/dev/loop0
#> mount -o subvol=@,compress=zstd $D /mnt/a8
#> mount --mkdir -o subvol=@home,compress=zstd $D /mnt/a8/home
  4. Ponha um "sistema" de brinquedo dentro: alguns arquivos de configuração copiados do /etc de verdade e uma nota na home. 
    #> mkdir -p /mnt/a8/etc /mnt/a8/home/ana
#> cp /etc/pacman.conf /etc/fstab /etc/hostname /etc/locale.conf /mnt/a8/etc/
#> printf 'Comprar café\nEstudar snapper\n' > /mnt/a8/home/ana/notas.txt
#> tree /mnt/a8
/mnt/a8
├── etc
│   ├── fstab
│   ├── hostname
│   ├── locale.conf
│   └── pacman.conf
└── home
    └── ana
        └── notas.txt

4 directories, 5 files

Parte 2: o snapper com @snapshots separado

  1. Crie a configuração para a "raiz" do projeto. O snapper cria sozinho um subvolume .snapshots dentro do @: 
    #> snapper -c projeto create-config /mnt/a8
#> btrfs subvolume list /mnt/a8
ID 256 gen 9 top level 5 path @
ID 257 gen 9 top level 5 path @home
ID 258 gen 9 top level 5 path @snapshots
ID 259 gen 10 top level 256 path .snapshots     « dentro do @ (top level 256)
  2. Troque esse .snapshots pelo @snapshots. É o passo que a Arch Wiki recomenda: se os snapshots morassem dentro do @, trocar o @ por um snapshot (o rollback da Parte 4) levaria os snapshots junto. Apague o subvolume criado pelo snapper, recrie a pasta e monte o @snapshots ali: 
    #> btrfs subvolume delete /mnt/a8/.snapshots
Delete subvolume 259 (no-commit): '/mnt/a8/.snapshots'
#> mkdir /mnt/a8/.snapshots
#> mount -o subvol=@snapshots,compress=zstd $D /mnt/a8/.snapshots
#> chmod 750 /mnt/a8/.snapshots
#> findmnt -R /mnt/a8 -o TARGET,SOURCE
TARGET               SOURCE
/mnt/a8              /dev/loop0[/@]
├─/mnt/a8/home       /dev/loop0[/@home]
└─/mnt/a8/.snapshots /dev/loop0[/@snapshots]
#> snapper -c projeto list
# │ Tipo   │ Pre # │ Data │ Usuário │ Limpeza │ Descrição │ Dados de usuário
──┼────────┼───────┼──────┼─────────┼─────────┼───────────┼─────────────────
0 │ single │       │      │ root    │         │ current   │

    O chmod 750 impede que usuários comuns entrem nos snapshots (eles têm cópias de arquivos de todo mundo). No sistema real, essa montagem vira uma linha no fstab.

  3. Ajuste os limites da limpeza: 5 fotos de hora em hora, 7 diárias, nenhuma semanal, mensal ou anual, e até 10 snapshots "numerados": 
    #> snapper -c projeto set-config TIMELINE_LIMIT_HOURLY=5 TIMELINE_LIMIT_DAILY=7 TIMELINE_LIMIT_WEEKLY=0 TIMELINE_LIMIT_MONTHLY=0 TIMELINE_LIMIT_YEARLY=0 NUMBER_LIMIT=10
#> snapper -c projeto get-config | grep -E 'TIMELINE|NUMBER_LIMIT'
NUMBER_LIMIT             │ 10
NUMBER_LIMIT_IMPORTANT   │ 10
TIMELINE_CLEANUP         │ yes
TIMELINE_CREATE          │ yes             « o timer vai fotografar esta configuração
TIMELINE_LIMIT_DAILY     │ 7
TIMELINE_LIMIT_HOURLY    │ 5
TIMELINE_LIMIT_MONTHLY   │ 0
TIMELINE_LIMIT_QUARTERLY │ 0
TIMELINE_LIMIT_WEEKLY    │ 0
TIMELINE_LIMIT_YEARLY    │ 0
TIMELINE_MIN_AGE         │ 3600

    Com isso, num dia qualquer você terá as 5 últimas horas e um snapshot por dia da última semana: umas 12 fotos, sempre renovadas.

Parte 3: fotos automáticas

  1. Conheça os dois timers. Um cria (timeline), o outro limpa (cleanup): 
    #> systemctl cat snapper-timeline.timer | grep -E '^On|^Description'
Description=Timeline of Snapper Snapshots
OnCalendar=hourly                                « de hora em hora, na hora cheia
#> systemctl cat snapper-timeline.service | grep -E '^Exec|^Description'
Description=Timeline of Snapper Snapshots
ExecStart=/usr/lib/snapper/systemd-helper --timeline
#> systemctl cat snapper-cleanup.timer | grep -E '^On|^Description'
Description=Hourly Cleanup of Snapper Snapshots
OnBootSec=10m                                    « 10 min depois do boot...
OnUnitActiveSec=1h                               « ...e depois a cada hora
#> systemctl cat snapper-cleanup.service | grep -E '^Exec'
ExecStart=/usr/lib/snapper/systemd-helper --cleanup

    Os dois rodam para todas as configurações listadas em /etc/conf.d/snapper que tenham TIMELINE_CREATE/*_CLEANUP ligados.

  2. Ligue os timers. Na máquina do guia, o snapper-timeline.timer já estava ligado por outra aula; ligamos o de limpeza para ver a saída (e o desligamos logo depois, para devolver a máquina como estava; o comando está na Parte 5): 
    #> systemctl enable --now snapper-cleanup.timer
Created symlink '/etc/systemd/system/timers.target.wants/snapper-cleanup.timer' → '/usr/lib/systemd/system/snapper-cleanup.timer'.
#> systemctl list-timers "snapper-*" --no-pager
NEXT                         LEFT LAST                          PASSED UNIT                   ACTIVATES
Fri 2026-10-16 14:00:00 -03 18min -                                  - snapper-timeline.timer snapper-timeline.service
-                               - Fri 2026-10-16 13:41:15 -03 28ms ago snapper-cleanup.timer  snapper-cleanup.service

2 timers listed.
Pass --all to see loaded but inactive timers, too.

    No seu sistema: systemctl enable --now snapper-timeline.timer snapper-cleanup.timer. O cleanup rodou na hora (o boot tinha sido havia mais de 10 minutos) e não apagou nada, porque nada tinha mais de uma hora.

  3. Tire as fotos manuais que vamos usar: uma marcada como timeline (igual às do timer) e a de referência, "sistema limpo": 
    #> snapper -c projeto create -c timeline -d timeline
#> snapper -c projeto create -c number -d "sistema limpo"
#> snapper -c projeto list
# │ Tipo   │ Pre # │ Data                     │ Usuário │ Limpeza  │ Descrição     │ Dados de usuário

#> ls -a /mnt/a8/.snapshots/2/snapshot /mnt/a8/.snapshots/2/snapshot/home

    A home do snapshot está vazia: o @home é outro subvolume e não entra na foto do @. É exatamente o que queremos: restaurar o sistema não desfaz os seus arquivos pessoais.

  4. Espere a hora cheia (opcional). Às 14:00, o timer fotografou sozinho: 
    #> journalctl -u snapper-timeline.service --since "-40min" --no-pager -o short | tail -3

    Ele aparece como o snapshot 4 na lista do fim da Parte 4.

Parte 4: o estrago e a volta

  1. Estrague o "sistema": apague dois arquivos, altere um e crie lixo. Depois, uma foto do estrago (para comparar): 
    #> rm /mnt/a8/etc/pacman.conf /mnt/a8/etc/fstab
#> echo "configuração estragada" > /mnt/a8/etc/hostname
#> echo "lixo" > /mnt/a8/etc/arquivo-novo.conf
#> ls /mnt/a8/etc
arquivo-novo.conf
hostname
locale.conf
#> snapper -c projeto create -c number -d "depois do estrago"
  2. Veja o que mudou entre o "sistema limpo" (2) e o estrago (3): 
    #> snapper -c projeto status 2..3
+..... /mnt/a8/etc/arquivo-novo.conf
-..... /mnt/a8/etc/fstab
c..... /mnt/a8/etc/hostname
-..... /mnt/a8/etc/pacman.conf
#> snapper -c projeto diff 2..3 /mnt/a8/etc/hostname
--- /mnt/a8/.snapshots/2/snapshot/etc/hostname	2026-10-16 13:40:46.442003144 -0300
+++ /mnt/a8/.snapshots/3/snapshot/etc/hostname	2026-10-16 13:41:22.913750324 -0300
@@ -1 +1 @@
-notebook
+configuração estragada
  3. Volte com undochange. 2..0 = "desfaça tudo o que mudou do snapshot 2 até agora": 
    #> snapper -c projeto undochange 2..0
criar:2 modificar:1 remover:1        « recriou 2, consertou 1, apagou o lixo
#> echo $?
0
#> ls /mnt/a8/etc
fstab
hostname
locale.conf
pacman.conf
#> cat /mnt/a8/etc/hostname
notebook
#> snapper -c projeto status 2..0
#>                                    « nenhuma diferença: igual ao "sistema limpo"

    O undochange é ótimo para estragos parciais, com o sistema funcionando. Quando o estrago é grande (o sistema nem liga), a saída é trocar o subvolume inteiro.

  4. Tente o rollback do snapper: 
    #> snapper -c projeto rollback 2
O comando 'rollback' não pode ser usado num subvolume não-root /mnt/a8.
#> echo $?
1

    O snapper rollback só funciona na configuração do / de verdade (ele muda o subvolume padrão do Btrfs para o próximo boot). No projeto, fazemos o mesmo "à mão", que é também o que você faria pelo pendrive de resgate.

  5. Estrague de vez (apague o /etc inteiro) e faça o rollback manual: monte o topo do Btrfs (subvolid=5), renomeie o @ quebrado e crie um @ novo a partir do snapshot 2: 
    #> rm -r /mnt/a8/etc
#> ls /mnt/a8
home
#> umount -R /mnt/a8
#> mount -o subvolid=5 /dev/loop0 /mnt/a8
#> ls /mnt/a8
@
@home
@snapshots
#> mv /mnt/a8/@ /mnt/a8/@quebrado
#> btrfs subvolume snapshot /mnt/a8/@snapshots/2/snapshot /mnt/a8/@
Create snapshot of '/mnt/a8/@snapshots/2/snapshot' in '/mnt/a8/@'
#> btrfs subvolume list /mnt/a8
ID 256 gen 13 top level 5 path @quebrado
ID 257 gen 12 top level 5 path @home
ID 258 gen 13 top level 5 path @snapshots
ID 260 gen 10 top level 258 path @snapshots/1/snapshot
ID 261 gen 11 top level 258 path @snapshots/2/snapshot
ID 262 gen 12 top level 258 path @snapshots/3/snapshot
ID 263 gen 14 top level 5 path @                      « o @ novo, gravável
    mount -o subvolid=5
    Monta o topo do Btrfs, onde os subvolumes aparecem como pastas.
    mv @ @quebrado
    Renomear um subvolume é instantâneo. Guarde o quebrado até ter certeza.
    btrfs subvolume snapshot (sem -r)
    Cria um snapshot gravável do snapshot 2 (que é só leitura) com o nome @.
  6. Monte de novo como antes e confira:

#> mount -o subvol=@,compress=zstd /dev/loop0 /mnt/a8
#> ls /mnt/a8 /mnt/a8/etc

#> umount /var/tmp/a8/topo && rmdir /var/tmp/a8/topo

Parte 5: desmontar sem deixar lixo

Aqui o projeto ensinou uma lição de verdade. O jeito óbvio falhou:

#> snapper -c projeto delete-config
Falha ao excluir a configuração (deleting snapshot failed).
#> echo $?
1

O delete-config quer apagar o subvolume .snapshots que ele mesmo criou, mas no nosso layout ali está montado o @snapshots. Refizemos o teste numa imagem menor (configuração t2, mesmo layout) para achar a ordem que funciona: apagar os snapshots, desmontar o @snapshots, recolocar um subvolume .snapshots vazio e só então apagar a configuração:

#> snapper -c t2 delete 1-2
#> umount /mnt/a8/.snapshots
#> snapper -c t2 delete-config
Erro de E/S (.snapshots is not a btrfs subvolume).      « ainda falta um passo
#> rmdir /mnt/a8/.snapshots
#> btrfs subvolume create /mnt/a8/.snapshots
Create subvolume '/mnt/a8/.snapshots'
#> snapper -c t2 delete-config
#> echo $?
0
#> snapper list-configs
Configuração │ Subvolume
─────────────┼──────────
#> grep SNAPPER_CONFIGS /etc/conf.d/snapper
SNAPPER_CONFIGS=""

Por fim, desmonte, solte o loop, apague a imagem e devolva o timer ao estado original:

#> umount -R /mnt/a8
#> losetup -d /dev/loop0
#> rm /var/tmp/a8/projeto.img
#> systemctl disable --now snapper-cleanup.timer
Removed '/etc/systemd/system/timers.target.wants/snapper-cleanup.timer'.
Apague a configuração antes da imagem

Se você apagar a imagem com a configuração ainda registrada, o timer do snapper vai tentar fotografar uma pasta que não é mais Btrfs, toda hora, e o delete-config passa a responder Erro de E/S (query default id failed, subvolume is not a btrfs subvolume). Aí a limpeza é manual: apagar /etc/snapper/configs/NOME, tirar o nome de SNAPPER_CONFIGS em /etc/conf.d/snapper e reiniciar o serviço snapperd. (Aconteceu na primeira tentativa deste projeto.)

Como ficaria no sistema real

Esta parte é ilustrativa: é o mesmo projeto, mas com a raiz de verdade. Exige instalar o Arch com Btrfs (a máquina do guia usa ext4) e mexe no boot, então faça com calma e com backup.

EtapaNo projetoNo sistema real
InstalaçãoImagem + loopmkfs.btrfs na partição da raiz, subvolumes @, @home, @var_log, @snapshots, montagem com subvol= e genfstab (aula Btrfs); pacstrap com btrfs-progs
Configuraçãosnapper -c projeto create-config /mnt/a8snapper -c root create-config /, a mesma troca do .snapshots pelo @snapshots, e a linha do /.snapshots no fstab
Fotos automáticasTimers + TIMELINE_*Igual: systemctl enable --now snapper-timeline.timer snapper-cleanup.timer
Foto a cada pacmancreate -t pre/post à mãopacman -S snap-pac: um par pre/post por transação, sozinho
Boot num snapshot—pacman -S grub-btrfs inotify-tools, systemctl enable --now grub-btrfsd, e o hook grub-btrfs-overlayfs no fim do HOOKS= + mkinitcpio -P
Desfazer arquivosundochange 2..0Igual (com -c root, que é o padrão)
Voltar o sistemamv @ @quebrado + snapshot gravávelO mesmo mv @ @quebrado + snapshot gravável, pelo pendrive ou com o sistema ligado num snapshot pelo GRUB. (O snapper rollback só funciona se a raiz for montada pelo subvolume padrão, e não com subvol=/@ no fstab)

Com snap-pac e grub-btrfs, o dia a dia fica assim:

  1. Você roda sudo pacman -Syu. O hook 05-snap-pac-pre.hook cria o snapshot pre antes de qualquer arquivo mudar; o zz-snap-pac-post.hook cria o post no fim (o conteúdo dos hooks está na aula Snapshots).
  2. O grub-btrfsd percebe os snapshots novos em /.snapshots e atualiza o submenu "Arch Linux snapshots" do GRUB.
  3. A atualização quebrou o boot? No GRUB, escolha o snapshot pre da atualização. O sistema liga como era (só leitura, com a camada gravável temporária do overlayfs).
  4. Já dentro, monte o topo do Btrfs (mount -o subvolid=5 /dev/sda3 /mnt), troque o @ como na Parte 4 (mv /mnt/@ /mnt/@quebrado e btrfs subvolume snapshot /mnt/@snapshots/N/snapshot /mnt/@) e reinicie. Depois, com calma, descubra o que quebrou antes de atualizar de novo (as notícias costumam explicar).
Cuidados do rollback no sistema real
  • O /boot (partição EFI, FAT32) não entra nos snapshots. Se você voltar a raiz para antes de uma atualização do kernel, os módulos em /usr/lib/modules voltam, mas o kernel no /boot continua o novo: reinstale o kernel (pacman -S linux) depois do rollback, ou use o LTS para ligar.
  • O banco de dados do pacman volta junto com o @ (ele fica em /var/lib/pacman, dentro do @), o que é bom: pacotes e banco continuam combinando.
  • Os logs ficam no @var_log e não voltam: você consegue ler o que deu errado.

Desafios

1. Pre e post à mão

Antes de editar /mnt/a8/etc/pacman.conf, crie um par pre/post com o atalho que roda um comando entre os dois:

snapper -c projeto create "sed -i 's/^#Color/Color/' /mnt/a8/etc/pacman.conf" -d "ligar cores"

2. Por que o snapshot do @ tinha a pasta home vazia?

3. No rollback manual, por que criar o @ novo com btrfs subvolume snapshot sem -r?

4. Num sistema real com snapper, o que não volta num rollback da raiz?

Resumo

  • Layout: @, @home e @snapshots no topo; o .snapshots do snapper trocado pelo @snapshots.
  • set-config define quantas fotos manter; os timers snapper-timeline e snapper-cleanup criam e limpam sozinhos.
  • Estrago pequeno: status, diff, undochange N..0. Estrago grande: trocar o @ por um snapshot gravável (ou snapper rollback na raiz real).
  • Para desmontar o laboratório: apagar snapshots, recolocar o subvolume .snapshots, delete-config, só então a imagem.
  • No sistema real, snap-pac + grub-btrfs fecham o ciclo: foto a cada pacman e boot direto num snapshot.

Na Arch Wiki: o roteiro completo, incluindo o layout com @snapshots e a restauração, está em Snapper (em português), com o layout em Suggested filesystem layout e a volta do sistema em Restoring / to its previous snapshot; os subvolumes e snapshots do Btrfs em Btrfs (em português); e o boot nos snapshots na página do grub-btrfs.
