Arch Rolling Release

No Arch não existe "a versão 12" nem "a versão 26.04". Cada programa é atualizado assim que sai uma versão nova e passa pelos testes, e o seu sistema acompanha com um único comando. Isso se chama rolling release (lançamento contínuo). Esta aula mostra o que isso significa na prática, com as versões reais da VM do guia, e as duas regras que evitam quase todos os problemas: nunca fazer atualização parcial e ler as notícias.

Você vai aprender
  • A diferença entre lançamento por versões e lançamento contínuo.
  • Para que serve a ISO mensal, se o sistema não tem versão.
  • Como ler as versões dos pacotes (7.2.10.arch1-1, 1:26.2.4-1…) e ver o que mudou.
  • O que são os repositórios testing e staging.
  • Por que a atualização parcial é proibida e como acompanhar as notícias.

Versões × lançamento contínuo

Pense em duas formas de receber notícias. A revista anual junta tudo o que aconteceu e entrega um volume grosso uma vez por ano; entre uma edição e outra, nada muda. O jornal diário entrega um pouco todo dia; você nunca precisa "trocar de edição", só ler o de hoje.

O Debian e o Ubuntu são a revista: a cada versão (Debian 13, Ubuntu 26.04) os programas são congelados, testados juntos e só recebem correções de segurança até a próxima versão. Para ganhar programas novos, você "atualiza a versão" do sistema inteiro. O Arch é o jornal: cada pacote anda sozinho, e o sudo pacman -Syu traz o que saiu desde a última vez.

Por versões (Debian, Ubuntu, Fedora)Rolling (Arch)
Programas novosSó na próxima versão do sistemaDias depois do lançamento
Troca de versão do sistemaA cada 6 meses a 2 anos, com um processo próprioNunca
Tamanho de cada mudançaGrande e raraPequena e frequente
Quem testa a combinaçãoA distribuição, por mesesA distribuição, por dias; o resto do teste é o uso real

O sistema não tem número de versão

Peça ao Arch a versão dele e veja o que ele responde:

$ cat /etc/os-release
NAME="Arch Linux"
PRETTY_NAME="Arch Linux"       « no Ubuntu, aqui aparece "Ubuntu 26.04 LTS"
ID=arch
BUILD_ID=rolling               « no lugar do VERSION_ID: "contínuo"
ANSI_COLOR="38;2;23;147;209"
HOME_URL="https://archlinux.org/"
DOCUMENTATION_URL="https://wiki.archlinux.org/"
SUPPORT_URL="https://bbs.archlinux.org/"
BUG_REPORT_URL="https://gitlab.archlinux.org/groups/archlinux/-/issues"
PRIVACY_POLICY_URL="https://terms.archlinux.org/docs/privacy-policy/"
LOGO=archlinux-logo
$ cat /etc/arch-release
                               « vazio: o arquivo existe só para dizer "isto é um Arch"
$ ls -l /etc/arch-release
-rw-r--r-- 1 root root 1 12 out  2025 /etc/arch-release

Não há VERSION_ID, e o /etc/arch-release tem 1 byte (só uma quebra de linha). Programas que precisam saber "que sistema é este" olham o ID=arch; a "versão" do seu Arch é, na prática, a data da última atualização.

A ISO mensal

Se não há versão, o que é aquele arquivo archlinux-2026.10.01-x86_64.iso? É só um retrato do mês: uma imagem para dar boot e instalar, gerada no dia 1º de cada mês com os pacotes daquele dia. Ela não é "o Arch de outubro": o sistema que você instala com ela baixa os pacotes da internet na hora da instalação (o pacstrap), então ele já nasce atualizado.

A VM do guia mostra isso bem. Ela foi instalada com uma ISO de junho, e o próprio leitor de CD da VM mostra o nome:

Qual ISO usar?

Sempre a mais nova (em outubro de 2026, a 2026.10.01). Uma ISO antiga ainda instala, mas pode ter chaves de assinatura vencidas ou não reconhecer hardware novo. Depois de instalado, a ISO não importa mais: você nunca "atualiza a ISO". Veja Baixar e Verificar a ISO.

O que muda toda semana

O que muda são os pacotes, cada um no seu ritmo. Veja as versões de quatro pacotes importantes na VM, em outubro de 2026:

pacman
O gerenciador de pacotes.
-Q
Query: pergunta ao banco de dados local, o dos pacotes instalados (não usa a internet).
linux bash pacman glibc
Os pacotes que você quer ver: o kernel, o shell, o próprio pacman e a biblioteca C (a base de quase todos os programas).
$ pacman -Q linux bash pacman glibc
linux 7.2.10.arch1-1                   « o kernel
bash 5.3.20-1
pacman 7.1.0.r9.g54d9411-3             « uma versão tirada direto do git do pacman
glibc 2.44+r50+g1848099f063e-1         « idem: a glibc 2.44 mais 50 mudanças do git
$ echo $?
0

Cada linha é nome versão-lançamento. As versões parecem estranhas, mas seguem regras:

ExemploParteSignificado
bash 5.3.20-15.3.20A versão do programa, como os autores lançaram.
-1O pkgrel: quantas vezes o Arch empacotou essa mesma versão. Uma correção no pacote vira -2.
linux 7.2.10.arch1-1.arch1Primeira revisão do kernel feita pelo Arch. No uname -r ela aparece como 7.2.10-arch1-1 (com hífen).
pacman 7.1.0.r9.g54d9411-3.r9.g54d9411Tirado do git: 9 mudanças depois da 7.1.0, no commit 54d9411.
mesa 1:26.2.4-11:A época (epoch): usada quando o esquema de versões mudou e o número novo pareceria "menor" que o antigo. Ela vence qualquer comparação.

Para saber quando cada pacote foi compilado e instalado, use -Qi (info):

$ pacman -Qi linux | grep -E "^(Nome|Versão|Data|Motivo|Tamanho)"
Nome                 : linux
Versão               : 7.2.10.arch1-1
Tamanho instalado    : 161,60 MiB
Data da compilação   : seg 12 out 2026 03:58:10      « o Arch empacotou na segunda
Data de instalação   : sex 16 out 2026 12:08:47      « chegou à VM na sexta
Motivo da instalação : Instalado explicitamente
$ pacman -Qi bash | grep -E "^(Data)"
Data da compilação   : ter 15 set 2026 16:47:19      « o bash estava parado havia um mês
Data de instalação   : sex 16 out 2026 12:08:24

O kernel tinha quatro dias; o Bash, um mês. Cada pacote anda no seu ritmo. Numa semana típica, algumas dezenas de pacotes do seu sistema ganham versão nova.

Ver o que há para atualizar, sem mexer em nada

O checkupdates, do pacote pacman-contrib, baixa a lista nova numa pasta temporária e compara com o que você tem. Ele não muda o sistema e roda sem sudo:

$ checkupdates
$ echo $?
2                              « 2 = nada para atualizar; 0 = há atualizações (e ele lista)

Quando há atualizações, cada linha mostra pacote versão-atual -> versão-nova. Não mostrar nada não é erro: o código de saída 2 diz que estava tudo em dia (a VM tinha sido atualizada horas antes).

Missão: compare a versão do pacote do kernel com a do kernel em uso. Rode pacman -Q linux e depois uname -r. Repare no ponto (.arch1) de um e no hífen (-arch1) do outro. Experimente também pacman -Q bash pacman glibc.

testing e staging: onde os pacotes esperam

Um pacote novo não vai direto para você. O caminho, simplificado:

  1. staging: quando uma biblioteca muda de um jeito que exige recompilar muitos outros pacotes, tudo é recompilado aqui primeiro, longe dos usuários.
  2. testing (core-testing, extra-testing): o pacote fica disponível para voluntários e desenvolvedores testarem.
  3. core / extra: depois de aprovado, ele entra nos repositórios que todo mundo usa.

Os repositórios testing vêm desligados. Eles aparecem comentados (com #) no /etc/pacman.conf da VM:

# The testing repositories are disabled by default. To enable, uncomment the
# repo name header and Include lines. You can add preferred servers immediately
# after the header, and they will be used before the default mirrors.

#[core-testing]
#Include = /etc/pacman.d/mirrorlist

[core]
Include = /etc/pacman.d/mirrorlist

#[extra-testing]
#Include = /etc/pacman.d/mirrorlist

[extra]
Include = /etc/pacman.d/mirrorlist

# If you want to run 32 bit applications on your x86_64 system,
# enable the multilib repositories as required here.

#[multilib-testing]
#Include = /etc/pacman.d/mirrorlist

#[multilib]
Não ligue o testing "para ter coisas mais novas"

O testing é para quem vai testar e relatar problemas. Quem liga e depois desliga fica com pacotes de versões que não existem nos repositórios normais. Deixe como está. O multilib é outro assunto (programas de 32 bits, como o Steam) e é seguro de ativar quando você precisar.

A regra de ouro: nada de atualização parcial

No Arch, todos os pacotes dos repositórios foram compilados uns contra os outros, na mesma época. Quando uma biblioteca muda de versão de um jeito incompatível, todos os programas que usam essa biblioteca são recompilados juntos e chegam juntos. O pacman registra essas amarrações:

$ pacman -Qi pacman | grep -E "^(Provê|Depende de)"
Provê                : libalpm.so=16-64     « o pacman entrega a biblioteca libalpm versão 16
Depende de           : bash  coreutils  curl  libcurl.so=4-64  gawk  gettext  glibc  gnupg  gpgme  libgpgme.so=45-64  grep  libarchive  libarchive.so=13-64  openssl  libcrypto.so=3-64  pacman-mirrorlist  systemd  libmakepkg-dropins

Entradas como libcurl.so=4-64 dizem: "este programa precisa da versão 4 da biblioteca libcurl". Se só uma parte do sistema for atualizada, um programa novo pode exigir uma biblioteca que o resto do sistema ainda não tem, ou o contrário, e aí ele nem abre.

Isso é a atualização parcial. Ela acontece quando você baixa a lista nova de pacotes (-y) mas não atualiza tudo (-u):

Nunca rode pacman -Sy pacote

sudo pacman -Sy firefox parece inocente: "atualize a lista e instale o Firefox". Mas o Firefox novo vem compilado contra as bibliotecas novas, que você não instalou. O resultado pode ser um programa que não abre ou, se for algo central, um sistema que não liga. As formas certas são:

  • sudo pacman -S firefox (instala usando a lista que você já tem), ou
  • sudo pacman -Syu firefox (atualiza tudo e instala o Firefox).

Pelo mesmo motivo, não segure pacotes "para sempre" com IgnorePkg e não instale pacotes antigos soltos. Os detalhes estão em Atualizar o Sistema.

ComandoSeguro?Por quê
sudo pacman -SyuSimBaixa a lista nova e atualiza tudo junto.
sudo pacman -S pacoteSimUsa a mesma lista com que o sistema foi atualizado.
sudo pacman -Syu pacoteSimAtualiza tudo e instala o pacote.
sudo pacman -Sy pacoteNãoLista nova, sistema velho: atualização parcial.
sudo pacman -Sy e mais nadaNãoDeixa a armadilha pronta para o próximo -S.
checkupdatesSimUsa uma cópia temporária da lista; não toca no sistema.

Leia as notícias antes de atualizar

Quando uma atualização precisa de uma ação sua (um arquivo para editar, um comando antes ou depois), o Arch publica uma notícia em archlinux.org/news. Elas são poucas (menos de uma por mês) e curtas. Há três jeitos de acompanhar:

JeitoComo
SiteAbra archlinux.org antes de atualizar: as notícias ficam na página inicial.
RSS ou e-mailO feed https://archlinux.org/feeds/news/ num leitor de RSS, ou a lista de e-mail arch-announce.
No terminalAjudantes do AUR como o yay e o paru mostram as notícias; o informant trava a atualização até você ler.

Na VM do guia, o yay está instalado (ele vem do AUR; veja yay e paru):

yay
Um ajudante do AUR que também aceita as opções do pacman.
-P
Print: operações que só mostram informações.
w
News: as notícias do archlinux.org. Com um w, só as que saíram depois da sua última atualização; com ww, todas as recentes.
$ yay -Pw
$ echo $?
0                              « nada novo desde a última atualização: está tudo lido
$ yay -Pww | grep -E '^[0-9]{4}-[0-9]{2}-[0-9]{2} '

O grep deixou só as linhas de título (data e assunto); sem ele, o yay mostra cada notícia inteira, em inglês, com os comandos a rodar. Leia o título e pergunte: "eu uso isso?". Se a resposta for não, siga em frente.

O informant (do AUR) vai além: ele se instala como um hook do pacman e interrompe o pacman -Syu enquanto houver notícia não lida; informant read marca como lida. Ele não foi instalado na VM, então esta parte é ilustrativa.

Quando não funciona

Instalei um programa e ele não abre: "error while loading shared libraries"

Causa provável: uma atualização parcial. O programa novo procura uma versão de biblioteca (libalgo.so.N) que o resto do sistema ainda não tem.

Como confirmar: veja no /var/log/pacman.log se houve um pacman -Sy seguido de -S sem -u.

Como resolver: complete a atualização com sudo pacman -Syu. Se o sistema não liga mais, veja Resgate com chroot.

O checkupdates não mostrou nada 
$ checkupdates
$ echo $?
2

Causa: não há atualizações. Não é erro.

Como confirmar: o código 2 quer dizer "nada pendente"; 1 seria um erro de verdade (sem internet, por exemplo).

Uma atualização pediu para eu fazer algo e eu não fiz

Causa: a notícia não foi lida antes do -Syu.

Como resolver: abra a notícia correspondente (pela data) e faça os passos agora; a maioria funciona do mesmo jeito depois da atualização. Os casos comuns estão em Erros de Atualização.

Resumo

  • Rolling release: os pacotes são atualizados continuamente; o sistema não tem versão (BUILD_ID=rolling).
  • A ISO mensal é só para instalar; o sistema instalado já nasce com os pacotes do dia.
  • Versões: versão-pkgrel, às vezes com época (1:) ou trechos do git (.r9.g54d9411).
  • testing e staging são etapas antes do core/extra; ficam desligados.
  • Atualização parcial (-Sy pacote) é proibida: use -Syu ou -S.
  • Leia as notícias (site, RSS, yay -Pw) antes de atualizar; são menos de uma por mês.
