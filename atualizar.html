Atualizar o Sistema

O Arch é rolling release: não existe "Arch 2027" para instalar por cima. O sistema inteiro anda junto, um pouco por semana, com um único comando: sudo pacman -Syu. Nesta aula você aprende o que cada letra faz, por que atualizar "só um pacote" é proibido no Arch, e os hábitos que evitam sustos.

Você vai aprender
  • O que fazem o S, o y e o u de pacman -Syu, e a saída de cada parte.
  • Ver o que tem para atualizar sem atualizar (checkupdates, pacman -Qu).
  • O que é uma atualização parcial e por que ela quebra programas.
  • Ler as notícias antes, com que frequência atualizar e quando reiniciar.

As três letras de -Syu

sudo
Atualizar muda o sistema: precisa de root.
-S
sync: trabalhar com os repositórios.
y
refresh: baixar o catálogo novo (core.db, extra.db) dos espelhos. Sem ele, o pacman não sabe que existem versões novas.
u
sysupgrade: comparar o que está instalado com o catálogo e atualizar tudo o que tiver versão nova.

Em 16/10/2026, a VM do guia estava em dia. A saída real foi esta:

$ sudo pacman -Syu
[sudo] senha para ana:
:: Sincronizando a base de dados de pacotes...          « o "y": baixa o catálogo
 core está atualizado                                    « o catálogo do core não mudou desde a última vez
 extra está atualizado
:: Iniciando atualização completa do sistema...          « o "u": compara instalado × catálogo
nada para fazer                                          « nenhum pacote tem versão nova
$ echo $?
0

Quando o catálogo mudou, no lugar de está atualizado aparece uma barra de download para cada repositório (o extra.db tem uns 8,5 MiB):

:: Sincronizando a base de dados de pacotes...
 core                  127,9 KiB   318 KiB/s 00:00 [######################] 100%
 extra                   8,5 MiB  2,68 MiB/s 00:03 [######################] 100%

Quando há atualizações

Para mostrar uma atualização sem mexer na VM, fizemos um exemplo controlado: uma cópia do banco de dados de pacotes em que o htop e o linux aparecem numa versão anterior. O pacman (de verdade) respondeu assim, e respondemos "não":

$ sudo pacman -Su                                        « -Su = o -Syu sem baixar o catálogo de novo
:: Iniciando atualização completa do sistema...
resolvendo dependências...
procurando pacotes conflitantes...

Pacotes (2) htop-3.5.3-1  linux-7.2.10.arch1-1            « as versões NOVAS que vão entrar

Tamanho total instalado:  162,01 MiB
Alteração no tamanho:       0,00 MiB                       « quanto o disco ganha ou perde

:: Continuar a instalação? [S/n] n

Não apareceu Tamanho total download porque esses dois arquivos já estavam no cache; normalmente ele aparece. A lista mostra só a versão nova. Para ver também a antiga, ligue a opção VerbosePkgLists no /etc/pacman.conf (veja pacman Avançado). A mesma transação fica assim:

Pacote (2)  Versão antiga  Versão nova       Diferença

extra/htop  3.5.2-1        3.5.3-1            0,00 MiB
core/linux  7.2.9.arch1-1  7.2.10.arch1-1     0,00 MiB     « um kernel novo: reinicie depois

Depois do S, a sequência é a mesma da instalação (veja pacman: o Básico): baixar, conferir chaves e integridade, atualizando htop..., e os hooks. Quando o kernel está na lista, um dos hooks refaz o initramfs. Trecho real da VM:

:: Executando hooks pós-transação...
…
(11/18) Updating linux initcpios...
==> Building image from preset: /etc/mkinitcpio.d/linux.preset: 'default'
==> Using default configuration file: '/etc/mkinitcpio.conf'
  -> -k /boot/vmlinuz-linux -g /boot/initramfs-linux.img
==> Starting build: '7.2.10-arch1-1'
…
==> Initcpio image generation successful
Não interrompa no meio

Depois de :: Processando alterações do pacote..., não feche o terminal, não aperte Ctrl+C e não desligue o computador (notebook na tomada). Uma atualização interrompida pode deixar metade dos arquivos de um pacote novo e metade do velho, e a trava db.lck para trás. Se acontecer, veja Erros de Atualização e Resgate com chroot.

Ver o que tem para atualizar, sem atualizar

checkupdates (o jeito seguro)

O checkupdates vem no pacote pacman-contrib (instale com sudo pacman -S pacman-contrib). Ele baixa o catálogo novo numa cópia temporária em /tmp, sem tocar no catálogo do sistema, e lista o que mudou. Não precisa de root.

$ checkupdates
$ echo $?
2                                       « 2 = não há atualizações

Nada na tela e código 2: tudo em dia. Quando há atualizações, cada linha mostra nome versão-instalada -> versão-nova, e o código é 0. No exemplo controlado, a lista (tirada com pacman -Qu, que o checkupdates usa por dentro) foi:

htop 3.5.2-1 -> 3.5.3-1
linux 7.2.9.arch1-1 -> 7.2.10.arch1-1
Código de saída do checkupdatesSignificado
0Há atualizações (a lista foi impressa).
1Erro (sem internet, espelho fora do ar…).
2Nenhuma atualização.

pacman -Qu (só com o catálogo que você já tem)

pacman -Qu (query upgrades) faz a mesma comparação, mas com o catálogo que já está no disco, que pode ser velho. Ele não baixa nada:

$ pacman -Qu
$ echo $?
1                                       « 1 = nada (pelo catálogo atual)
Por que não "pacman -Sy" para ver se tem novidade?

Porque pacman -Sy atualiza o catálogo do sistema sem atualizar os pacotes. A partir daí, qualquer pacman -S programa instala a versão do catálogo novo num sistema velho: é a atualização parcial, assunto da próxima seção. O checkupdates existe justamente para evitar isso.

Atualização parcial é proibida

No Arch, todos os pacotes de um mesmo momento são compilados uns contra os outros. A Arch Wiki é direta: atualizações parciais não são suportadas. Atualização parcial é qualquer situação em que parte do sistema fica numa "época" e parte em outra. As formas mais comuns:

ComandoPor que é parcial
pacman -Sy pacoteBaixa o catálogo novo e instala só aquele pacote na versão nova, com o resto velho.
pacman -Sy e, dias depois, pacman -S pacoteA mesma coisa, em dois passos.
IgnorePkg = pacote no pacman.confO pacote fica parado enquanto o resto anda.
Instalar um .pkg.tar.zst antigo com pacman -UUma peça de outra época (às vezes necessário; veja downgrade).

Por que quebra: as bibliotecas

Programas usam bibliotecas compartilhadas (arquivos .so, de shared object) que ficam em /usr/lib. O número no nome é a versão da "interface": libncursesw.so.6. Quando a biblioteca muda de forma incompatível, o número sobe (de .so.6 para .so.7), e o arquivo antigo some na atualização. O pacman anota essa relação nos pacotes:

$ pacman -Qi htop | grep Depende
Depende de           : libcap  libcap.so=2-64  libnl  ncurses  libncursesw.so=6-64    « precisa da versão 6

Agora imagine um exemplo (ilustrativo): a ncurses nova traz libncursesw.so.7. No repositório, o htop e todos os outros programas que a usam são recompilados para a 7 e publicados juntos. Se você roda sudo pacman -Sy htop, entra o htop novo (que pede a 7), mas a sua ncurses continua na 6. O pacman até puxaria a ncurses nova como dependência, mas aí todos os outros programas, que não foram atualizados, continuam pedindo a 6, que acabou de sumir. O resultado é programa que não abre.

Um caso real na VM do guia

Esse problema aconteceu de verdade na VM, com o paru (um ajudante do AUR instalado já compilado, o paru-bin). Ele foi compilado contra a biblioteca do pacman, libalpm.so.15, mas o pacman do sistema já fornece a libalpm.so.16:

$ paru --version
paru: error while loading shared libraries: libalpm.so.15: cannot open shared object file: No such file or directory
$ echo $?
127
$ ls /usr/lib/libalpm.so*
/usr/lib/libalpm.so
/usr/lib/libalpm.so.16                       « só existe a 16
/usr/lib/libalpm.so.16.0.1
$ ldd /usr/bin/paru | grep alpm
	libalpm.so.15 => not found               « o paru pede a 15
$ pacman -Qi pacman | grep Provê
Provê                : libalpm.so=16-64

É exatamente a mensagem que você vê depois de uma atualização parcial: error while loading shared libraries: libXXX.so.N: cannot open shared object file. Aqui a causa é o AUR (pacotes do AUR não são recompilados junto com o Arch; veja yay e paru), mas o mecanismo é o mesmo.

A regra

Para instalar algo, use sudo pacman -S pacote (com o catálogo que você já tem) ou, se faz tempo que não atualiza, sudo pacman -Syu pacote (atualiza tudo e instala junto). Nunca pacman -Sy pacote. E se você rodou pacman -Sy sozinho, o próximo comando deve ser pacman -Su.

Antes de atualizar: as notícias

Às vezes uma atualização precisa de uma intervenção manual: trocar um pacote por outro, editar uma configuração, rodar um comando antes. O Arch avisa em archlinux.org/news (também por RSS e pela lista de e-mails arch-announce). O hábito é simples: antes do -Syu, olhe as notícias. São poucas por mês.

O ajudante yay mostra as notícias não lidas no terminal com yay -Pw (na VM, em 16/10/2026, não havia nenhuma, e a saída foi vazia). O pacman em si não mostra notícias.

Com que frequência?

  • Uma vez por semana (ou a cada poucos dias) é o ritmo mais tranquilo: poucas mudanças por vez, fácil de saber o que causou um problema.
  • Evite ficar meses sem atualizar: o salto fica grande, as chaves de assinatura podem ficar velhas (veja Chaves e Assinaturas) e as notícias acumulam.
  • Atualize quando tiver alguns minutos para ler a saída, não às pressas antes de uma reunião.
  • Atualizar automaticamente (por um timer) não é recomendado no Arch: ninguém leria as notícias nem os avisos de .pacnew.

Depois de atualizar: reiniciar?

Programas que já estão rodando continuam usando a versão antiga, carregada na memória. Para a maioria dos programas, basta fechá-los e abrir de novo. Três casos pedem reiniciar o computador:

Pacote atualizadoPor que reiniciar
linux (o kernel)O kernel em uso é o que foi carregado no boot. A atualização apaga os módulos dele de /usr/lib/modules, e coisas que carregam módulos depois (um pendrive, uma placa nova, o Wi-Fi) param de funcionar até reiniciar.
glibcÉ a biblioteca usada por quase todos os programas. Os que estão rodando ficam com a versão antiga na memória.
systemdO PID 1 e os serviços básicos só passam a usar a versão nova depois de reiniciar.

Como saber se o kernel em uso é o instalado

Compare o kernel em uso (uname -r, de release) com o kernel instalado (pacman -Q linux):

$ uname -r
7.2.10-arch1-1                 « em uso
$ pacman -Q linux
linux 7.2.10.arch1-1           « instalado: o mesmo (o pacote escreve ".arch1", o kernel "-arch1")
$ ls /usr/lib/modules
6.18.57-1-lts                  « módulos do linux-lts
7.2.10-arch1-1                 « módulos do kernel em uso

Se depois de uma atualização o pacman -Q linux mostrar uma versão mais nova que o uname -r, você está rodando um kernel cujos módulos já não existem no disco: reinicie. A mesma comparação revelou um problema real na VM: depois de instalar o linux-lts, o uname -r passou a responder 6.18.57-1-lts enquanto o kernel principal instalado era o 7.2.10. O GRUB estava iniciando o LTS por padrão (a história está em Kernels).

Reiniciar serviços sem reiniciar o computador

Atualizou o nginx ou o openssh? sudo systemctl restart nginx basta (veja systemctl e Serviços). Reiniciar a máquina inteira é para kernel, glibc e systemd.

Os arquivos .pacnew

Às vezes a atualização termina com uma linha assim:

atenção: /etc/pacman.d/mirrorlist instalado como /etc/pacman.d/mirrorlist.pacnew

Não é erro: o pacote trouxe uma versão nova de um arquivo de configuração que você tinha alterado, e o pacman não sobrescreveu o seu. Você decide o que juntar. Essa linha ilustra o formato; a aula .pacnew e .pacsave mostra um caso real e como resolver com pacdiff.

Experimente

No simulador, a senha da ana é ana.

Missão 1: atualize o sistema da ana. Leia a saída: o catálogo mudou? Havia pacotes para atualizar?

Missão 2: confira se o kernel em uso é o mesmo que está instalado (dois comandos). É preciso reiniciar?

Quando não funciona

"error while loading shared libraries" 
$ paru --version
paru: error while loading shared libraries: libalpm.so.15: cannot open shared object file: No such file or directory

O que aconteceu: o programa pede uma versão de biblioteca que não existe mais. Causas: atualização parcial, ou um pacote do AUR compilado contra a versão antiga.

Como confirmar: pacman -Qo /usr/bin/paru diz de que pacote é o programa; pacman -Qm diz se ele é do AUR.

Como resolver: primeiro sudo pacman -Syu (acaba com qualquer atualização parcial). Se o programa é do AUR, recompile/reinstale o pacote dele (veja makepkg).

"falha ao obter o arquivo" / "falha ao sincronizar todas as bases de dados"

O que aconteceu: sem internet, ou o espelho está fora do ar ou desatualizado.

Como resolver: confira a rede (ping archlinux.org) e troque de espelho: Espelhos (reflector).

"a assinatura de … tem confiança desconhecida" ou "é inválida"

O que aconteceu: quase sempre, o chaveiro do Arch no seu sistema está velho (você ficou muito tempo sem atualizar).

Como resolver: atualize o chaveiro primeiro e depois o resto: sudo pacman -Sy archlinux-keyring && sudo pacman -Su. Este é o único caso em que -Sy pacote é a recomendação oficial, porque o -Su vem logo em seguida. Detalhes em Chaves e Assinaturas.

"conflitos de arquivos", "existe no sistema de arquivos", dependências que não fecham

O que aconteceu: erros que aparecem no meio de um -Syu e param a transação antes de mexer no sistema.

Como resolver: leia a mensagem inteira, procure nas notícias e veja Erros de Atualização, que trata cada um.

"não foi possível travar a base de dados"

O que aconteceu: outro pacman está rodando, ou um anterior foi interrompido.

Como resolver: veja o passo a passo em pacman: o Básico (confira pgrep -a pacman antes de apagar /var/lib/pacman/db.lck).

Resumo

  • sudo pacman -Syu: y baixa o catálogo, u atualiza tudo. "nada para fazer" = em dia.
  • checkupdates mostra o que há sem mexer no sistema.
  • Nunca pacman -Sy pacote: atualização parcial quebra bibliotecas (error while loading shared libraries).
  • Leia archlinux.org/news antes; atualize mais ou menos uma vez por semana.
  • Reinicie depois de atualizar linux, glibc ou systemd; compare uname -r com pacman -Q linux.
