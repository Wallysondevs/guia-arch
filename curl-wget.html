Arch curl, wget, dig

Três ferramentas conversam com a internet pelo terminal. O curl faz requisições de todo tipo e mostra o que o servidor respondeu: é o favorito para testar sites e APIs. O wget é especialista em baixar arquivos. O dig pergunta ao DNS qual é o endereço de um nome. No Arch, só o curl vem garantido; os outros são pacotes à parte.

Você vai aprender
  • Por que todo Arch tem curl, e de qual pacote vêm o wget, o dig e o drill.
  • Ver o cabeçalho e o código HTTP de um site com curl -I, seguir redirecionamentos com -L e salvar com -o e -O.
  • Usar curl -s, -f e o código de saída em scripts (6, 7, 22, 28).
  • Baixar e retomar downloads com wget, que no Arch fala português.
  • Perguntar ao DNS com dig, nslookup, host e drill.

Esta aula supõe que a rede já funciona (veja ip, ping, ss). Todas as saídas são da VM do guia, baixando arquivos pequenos de verdade do site archlinux.org, numa pasta de teste.

O que já vem instalado

O curl está em todo Arch por um motivo simples: o próprio pacman depende dele para baixar pacotes (a biblioteca libcurl). Veja a linha "Necessário para":

$ pacman -Qi curl
Nome                 : curl
Versão               : 8.23.0-1
…
Necessário para      : appstream  cfitsio  devtools  flatpak  gettext  git  libelf  networkmanager  ostree  pacman  tpm2-tss   « o pacman precisa dele
…
Motivo da instalação : Instalado como dependência de outro pacote

Os outros, não. A situação de um Arch recém-instalado:

FerramentaPacoteVem instalado?
curlcurlSim (dependência do pacman)
wgetwgetNão (a VM do guia tem, porque as aulas usam)
dig, nslookup, hostbindNão
drillldnsNão
getentglibcSim
resolvectlsystemdSim, mas o serviço systemd-resolved vem desligado (veja ip, ping, ss)

No Debian e no Ubuntu, o dig vem num pacote chamado dnsutils (ou bind9-dnsutils). No Arch, ele faz parte do pacote bind, que é o servidor de DNS inteiro; o antigo bind-tools não existe mais. Não sabe de qual pacote vem um comando? Pergunte ao pacman com -F (de files; veja pacman Avançado):

$ dig +short archlinux.org
bash: dig: comando não encontrado
$ pacman -F dig
extra/bind 9.20.29-1
    usr/bin/dig                                « é este
extra/epic4 2.10.11-2
    usr/share/epic/script/dig                  « outro arquivo com o mesmo nome, não é o comando
extra/gstreamer-docs 1.28.8-1
    usr/share/doc/gstreamer/html/assets/js/search/dig
$ pacman -F drill
core/ldns 1.9.2-1
    usr/bin/drill

O que a instalação traria (transação real, respondida com n: nada foi instalado na VM):

#> pacman -S bind
resolvendo dependências...
procurando pacotes conflitantes...

Pacotes (6) dnssec-anchors-20250524-1  jemalloc-1:5.4.0-1
            libmaxminddb-1.14.1-1  liburcu-0.15.7-1  libuv-1.52.1-2
            bind-9.20.29-1

Tamanho total download:   2,86 MiB
Tamanho total instalado:  9,69 MiB

O bind traz o servidor (named), mas instalá-lo não liga servidor nenhum: como todo serviço no Arch, o named fica desligado até alguém dar systemctl enable. Você ganha só os comandos. Se quiser algo menor, o ldns (0,48 MiB) traz o drill, parecido com o dig.

Como as saídas do dig foram feitas

Para não instalar nada na VM compartilhada, os pacotes bind e ldns foram baixados numa pasta temporária e os programas rodaram de lá, sem instalar. As saídas desta aula são, portanto, do dig 9.20.29 e do drill 1.9.2 do Arch, na VM, exatamente como ficam depois de um sudo pacman -S bind.

Códigos HTTP em 30 segundos

Todo site responde a um pedido com um número de três dígitos, o código HTTP. O primeiro dígito já diz muito:

FaixaQuer dizerExemplos

3xxRedirecionamento: "o conteúdo está em outro endereço"301 Moved Permanently, 302 Found

curl: conversar com servidores

O curl (de client URL) pede um endereço e mostra a resposta na tela, por padrão. Experimente com um arquivo pequeno de texto, o robots.txt do site do Arch (as regras para robôs de busca):

$ curl https://archlinux.org/robots.txt
User-agent: *
Disallow: /packages/search/
Disallow: /packages/?
Disallow: /packages/?*
Sitemap: https://www.archlinux.org/sitemap.xml
Crawl-delay: 2

Numa página HTML, isso despeja centenas de linhas de código no terminal. Por isso, para testar um site, a opção mais usada é a -I, que pede só o cabeçalho da resposta.

Só o cabeçalho: -I

curl
O programa.
-I
I maiúsculo, de head (--head): só o cabeçalho, sem o conteúdo da página.
https://archlinux.org
O endereço, com o https://.
$ curl -I https://archlinux.org
HTTP/2 200                                                 « protocolo HTTP/2 e código 200: deu certo
server: nginx                                              « o programa servidor
date: Fri, 16 Oct 2026 17:55:58 GMT                        « hora do servidor (em GMT, 3 h à frente de Brasília)
content-type: text/html; charset=utf-8                     « o tipo do conteúdo: uma página HTML
content-length: 25437                                      « tamanho, em bytes (uns 25 KB)
cache-control: max-age=307
content-security-policy: base-uri 'none'; form-action 'self'; default-src 'self'; script-src 'self'; img-src 'self' data:; frame-ancestors 'none'
x-content-type-options: nosniff
referrer-policy: strict-origin
cross-origin-opener-policy: same-origin
x-frame-options: DENY
vary: Cookie
strict-transport-security: max-age=31536000; includeSubdomains; preload   « "só me acesse por https" (1 ano)
x-cache-status: HIT                                        « veio do cache do servidor

$ echo $?
0

A primeira linha é a que importa: 200. As outras são informações que o servidor manda sobre a resposta; as que começam com x- e as de segurança (content-security-policy, x-frame-options) são instruções para o navegador. O curl e as respostas HTTP ficam sempre em inglês, qualquer que seja o idioma do sistema. Num terminal de verdade, o nome de cada campo aparece em negrito.

Seguir redirecionamentos: -L

Peça o endereço com http:// (sem o "s") e veja o que acontece:

$ curl -I http://archlinux.org
HTTP/1.1 301 Moved Permanently                 « "mudou-se para sempre"
Server: nginx
Date: Fri, 16 Oct 2026 17:55:35 GMT
Content-Type: text/html
Content-Length: 162
Connection: keep-alive
Location: https://archlinux.org/              « o endereço novo

Sem -L, o curl para no primeiro redirecionamento e só mostra para onde ele aponta (o campo Location). Com -L (de location), ele segue até o destino final. Aqui, filtrando só as linhas de código e de endereço com o grep:

$ curl -sIL http://archlinux.org | grep -iE "^(http|location)"
HTTP/1.1 301 Moved Permanently
Location: https://archlinux.org/
HTTP/2 200                                    « seguiu e chegou

Salvar em arquivo: -o e -O

Para guardar a resposta num arquivo em vez de mostrar na tela, há duas opções, que diferem só na letra maiúscula:

-o pagina.html
o minúsculo: salva com o nome que você escolher.
-O
O maiúsculo: salva com o nome que está no fim do endereço (robots.txt). Não funciona se o endereço termina em /.
$ curl -o pagina.html https://archlinux.org
  % Total    % Received % Xferd  Average Speed  Time    Time    Time   Current
                                 Dload  Upload  Total   Spent   Left   Speed
100  25437 100  25437   0      0  20382      0   00:01   00:01              0
$ curl -O https://archlinux.org/robots.txt
  % Total    % Received % Xferd  Average Speed  Time    Time    Time   Current
                                 Dload  Upload  Total   Spent   Left   Speed
100    149 100    149   0      0     99      0   00:01   00:01              0
$ ls -l
total 32
-rw-r--r-- 1 ana ana 25437 16 out 14:55 pagina.html
-rw-r--r-- 1 ana ana   149 16 out 14:55 robots.txt

Quando salva em arquivo, o curl desenha uma tabela de progresso, que vai se atualizando durante o download. Lendo a linha final: 100% de 25437 bytes recebidos, velocidade média de download (Dload) de 20382 bytes por segundo, tempo total e gasto de 1 segundo.

Silencioso: -s (e -S)

Em scripts, a tabela de progresso atrapalha. O -s (de silent) esconde a tabela e também as mensagens de erro. Junte com -S (maiúsculo, show-error) para continuar vendo os erros:

$ curl -s -O https://archlinux.org/robots.txt
$ echo $?
0                                  « nada na tela, mas deu certo

Só o código, em uma linha: -w

O -w (de write-out) escreve informações no fim. Junto com -s -o /dev/null (descartar o conteúdo; veja Redirecionamento), sobra só o que você pediu:

$ curl -s -o /dev/null -w "%{http_code}\n" https://archlinux.org
200
$ curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" https://archlinux.org/naoexiste
404 0.819087s                                « página inexistente, respondeu em 0,8 s
$ curl -sSL -o /dev/null -w "%{http_code} %{url_effective}\n" http://archlinux.org
200 https://archlinux.org/                   « onde o -L terminou

curl em scripts: -f e o código de saída

Atenção a esta pegadinha: por padrão, o curl considera "sucesso" qualquer resposta do servidor, até um 404. O código de saída é 0:

$ curl -s https://archlinux.org/naoexiste | head -3; echo "código: ${PIPESTATUS[0]}"
<!DOCTYPE html>

<html lang="en">
código: 0                                    « a página de erro veio, e o curl achou ótimo

Com -f (de fail), uma resposta 400 ou maior vira erro 22. O trio -fsS é o mais usado em scripts: falha nos erros HTTP, sem tabela, mas mostrando a mensagem:

$ curl -fsS https://archlinux.org/naoexiste
curl: (22) The requested URL returned error: 404
$ echo $?
22

Assim dá para escrever: curl -fsS https://meusite.com.br/ > /dev/null || echo "site fora do ar".

Seu IP público

O IP que aparece no ip a é o da rede local. Para saber com qual IP você aparece na internet, pergunte a um site: curl -s https://ifconfig.me/ip. A resposta é um único endereço, como 203.0.113.45 (exemplo ilustrativo: o da VM não foi publicado, por ser o endereço real da casa do autor). Pode vir em IPv6.

wget: baixar arquivos

O wget (de web get, "pegar da web") foi feito para baixar: ele sempre salva em arquivo, mostra o progresso e sabe retomar downloads. Não vem no Arch mínimo: instale com sudo pacman -S wget (na VM, versão 1.25.0).

wget
O programa.
-O arch.html
Opcional: o nome do arquivo salvo (O maiúsculo, ao contrário do curl). Sem ele, o wget usa o nome do endereço (index.html quando o endereço termina em /).
https://archlinux.org
O endereço.
$ wget -O arch.html https://archlinux.org
--2026-10-16 15:09:22--  https://archlinux.org/                                       « data, hora e endereço
Carregou certificado CA "/etc/ssl/certs/ca-certificates.crt"                         « os certificados confiáveis
Resolvendo archlinux.org (archlinux.org)... 209.126.35.79, 2604:cac0:a104:d::3        « o nome virou IP (DNS)
Conectando-se a archlinux.org (archlinux.org)|209.126.35.79|:443... conectado.        « porta 443 = https
A requisição HTTP foi enviada, aguardando resposta... 200 OK                          « o servidor respondeu "OK"
Tamanho: 25437 (25K) [text/html]
Salvando em: ‘arch.html’

arch.html           100%[===================>]  24,84K  --.-KB/s    em 0s

2026-10-16 15:09:23 (56,3 MB/s) - ‘arch.html’ salvo [25437/25437]                    « terminou: bytes salvos/total

Ao contrário do curl, o wget conta a história do download em português (o pacote traz a tradução): resolveu o nome, conectou, recebeu a resposta 200 OK, mostrou o tamanho e salvou. Esse download foi rápido demais para a velocidade aparecer na barra (--.-KB/s); o resumo final mostra a média, 56,3 MB/s. A barra [====>] cresce durante o download. Quando a saída não é um terminal (num script que grava um log, por exemplo), a barra vira uma linha de pontos: 0K .......... .......... .... 100% 103K=0,2s.

DNS: de nome para endereço

O DNS (Domain Name System) é a "agenda telefônica" da internet: traduz archlinux.org em 209.126.35.79. Toda vez que o ping, o curl ou o wget mostram "Resolvendo…", é o DNS trabalhando. Quando um site "não abre" mas o ping 1.1.1.1 funciona, quase sempre o culpado é o DNS.

getent: sempre disponível

O getent vem com a glibc, então existe em qualquer Arch. Ele resolve o nome do mesmo jeito que os programas resolvem, incluindo o arquivo /etc/hosts:

$ getent hosts archlinux.org
2604:cac0:a104:d::3 archlinux.org             « prefere o IPv6 quando existe
$ getent ahostsv4 archlinux.org
209.126.35.79   STREAM archlinux.org          « só IPv4
209.126.35.79   DGRAM
209.126.35.79   RAW

dig: perguntar ao DNS em detalhes

O dig (de domain information groper, "o que tateia informações de domínio") pergunta direto ao servidor de DNS e mostra a resposta completa. Comece pela forma curta, com +short:

$ dig +short archlinux.org
209.126.35.79

Sem o +short, a saída é longa, mas tem partes úteis:

$ dig archlinux.org

; <<>> DiG 9.20.29 <<>> archlinux.org                          « versão do dig e a pergunta
;; global options: +cmd
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 38234    « NOERROR: o nome existe
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1

;; OPT PSEUDOSECTION:
; EDNS: version: 0, flags:; udp: 65494
;; QUESTION SECTION:
;archlinux.org.			IN	A                              « a pergunta: qual o IPv4 (registro A)?

;; ANSWER SECTION:
archlinux.org.		1	IN	A	209.126.35.79                « a resposta

;; Query time: 2 msec
;; SERVER: 10.0.2.3#53(10.0.2.3) (UDP)                       « quem respondeu: o DNS do /etc/resolv.conf
;; WHEN: Fri Oct 16 15:01:58 -03 2026
;; MSG SIZE  rcvd: 58
ParteSignificado
status: NOERRORA pergunta foi respondida. NXDOMAIN = o nome não existe; SERVFAIL = o servidor de DNS falhou.
QUESTION SECTIONO que foi perguntado. A = endereço IPv4.
ANSWER SECTIONA resposta: nome, TTL (segundos que a resposta pode ficar guardada em cache; aqui, 1), classe IN (internet), tipo e valor.

SERVERQual servidor respondeu, na porta 53 (a do DNS). Na VM, o 10.0.2.3 do VirtualBox; em casa, normalmente o roteador.

Um nome inexistente não é erro para o dig (código 0); o problema aparece no status:

$ dig nada.invalid | grep status
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN, id: 45022

Tipos de registro e outro servidor

Além do endereço, o DNS guarda outras informações, cada uma num tipo de registro. Saídas reais:

$ dig +short AAAA archlinux.org
2604:cac0:a104:d::3
$ dig +short MX archlinux.org
10 mail.archlinux.org.
$ dig +short NS archlinux.org
oxygen.ns.hetzner.com.
hydrogen.ns.hetzner.com.
helium.ns.hetzner.de.
$ dig +short -x 1.1.1.1
one.one.one.one.
$ dig +short @1.1.1.1 archlinux.org
209.126.35.79
ComandoPergunta
dig +short archlinux.orgIPv4 (registro A, o padrão)
dig +short AAAA archlinux.orgIPv6
dig +short MX archlinux.orgServidor de e-mail (o número é a prioridade)
dig +short NS archlinux.orgOs servidores de DNS responsáveis pelo domínio
dig +short -x 1.1.1.1DNS reverso: o nome de um IP
dig +short @1.1.1.1 archlinux.orgPergunta a um servidor específico (aqui, o da Cloudflare)

Perguntar a outro servidor com @ é o teste clássico: se dig @1.1.1.1 nome responde e o dig nome normal não, o problema está no DNS configurado na sua máquina (veja NetworkManager e iwd).

nslookup e host

O mesmo pacote bind traz mais dois: o nslookup, antigo e que também existe no Windows, e o host, que responde em frases curtas:

$ nslookup archlinux.org
Server:		10.0.2.3
Address:	10.0.2.3#53

Non-authoritative answer:                    « veio de um cache, não do servidor "dono" do domínio
Name:	archlinux.org
Address: 209.126.35.79
Name:	archlinux.org
Address: 2604:cac0:a104:d::3
$ host archlinux.org
archlinux.org has address 209.126.35.79
archlinux.org has IPv6 address 2604:cac0:a104:d::3
archlinux.org mail is handled by 10 mail.archlinux.org.

drill: a alternativa do ldns

O drill funciona como o dig, com uma saída parecida, e vem num pacote bem menor (ldns, do repositório core):

;; flags: qr rd ra ; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 0
;; QUESTION SECTION:
;; archlinux.org.	IN	A

;; ANSWER SECTION:
archlinux.org.	43	IN	A	209.126.35.79

;; AUTHORITY SECTION:

;; ADDITIONAL SECTION:

;; Query time: 1 msec
;; SERVER: 10.0.2.3

O drill não tem o +short; para outro tipo ou outro servidor, a ordem é a mesma do dig: drill MX archlinux.org, drill @1.1.1.1 archlinux.org.

Experimente

O terminal simulado não acessa a internet (o curl e o wget respondem com um aviso do simulador), mas o pacman dele conhece os pacotes reais. Use-o para descobrir e instalar as ferramentas.

Missão 1: o comando dig não existe. Descubra com o pacman qual pacote do repositório traz o arquivo usr/bin/dig.

Missão 2: instale o pacote que traz o dig, o host e o nslookup. Confira a lista de dependências e o tamanho antes de responder S. (A senha da ana é ana.)

Missão 3: mostre as informações do pacote curl instalado e encontre, na linha "Necessário para", o motivo de ele existir em todo Arch.

Quando não funciona

curl: (6) Could not resolve host 
$ curl https://nada.invalid/
curl: (6) Could not resolve host: nada.invalid
$ echo $?
6

O que aconteceu: o DNS não achou o nome. Erro de digitação, ou DNS sem resposta.

Como confirmar: getent hosts nada.invalid volta vazio (código 2); teste o mesmo nome com dig @1.1.1.1. No wget, o mesmo problema aparece como não foi possível resolver endereço de máquina (código 4).

curl: (7) Could not connect to server 
$ curl http://127.0.0.1:8080/
curl: (7) Failed to connect to 127.0.0.1:8080 after 0 ms: Could not connect to server
$ echo $?
7

O que aconteceu: a máquina existe, mas nada escuta naquela porta. O serviço está parado ou usa outra porta.

Como confirmar: ss -tln mostra as portas abertas (veja ip, ping, ss); systemctl status nginx mostra se o serviço está rodando (veja systemctl e Serviços).

curl: (28) Connection timed out 
$ curl -m 2 http://192.0.2.1/
curl: (28) Connection timed out after 2005 milliseconds
$ echo $?
28

O que aconteceu: ninguém respondeu dentro do tempo (aqui, 2 segundos, pelo -m 2). Máquina desligada, IP errado ou um firewall descartando os pacotes.

O 404 "passou" no script

O que aconteceu: sem -f, o curl devolve 0 mesmo quando o site responde 404 ou 500 (veja o exemplo com PIPESTATUS acima).

Como resolver: use curl -fsS; aí o código vira 22 e o || do script funciona.

"dig: comando não encontrado" (ou wget, ou nslookup) 
$ dig +short archlinux.org
bash: dig: comando não encontrado

O que aconteceu: no Arch, o dig, o host e o nslookup vêm no pacote bind, e o wget no pacote wget; nenhum vem no base.

Como resolver: sudo pacman -S bind (ou wget). Enquanto isso, getent hosts nome resolve nomes e curl -O URL baixa arquivos sem instalar nada. Para qualquer comando que falte, pacman -F comando diz o pacote (rode sudo pacman -Fy uma vez antes, para baixar a lista de arquivos).

curl: (60) SSL certificate problem

O que aconteceu: o certificado do site não é confiável: vencido, para outro nome, autoassinado, ou o relógio do seu computador está errado. No Arch, a última causa é comum logo depois da instalação, porque o NTP vem desligado.

Como confirmar: timedatectl; se a hora estiver errada e NTP service: inactive, ligue com sudo timedatectl set-ntp true. Não "resolva" com curl -k (ignora a segurança).

CódigoSignificado

Resumo

  • O curl vem em todo Arch (o pacman depende dele); wget (wget), dig/host/nslookup (bind) e drill (ldns) são instalados à parte. pacman -F descobre o pacote.
  • curl -I mostra o cabeçalho; -L segue redirecionamentos; -o/-O salvam; -s silencia.
  • Em scripts: curl -fsS e o código de saída (6 DNS, 7 conexão, 22 erro HTTP, 28 tempo).
  • wget baixa e fala português; -c retoma; os erros dão código 4 (rede) ou 8 (servidor).
  • getent hosts resolve sem instalar nada; dig +short nome pergunta ao DNS; @1.1.1.1 testa outro servidor.

Na Arch Wiki: o cURL e o Wget têm páginas próprias, com as opções e a configuração (~/.wgetrc, proxy); as ferramentas de DNS (dig, drill, getent) e a ordem em que o sistema resolve os nomes estão em Domain name resolution; o pacote bind como servidor, em BIND; e o pacman -F, em pacman: Search for a package that contains a specific file (pacman em português).
