Arch sudo, root e Usuários

No Linux, um usuário pode tudo: o root. Os outros, como a Ana, só mexem no que é deles. Para instalar programas ou mudar o sistema, a Ana pede emprestado o poder do root por um instante, com o sudo. No Arch, nada disso vem pronto: você instala o sudo, cria o usuário e decide quem pode usá-lo. Esta aula mostra cada peça, com as mensagens reais.

Você vai aprender
  • A diferença entre o root e um usuário comum, e por que não usar o root no dia a dia.
  • O grupo wheel e a linha do /etc/sudoers que libera o sudo, editada com o visudo.
  • Usar o sudo: a senha, as tentativas erradas, os 5 minutos, sudo -i, -s, -l e -k.
  • A diferença entre su e su -.
  • Criar um usuário com useradd e definir a senha com passwd.

root × usuária comum

Pense num prédio. O síndico tem a chave mestra: abre qualquer apartamento, a casa de máquinas, o quadro de luz. Cada morador tem só a chave do próprio apartamento. No Linux, o síndico é o root (número de usuário 0) e a Ana é uma moradora (número 1000).

$ whoami
ana
$ id
uid=1000(ana) gid=1000(ana) grupos=1000(ana),998(wheel)    « uid 1000; grupos ana e wheel
$ ls /root
ls: não foi possível abrir o diretório '/root': Permissão negada   « a casa do root
$ cat /etc/shadow
cat: /etc/shadow: Permissão negada      « onde ficam as senhas (embaralhadas)
$ ls -l /etc/shadow /etc/sudoers
-rw------- 1 root root  748 16 out 13:50 /etc/shadow
-r--r----- 1 root root 5029 16 out 12:10 /etc/sudoers

As permissões no começo de cada linha (-rw-------) dizem que só o dono, o root, lê esses arquivos (veja Permissões). A Ana não precisa disso no dia a dia, e é melhor assim.

rootana
Número (uid)01000
Pasta pessoal/root/home/ana
Prompt[root@notebook ~]#[ana@notebook ~]$
PodeTudo: instalar, apagar o sistema, ler senhasSó os próprios arquivos
Um erro de digitaçãoPode destruir o sistemaEstraga, no máximo, os arquivos dela
Não use o root como conta do dia a dia

Como root, um rm com um espaço no lugar errado apaga o sistema, e um programa com defeito (ou malicioso) pode fazer o mesmo. Use uma conta comum e peça o poder do root só para o comando que precisa: é o que o sudo faz.

O grupo wheel e o /etc/sudoers

O sudo (de superuser do, "o superusuário faz") consulta um arquivo de regras, o /etc/sudoers, para saber quem pode virar root. No Arch, o costume é liberar um grupo, o wheel, e colocar nele quem administra a máquina. O nome vem da gíria inglesa big wheel ("figurão").

Na instalação da VM, a Ana foi criada já dentro do wheel, e a linha do grupo estava comentada (desligada) no sudoers. Trecho real do log de instalação:

#> arch-chroot /mnt useradd -m -G wheel -s /bin/bash ana
#> arch-chroot /mnt id ana
uid=1000(ana) gid=1000(ana) groups=1000(ana),998(wheel)     « o live fala inglês
#> grep -n "wheel" /mnt/etc/sudoers
124:## Uncomment to allow members of group wheel to execute any command
125:# %wheel ALL=(ALL:ALL) ALL                « o # no começo desliga a linha
128:# %wheel ALL=(ALL:ALL) NOPASSWD: ALL
#> grep -n "^%wheel" /mnt/etc/sudoers; arch-chroot /mnt visudo -c
125:%wheel ALL=(ALL:ALL) ALL                   « depois de editar com o visudo: ligada
/etc/sudoers: parsed OK

A linha liberada, parte por parte:

%wheel
Quem: o % indica um grupo, então "todos os membros do grupo wheel". Sem %, seria um usuário (ana).
ALL=
Em quais máquinas a regra vale (útil quando o mesmo arquivo é usado em várias). ALL = em qualquer uma.
(ALL:ALL)
Como quem podem rodar comandos: qualquer usuário e qualquer grupo (normalmente, o root).
ALL
Quais comandos: todos.

Logo abaixo, a linha 128 tem a mesma regra com NOPASSWD:, que dispensa a senha. Ela fica comentada, e é melhor assim: sem senha, qualquer programa rodando como a Ana vira root sem você saber. Hoje, no sistema instalado:

$ getent group wheel
wheel:x:998:ana                        « o grupo 998 tem um membro: a ana

visudo: o único jeito certo de editar o sudoers

Um erro de digitação no /etc/sudoers pode deixar todo mundo sem sudo, inclusive você. Por isso ele não se edita com um editor comum: usa-se o visudo, que trava o arquivo, abre uma cópia, confere a sintaxe ao salvar e só então troca o arquivo de verdade.

No Arch, a primeira tentativa costuma dar este erro real:

#> visudo
visudo: nenhum editor encontrado (caminho do editor = /usr/bin/vi)

O visudo procura o vi, e o Arch não o instala (nem o pacote vim cria o comando vi). A solução é dizer qual editor usar na variável EDITOR:

sudo
Roda como root.
EDITOR=nano
Define o editor só para este comando. O sudoers do Arch deixa essa variável passar para o visudo (linha Defaults!/usr/bin/visudo env_keep += "SUDO_EDITOR EDITOR VISUAL").
visudo
Abre o /etc/sudoers com segurança.
sudo EDITOR=nano visudo

Ao salvar e sair, se não houver erro, o visudo não diz nada; se você não mudou nada, ele avisa visudo: /etc/sudoers.tmp sem alteração. Para só conferir o arquivo, sem abrir:

#> visudo -c
/etc/sudoers: análise OK               « -c = check: sintaxe correta
#> echo $?
0
Prefira um arquivo em /etc/sudoers.d/

A última linha do sudoers do Arch é @includedir /etc/sudoers.d: todo arquivo dessa pasta também vale. Em vez de mexer no arquivo principal, crie um arquivo seu: sudo EDITOR=nano visudo -f /etc/sudoers.d/10-wheel com a linha %wheel ALL=(ALL:ALL) ALL. Atualizações do pacote sudo nunca mexem nele.

Usando o sudo

sudo
"Rode o que vem a seguir como root." Pede a sua senha (não a do root).
pacman -Q bash
O comando a ser rodado, exatamente como você o escreveria.

A primeira vez

Na primeira vez que um usuário usa o sudo, ele recebe um pequeno sermão, e depois o pedido de senha:

$ sudo pacman -Q bash

Presumimos que você recebeu as instruções de sempre do administrador
de sistema local. Basicamente, resume-se a estas três coisas:

    #1) Respeite a privacidade dos outros.
    #2) Pense antes de digitar.
    #3) Com grandes poderes vêm grandes responsabilidades.

Por motivos de segurança, a senha que você digitar não será visível.

[sudo] senha para ana:                  « a senha da ana; nada aparece enquanto ela digita
bash 5.3.20-1
$ echo $?
0
$ sudo whoami
root                                   « não pediu senha de novo: vale por 5 minutos

O sermão aparece uma vez só por usuário. A partir daí, cada sudo mostra só a linha [sudo] senha para ana:. Depois de acertar, o sudo confia na Ana por 5 minutos naquele terminal; em outra janela ou aba, ele pergunta de novo.

Senha errada

$ sudo pacman -Q bash
[sudo] senha para ana:
Sinto muito, tente novamente.
[sudo] senha para ana:
Sinto muito, tente novamente.
[sudo] senha para ana:
sudo: 3 tentativas de senha incorreta   « desistiu: o comando não foi rodado
$ echo $?
1
Depois de três erros, até a senha certa falha por 10 minutos

O Arch vem com o pam_faillock: três senhas erradas em 15 minutos bloqueiam a conta por 10 minutos, e durante o bloqueio a senha correta também recebe Sinto muito, tente novamente., sem nenhum aviso. Isso foi conferido na VM. Os valores padrão estão comentados em /etc/security/faillock.conf (# deny = 3, # fail_interval = 900, # unlock_time = 600). Espere os 10 minutos ou, como root, rode faillock --user ana --reset.

Ver o que você pode: sudo -l

$ sudo -l
[sudo] senha para ana:
Entradas de Defaults correspondentes a ana em notebook:
    secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/bin

Padrão específico de comandos e "runas" de ana:
    Defaults!/usr/bin/visudo env_keep+="SUDO_EDITOR EDITOR VISUAL"

Usuário ana pode executar os seguintes comandos em notebook:
    (ALL : ALL) ALL                    « a regra do grupo wheel: tudo

O -l (list) mostra as regras que valem para você. O secure_path é o PATH usado pelos comandos do sudo: ele ignora o PATH da Ana, para que um programa falso na pasta dela não seja rodado como root.

Um shell de root: sudo -i e sudo -s

Para vários comandos seguidos como root, abra um shell de root. Há duas formas:

$ sudo -i
[sudo] senha para ana:
#> whoami; pwd; echo $HOME
root
/root                                  « -i: login completo, vai para a casa do root
/root
#> exit
sair                                   « o Bash em português escreve "sair" ao fechar
$ sudo -s
[sudo] senha para ana:
#> whoami; pwd; echo $HOME
root
/home/ana                              « -s: continua na pasta onde estava
/root
#> exit
exit
FormaPastaAmbienteUse para
sudo -i/rootO de um login do root (lê os arquivos de login dele)Uma sessão de administração "limpa"; os comandos # da Wiki
sudo -sContinua onde estavaUm shell de root, mantendo boa parte do ambienteTrabalhar como root na pasta atual

Nos dois casos, exit (ou Ctrl+D) volta para a Ana. Não fique como root mais do que precisa.

Esquecer a senha: sudo -k

$ sudo true
[sudo] senha para ana:
$ sudo -k                              « -k = kill: esquece a senha agora
$ sudo whoami
[sudo] senha para ana:                 « perguntou de novo
root

Útil antes de sair de perto do computador, ou para testar se a senha ainda está pedindo.

O sudo e o redirecionamento

Uma armadilha clássica: gravar num arquivo do sistema com >.

$ sudo echo teste > /etc/a1-teste.conf
bash: /etc/a1-teste.conf: Permissão negada
$ echo $?
1

Por quê, se tem sudo? Porque quem abre o arquivo para o > é o shell da Ana, antes mesmo de rodar o sudo. Só o echo virou root. Repare que nem a senha foi pedida. As saídas: usar o tee (que abre o arquivo ele mesmo) com sudo, ou abrir um shell de root com sudo -i.

echo teste | sudo tee /etc/arquivo.conf

O tee grava no arquivo e também mostra o texto na tela. Para acrescentar no fim do arquivo em vez de trocar o conteúdo, use sudo tee -a.

Missão: descubra quem o sudo faz você ser: rode sudo whoami e digite a senha ana (no simulador) quando ele pedir. Depois rode whoami sem sudo e compare.

Missão: abra um shell de root com sudo -i, repare no prompt [root@notebook ~]# e confira a pasta com pwd. Para voltar a ser a Ana, digite exit.

su e su -

O su (substitute user, "trocar de usuário") é mais antigo que o sudo. A diferença principal: ele pede a senha do usuário de destino. Para virar root com su, você precisa da senha do root.

ComandoPede a senha dePasta e ambiente
surootFica na pasta atual e mantém boa parte das variáveis da Ana
su - (ou su -l)rootLogin completo: vai para /root, ambiente limpo
su - brunobrunoLogin completo como o usuário bruno
sudo -ia suaComo o su -, mas autorizado pelo sudoers

Sem a senha certa:

$ su -
Senha:                                 « a senha do ROOT, não a da ana
su: Falha de autenticação
$ echo $?
1

Se você definiu uma senha para o root na instalação (o passwd da aula Configurar o Sistema), o su - funciona com ela. Se não definiu, a conta do root fica sem senha válida e só se chega a ela pelo sudo; muita gente prefere assim. Seja como for, prefira o su - ao su: o "meio root" do su sem hífen, com as variáveis da Ana, causa confusões difíceis de entender.

Criar um usuário

Vamos criar um usuário para o Bruno, que também vai administrar a máquina.

sudo
Criar usuários é tarefa de root.
useradd
O programa que cria contas.
-m
Make home: cria a pasta pessoal /home/bruno. Sem ele, o usuário fica sem pasta.
-G wheel
Grupos extras: coloca o Bruno no wheel (pode usar sudo). Para vários, separe com vírgula: -G wheel,audio.
-s /bin/bash
O shell de login. No Arch, o padrão do useradd já é o Bash, mas é bom deixar explícito.
bruno
O nome do usuário: minúsculas, sem espaços nem acentos.

Num shell de root (sudo -i):

#> useradd -m -G wheel -s /bin/bash bruno
#> echo $?
0                                      « nenhuma mensagem: deu certo
#> id bruno
uid=1001(bruno) gid=1001(bruno) grupos=1001(bruno),998(wheel)   « o próximo número livre: 1001
#> ls -ld /home/ana /home/bruno
drwx------ 16 ana   ana   4096 16 out 13:28 /home/ana
drwx------  2 bruno bruno 4096 16 out 13:29 /home/bruno       « modo 700: só o dono entra
#> ls -la /home/bruno
total 20
drwx------ 2 bruno bruno 4096 16 out 13:29 .
drwxr-xr-x 4 root  root  4096 16 out 13:29 ..
-rw-r--r-- 1 bruno bruno   21 15 set 16:47 .bash_logout
-rw-r--r-- 1 bruno bruno   57 15 set 16:47 .bash_profile
-rw-r--r-- 1 bruno bruno  172 15 set 16:47 .bashrc

Fora do shell de root, a mesma coisa seria sudo useradd -m -G wheel -s /bin/bash bruno. Três coisas para notar. O useradd não diz nada quando dá certo (código 0). No Arch, a pasta pessoal nasce com modo 700 (drwx------): nem os outros usuários conseguem listar o que há dentro (o Debian e o Ubuntu usam 750 ou 755). E os três arquivos vieram do modelo em /etc/skel, por isso têm data de setembro, a do pacote bash.

A senha: passwd

O usuário recém-criado ainda não tem senha e não consegue entrar. Como root, defina uma (de fora do shell de root: sudo passwd bruno):

#> passwd bruno
Nova senha:                            « nada aparece enquanto você digita
Redigite a nova senha:
passwd: senha atualizada com sucesso

Se as duas digitações não baterem:

#> passwd bruno
Nova senha:
Redigite a nova senha:
As senhas não são iguais.
passwd : Falha na verificação preliminar por serviço de senha
passwd: senha inalterada
#> echo $?
10

Cada usuário troca a própria senha com passwd, sem nome e sem sudo; aí ele pede antes a senha atual:

$ passwd
Mudando senha para ana.
Atual senha:
Nova senha:
Redigite a nova senha:
passwd: senha atualizada com sucesso

Errando a senha atual, nada muda:

$ passwd
Mudando senha para ana.
Atual senha:
passwd : Falha de autenticação
passwd: senha inalterada
Entrar no grupo depois

Se o usuário já existe, acrescente um grupo com sudo usermod -aG wheel bruno. O -a (append) é essencial: sem ele, o -G substitui todos os grupos extras do usuário. A mudança só vale no próximo login dele. Remover um usuário e a pasta dele: sudo userdel -r bruno (o aviso spool de mail … não foi encontrado é normal no Arch). Usuários e grupos a fundo estão em Usuários e Grupos.

Qual usar?

Use o sudo: é o que a Wiki, os fóruns e este guia assumem, e o sudo -i resolve quando você precisa de vários comandos seguidos. Mantenha o su - (com senha no root) como plano B: se um dia você quebrar o sudoers, ele ainda funciona. run0, doas e sudo-rs são alternativas para quem já domina o básico.

Quando não funciona

"bruno não está no arquivo sudoers." 
$ sudo pacman -Q bash
…                                      « o sermão da primeira vez (omitido)
[sudo] senha para bruno:
bruno não está no arquivo sudoers.
$ echo $?
1

Causa: o usuário não está no grupo wheel, ou a linha %wheel do sudoers está comentada. A senha estava certa; o que faltou foi permissão.

Como confirmar: id bruno (aparece 998(wheel)?) e sudo grep -n '^%wheel' /etc/sudoers (com outro usuário que tenha sudo).

Como resolver: com um usuário que já tenha sudo (ou com su -), rode usermod -aG wheel bruno; o Bruno precisa sair e entrar de novo. Se a linha estiver comentada, descomente com o visudo. Versões antigas do sudo acrescentavam "Este incidente será relatado"; a de 2026 não diz mais isso, mas a tentativa fica registrada no journal.

"Sinto muito, tente novamente." (com a senha certa)

Causa: ou a senha estava errada de verdade (teclado em outro layout? Caps Lock?), ou a conta está bloqueada pelo faillock depois de três erros.

Como confirmar: como root, faillock --user ana lista as tentativas recentes.

Como resolver: espere 10 minutos ou, como root, faillock --user ana --reset.

"visudo: nenhum editor encontrado" 
#> visudo
visudo: nenhum editor encontrado (caminho do editor = /usr/bin/vi)

Causa: o vi não vem instalado no Arch.

Como resolver: sudo EDITOR=nano visudo (ou EDITOR=vim). Para não precisar repetir, ponha export EDITOR=nano no seu ~/.bash_profile.

"Permissão negada" mesmo com sudo 
$ sudo echo teste > /etc/a1-teste.conf
bash: /etc/a1-teste.conf: Permissão negada

Causa: o redirecionamento > é feito pelo seu shell, sem privilégios.

Como resolver: echo teste | sudo tee /etc/arquivo ou um shell de root (sudo -i).

"sudo: um terminal é necessário para ler a senha"

A mensagem real completa: sudo: um terminal é necessário para ler a senha; use a opção -S para ler a entrada padrão ou configure um auxiliar de askpass, seguida de sudo: uma senha é necessária.

Causa: o sudo foi chamado sem terminal (num script rodado por um serviço, por exemplo) e não tem como perguntar a senha.

Como resolver: rode o script a partir de um terminal, ou rode o script inteiro como root (por um serviço do systemd, por exemplo; veja Timers). Evite o NOPASSWD como atalho.

"bash: sudo: comando não encontrado"

Causa: o pacote sudo não foi instalado: ele não faz parte do base.

Como resolver: entre como root (no login do console ou com su -), rode pacman -S sudo e libere o wheel com o visudo. Na VM, o sudo foi instalado já no pacstrap (veja Espelhos e pacstrap).

"sudo: uma senha é necessária" com -n 
$ sudo -n true
sudo: uma senha é necessária
$ echo $?
1

Causa: o -n (non-interactive) proíbe o sudo de perguntar a senha; se ela não está guardada dos últimos 5 minutos, ele falha. É usado em scripts para testar "já tenho sudo?".

2. Em %wheel ALL=(ALL:ALL) ALL, o que significa o %?

3. O visudo respondeu nenhum editor encontrado (caminho do editor = /usr/bin/vi). O que fazer?

4. Por que sudo echo x > /etc/arquivo dá "Permissão negada"?

5. A Ana errou a senha do sudo três vezes e agora até a senha certa é recusada. Por quê?

sudo usermod audio carla

Resumo

  • root (uid 0) pode tudo; use uma conta comum e o sudo só quando precisar.
  • No Arch, quem está no grupo wheel usa o sudo se a linha %wheel ALL=(ALL:ALL) ALL estiver ligada no /etc/sudoers.
  • Edite o sudoers só com sudo EDITOR=nano visudo (o vi não vem instalado); prefira arquivos em /etc/sudoers.d/.
  • O sudo pede a sua senha, sem mostrá-la, e a guarda por 5 minutos naquele terminal; três erros bloqueiam a conta por 10 minutos.
  • sudo -i e su - abrem um shell de root com login; su pede a senha do root.
  • useradd -m -G wheel -s /bin/bash nome + passwd nome; a pasta nasce com modo 700.

Na Arch Wiki: o sudo está em Sudo (em português, tradução antiga); usuários e grupos, em Users and groups (em português); o su, em su; as alternativas, em doas e run0; e o bloqueio por senhas erradas, em Security — Lock out user after three failed login attempts.
