Discos: lsblk, df e du

Antes de montar um disco novo, mexer no fstab ou descobrir por que o espaço acabou, você precisa enxergar os discos: quais existem, como estão divididos, que sistema de arquivos cada parte usa, onde ela aparece nas pastas e quanto espaço sobra. Esta aula mostra as ferramentas que respondem a cada uma dessas perguntas, todas com a saída real do Arch da ana.

Você vai aprender
  • O que são disco, partição, sistema de arquivos e ponto de montagem, e como o Linux dá nome a eles (sda, nvme0n1p2…).
  • Ler o lsblk (com -f e -o), o blkid e o fdisk -l.
  • Ver o espaço livre com df -h e o que ocupa espaço com du -sh.
  • Ver o que está montado onde com findmnt.
  • Saber se o seu SSD aceita TRIM e ligar o fstrim.timer, que no Arch vem desligado.

Disco, partição, sistema de arquivos e montagem

Pense num armário:

  • O disco (SSD, HD, pendrive) é o armário inteiro.
  • As partições são as gavetas: pedaços do disco separados por uma tabela (no Arch moderno, a tabela GPT). Você criou as da ana em Particionar o Disco.
  • O sistema de arquivos (ext4, FAT32, Btrfs…) é o jeito de organizar o que vai dentro de cada gaveta: pastas, nomes, permissões. Ele é criado ao formatar.
  • A montagem é pendurar a gaveta numa pasta. No Linux não existe "C:" nem "D:": tudo fica numa árvore só, que começa em /, e cada partição aparece numa pasta dela (o ponto de montagem).

Os nomes dos discos no Linux

Cada disco e cada partição vira um arquivo especial dentro de /dev (de devices, dispositivos). O nome conta que tipo de aparelho é:

NomeO que éPartições
/dev/sda, sdb…Disco SATA, SCSI ou USB (scsi disk, a = o primeiro)sda1, sda2…
/dev/nvme0n1SSD NVMe (controladora 0, namespace 1)nvme0n1p1, nvme0n1p2… (com p)
/dev/mmcblk0Cartão SD ou memória eMMCmmcblk0p1…
/dev/sr0Leitor de CD/DVD (SCSI ROM)—
/dev/loop0Um arquivo usado como se fosse um disco (a ISO no ambiente live, por exemplo)—
/dev/zram0Um disco feito de memória RAM comprimida (veja Swap e zram)—
A letra pode mudar

O sda de hoje pode virar sdb amanhã, se você ligar um pendrive antes de ligar o computador ou trocar o cabo de porta. Por isso o /etc/fstab do Arch não usa esses nomes, e sim o UUID de cada partição (você vai ver logo abaixo e em mount e fstab).

lsblk: a árvore dos discos

lsblk
list block devices: lista os "dispositivos de bloco", que são os discos, as partições e tudo o que funciona como um disco. Não precisa de root.
$ lsblk
NAME   MAJ:MIN RM  SIZE RO TYPE MOUNTPOINTS
sda      8:0    0   30G  0 disk                  « o disco inteiro: 30 GiB
├─sda1   8:1    0    1G  0 part /boot            « partição EFI
├─sda2   8:2    0    4G  0 part [SWAP]           « swap: não é montada numa pasta
└─sda3   8:3    0   25G  0 part /                « a raiz do sistema
sr0     11:0    1 1024M  1 rom                   « o leitor de CD da máquina virtual

Os traços ├─ e └─ mostram quem está dentro de quem: as três partições estão dentro do disco sda. As colunas:

ColunaSignificaNa ana
NAMENome em /devsda3 = /dev/sda3
MAJ:MINNúmeros internos do kernel (tipo de driver : número do aparelho)Raramente importa
RMRemovable: 1 se é removívelO CD (sr0) é 1
SIZETamanho (em GiB, MiB…)30G, 1G, 4G, 25G
RORead only: 1 se é só leituraO CD é 1
TYPEdisk, part (partição), rom, loop, crypt, lvm…—
MOUNTPOINTSOnde está montado (vazio = não está montado)/, /boot, [SWAP]

Compare com o que você montou à mão na instalação: sda1 em /boot, sda2 como swap e sda3 em /. É o mesmo desenho, agora visto de dentro do sistema instalado.

O UUID da FAT32 é curto (C509-6CB1) porque esse formato antigo só guarda 8 dígitos. No ext4 e na swap ele tem 36 caracteres. Os mesmos UUIDs apareceram na tela quando você formatou (mkswap mostrou UUID=02576132-… e o mkfs.ext4 mostrou Filesystem UUID: 75d167c8-…), e são eles que o genfstab -U escreveu no /etc/fstab.

blkid: os identificadores, direto da fonte

O blkid (block id) lê o começo de cada partição e mostra o tipo e os identificadores. É o comando clássico para copiar um UUID.

A pegadinha: sem root, ele não mostra nada

$ blkid
$ echo $?
0

Nenhuma linha, nenhum erro e código 0. Como usuário comum, o blkid só consegue ler o próprio cache, que no Arch começa vazio; ele não tem permissão para abrir /dev/sda3. Não é que o disco não tenha UUID: falta o sudo.

$ sudo blkid
/dev/sda2: UUID="02576132-0458-4975-916f-94e08af9a31c" TYPE="swap" PARTUUID="70da2fa4-d42b-4f7b-916b-1385531205b8"
/dev/sda3: UUID="75d167c8-1dad-4d0a-a0ae-b063058a18e9" BLOCK_SIZE="4096" TYPE="ext4" PARTUUID="431c3f9d-d4b9-4e4d-b16a-d5399a4aee27"
/dev/sda1: UUID="C509-6CB1" BLOCK_SIZE="512" TYPE="vfat" PARTUUID="42528876-2401-45ed-aa76-555fea61a03e"

Para pegar só o valor (útil em scripts e para colar no fstab):

-s UUID
show: mostra só esta etiqueta.
-o value
output: só o valor, sem UUID="…".
/dev/sda3
A partição.
$ sudo blkid -s UUID -o value /dev/sda3
75d167c8-1dad-4d0a-a0ae-b063058a18e9
Sem sudo: as pastas /dev/disk/by-*

O Linux também cria atalhos com esses nomes. Qualquer usuário pode listá-los, e é assim que o sistema acha a partição certa no boot:

$ ls -l /dev/disk/by-uuid/
total 0
lrwxrwxrwx 1 root root 10 16 out 13:06 02576132-0458-4975-916f-94e08af9a31c -> ../../sda2
lrwxrwxrwx 1 root root 10 16 out 13:06 75d167c8-1dad-4d0a-a0ae-b063058a18e9 -> ../../sda3
lrwxrwxrwx 1 root root 10 16 out 13:06 C509-6CB1 -> ../../sda1

Também existem /dev/disk/by-partuuid/, by-label/ (só quando há rótulos) e by-id/ (pelo modelo e número de série).

fdisk -l: a tabela de partições

O fdisk é o programa que você usou para particionar. Com -l (list) ele só mostra a tabela, sem mudar nada. Precisa de root.

$ sudo fdisk -l
Disco /dev/sda: 30 GiB, 32212254720 bytes, 62914560 setores
Modelo de disco: VBOX HARDDISK                       « o "modelo" do disco virtual do VirtualBox
Unidades: setor de 1 * 512 = 512 bytes
Tamanho de setor (lógico/físico): 512 bytes / 512 bytes
Tamanho E/S (mínimo/ótimo): 512 bytes / 512 bytes
Tipo de rótulo do disco: gpt                         « a tabela é GPT
Identificador do disco: B4ACDE31-D734-4B75-BD81-9A429F7F3949

Dispositivo   Início      Fim  Setores Tamanho Tipo
/dev/sda1       2048  2099199  2097152      1G Sistema EFI
/dev/sda2    2099200 10487807  8388608      4G Linux swap
/dev/sda3   10487808 62912511 52424704     25G Linux sistema de arquivos

Início e Fim são posições em setores de 512 bytes. A primeira partição começa no setor 2048 (1 MiB do começo do disco), o alinhamento padrão que deixa SSDs mais rápidos. A coluna Tipo é o tipo da partição na tabela GPT (que você escolheu no fdisk com o comando t), e não o sistema de arquivos que está dentro dela.

fdisk sem -l edita o disco

fdisk /dev/sda (sem -l) abre o editor de partições. Nada é gravado até você digitar w, mas não brinque com ele no disco em uso. Para só olhar, sempre fdisk -l ou lsblk.

df: quanto espaço sobra

df
disk free: espaço livre de cada sistema de arquivos montado.
-h
human-readable: tamanhos em K, M, G em vez de blocos de 1 KiB.
$ df -h
Sist. Arq.      Tam. Usado Disp. Uso% Montado em
/dev/sda3        25G  4,9G   19G  22% /                       « o que interessa: a raiz
devtmpfs        1,9G     0  1,9G   0% /dev
tmpfs           1,9G     0  1,9G   0% /dev/shm
efivarfs        256K   12K  240K   5% /sys/firmware/efi/efivars
tmpfs           778M  596K  778M   1% /run
none            1,0M     0  1,0M   0% /run/credentials/systemd-journald.service
tmpfs           1,9G  4,0K  1,9G   1% /tmp                    « /tmp fica na memória
/dev/sda1      1022M   93M  930M  10% /boot                   « a partição EFI
none            1,0M     0  1,0M   0% /run/credentials/getty@tty1.service
tmpfs           389M  4,0K  389M   1% /run/user/1000
tmpfs           389M  4,0K  389M   1% /run/user/0

Muita coisa ali não é disco. tmpfs e devtmpfs são sistemas de arquivos na memória RAM (somem ao desligar); efivarfs são as variáveis da placa-mãe UEFI. No Arch, o /tmp é um tmpfs: o que você grava lá vai para a RAM e desaparece no próximo boot. Os discos de verdade são as linhas que começam com /dev/.

ColunaSignifica
Sist. Arq.De onde vem (partição ou tipo virtual)
Tam. / Usado / Disp.Tamanho total, usado e disponível para você
Uso%Porcentagem usada. Acima de 90% é hora de limpar
Montado emA pasta onde ele aparece
Por que 4,9G + 19G não dá 25G?

O ext4 reserva 5% do espaço para o root, para que o sistema continue funcionando (logs, pacman) mesmo quando um usuário enche o disco. 5% de 25G são cerca de 1,2G: é a diferença que "sumiu". Essa reserva não aparece em Disp..

Formas mais úteis do df

$ df -h /
Sist. Arq.      Tam. Usado Disp. Uso% Montado em
/dev/sda3        25G  4,9G   19G  22% /
$ df -h /home/ana/Downloads
Sist. Arq.      Tam. Usado Disp. Uso% Montado em
/dev/sda3        25G  4,9G   19G  22% /
$ df -hT -x tmpfs -x devtmpfs -x efivarfs
Sist. Arq.     Tipo  Tam. Usado Disp. Uso% Montado em
/dev/sda3      ext4   25G  4,9G   19G  22% /
/dev/sda1      vfat 1022M   93M  930M  10% /boot
  • df -h /: só o sistema de arquivos da raiz.
  • df -h /home/ana/Downloads: o df aceita qualquer pasta e responde em que partição ela está. Na ana, tudo fica em /dev/sda3, porque não existe uma partição separada para /home.
  • -T acrescenta a coluna Tipo; cada -x tipo esconde um tipo (exclude). Resultado: só os discos de verdade.

df -i: quando "acaba o espaço" com o disco vazio

$ df -i /
Sist. Arq.        Inós IUsado  ILivre IUso% Montado em
/dev/sda3      1638400 130554 1507846    8% /

Cada arquivo gasta um inode (a ficha que guarda dono, permissões e onde estão os dados). O ext4 cria um número fixo deles na formatação: na ana, 1.638.400 (o mesmo "1638400 inodes" que o mkfs.ext4 mostrou). Milhões de arquivos minúsculos podem esgotar os inodes antes do espaço, e aí aparece Não há espaço disponível no dispositivo com o df -h mostrando espaço livre.

Missão: mostre quanto espaço livre existe na raiz (/), com os tamanhos em G e M.

du: o que está ocupando espaço

O df diz quanto está ocupado; o du diz quem ocupa.

du
disk usage: soma o espaço usado por pastas e arquivos.
-s
summarize: um total por argumento, sem listar cada subpasta.
-h
Tamanhos legíveis.
~/aur
A pasta a medir.
$ du -sh ~/aur
61M	/home/ana/aur
$ du -sh ~/aur/*
932K	/home/ana/aur/downgrade
25M	/home/ana/aur/paru-bin
35M	/home/ana/aur/yay-bin

O ~/aur/* vira os nomes das três pastas, e o du soma cada uma. São as pastas onde a ana compilou programas do AUR (veja makepkg): os pacotes prontos que ficaram lá dentro ocupam a maior parte.

Ordenar do menor para o maior

$ du -h --max-depth=1 ~/aur | sort -h
932K	/home/ana/aur/downgrade
25M	/home/ana/aur/paru-bin
35M	/home/ana/aur/yay-bin
61M	/home/ana/aur

--max-depth=1 mostra um nível de subpastas mais o total; o sort -h entende os sufixos K, M e G (um sort -n comum colocaria 932K depois de 61M). Os maiores ficam no fim, perto do prompt, onde você vai ler.

Não rode du em / inteiro

du -sh / percorre todos os arquivos do sistema, pode levar minutos e deixa o computador lento. Comece pelas suspeitas de sempre: /var/cache/pacman/pkg, /var/log/journal, ~/.cache, ~/Downloads. Se quiser explorar com setas, o pacote ncdu faz isso de forma interativa.

Curiosidade: ls e du discordam

O ls -l mostra o tamanho aparente de um arquivo; o du, o espaço realmente gasto no disco. Na máquina de laboratório da ana, os arquivos de Downloads foram criados "esparsos" (o tamanho está anotado, mas o conteúdo é vazio e não ocupa blocos), então a diferença salta aos olhos:

$ ls -lh ~/Downloads
total 0
-rw-rw-r-- 1 ana ana 1,5G 10 out 21:14 archlinux-x86_64.iso
-rw-rw-r-- 1 ana ana  48K 15 out 08:47 foto.jpg
-rw-rw-r-- 1 ana ana 100M  1 out 19:30 fotos-viagem.zip
-rw-rw-r-- 1 ana ana 2,3M 13 out 11:02 manual.pdf
-rw-rw-r-- 1 ana ana 5,0M  9 out 20:10 musica.mp3

$ findmnt /boot
TARGET SOURCE    FSTYPE OPTIONS

-t ext4,vfat
Só estes tipos.
-n
noheadings: sem a linha de títulos.
-o SOURCE,FSTYPE
Só estas colunas (como no lsblk). Ótimo em scripts: "de qual partição vem a raiz?"

A coluna OPTIONS mostra as opções de montagem em uso (rw = leitura e escrita, relatime = forma econômica de gravar a data de acesso). Elas vêm do /etc/fstab, assunto da próxima aula. O findmnt também confere o fstab com findmnt --verify: veja em mount e fstab.

SSD e TRIM

O que é o TRIM

Quando você apaga um arquivo, o sistema de arquivos só marca aqueles blocos como livres; o SSD não fica sabendo. Para gravar de novo num bloco já usado, o SSD precisa apagá-lo antes, e isso é lento. O TRIM (o comando de discard) é o aviso "estes blocos estão livres, pode limpá-los quando quiser". Com ele, o SSD mantém a velocidade e se desgasta de forma mais uniforme. HDs comuns (de disco giratório) não precisam disso.

O seu disco é SSD? Aceita TRIM?

$ lsblk -d -o NAME,ROTA,DISC-GRAN,DISC-MAX,MODEL
NAME ROTA DISC-GRAN DISC-MAX MODEL
sda     0      512B       2G VBOX HARDDISK
sr0     0        0B       0B VBOX CD-ROM
-d
nodeps: só os discos, sem as partições.
ROTA
rotational: 1 = disco que gira (HD); 0 = não gira (SSD, NVMe, pendrive).
DISC-GRAN / DISC-MAX
Granularidade e tamanho máximo do discard. Diferente de 0 = o disco aceita TRIM.

O disco virtual da ana se apresenta como não rotativo (ROTA 0) e aceita TRIM. Num notebook com NVMe, o normal é ver ROTA 0 e valores em DISC-GRAN/DISC-MAX. lsblk --discard mostra as mesmas colunas para todas as partições.

No Arch, o fstrim.timer vem desligado

O pacote util-linux traz o fstrim.timer, um timer do systemd que roda o TRIM uma vez por semana. Ubuntu e Fedora o deixam ligado; o Arch não liga serviços por você. Confira:

$ systemctl status fstrim.timer
○ fstrim.timer - Discard unused filesystem blocks once a week
     Loaded: loaded (/usr/lib/systemd/system/fstrim.timer; disabled; preset: disabled)   « desligado
     Active: inactive (dead)
    Trigger: n/a
   Triggers: ● fstrim.service
       Docs: man:fstrim

disabled quer dizer que ele não sobe no boot; inactive (dead), que não está rodando agora; preset: disabled, que a política padrão do Arch é deixá-lo assim. Para ligar (e já começar a contar):

sudo systemctl enable
Liga no boot (cria um atalho em timers.target.wants).
--now
E também inicia agora, sem esperar o próximo boot.
fstrim.timer
O timer (o serviço que ele dispara é o fstrim.service).
$ sudo systemctl enable --now fstrim.timer
Created symlink '/etc/systemd/system/timers.target.wants/fstrim.timer' → '/usr/lib/systemd/system/fstrim.timer'.
$ systemctl list-timers fstrim.timer
NEXT                          LEFT LAST PASSED UNIT         ACTIVATES
Mon 2026-10-19 01:00:05 -03 2 days -         - fstrim.timer fstrim.service

1 timers listed.
Pass --all to see loaded but inactive timers, too.

Pronto: na próxima segunda-feira de madrugada ele roda sozinho (LAST com - = nunca rodou). O serviço executa fstrim --listed-in /etc/fstab:/proc/self/mountinfo, ou seja, faz o TRIM em tudo o que está no fstab. Para desligar: sudo systemctl disable --now fstrim.timer.

Rodar o TRIM agora, à mão

$ sudo fstrim -av
/boot: 929,2 MiB (974372864 bytes) descartado em /dev/sda1
/: 19,6 GiB (21005733888 bytes) descartado em /dev/sda3

-a = todos os sistemas de arquivos montados que aceitam TRIM; -v = verbose, mostra quanto foi avisado. Na primeira vez o número é quase todo o espaço livre; nas seguintes, só o que foi apagado desde a última. Sem sudo, o fstrim -av não mostra nada e sai com código 0, porque não consegue abrir nenhum disco: mais um comando que "falha em silêncio".

Quando não funciona

O blkid não mostra nada 
$ blkid
$ echo $?
0

O que aconteceu: sem root, o blkid só consulta o cache, vazio.

Como resolver: sudo blkid, ou use lsblk -f, que mostra os mesmos UUIDs sem precisar de root.

"não foi possível abrir /dev/sda: Permissão negada" 
$ fdisk -l
fdisk: não foi possível abrir /dev/sda: Permissão negada
fdisk: não foi possível abrir /dev/sr0: Permissão negada
$ echo $?
0

O que aconteceu: só o root pode ler o disco "cru". Repare que o código de saída é 0 mesmo assim: num script, não confie nele para saber se deu certo.

Como resolver: sudo fdisk -l.

"/dev/sdb: Arquivo ou diretório inexistente" 
$ lsblk /dev/sdb
lsblk: /dev/sdb: Arquivo ou diretório inexistente
$ echo $?
32

O que aconteceu: esse disco não existe (ou o pendrive não foi reconhecido).

Como confirmar: rode lsblk sem argumentos e veja os nomes que existem. Num notebook com NVMe não há sda: o disco é nvme0n1. Logo depois de ligar um pendrive, journalctl -k -n 20 mostra se o kernel o detectou (veja Logs).

"Não há espaço disponível no dispositivo"

O que aconteceu: o sistema de arquivos encheu (ou acabaram os inodes).

Como confirmar: df -h / (espaço) e df -i / (inodes).

Como resolver: procure os culpados com sudo du -sh /var/cache/pacman/pkg /var/log/journal ~/.cache ~/Downloads. O cache do pacman e o journal se limpam com segurança (veja Cache e Órfãos e Logs). Se a /boot encheu, o pacman falha ao atualizar o kernel; veja Kernels.

Exercícios

1. Só os discos de verdade

Complete para mostrar o espaço livre com o tipo de cada sistema de arquivos, escondendo os tmpfs:

df -h -x

2. O maior por último

Complete para listar as subpastas de ~/aur da menor para a maior:

du -h --max-depth=1 ~/aur | sort

3. Num notebook com SSD NVMe, qual é o nome da segunda partição do primeiro disco?

Resumo

  • Disco → partições → sistema de arquivos → montado numa pasta. Os nomes ficam em /dev (sda3, nvme0n1p2) e podem mudar; o UUID não muda.
  • lsblk (e -f, -o) mostra tudo sem root; blkid e fdisk -l precisam de sudo.
  • df -h = espaço livre de cada montagem; du -sh = quanto uma pasta ocupa.
  • findmnt mostra o que está montado onde e com quais opções.
  • SSD: confira com lsblk --discard e ligue o fstrim.timer, que no Arch vem desligado.

Na Arch Wiki: os nomes de dispositivos e o lsblk estão em Device file; UUID, PARTUUID, rótulos e /dev/disk/by-*, em Persistent block device naming (em português); os tipos de sistema de arquivos, em File systems (em português); e o TRIM, em Solid state drive.
