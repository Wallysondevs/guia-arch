Arch .bashrc, alias e PATH

Toda vez que você abre um terminal, o bash (o programa que lê o que você digita) executa alguns arquivos de configuração. O principal é o ~/.bashrc: é ali que você cria atalhos (alias), define variáveis e diz onde o sistema deve procurar programas (o PATH). O Arch entrega uma configuração mínima, de 10 linhas, e espera que você monte a sua.

Você vai aprender
  • O que tem no ~/.bashrc e no ~/.bash_profile do Arch, e a diferença entre os dois.
  • Ler o prompt [\u@\h \W]\$ e mudá-lo.
  • Criar, listar e remover alias (alias, unalias) e torná-los permanentes com source.
  • Ver o PATH, acrescentar o ~/.local/bin e descobrir o que vai rodar com which e type.
  • Onde fica a configuração do sistema todo (/etc/profile, /etc/profile.d/, /etc/bash.bashrc) e como o bash-completion completa comandos com Tab.

Antes dos arquivos: variáveis

Uma variável é um nome que guarda um valor. O bash já começa com várias, chamadas variáveis de ambiente, que os programas consultam para saber quem você é, qual é a sua pasta pessoal e assim por diante. Para ler uma, coloque $ antes do nome (veja também Variáveis e Argumentos):

echo
Mostra na tela o que recebeu.
$HOME
O $ pede ao bash para trocar o nome pelo valor antes de rodar o echo.
$ echo $SHELL $HOME $USER $LANG
/bin/bash /home/ana ana pt_BR.UTF-8
$ echo $EDITOR

Para ver todas as variáveis de ambiente, use env (ou printenv); para uma só, printenv NOME, que devolve código 1 se ela não existir.

Os arquivos do Arch: .bashrc e .bash_profile

Quando um usuário é criado com useradd -m (veja Usuários e Grupos), a pasta pessoal ganha três arquivos ocultos, copiados de /etc/skel (de skeleton, "esqueleto"). Eles vêm do pacote bash:

$ ls -la /etc/skel
total 20
drwxr-xr-x  2 root root 4096 16 out 12:08 .
drwxr-xr-x 70 root root 4096 16 out 14:51 ..
-rw-r--r--  1 root root   21 15 set 16:47 .bash_logout
-rw-r--r--  1 root root   57 15 set 16:47 .bash_profile
-rw-r--r--  1 root root  172 15 set 16:47 .bashrc
$ pacman -Qo /etc/skel/.bashrc
/etc/skel/.bashrc pertence a bash 5.3.20-1

O ~/.bashrc, linha por linha

São 172 bytes. O arquivo inteiro:

$ cat ~/.bashrc
#
# ~/.bashrc
#

# If not running interactively, don't do anything
[[ $- != *i* ]] && return

alias ls='ls --color=auto'
alias grep='grep --color=auto'
PS1='[\u@\h \W]\$ '
LinhaO que faz
# …Comentários: o bash ignora tudo depois do #.
[[ $- != *i* ]] && return"Se este shell não é interativo, pare aqui." O $- guarda as opções do shell; o i aparece quando há uma pessoa digitando. Assim, scripts e comandos remotos (ssh máquina comando) não carregam alias e prompt, que só servem para gente.
alias ls='ls --color=auto'É por isso que o ls tem cores: o ls que você digita vira ls --color=auto.
alias grep='grep --color=auto'Destaca em cor o trecho encontrado pelo grep.
PS1='[\u@\h \W]\$ 'O desenho do prompt (seção própria, abaixo).

Compare com outras distribuições: o Arch não tem ll, la, histórico configurado nem prompt colorido. É o "faça você mesmo" do Arch: o mínimo, e você acrescenta o que quiser.

O ~/.bash_profile e o ~/.bash_logout

$ cat ~/.bash_profile
#
# ~/.bash_profile
#

[[ -f ~/.bashrc ]] && . ~/.bashrc
$ cat ~/.bash_logout
#
# ~/.bash_logout
#

O .bash_profile só tem uma linha de verdade: "se o ~/.bashrc existe (-f), leia-o" (o . é o mesmo que source, explicado adiante). O .bash_logout roda quando você sai de um shell de login, e vem vazio.

Shell de login × shell interativo: quem lê o quê

Por que dois arquivos? Porque o bash é aberto de dois jeitos:

SituaçãoTipo de shellLê
Login no TTY (tela preta, Ctrl+Alt+F3) ou entrar por sshDe login/etc/profile, depois ~/.bash_profile (que lê o ~/.bashrc)
Abrir um terminal no desktop (GNOME, KDE…), ou digitar bashInterativo, não de login/etc/bash.bashrc, depois ~/.bashrc
Rodar um script (bash script.sh)Não interativoNenhum dos dois

Dá para perguntar ao bash qual é o caso:

$ shopt -q login_shell && echo "shell de login" || echo "não é de login"
não é de login
$ bash -lc 'shopt -q login_shell && echo "shell de login"'
shell de login                                       « o -l abre um shell de login

A regra prática da Arch Wiki:

  • ~/.bashrc: alias, funções, o prompt, opções do terminal. Tudo o que é "para gente digitando".
  • ~/.bash_profile: variáveis de ambiente que valem para a sessão inteira (PATH, EDITOR), lidas uma vez no login.
E o ~/.profile dos tutoriais?

Muitos tutoriais (do Debian e do Ubuntu) mandam editar o ~/.profile. Num shell de login, o bash lê só o primeiro que existir entre ~/.bash_profile, ~/.bash_login e ~/.profile. Como o Arch já cria o ~/.bash_profile, um ~/.profile que você criar será ignorado pelo bash. No Arch, use o ~/.bash_profile.

O prompt do Arch: PS1

O prompt [ana@notebook ~]$ é desenhado a partir da variável PS1 (Prompt String 1). Os pedaços com barra invertida são trocados a cada linha:

$ echo "$PS1"
[\u@\h \W]\$
[
Um colchete, literal.
\u
O usuário (user): ana.
@
Uma arroba, literal.
\h
O nome da máquina (hostname), até o primeiro ponto: notebook.
\W
Só o nome da pasta atual (W maiúsculo); a pasta pessoal aparece como ~. Em /home/ana/Documentos/projetos, mostra projetos.
]
Fecha o colchete.
\$
$ para usuários comuns, # para o root. É assim que o prompt do root vira [root@notebook ~]#.

Para experimentar, mude o PS1 no próprio terminal. Vale só até fechar (ou até reler o .bashrc):

$ PS1='\u em \w\$ '
ana em ~$ cd Documentos/projetos
ana em ~/Documentos/projetos$ cd                      « \w (minúsculo): o caminho inteiro
ana em ~$ source ~/.bashrc
[ana@notebook ~]$                                     « voltou ao PS1 do .bashrc
CódigoViraCódigoVira
\uusuário\wcaminho completo (~/Documentos/projetos)
\hmáquina\Wsó a pasta (projetos)
\thora (14:30:00)\ddata (sex out 16)
\$$ ou #\nquebra de linha

Cores entram com códigos de escape, sempre entre \[ e \] (para o bash não errar a largura da linha). Um prompt verde e em negrito: PS1='\[\e[1;32m\][\u@\h \W]\$\[\e[0m\] ' (1;32 = negrito verde; 0 = volta ao normal). Gostou? Troque a linha PS1= do seu ~/.bashrc.

Se o .bashrc não definir nenhum PS1, quem desenha o prompt é o /etc/bash.bashrc, com o mesmo [\u@\h \W]\$ (veja a seção do sistema, abaixo). O root, que tem o seu próprio /root/.bashrc, cai nesse caso quando o arquivo não existe.

alias: atalhos para comandos

Um alias ("apelido") é um nome curto que o bash troca por um comando maior, antes de rodar. Para ver todos, digite alias sem nada. No Arch, a lista é curtíssima:

$ alias
alias grep='grep --color=auto'
alias ls='ls --color=auto'
$ ll
bash: ll: comando não encontrado
$ echo $?
127                                   « 127 = comando não encontrado

O ll que você vê em tutoriais não é um programa: é um alias que outras distribuições trazem pronto. No Arch, você cria.

Criar um alias

alias
O comando que cria apelidos.
ll
O nome do atalho.
=
Sem espaço antes nem depois.
'ls -lh'
O comando completo, entre aspas simples (por causa do espaço; veja Variáveis sobre aspas).
$ alias ll='ls -lh'
$ ll Documentos
total 16K
-rw-rw-r-- 1 ana ana  389 15 out 09:07 acesso.log
-rw-rw-r-- 1 ana ana  132 14 out 18:12 alunos.csv
-rw-rw-r-- 1 ana ana   69 14 out 17:40 notas.txt
drwxrwxr-x 3 ana ana 4,0K 15 out 09:15 projetos
-rw-rw-r-- 1 ana ana 8,2K 14 out 17:40 relatorio.odt

O ll Documentos virou ls -lh Documentos: o que você escreve depois do alias é acrescentado no fim. (As colunas do ls -l estão explicadas em ls.)

Listar, conferir e remover

$ type ll
ll está apelidada para `ls -lh'
$ alias
alias grep='grep --color=auto'
alias ll='ls -lh'
alias ls='ls --color=auto'
$ alias ll                             « só um
alias ll='ls -lh'
$ unalias ll                           « remove
$ ll
bash: ll: comando não encontrado
$ unalias nada
bash: unalias: nada: não encontrado
$ echo $?
1

Um alias criado assim vale só neste terminal: some quando você o fecha. Para que dure, ele precisa ir para o ~/.bashrc (próxima seção).

Passar por cima de um alias

Um alias com o nome de um comando "ganha" dele. Um exemplo comum é fazer o rm sempre perguntar:

$ alias rm='rm -i'
$ type rm
rm está apelidada para `rm -i'
$ touch teste.txt
$ \rm teste.txt                        « a barra invertida ignora o alias: apaga sem perguntar
$ ls teste.txt
ls: não foi possível acessar 'teste.txt': Arquivo ou diretório inexistente
$ unalias rm

Outra forma de rodar o comando original é command rm teste.txt.

Tornar permanente: editar o .bashrc e usar source

Para o alias sobreviver, acrescente a linha no fim do ~/.bashrc. Com o editor (nano ~/.bashrc; veja nano e vim) ou com um comando só: o >> acrescenta no fim, sem apagar o que existe (veja Redirecionamento).

Dois sinais, nunca um

echo "…" > ~/.bashrc, com um > só, apaga o arquivo inteiro e deixa só a linha nova: some o prompt do Arch. Se acontecer, recupere o original com cp /etc/skel/.bashrc ~/.

$ echo "alias ll='ls -lh'" >> ~/.bashrc
$ tail -3 ~/.bashrc
alias grep='grep --color=auto'
PS1='[\u@\h \W]\$ '
alias ll='ls -lh'                      « a linha nova, no fim
$ ll
bash: ll: comando não encontrado        « ainda não!

O ll ainda não funciona porque o .bashrc só é lido quando o terminal abre. Você pode abrir outro terminal, ou mandar o terminal atual reler o arquivo com source:

source
Executa um arquivo dentro do shell atual (não num shell novo), então o que ele cria fica valendo aqui. Também se escreve só com um ponto: .
~/.bashrc
O arquivo a reler.
$ source ~/.bashrc
$ type ll
ll está apelidada para `ls -lh'
$ . ~/.bashrc                          « o mesmo, com o ponto
$ echo $?
0

PATH: onde o bash procura programas

Quando você digita ls, o bash não sabe de cara onde está o programa. Ele procura numa lista de pastas, na ordem, e roda o primeiro que encontrar. Essa lista é a variável PATH ("caminho"), com as pastas separadas por dois-pontos. O tr troca cada : por uma quebra de linha, para ficar legível (veja sort, uniq, cut, wc, tr):

$ echo $PATH
/usr/local/sbin:/usr/local/bin:/usr/bin:/usr/bin/site_perl:/usr/bin/vendor_perl:/usr/bin/core_perl
$ echo $PATH | tr ":" "\n"
/usr/local/sbin
/usr/local/bin
/usr/bin                       « quase todos os programas do Arch estão aqui
/usr/bin/site_perl             « estas três: scripts do Perl
/usr/bin/vendor_perl
/usr/bin/core_perl
PastaPara quêQuem acrescentou
/usr/local/sbin, /usr/local/binProgramas que você instala à mão, fora do pacman (ficam antes, então "ganham" dos do sistema)/etc/profile
/usr/binTudo o que o pacman instala/etc/profile
/usr/bin/*_perlScripts do Perl/etc/profile.d/perlbin.sh, do pacote perl

Repare: não há /bin, /sbin nem /usr/sbin. No Arch, todas são atalhos para /usr/bin, então não precisam estar no PATH:

$ ls -l /bin /sbin /usr/sbin
lrwxrwxrwx 1 root root 7 12 out  2025 /bin -> usr/bin
lrwxrwxrwx 1 root root 7 12 out  2025 /sbin -> usr/bin
lrwxrwxrwx 1 root root 3 12 out  2025 /usr/sbin -> bin

Por isso, no Arch, o PATH da ana e o do root são iguais, e comandos de administração como useradd e reboot são encontrados por qualquer usuário (só que o sistema recusa a ação sem permissão; veja sudo, root e Usuários). É diferente do Debian, onde a usuária comum não tem /sbin no PATH.

Acrescentar uma pasta: o ~/.local/bin

A Ana quer guardar os próprios scripts e rodá-los pelo nome, de qualquer pasta. O lugar convencional é ~/.local/bin. No Arch, ao contrário do Debian, essa pasta não entra no PATH sozinha. Veja o problema:

$ mkdir -p ~/.local/bin
$ printf '#!/bin/bash\necho "Olá, $USER! Hoje é $(date +%%A)."\n' > ~/.local/bin/ola
$ cat ~/.local/bin/ola
#!/bin/bash
echo "Olá, $USER! Hoje é $(date +%A)."
$ chmod +x ~/.local/bin/ola
$ ola
bash: ola: comando não encontrado            « a pasta não está no PATH
$ ~/.local/bin/ola
Olá, ana! Hoje é sexta.                      « com o caminho, funciona

(O chmod +x dá permissão de execução; veja chmod. Scripts são o assunto de Primeiro Script.) Agora, acrescente a pasta no começo do PATH, sem apagar o resto:

export
Torna a variável visível para os programas que o bash abrir.
PATH=
Atribui um novo valor ao PATH. Sem espaços em volta do =.
"$HOME/.local/bin
A pasta nova (o $HOME vira /home/ana)…
:$PATH"
…seguida de dois-pontos e do PATH antigo. Nunca esqueça o $PATH.
$ export PATH="$HOME/.local/bin:$PATH"
$ echo $PATH | tr ":" "\n" | head -3
/home/ana/.local/bin                       « a nova, em primeiro
/usr/local/sbin
/usr/local/bin
$ ola
Olá, ana! Hoje é sexta.
$ which ola
/home/ana/.local/bin/ola
$ type ola
ola está na tabela hash (/home/ana/.local/bin/ola)    « o bash já guardou onde ele está

Esquecer o $PATH no fim deixa o PATH só com a pasta nova, e os comandos do sistema "somem". Testando num bash à parte (bash -c), para não estragar o terminal atual:

$ bash -c 'PATH="$HOME/.local/bin"; ls'
bash: linha 1: ls: comando não encontrado

PATH permanente: no ~/.bash_profile

O export acima vale só neste terminal. Para ficar permanente, coloque a mesma linha no ~/.bash_profile, que é lido no login (a recomendação da Arch Wiki para variáveis de ambiente). Repare nas aspas simples: o $HOME e o $PATH precisam ir literalmente para o arquivo, para serem trocados a cada login:

$ echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bash_profile
$ cat ~/.bash_profile
#
# ~/.bash_profile
#

[[ -f ~/.bashrc ]] && . ~/.bashrc
export PATH="$HOME/.local/bin:$PATH"

Vale a partir do próximo login (sair e entrar de novo na sessão, ou abrir um novo login no TTY ou por SSH). Pôr no ~/.bashrc também funciona para os terminais, mas cada source ~/.bashrc acrescentaria a pasta de novo, deixando o PATH repetido.

export: variáveis para os outros programas

Uma variável criada sem export existe só dentro do bash atual; os programas que ele abre não a enxergam. Veja a diferença (o bash -c abre um bash "filho" que roda um comando):

$ CIDADE=Recife
$ echo $CIDADE
Recife
$ bash -c 'echo "o filho vê: [$CIDADE]"'
o filho vê: []                           « sem export, o filho não enxerga
$ export CIDADE
$ bash -c 'echo "o filho vê: [$CIDADE]"'
o filho vê: [Recife]

Regra prática: use export para tudo o que um programa precisa ler. O exemplo mais útil no Arch é escolher o editor, já que nenhum vem definido: echo 'export EDITOR=nano' >> ~/.bash_profile. Daí em diante, crontab -e, git commit e sudo systemctl edit abrem o nano. Para um programa só, uma vez, ponha a variável na frente do comando: EDITOR=nano crontab -e.

A configuração do sistema todo

Antes dos seus arquivos, o bash lê os do sistema, em /etc. Valem para todos os usuários; só o root edita.

O coração do /etc/profile (trecho real):

# Append "$1" to $PATH when not already in.
# This function API is accessible to scripts in /etc/profile.d
append_path () {
    case ":$PATH:" in
        *:"$1":*)
            ;;
        *)
            PATH="${PATH:+$PATH:}$1"
    esac
}

# Append our default paths
append_path '/usr/local/sbin'
append_path '/usr/local/bin'
append_path '/usr/bin'

# Force PATH to be environment
export PATH

# Load profiles from /etc/profile.d
if test -d /etc/profile.d/; then
	for profile in /etc/profile.d/*.sh; do
		test -r "$profile" && . "$profile"
	done
	unset profile
fi

A função append_path acrescenta uma pasta no fim do PATH só se ela ainda não estiver lá. Depois, o laço for (veja Laços) lê cada .sh da pasta /etc/profile.d/:

$ ls /etc/profile.d/

flatpak.sh

Cada um foi instalado por um pacote: o locale.sh (do filesystem) lê o /etc/locale.conf e define o LANG; o perlbin.sh (do perl) acrescenta as pastas do Perl ao PATH; o flatpak.sh deixa os aplicativos Flatpak aparecerem no menu; os dois do systemd cuidam de detalhes do prompt e do terminal. Os .csh são para outro shell, o csh, e o bash os ignora.

Quer uma configuração para todos os usuários?

Não edite o /etc/profile: ele pertence ao pacote filesystem, e uma atualização pode gerar um .pacnew (veja .pacnew e .pacsave). Crie o seu arquivo, por exemplo /etc/profile.d/meu.sh com export EDITOR=nano. Ele é lido no próximo login de qualquer usuário, e nenhum pacote mexe nele.

bash-completion: Tab que entende os comandos

Sem nada instalado, o Tab do bash completa nomes de comandos e de arquivos. O pacote bash-completion ensina o Tab a completar também as opções e os argumentos de cada programa: pacotes no pacman, serviços no systemctl, ramos no git… Ele não vem no base; a VM do guia tem porque foi instalado junto com os pacotes das aulas:

#> pacman -Syu --noconfirm --needed base-devel git bash-completion pacman-contrib … wget rsync inetutils …

No seu Arch: sudo pacman -S bash-completion e abra um terminal novo (o /etc/bash.bashrc carrega o pacote sozinho). As regras de cada programa ficam em /usr/share/bash-completion/completions/, e quem as instala é o próprio programa: a do pacman vem no pacote pacman; a do systemctl, no systemd.

Testes reais na VM (a tecla Tab não aparece na tela; o « indica onde ela foi apertada):

$ pacman -Q --inf                  « Tab
$ pacman -Q --info                 « completou a opção
$ systemctl sta                    « Tab Tab (duas vezes: há mais de uma opção)
start   status
$ ls /etc/pacm                     « Tab
$ ls /etc/pacman.                  « completou até onde pacman.conf e pacman.d são iguais

As regras são carregadas sob demanda: o bash só lê a regra do pacman na primeira vez que você aperta Tab depois de digitar pacman. Dá para ver isso com o comando interno complete -p, que mostra a regra de um comando:

$ complete -p pacman
bash: complete: pacman: nenhuma especificação de completação     « antes de qualquer Tab
$ pacman -Q --inf                                                « Tab
$ complete -p pacman
complete -F _pacman pacman                                       « depois: a função _pacman cuida do Tab

Experimente

O terminal simulado tem o .bashrc e o .bash_profile reais do Arch e entende alias, export, source e o PS1. Teste à vontade: nada que você fizer aqui muda o seu computador.

Missão 1: o ll não existe no Arch. Crie o alias ll para ls -lh e rode ll. Depois confira com type ll.

Missão 2: já existe um script em ~/.local/bin/ola, mas ola dá "comando não encontrado". Acrescente a pasta ao começo do PATH, sem perder o resto, e rode ola só pelo nome.

Missão 3: torne permanente um alias la (para ls -lhA): acrescente-o ao fim do ~/.bashrc (cuidado: >>, não >) e faça o terminal atual reler o arquivo.

Missão 4: mude o prompt para mostrar o caminho inteiro da pasta (troque \W por \w) e entre em Documentos/projetos para ver a diferença. Para voltar ao original, source ~/.bashrc.

Quando não funciona

"erro de sintaxe: fim inesperado do arquivo" ao abrir o terminal

Para reproduzir, a Ana acrescentou um if sem o fi no fim do .bashrc (que já tinha o alias ll na linha 11):

$ echo 'if true; then' >> ~/.bashrc
$ source ~/.bashrc
bash: /home/ana/.bashrc: linha 13: erro de sintaxe: fim inesperado do arquivo do comando `if' na linha 12
$ bash -i -c true                     « o mesmo erro aparece em todo terminal novo
bash: /home/ana/.bashrc: linha 13: erro de sintaxe: fim inesperado do arquivo do comando `if' na linha 12

O que aconteceu: você abriu um if, uma aspa ou um { e não fechou. O bash leu até o fim do arquivo procurando o fechamento. O terminal abre, mas sem a sua configuração.

Como resolver: a mensagem diz onde o bloco começou (na linha 12). Abra com nano ~/.bashrc, vá até a linha (Ctrl+_ no nano) e feche o bloco (fi, aspa ou }). Para testar sem abrir terminal: bash -n ~/.bashrc (só confere a sintaxe). Em último caso, volte ao original: cp /etc/skel/.bashrc ~/.bashrc. Antes de editar, faça uma cópia: cp ~/.bashrc ~/.bashrc.bak.

"alias: x: não encontrado" 
$ alias x = 'ls'
bash: alias: x: não encontrado
bash: alias: =: não encontrado
alias ls='ls --color=auto'

O que aconteceu: há espaços em volta do =. O bash entendeu três palavras separadas e tentou mostrar três alias: x e = não existem, e ls existe (por isso a terceira linha).

Como resolver: escreva tudo junto: alias x='ls'.

Criei o script, mas "comando não encontrado" (código 127)

O que aconteceu: a pasta do script não está no PATH (no Arch, ~/.local/bin não entra sozinha), ou você pôs o export no ~/.bash_profile e ainda não fez login de novo.

Como confirmar: echo $PATH | tr ":" "\n". Se a pasta está lá, confira a permissão de execução: ls -l ~/.local/bin/ (precisa do x).

Como resolver: export PATH="$HOME/.local/bin:$PATH" no terminal atual e a mesma linha no ~/.bash_profile; saia e entre na sessão.

"which: no ll in (…)" 
$ which ll
which: no ll in (/usr/local/sbin:/usr/local/bin:/usr/bin:/usr/bin/site_perl:/usr/bin/vendor_perl:/usr/bin/core_perl)

O que aconteceu: o which só procura arquivos no PATH; ele não enxerga alias, funções nem comandos internos. Mesmo com o alias criado, a resposta seria essa.

Como resolver: use type ll.

Mudei o .bashrc e nada aconteceu

O que aconteceu: o arquivo só é lido quando o terminal abre. Ou você editou o arquivo errado: um ~/.profile é ignorado no Arch, porque o ~/.bash_profile existe.

Como resolver: source ~/.bashrc (ou abra um terminal novo). Variáveis de ambiente vão no ~/.bash_profile e valem no próximo login.

O Tab não completa opções nem nomes de pacotes

O que aconteceu: o bash-completion não vem no base.

Como confirmar: pacman -Q bash-completion → erro: o pacote "bash-completion" não foi encontrado.

Como resolver: sudo pacman -S bash-completion e abra um terminal novo.

Resumo

  • O ~/.bashrc do Arch tem 10 linhas: o teste de shell interativo, os alias ls e grep e o PS1='[\u@\h \W]\$ '. Não há ll.
  • O ~/.bash_profile (login) só lê o ~/.bashrc; é o lugar das variáveis de ambiente. O ~/.profile é ignorado.
  • alias nome='comando' cria; unalias remove; type confere; para durar, >> ~/.bashrc e source ~/.bashrc.
  • O PATH do Arch é o mesmo para todos (/bin e /sbin são atalhos de /usr/bin); o ~/.local/bin não entra sozinho: export PATH="$HOME/.local/bin:$PATH".
  • /etc/profile monta o PATH e lê /etc/profile.d/; o /etc/bash.bashrc define o prompt padrão e carrega o bash-completion (que se instala à parte).
