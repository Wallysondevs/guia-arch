Arch Primeiro Script

Um shell script é um arquivo de texto com comandos, um por linha, que o Bash executa em sequência. Tudo o que você digita no terminal pode virar script. Assim, aquela sequência de comandos que você repete toda semana no Arch (ver o kernel, contar os pacotes do AUR, olhar o disco) vira um comando só, que você roda quando quiser.

Você vai aprender
  • Criar um script e entender a primeira linha (o shebang), e por que no Arch o sh é o próprio Bash.
  • Por que aparece "Permissão negada" e como o chmod +x resolve.
  • Cinco formas de executar um script, e o que muda entre elas.
  • Guardar seus scripts em ~/.local/bin, que o Arch não coloca no PATH sozinho.
  • O código de saída, o modo seguro set -euo pipefail, o bash -x e os erros reais (incluindo o ^M de arquivos vindos do Windows).

Antes, é bom conhecer o terminal (O Terminal no Arch), um editor (nano e vim) e as permissões (Entendendo Permissões). Os exemplos rodam na máquina notebook, com a usuária ana, e as saídas vêm de um Arch Linux real.

O que é um script, afinal?

Pense numa receita de bolo: uma lista de passos, em ordem, que qualquer pessoa pode seguir. Um script é a mesma coisa para o computador. Em vez de você digitar:

$ uname -r
7.2.10-arch1-1
$ pacman -Qm | wc -l
4
$ df -h / | tail -1
/dev/sda3        25G  4,9G   19G  22% /

…você escreve esses comandos num arquivo uma vez e, daí em diante, roda o arquivo. O programa que lê e executa o arquivo é o mesmo que lê o que você digita: o Bash, o shell padrão do Arch (versão 5.3.20 em outubro de 2026). Por isso se chama shell script: um roteiro para o shell.

Antes de começar: onde guardar os scripts

Para aprender, crie uma pasta só para os testes. A Ana vai usar ~/scripts:

$ mkdir -p ~/scripts
$ cd ~/scripts

O -p evita erro se a pasta já existir. Mais adiante você vai ver a pasta "oficial" para os scripts prontos, ~/.local/bin, e por que no Arch ela precisa de um passo a mais.

Passo 1: escrever o script

Abra o editor com nano ola.sh (o Arch não vem com editor: o nano é um pacote à parte, veja nano e vim) e digite o conteúdo abaixo. A extensão .sh não é obrigatória, mas ajuda a reconhecer o que é script.

#!/usr/bin/env bash
# ola.sh — meu primeiro script no Arch
# Mostra uma saudação, a data, o kernel e a pasta atual.

echo "Olá, $USER!"
echo "Hoje é $(date +%d/%m/%Y)."
echo "Kernel em uso: $(uname -r)"
echo "Você está em: $(pwd)"

Salve com Ctrl+O, Enter, e saia com Ctrl+X. Veja o que cada linha faz:

#!/usr/bin/env bash
O shebang: diz qual programa deve ler o arquivo. Precisa ser a primeira linha, sem nada antes (nem uma linha em branco).
# ola.sh — …
Um comentário: toda linha que começa com # é ignorada pelo Bash. Serve para você (e quem ler depois) entender o script.
(linha em branco)
Linhas vazias também são ignoradas. Use-as para separar partes.
echo "Olá, $USER!"
Mostra um texto. $USER é trocado pelo nome do usuário (variáveis são a próxima aula).
$(date +%d/%m/%Y)
Roda o date e coloca a saída dele dentro do texto.
$(uname -r)
Idem com o uname -r, que mostra a versão do kernel.
$(pwd)
Idem com o pwd, a pasta atual.

Comentários: escreva para o "você do futuro"

Daqui a três meses você não vai lembrar por que escreveu aquela linha. Comente o porquê, não o óbvio:

# Ruim: repete o que o comando já diz
pacman -Qm      # lista pacotes com -Qm

# Bom: explica a intenção
pacman -Qm      # pacotes que não vieram dos repositórios (quase sempre, do AUR)

O # no meio da linha também começa um comentário: tudo dali até o fim da linha é ignorado. Só não vale dentro de aspas (echo "nota #1" mostra o #).

O shebang em detalhe

O nome vem de sharp (#) + bang (!). Quando você executa o arquivo como programa, o kernel lê essa linha e chama o programa indicado para interpretar o resto.

ShebangSignificado no Arch
#!/usr/bin/env bash"Procure o bash no PATH e use-o." Funciona em qualquer distribuição, mesmo que o bash esteja em outra pasta. É a forma recomendada. O env vem do pacote coreutils.
#!/bin/bashUsa o bash nesse caminho exato. No Arch, /bin é um link para /usr/bin, então é o mesmo arquivo /usr/bin/bash. Funciona igual.
#!/bin/shUsa o sh. No Arch, /bin/sh é um link para o próprio bash (que se comporta como um shell POSIX). No Debian e no Ubuntu, sh é o dash, mais limitado. Veja o cuidado em "Quando não funciona".
#!/usr/bin/env python3O mesmo truque serve para outras linguagens (no Arch o pacote é python).

Você pode conferir isso na sua máquina:

$ ls -ld /bin
lrwxrwxrwx 1 root root 7 12 out  2025 /bin -> usr/bin        « /bin é só um atalho para /usr/bin
$ ls -l /bin/sh
lrwxrwxrwx 1 root root 4 15 set 16:47 /bin/sh -> bash          « sh = bash, no Arch
$ pacman -Qo /usr/bin/env /usr/bin/bash
/usr/bin/env pertence a coreutils 9.12-2
/usr/bin/bash pertence a bash 5.3.20-1

Passo 2: executar

A forma mais simples é entregar o arquivo ao bash. Não precisa de nenhuma preparação:

bash
O interpretador (o programa que vai ler o script).
ola.sh
O arquivo que ele vai ler e executar, linha por linha.
$ bash ola.sh
Olá, ana!
Hoje é 16/10/2026.
Kernel em uso: 7.2.10-arch1-1
Você está em: /home/ana/scripts

Agora tente rodar como um programa, com ./ na frente. O ./ significa "o arquivo que está nesta pasta" (o . é a pasta atual, veja Caminhos):

$ ./ola.sh
bash: ./ola.sh: Permissão negada
$ echo $?
126                                         « 126 = o arquivo existe, mas não pode ser executado

Todo arquivo novo nasce sem permissão de execução, por segurança: assim, um arquivo baixado da internet não sai rodando sozinho. Veja o ls -l: não há nenhum x.

$ ls -l ola.sh
-rw-r--r-- 1 ana ana 239 16 out 14:54 ola.sh

As permissões rw-r--r-- vêm da umask padrão do Arch (022): você lê e escreve, os outros só leem. (No Debian e no Ubuntu, o mesmo arquivo nasceria rw-rw-r--.) Veja Entendendo Permissões.

Dar permissão de execução: chmod +x

chmod
Change mode: muda as permissões (veja chmod).
+x
Acrescenta (+) a permissão de execução (x, de execute) para todos.
ola.sh
O arquivo.
$ chmod +x ola.sh
$ ls -l ola.sh
-rwxr-xr-x 1 ana ana 239 16 out 14:54 ola.sh          « agora tem x
$ ./ola.sh
Olá, ana!
Hoje é 16/10/2026.
Kernel em uso: 7.2.10-arch1-1
Você está em: /home/ana/scripts

O chmod +x é feito uma vez só. Você pode editar o script quantas vezes quiser depois: a permissão continua lá.

Missão: a máquina já tem um script pronto e executável em Documentos/projetos/backup.sh. Veja o conteúdo dele com cat, confira o x nas permissões com ls -l, rode-o com ./Documentos/projetos/backup.sh e veja o código de saída com echo $?.

Missão: o simulador não tem editor, então crie o script com printf: printf '#!/usr/bin/env bash\necho "Oi do Arch"\n' > oi.sh (o \n é a quebra de linha). Confira com cat oi.sh, tente ./oi.sh e veja a "Permissão negada"; depois dê o chmod +x e rode de novo.

Cinco formas de executar um script

FormaPrecisa de x?Usa o shebang?Quando usar
bash ola.shNãoNão (sempre bash)Testar rápido; rodar um script baixado sem mudar permissões.
./ola.shSimSimO jeito normal, estando na pasta do script.
~/scripts/ola.shSimSimDe qualquer pasta, com o caminho completo. É o jeito certo em timers e no cron.
ola (só o nome)SimSimQuando o script está numa pasta do PATH, como ~/.local/bin.
source ola.shNãoNãoQuando o script deve mudar o seu terminal (variáveis, cd).

Rodar só pelo nome (e o PATH do Arch)

Sem o ./, o Bash não olha a pasta atual: ele procura o nome nas pastas da variável PATH, uma lista separada por :.

$ ola.sh
bash: ola.sh: comando não encontrado
$ echo $?
127                                         « 127 = comando não encontrado
$ echo $PATH
/usr/local/sbin:/usr/local/bin:/usr/bin:/usr/bin/site_perl:/usr/bin/vendor_perl:/usr/bin/core_perl

Repare: não há nenhuma pasta da sua home no PATH. O Debian e o Ubuntu incluem ~/.local/bin automaticamente (pelo ~/.profile); o Arch, fiel ao "você decide", não: o /etc/profile só põe as pastas do sistema, e o ~/.bash_profile do Arch apenas carrega o ~/.bashrc. Então são dois passos:

  1. Criar a pasta e copiar o script para lá, já sem o .sh (assim ele parece um comando qualquer): 
    $ mkdir -p ~/.local/bin
$ cp ola.sh ~/.local/bin/ola
$ ola
bash: ola: comando não encontrado            « a pasta ainda não está no PATH
  2. Pôr a pasta no PATH, no fim do ~/.bashrc, e recarregar: 
    $ echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc
$ source ~/.bashrc
$ ola
Olá, ana!
Hoje é 16/10/2026.
Kernel em uso: 7.2.10-arch1-1
Você está em: /home/ana/scripts
$ type ola
ola está na tabela hash (/home/ana/.local/bin/ola)
echo '…' >> ~/.bashrc
Acrescenta a linha no fim do .bashrc. São dois >: com um só, você apagaria o arquivo inteiro.
export PATH=
Redefine o PATH e o "exporta" para os programas abertos a partir deste terminal.
"$HOME/.local/bin:$PATH"
A sua pasta na frente, seguida do PATH antigo ($PATH). As aspas simples do echo fazem a linha ir para o arquivo literalmente, com os $.
source ~/.bashrc
Relê o arquivo neste terminal. Os terminais novos já abrem com o PATH certo.

Os detalhes do .bashrc e do PATH estão em .bashrc, alias, PATH.

source: rodar dentro do terminal atual

Normalmente, o script roda num bash separado, que termina quando o script acaba. Por isso um cd dentro do script não muda a pasta do seu terminal. Com source (ou o atalho .), os comandos rodam no seu bash, como o source ~/.bashrc que você acabou de usar:

#!/usr/bin/env bash
cd ~/Documentos/projetos
echo "Entrei em $(pwd)"
$ bash vai.sh
Entrei em /home/ana/Documentos/projetos
$ pwd
/home/ana/scripts                           « o terminal continuou onde estava
$ source vai.sh
Entrei em /home/ana/Documentos/projetos
$ pwd
/home/ana/Documentos/projetos               « com source, o cd valeu aqui

O que o script devolve: o código de saída

Todo comando termina com um código de saída (exit status), um número de 0 a 255. Todo script também. Por padrão, é o código do último comando que rodou, mas você pode escolher com exit. Um exemplo bem do Arch: avisar se o pacman está travado. Enquanto um pacman trabalha, ele cria o arquivo /var/lib/pacman/db.lck; se o computador desligar no meio, esse arquivo fica para trás e trava os próximos (veja pacman).

#!/usr/bin/env bash
# Avisa se o pacman está travado (outro pacman rodando ou um travamento antigo).
if [ -e /var/lib/pacman/db.lck ]; then
    echo "O pacman está travado: existe /var/lib/pacman/db.lck"
    exit 1
else
    echo "O pacman está livre."
    exit 0
fi
$ bash verifica.sh
O pacman está livre.
$ echo $?
0
$ bash verifica.sh && echo "pode atualizar" || echo "espere o outro pacman"
O pacman está livre.
pode atualizar

O if será explicado em Condicionais. Por enquanto, guarde a tabela:

CódigoSignificado
0Sucesso ("zero problemas").
1Erro genérico (o mais comum). O pacman devolve 1 quando um pacote não existe.
2Uso errado do comando ou erro de sintaxe no script.
126O arquivo existe, mas não pode ser executado (falta x).
127Comando não encontrado.
130Interrompido com Ctrl+C.

Um script útil: o resumo do seu Arch

Juntando comandos que você já conhece, a Ana fez um script que mostra o estado da máquina, e o guardou direto em ~/.local/bin:

#!/usr/bin/env bash
# resumo — o estado do meu Arch em poucas linhas

echo "=== $(uname -n) — $(date '+%d/%m/%Y %H:%M') ==="
echo "Kernel:   $(uname -r)"
echo "Pacotes:  $(pacman -Q | wc -l) instalados"
echo "Do AUR:   $(pacman -Qm | wc -l)"
echo
echo "Disco (/):"
df -h / | tail -1
LinhaO que faz
$(uname -n)O nome da máquina. (O comando hostname também serve, mas no Arch ele vem do pacote inetutils, que nem toda instalação tem; o uname está sempre lá.)
date '+%d/%m/%Y %H:%M'Data e hora. As aspas são necessárias por causa do espaço no formato.
pacman -Q | wc -l-Q lista todos os pacotes instalados, um por linha; o wc -l conta as linhas.
pacman -Qm | wc -l-Qm (foreign) lista os pacotes que não estão nos repositórios: quase sempre, os do AUR.
echoSem texto, só pula uma linha.
df -h / | tail -1Espaço da partição raiz, só a última linha (sem o cabeçalho). Veja lsblk, df, du.
$ resumo
bash: /home/ana/.local/bin/resumo: Permissão negada     « esqueceu o chmod
$ chmod +x ~/.local/bin/resumo
$ resumo
=== notebook — 16/10/2026 14:56 ===
Kernel:   7.2.10-arch1-1
Pacotes:  408 instalados
Do AUR:   4

Disco (/):

Missão: este é um resumo menor, sem o disco e sem a linha do AUR (e com uma variável nova, $BASH_VERSION, a versão do Bash). Acrescente, depois da linha dos pacotes, uma linha que mostre Do AUR: seguido da quantidade de pacotes de fora dos repositórios (pacman -Qm | wc -l) e clique em Rodar. Experimente também apagar a primeira linha (o shebang): com bash resumo.sh, que é como o editor roda, o script continua funcionando. Por quê?

(Resposta: bash resumo.sh não usa o shebang, porque você já disse qual programa deve ler o arquivo. O shebang só importa quando o script é executado como programa, com ./ ou pelo nome.)

Scripts mais seguros: set -euo pipefail

Por padrão, o Bash é tolerante demais: se um comando falha, ele segue para o próximo como se nada tivesse acontecido. Num script que apaga arquivos ou mexe no sistema, isso é perigoso. Coloque esta linha logo depois do shebang:

set
Muda o comportamento do Bash a partir desta linha.
-e
(errexit) Para o script no primeiro comando que falhar.
-u
(nounset) Trata como erro o uso de uma variável que não existe, como um erro de digitação.
-o pipefail
Num pipe (a | b), considera que falhou se qualquer parte falhar, não só a última.
#!/usr/bin/env bash
set -euo pipefail

pacman -Qi pacote-que-nao-existe
echo "Esta linha nunca será executada."
$ bash seguro.sh
erro: o pacote "pacote-que-nao-existe" não foi encontrado
$ echo $?
1                                           « parou no erro e devolveu o código do pacman

Veja o -u pegando um erro de digitação. A variável certa era $pacote:

#!/usr/bin/env bash
set -u
pacote="firefox"
echo "Procurando $pacoet"
$ bash digitacao.sh
digitacao.sh: linha 4: pacoet: variável não associada
$ echo $?
1

Sem o set -u, o script mostraria só "Procurando " e seguiria em frente, sem avisar. Imagine isso num sudo pacman -Rns $pacoet.

O modo seguro tem pegadinhas

Com -e, um comando que "falha de propósito" (como um grep que não acha nada, ou o pacman -Qdt quando não há órfãos, que devolve 1) também para o script. Nesses casos, teste o comando com if (próximas aulas) ou acrescente || true. O Guia Bash tem uma aula inteira sobre isso (link no fim).

Encontrar erros: bash -x, bash -n e shellcheck

Com -x, o Bash mostra cada comando antes de executá-lo, já com as variáveis substituídas. As linhas que começam com + são o "rastro":

$ bash -x ola.sh
+ echo 'Olá, ana!'                          « o comando, já com $USER trocado
Olá, ana!                                   « a saída dele
++ date +%d/%m/%Y                           « ++ = rodou dentro de $( )
+ echo 'Hoje é 16/10/2026.'
Hoje é 16/10/2026.
++ uname -r
+ echo 'Kernel em uso: 7.2.10-arch1-1'
Kernel em uso: 7.2.10-arch1-1
++ pwd
+ echo 'Você está em: /home/ana/scripts'
Você está em: /home/ana/scripts

Com -n (noexec), o Bash só lê o script e procura erros de sintaxe, sem executar nada. Ótimo antes de rodar um script que mexe no sistema:

$ bash -n quebrado.sh
quebrado.sh: linha 6: erro de sintaxe: fim inesperado do arquivo do comando `if' na linha 2
$ echo $?
2

O shellcheck lê o script e aponta erros e más práticas antes de você rodar. Ele está no repositório extra:

$ pacman -Si shellcheck

…

Ele é escrito em Haskell, por isso puxa muitas bibliotecas haskell-*: em outubro de 2026, numa instalação como a da Ana, eram 55 pacotes e cerca de 22 MiB de download. Instale com sudo pacman -S shellcheck. Veja o que ele diz deste script de três linhas:

#!/usr/bin/env bash

Quando não funciona

"Permissão negada" 
$ ./ola.sh
bash: ./ola.sh: Permissão negada
$ echo $?
126

O que aconteceu: o arquivo não tem permissão de execução.

Como confirmar: ls -l ola.sh não mostra nenhum x.

Como resolver: chmod +x ola.sh, ou rode com bash ola.sh. Se o arquivo estiver num pendrive FAT32 ou NTFS, o chmod não funciona lá: use bash ou copie para a pasta pessoal.

"comando não encontrado" com o arquivo bem ali 
$ ola.sh
bash: ola.sh: comando não encontrado
$ echo $?
127

O que aconteceu: sem ./, o Bash só procura nas pastas do PATH, e a pasta atual não está lá.

Como resolver: use ./ola.sh, o caminho completo, ou mova o script para ~/.local/bin. Se você já moveu e continua "não encontrado", falta pôr a pasta no PATH: no Arch ela não vem lá (veja "Rodar só pelo nome", acima).

env: “bash\r”: Arquivo ou diretório inexistente (o ^M do Windows) 
$ ./script-do-windows.sh
env: “bash\r”: Arquivo ou diretório inexistente
env: usa -[v]S para passar opções em linhas shebang
$ echo $?
127

O que aconteceu: o arquivo foi salvo no Windows (ou baixado de um site que o gravou assim). O Windows termina cada linha com dois caracteres, \r\n; o Linux usa só o \n. O \r sobrou colado no fim do shebang, e o env procurou um programa chamado "bash\r", que não existe.

Como confirmar: o cat -A mostra os caracteres invisíveis. O \r aparece como ^M e o fim de linha como $:

$ cat -A script-do-windows.sh
#!/usr/bin/env bash^M$
echo "OlM-CM-! do Windows"^M$                « o "á" vira M-CM-! (são 2 bytes em UTF-8)

Como resolver: apague os \r do fim das linhas com o sed (veja sed):

$ sed -i 's/\r$//' script-do-windows.sh
$ ./script-do-windows.sh
Olá do Windows

Outra opção é o programa dos2unix, que não vem instalado: sudo pacman -S dos2unix e depois dos2unix script-do-windows.sh.

"erro de sintaxe: fim inesperado do arquivo" 
$ bash quebrado.sh
quebrado.sh: linha 6: erro de sintaxe: fim inesperado do arquivo do comando `if' na linha 2

O que aconteceu: um bloco aberto não foi fechado: faltou o fi de um if, o done de um laço, ou uma aspa.

Como resolver: o Bash 5.3 do Arch já diz onde o bloco começou (na linha 2); a "linha 6" é o fim do arquivo, onde ele percebeu a falta. Vá à linha 2 e feche o bloco. Versões antigas do Bash (como a do Debian 13) só mostram "fim prematuro do arquivo", sem a pista.

Funciona no seu Arch, mas dá [[: not found no Debian ou no Ubuntu 
$ cat testa.sh
#!/usr/bin/env bash
if [[ -f /etc/arch-release ]]; then echo "Isto é um Arch Linux"; fi
$ sh testa.sh
Isto é um Arch Linux                         « no Arch, sh é o bash: funciona

O que aconteceu: rodar sh script.sh ignora o shebang e usa o sh. No Arch, sh é o Bash, então recursos do Bash como [[ ]] funcionam. No Debian e no Ubuntu, sh é o dash, e o mesmo comando falha com testa.sh: 2: [[: not found.

Como resolver: rode scripts Bash com bash script.sh ou ./script.sh, nunca com sh, e use o shebang #!/usr/bin/env bash. Se você quer escrever scripts que rodem em sh de verdade, teste-os com o dash: sudo pacman -S dash e dash script.sh.

5. ./backup.sh responde "Permissão negada" e echo $? mostra 126. O que falta?

6. Um script dá env: “bash\r”: Arquivo ou diretório inexistente. Qual a causa?

7. Um script faz cd /tmp. Depois de ./script.sh, em que pasta o seu terminal está?

Resumo

  • Script = arquivo de texto com comandos. A primeira linha é o shebang: #!/usr/bin/env bash. Linhas com # são comentários.
  • bash script.sh roda sem preparação; para ./script.sh, antes rode chmod +x (uma vez).
  • Para rodar pelo nome, guarde em ~/.local/bin e, no Arch, ponha essa pasta no PATH pelo ~/.bashrc.
  • O código de saída diz se deu certo: 0 é sucesso, 126 é "sem permissão", 127 é "não encontrado".
  • Use set -euo pipefail, depure com bash -x/bash -n e revise com shellcheck. ^M no cat -A = arquivo do Windows.
