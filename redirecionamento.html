Arch Redirecionamento

Normalmente, o que um comando responde aparece na tela. Redirecionar é mandar essa resposta para outro lugar, como um arquivo, ou pegar a entrada de um arquivo em vez do teclado. Com três ou quatro símbolos você salva a lista dos seus pacotes, separa erros de resultados e cria arquivos de configuração.

Você vai aprender
  • O que são os três canais de todo comando: entrada, saída e erro.
  • A diferença entre > (substitui) e >> (acrescenta), e a proteção noclobber.
  • Como separar ou juntar erros com 2>, 2>&1, &> e /dev/null.
  • A usar <, here-doc e here-string para dar entrada a um comando.
  • Por que sudo echo … > /etc/arquivo dá "Permissão negada", e como gravar como root com sudo tee.

Quem faz o redirecionamento é o shell (o Bash), não o comando. Por isso tudo aqui vale para qualquer programa: ls, pacman, grep… O shell do Arch é o Bash 5.3 (veja O Terminal no Arch).

Os três canais de um comando

Todo programa que roda no terminal nasce com três "canos" ligados. Cada um tem um número (o descritor de arquivo), e é por esse número que você o redireciona.

               ┌───────────┐ ── 1 · saída (stdout) ──►  tela
  teclado ──►  │  comando  │
  0 · entrada  └───────────┘ ── 2 · erro (stderr)  ──►  tela
NúmeroNomeEm inglêsPara onde vai, sem redirecionar
0Entrada padrãostandard input, stdinVem do teclado
1Saída padrãostandard output, stdoutVai para a tela: a resposta "normal"
2Saída de errostandard error, stderrVai para a tela também: as mensagens de erro

Dá para ver os três canais de verdade. No Linux, a pasta /proc/self/fd mostra os descritores do próprio comando que está rodando:

$ ls -l /proc/self/fd
total 0
lrwx------ 1 ana ana 64 16 out 15:01 0 -> /dev/pts/0     « entrada: o terminal
lrwx------ 1 ana ana 64 16 out 15:01 1 -> /dev/pts/0     « saída: o terminal
lrwx------ 1 ana ana 64 16 out 15:01 2 -> /dev/pts/0     « erro: o terminal
lr-x------ 1 ana ana 64 16 out 15:01 3 -> /proc/13267/fd « (a pasta que o ls abriu para ler)

Os três apontam para /dev/pts/0, o seu terminal. Como a saída e o erro aparecem na mesma tela, parecem uma coisa só. Mas são canais separados, e isso vai fazer diferença daqui a pouco. Redirecionar é justamente trocar para onde um desses números aponta.

Gravar a saída num arquivo: >

O sinal > (maior que) pega a saída do comando e grava num arquivo, em vez de mostrar na tela.

ls Documentos
O comando, que normalmente mostraria a lista na tela.
>
"Mande a saída (canal 1) para…" (é o mesmo que 1>).
lista.txt
…este arquivo. Se não existir, é criado.
$ ls Documentos > lista.txt
$ cat lista.txt
acesso.log
alunos.csv
notas.txt
projetos
relatorio.odt

Repare em duas coisas:

  • O primeiro comando não mostrou nada: a lista foi para o arquivo, não para a tela.
  • No arquivo, cada nome está numa linha. Quando a saída não é a tela, o ls não organiza em colunas nem colore.

Um uso muito do Arch: a lista dos seus pacotes

Antes de reinstalar o sistema, todo usuário de Arch salva a lista de pacotes que instalou de propósito. O pacman -Qqe lista só os nomes (q = quiet) dos pacotes explícitos (e); com >, vira um arquivo:

$ pacman -Qqe > pacotes.txt
$ wc -l pacotes.txt
45 pacotes.txt                      « 45 pacotes instalados de propósito
$ head -n 3 pacotes.txt
arch-install-scripts
base
base-devel

Mais adiante você vai ver como usar esse arquivo de volta, com <. As opções do -Q estão em pacman: o Básico.

Atenção: > substitui o conteúdo

Se o arquivo já existe, o > apaga tudo o que havia nele antes de gravar. Ele não pergunta.

$ echo "primeira linha" > teste.txt
$ echo "segunda linha" > teste.txt
$ cat teste.txt
segunda linha                       « a primeira sumiu
O arquivo é esvaziado antes de o comando rodar

O shell prepara o redirecionamento antes de executar o comando. Por isso, sort frutas.txt > frutas.txt apaga o arquivo: quando o sort vai ler, ele já está vazio. Grave sempre num arquivo diferente (ou use sed -i, veja sed).

Acrescentar ao final: >>

Dois sinais, >>, gravam no fim do arquivo, sem apagar o que já estava lá. É o que você quer para diários, logs e listas.

echo "kiwi"
Produz uma linha de texto.
>>
"Acrescente ao final de…" (em inglês, append).
frutas.txt
O arquivo. Também é criado se não existir.
$ echo "kiwi" >> frutas.txt
$ tail -n 3 frutas.txt
maçã
banana
kiwi                                « a linha nova entrou no fim

Um uso clássico é registrar quando algo aconteceu:

$ echo "$(date +%F) backup feito" >> diario.txt
$ cat diario.txt
2026-10-16 backup feito

Missão: grave a lista de arquivos da pasta Downloads num arquivo chamado downloads.txt. Depois acrescente, no fim dele, a linha fim da lista. Confira com cat downloads.txt.

A proteção noclobber

Como o > apaga sem perguntar, o Bash tem uma trava opcional: set -o noclobber (clobber = "atropelar"). Com ela ligada, o > se recusa a sobrescrever um arquivo que já existe. O >> continua funcionando, e o >| força a sobrescrita quando você tem certeza:

$ set -o noclobber
$ echo "teste" > tudo.txt
bash: tudo.txt: impossível sobrescrever arquivo existente
$ echo $?
1
$ echo "teste" >| tudo.txt          « >| = "sim, eu quero sobrescrever"
$ cat tudo.txt
teste
$ set +o noclobber                  « desliga a trava

O .bashrc que o Arch cria para cada usuário não liga essa trava. Se quiser ela sempre, acrescente set -o noclobber ao seu ~/.bashrc (veja .bashrc, alias, PATH).

Prova: o erro "vaza" para a tela

Agora vamos pedir dois itens ao ls: a pasta Documentos, que existe, e nada, que não existe. A saída vai para um arquivo. Veja o que acontece:

$ ls Documentos nada > saida.txt
ls: não foi possível acessar 'nada': Arquivo ou diretório inexistente    « apareceu mesmo assim!
$ echo $?
2                                   « o ls avisa que houve problema
$ cat saida.txt
Documentos:
acesso.log
alunos.csv
notas.txt
projetos
relatorio.odt                       « o arquivo só tem a parte boa

O > redireciona só o canal 1 (saída). A mensagem de erro sai pelo canal 2, que continua apontando para a tela. Para mexer no erro, você precisa dizer o número dele.

Redirecionar erros: 2>

ls Documentos nada
Um comando que vai produzir saída e erro.
2>
"Mande o canal 2 (erros) para…". Sem espaço entre o 2 e o >.
erros.txt
…este arquivo.
$ ls Documentos nada 2> erros.txt
Documentos:
acesso.log  alunos.csv  notas.txt  projetos  relatorio.odt     « a saída boa veio para a tela
$ cat erros.txt
ls: não foi possível acessar 'nada': Arquivo ou diretório inexistente   « o erro foi para o arquivo

Para não apagar erros antigos, use 2>>, que acrescenta.

Missão: rode ls Imagens nada mandando só os erros para o arquivo erros.txt. A lista de imagens deve continuar aparecendo na tela.

Jogar fora: /dev/null

/dev/null é um arquivo especial que descarta tudo o que recebe. É o "buraco negro" do Linux: qualquer um pode escrever nele, e ler dele não devolve nada.

$ ls -l /dev/null
crw-rw-rw- 1 root root 1, 3 16 out 14:51 /dev/null    « c = dispositivo; todos podem ler e escrever
$ echo "some" > /dev/null
$ cat /dev/null                     « não mostra nada: o texto sumiu
$

Ele é útil quando você só quer o resultado e não se importa com os avisos. Exemplo: ler a primeira linha de três arquivos do /etc, sendo que um deles (/etc/shadow, as senhas) só o root pode ler:

$ head -n 1 /etc/hostname /etc/shadow /etc/locale.conf
==> /etc/hostname <==
notebook
head: não foi possível abrir '/etc/shadow' para leitura: Permissão negada    « ruído

==> /etc/locale.conf <==
LANG=pt_BR.UTF-8
$ head -n 1 /etc/hostname /etc/shadow /etc/locale.conf 2>/dev/null
==> /etc/hostname <==
notebook

==> /etc/locale.conf <==
LANG=pt_BR.UTF-8                    « só o que interessa

"Está instalado?" — só o código de saída

Às vezes você não quer ver nada, só saber se deu certo. O pacman -Q responde com o código: 0 se o pacote está instalado, 1 se não. A mensagem de erro do pacman sai pelo canal 2:

$ pacman -Q tmux
erro: o pacote "tmux" não foi encontrado     « canal 2
$ echo $?
1
$ pacman -Q tmux 2>/dev/null
$ echo $?
1                                   « o erro sumiu, mas o código continua
$ pacman -Q bash > /dev/null
$ echo $?
0                                   « bash está instalado
$ pacman -Q firefox &> /dev/null && echo "firefox instalado" || echo "firefox não instalado"
firefox não instalado

No último, &> /dev/null joga fora saída e erro (explicado logo abaixo), e o &&/|| escolhe a frase pelo código. É um padrão muito comum em scripts (veja Condicionais).

Saída e erro no mesmo arquivo: 2>&1

Às vezes você quer tudo junto, por exemplo num log. Para isso, primeiro mande a saída para o arquivo e, depois, diga que o erro (2) vai para o mesmo lugar da saída (1).

ls Documentos nada
O comando.
> tudo.txt
Primeiro: a saída (1) vai para tudo.txt.
2>&1
Depois: o erro (2) vai para onde o 1 aponta agora. O & indica que 1 é um canal, não um arquivo chamado "1".
$ ls Documentos nada > tudo.txt 2>&1
$ cat tudo.txt
ls: não foi possível acessar 'nada': Arquivo ou diretório inexistente    « o erro também entrou
Documentos:
acesso.log
alunos.csv
notas.txt
projetos
relatorio.odt

O Bash tem um atalho que faz a mesma coisa: &> (e &>> para acrescentar).

$ ls Documentos nada &> tudo2.txt
$ cmp tudo.txt tudo2.txt && echo iguais
iguais
A ordem importa

comando 2>&1 > arquivo não junta os dois. O 2>&1 é lido primeiro, quando o 1 ainda aponta para a tela. Então o erro continua na tela, e só a saída vai para o arquivo. Escreva sempre > arquivo 2>&1.

O contrário também existe: >&2 manda a saída de um comando para o canal de erro. É assim que os scripts escrevem as suas mensagens de erro: echo "arquivo não encontrado" >&2.

Ler a entrada de um arquivo: <

O < faz o caminho contrário: em vez do teclado, a entrada (canal 0) vem de um arquivo. Muitos comandos aceitam o nome do arquivo direto, mas há uma diferença sutil:

$ wc -l frutas.txt
8 frutas.txt                 « o wc abriu o arquivo e sabe o nome dele
$ wc -l < frutas.txt
8                            « o wc só recebeu o conteúdo, sem nome

(São 8 linhas porque acrescentamos o kiwi lá em cima.) A segunda forma é ótima para scripts, quando você quer só o número:

$ echo "Tenho $(wc -l < frutas.txt) frutas na lista"
Tenho 8 frutas na lista

De volta à lista de pacotes

O pacman aceita um - no lugar dos nomes, que quer dizer "leia os nomes da entrada padrão". Junto com <, ele instala a lista que você salvou com pacman -Qqe > pacotes.txt. O --needed pula o que já está instalado. Num sistema que já tem tudo, a resposta é esta (aqui com uma lista curta, de três pacotes):

$ printf "base\nbash\nsed\n" > tres.txt
$ sudo pacman -S --needed - < tres.txt
[sudo] senha para ana:
atenção: base-3-3 está atualizado -- ignorando
atenção: bash-5.3.20-1 está atualizado -- ignorando
atenção: sed-4.10-2 está atualizado -- ignorando
nada para fazer

Numa instalação nova, o mesmo comando instalaria tudo de uma vez. A Arch Wiki chama isso de "reinstalar a partir de uma lista" (link no fim da página).

Texto no próprio comando: here-doc e here-string

O here-doc ("documento aqui") envia várias linhas digitadas como entrada. Ele começa com <<FIM e termina na linha que tem só FIM. Junto com >, é a forma mais prática de criar um arquivo de várias linhas dentro de um script.

cat
Repete o que recebe.
<<FIM
"A entrada são as próximas linhas, até aparecer FIM." O nome FIM é livre; EOF (end of file) é o mais comum.
> config.txt
Grava o resultado no arquivo.
$ cat <<FIM > config.txt
> nome=loja
> porta=8080
> FIM
$ cat config.txt
nome=loja
porta=8080

O > no começo das linhas do meio é o prompt de continuação do Bash. Você não digita esse sinal. Dentro do here-doc, as variáveis são trocadas pelo valor; com o nome entre aspas (<<'EOF'), o texto vai exatamente como está:

$ cat <<EOF
> Usuária: $USER
> EOF
Usuária: ana
$ cat <<'EOF'
> Usuária: $USER
> EOF
Usuária: $USER

A here-string, <<<, manda uma única linha:

$ tr a-z A-Z <<< "ola mundo"
OLA MUNDO

Gravar num arquivo do root: sudo tee

Este é um dos erros mais comuns de quem está começando. A ana quer acrescentar um apelido de rede no /etc/hosts, que é do root:

$ ls -l /etc/hosts
-rw-r--r-- 1 root root 119 12 out  2025 /etc/hosts    « só o root escreve
$ echo "192.168.0.50 servidor" >> /etc/hosts
bash: /etc/hosts: Permissão negada
$ sudo echo "192.168.0.50 servidor" >> /etc/hosts
bash: /etc/hosts: Permissão negada                     « nem com sudo!

Por que o sudo não resolveu? Repare que quem reclama é o bash:, não o sudo. Quem abre o arquivo para escrever é o seu shell, que roda como a ana, e ele faz isso antes de rodar o comando. O sudo só eleva o echo, que não precisa de poder nenhum. O >> ficou de fora.

  sudo echo "…"  >> /etc/hosts
  └─── root ───┘  └── ana (o shell) ──► Permissão negada

A solução é ter um programa rodando como root que escreva no arquivo. Esse programa é o tee: ele lê a entrada e grava num arquivo (e também mostra na tela). Com sudo na frente, quem abre o arquivo é o tee do root:

echo "192.168.0.50 servidor"
Produz a linha, como a ana (não precisa de root).
|
Um pipe: a saída do echo vira a entrada do próximo comando.
sudo tee
O tee, rodando como root.
-a
append: acrescenta no fim (como >>). Sem o -a, o tee substitui o arquivo (como >)!
/etc/hosts
O arquivo do root.
$ echo "192.168.0.50 servidor" | sudo tee -a /etc/hosts
[sudo] senha para ana:
192.168.0.50 servidor               « o tee mostra o que gravou
$ tail -n 1 /etc/hosts
192.168.0.50 servidor

No laboratório, o /etc/hosts é compartilhado, então este sudo tee -a foi feito num arquivo de teste do root, com a mesma saída (a sessão acima é ilustrativa quanto ao caminho). No primeiro sudo de um Arch novo, antes da senha aparece o "sermão" do sudo ("Presumimos que você recebeu as instruções de sempre…"). Para não ver a linha repetida na tela, acrescente > /dev/null no fim: echo "…" | sudo tee -a /etc/hosts > /dev/null.

Missão (simulada, nada muda no seu computador): acrescente a linha 192.168.0.50 servidor ao fim do /etc/hosts. Tente primeiro com >> para ver o erro; depois faça do jeito certo. A senha da ana é ana.

Quando não funciona

O arquivo ficou vazio 
$ sort frutas.txt > frutas.txt
$ cat frutas.txt
$ wc -l frutas.txt
0 frutas.txt                      « o arquivo foi esvaziado

O que aconteceu: o > esvaziou frutas.txt antes de o sort ler.

Como resolver: grave em outro arquivo e depois renomeie: sort frutas.txt > ordenado.txt && mv ordenado.txt frutas.txt. O conteúdo perdido não volta, a não ser que você tenha backup (ou snapshots, veja Snapshots).

"impossível sobrescrever arquivo existente" 
$ echo "teste" > tudo.txt
bash: tudo.txt: impossível sobrescrever arquivo existente

O que aconteceu: a proteção noclobber está ligada (alguém rodou set -o noclobber ou colocou isso no ~/.bashrc).

Como confirmar: set -o | grep noclobber mostra on.

Como resolver: se tiver certeza, force com >|: echo "teste" >| tudo.txt. Para desligar a proteção: set +o noclobber.

"Arquivo ou diretório inexistente" ao gravar 
$ ls > relatorios/hoje.txt
bash: relatorios/hoje.txt: Arquivo ou diretório inexistente

O que aconteceu: o > cria o arquivo, mas não cria pastas. A pasta relatorios não existe.

Como resolver: mkdir -p relatorios e repita o comando (veja touch e mkdir).

"Permissão negada" mesmo com sudo 
$ sudo echo "192.168.0.50 servidor" >> /etc/hosts
bash: /etc/hosts: Permissão negada

O que aconteceu: o redirecionamento é feito pelo seu shell (a ana), não pelo sudo. A mensagem começa com bash:, o que confirma que quem falhou foi o shell.

Como resolver: echo "…" | sudo tee -a /etc/hosts, ou sudo sh -c 'echo "…" >> /etc/hosts'.

Usei 2>&1 e o erro continuou na tela 
$ ls Documentos nada 2>&1 > tudo.txt
ls: não foi possível acessar 'nada': Arquivo ou diretório inexistente

O que aconteceu: a ordem está trocada. Quando o 2>&1 foi lido, o canal 1 ainda era a tela.

Como resolver: ls Documentos nada > tudo.txt 2>&1, ou o atalho &> tudo.txt.

Escrevi 2 > erros.txt (com espaço)

O que aconteceu: com espaço, o 2 deixa de ser o número do canal e vira um argumento do comando. ls nada 2 > erros.txt procura um arquivo chamado "2", e o erro continua na tela.

Como resolver: escreva 2> grudado.

Exercícios

1. Acrescentar sem apagar

Complete para adicionar a linha "reunião às 15h" ao fim de agenda.txt, sem perder o que já está lá:

echo "reunião às 15h" agenda.txt

2. Esconder os erros

Complete para ver a primeira linha dos arquivos sem as mensagens de "Permissão negada":

head -n 1 /etc/hostname /etc/shadow

3. Tudo no mesmo log

Complete para gravar saída e erros de ./backup.sh no arquivo backup.log:

./backup.sh > backup.log

4. Arquivo do root

Complete para acrescentar uma linha ao /etc/hosts como root:

echo "10.0.0.5 nas" | sudo /etc/hosts

5. Você rodou ls Documentos nada > saida.txt. O que acontece com a mensagem de erro sobre "nada"?

6. A ana rodou sudo echo "x" > /etc/teste e recebeu "bash: /etc/teste: Permissão negada". Por quê?

Resumo

  • Todo comando tem três canais: 0 (entrada), 1 (saída) e 2 (erro).
  • > grava substituindo, >> grava acrescentando. Os dois criam o arquivo, mas não a pasta. noclobber protege contra o >.
  • 2> mexe só nos erros; 2>/dev/null joga os erros fora; o código de saída continua valendo.
  • Para juntar tudo: > arquivo 2>&1, nessa ordem, ou &> arquivo.
  • < usa um arquivo como entrada; pacman -Qqe > lista e pacman -S --needed - < lista salvam e restauram seus pacotes.
  • Para escrever em arquivos do root: echo … | sudo tee -a /etc/arq. sudo echo … > /etc/arq não funciona.

O truque de salvar e restaurar a lista de pacotes está em pacman/Tips and tricks — List of installed packages e Install packages from a list.
