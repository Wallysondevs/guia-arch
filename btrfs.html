Arch Btrfs

O Btrfs (lê-se "bê-tê-ér-éfe-ésse", ou "butter FS"; o nome vem de B-tree file system) é um sistema de arquivos moderno que faz o que o ext4 não faz: subvolumes, snapshots instantâneos, compressão transparente e conferência de cada bloco por soma de verificação. É a base dos snapshots automáticos que deixam você "voltar no tempo" depois de uma atualização ruim.

Você vai aprender
  • O que é cópia na escrita (CoW), subvolume e snapshot, sem mistério.
  • Criar um Btrfs com mkfs.btrfs e o layout de subvolumes mais usado no Arch (@, @home, @var_log, @snapshots).
  • Montar com subvol= e compress=zstd e ler o espaço com btrfs filesystem df e usage.
  • Conferir a saúde dos dados com btrfs scrub (e ver um erro de verdade).
  • O que muda na instalação do Arch quando a raiz é Btrfs.

Os conceitos antes dos comandos

Cópia na escrita (CoW)

No ext4, quando você altera um arquivo, os blocos antigos são sobrescritos no lugar. No Btrfs, a alteração é gravada em blocos novos e só no fim o sistema "aponta" para eles. Os blocos antigos continuam lá até ninguém mais precisar deles. Isso se chama cópia na escrita (copy-on-write, CoW).

Pense num caderno: em vez de apagar uma frase com borracha, você escreve a frase nova numa folha limpa e muda o índice para apontar para ela. Se faltar luz no meio, o índice ainda aponta para a versão antiga, inteira. E se você guardar uma cópia do índice antigo, ganhou de graça uma "foto" do caderno naquele momento: isso é um snapshot.

Subvolume

Um subvolume parece uma pasta, mas é uma árvore de arquivos independente dentro do mesmo Btrfs. Ele pode ser montado sozinho (como se fosse uma partição) e pode ganhar snapshots próprios. Todos os subvolumes dividem o mesmo espaço livre: não é preciso decidir tamanhos, como nas partições.

Snapshot

Um snapshot é um subvolume novo que começa compartilhando todos os blocos com o original. Por causa do CoW, ele é criado em menos de um segundo e quase não ocupa espaço; só passa a ocupar quando os arquivos mudam. Os snapshots têm aula própria: Snapshots (snapper).

Compressão e somas de verificação

O Btrfs pode comprimir os dados ao gravar (com zstd, lzo ou zlib) e descomprimir ao ler, sem você perceber. E guarda uma soma de verificação (checksum, por padrão crc32c) de cada bloco: se o disco devolver um bloco estragado, o Btrfs percebe e avisa, em vez de entregar lixo ao programa.

Recursoext4Btrfs
Snapshots instantâneosNãoSim
Subvolumes (vários "/" e "/home" no mesmo espaço)NãoSim
Compressão transparenteNãoSim (compress=zstd)
Soma de verificação dos dadosNão (só metadados)Sim

O laboratório: um disco de mentira

A máquina do guia (a notebook) foi instalada com raiz ext4, como em Formatar e Montar. Para treinar Btrfs sem arriscar nada, vamos usar um arquivo-imagem: um arquivo comum que o Linux trata como se fosse um disco. Tudo o que você fizer nele fica dentro do arquivo; para "jogar o disco fora", basta apagar o arquivo.

truncate
Muda o tamanho de um arquivo (e cria se não existir).
-s 3G
Tamanho: 3 GiB. O arquivo é esparso: só ocupa espaço real quando algo é gravado nele.
/var/tmp/a8/disco.img
O arquivo-imagem.
#> mkdir -p /var/tmp/a8 /mnt/a8
#> truncate -s 3G /var/tmp/a8/disco.img
#> ls -lh /var/tmp/a8/disco.img
-rw-r--r-- 1 root root 3,0G 16 out 13:22 /var/tmp/a8/disco.img   « o tamanho "anunciado"
#> du -h /var/tmp/a8/disco.img
0	/var/tmp/a8/disco.img                                         « o espaço realmente usado
#> losetup -f --show /var/tmp/a8/disco.img
/dev/loop1                                                         « o "disco" novo

losetup (de loop setup) liga o arquivo a um dispositivo de loop, /dev/loopN. -f pega o primeiro livre e --show imprime qual foi. Daqui em diante, /dev/loop1 é o nosso "disco". No seu computador o número pode ser outro: use o que o comando mostrar.

Formatar apaga tudo

Os comandos desta aula destroem o conteúdo do dispositivo indicado. No laboratório isso é um arquivo. No seu computador, confira três vezes com lsblk antes de escrever /dev/sdX ou /dev/nvme0n1pN (veja lsblk, df, du).

Subvolumes: o layout do Arch

Depois de formatar, o Btrfs tem um único subvolume, o topo (top level, ID 5). Monte o topo e crie os subvolumes dentro dele:

btrfs
A ferramenta única do Btrfs (pacote btrfs-progs).
subvolume create
Grupo subvolume, ação create. Pode abreviar: btrfs su cr.
/mnt/a8/@home
Onde criar. O @ no começo é só uma convenção de nome, não tem efeito especial.
#> mount /dev/loop1 /mnt/a8
#> btrfs subvolume create /mnt/a8/@
Create subvolume '/mnt/a8/@'
#> btrfs subvolume create /mnt/a8/@home
Create subvolume '/mnt/a8/@home'
#> btrfs subvolume create /mnt/a8/@var_log
Create subvolume '/mnt/a8/@var_log'
#> btrfs subvolume create /mnt/a8/@snapshots
Create subvolume '/mnt/a8/@snapshots'
#> btrfs subvolume list /mnt/a8
ID 256 gen 9 top level 5 path @
ID 257 gen 9 top level 5 path @home
ID 258 gen 9 top level 5 path @var_log
ID 259 gen 9 top level 5 path @snapshots
#> ls -l /mnt/a8
total 0
drwxr-xr-x 1 root root 0 16 out 13:23 @
drwxr-xr-x 1 root root 0 16 out 13:23 @home
drwxr-xr-x 1 root root 0 16 out 13:23 @snapshots
drwxr-xr-x 1 root root 0 16 out 13:23 @var_log
Coluna de subvolume listSignificado
ID 256Número do subvolume. O topo é sempre o 5; os criados começam em 256.
gen 9Geração: um contador de transações. Sobe a cada gravação no subvolume.
top level 5Dentro de qual subvolume ele está (aqui, no topo).
path @homeO caminho a partir do topo.

Por que separar em subvolumes?

Um snapshot de um subvolume não inclui os subvolumes de dentro dele. É isso que permite voltar o sistema (/) para ontem sem desfazer o trabalho de hoje em /home, e sem apagar os logs que explicam o que deu errado.

SubvolumeMontado emPor que separado
@/O sistema. É ele que ganha snapshots antes de cada atualização.
@home/homeSeus arquivos não "voltam no tempo" quando você restaura o sistema.
@var_log/var/logOs logs sobrevivem a uma restauração (você vai querer ler o que aconteceu).
@snapshots/.snapshotsOnde o snapper guarda os snapshots de @, fora do próprio @.
@pkg (opcional)/var/cache/pacman/pkgNão guardar o cache de pacotes em todos os snapshots.

Esse é o layout sugerido na Arch Wiki para usar com o snapper, e o que o archinstall cria quando você escolhe Btrfs. Nada obriga a usá-lo, mas ele evita muita dor de cabeça.

Montar com subvol= e compress=zstd

Agora desmonte o topo e monte cada subvolume no seu lugar, como seria numa instalação:

mount
Monta um sistema de arquivos.
--mkdir
Cria a pasta de destino se ela não existir.
-o subvol=@home,compress=zstd
Opções: qual subvolume montar e ligar a compressão zstd.
/dev/loop1
O dispositivo (o mesmo para todos os subvolumes).
/mnt/a8/home
Onde montar.
#> umount /mnt/a8
#> mount -o subvol=@,compress=zstd /dev/loop1 /mnt/a8
#> mount --mkdir -o subvol=@home,compress=zstd /dev/loop1 /mnt/a8/home
#> mount --mkdir -o subvol=@var_log,compress=zstd /dev/loop1 /mnt/a8/var/log
#> mount --mkdir -o subvol=@snapshots,compress=zstd /dev/loop1 /mnt/a8/.snapshots
#> findmnt -R /mnt/a8

├─/mnt/a8/var/log    /dev/loop1[/@var_log]   btrfs  rw,relatime,compress=zstd:3,ssd,discard=async,space_cache=v2,subvolid=258,subvol=/@var_log
└─/mnt/a8/.snapshots /dev/loop1[/@snapshots] btrfs  rw,relatime,compress=zstd:3,ssd,discard=async,space_cache=v2,subvolid=259,subvol=/@snapshots
#> lsblk /dev/loop1
NAME  MAJ:MIN RM SIZE RO TYPE MOUNTPOINTS

                              /mnt/a8/var/log
                              /mnt/a8/home
                              /mnt/a8

O mesmo dispositivo aparece montado quatro vezes, cada vez mostrando um subvolume (o [/@home] na coluna SOURCE). As opções que você não pediu foram ligadas sozinhas:

OpçãoO que faz
compress=zstd:3Compressão zstd no nível 3 (o padrão; vai de 1 a 15). Só vale para o que for gravado depois da montagem.
ssdOtimizações para SSD, detectadas automaticamente.
discard=asyncAvisa o SSD sobre blocos liberados, em segundo plano (padrão desde o kernel 6.2 em SSDs).
space_cache=v2A árvore de espaço livre, padrão moderno.
subvolid=256O ID do subvolume montado (equivale ao subvol=).
relatimeNão grava a hora de acesso a cada leitura. Muita gente usa noatime no Btrfs para reduzir escritas (e o CoW que elas causam).

A compressão funcionando

Repare: o texto de 908 KiB quase não aparece no used. Para ver melhor, grave 100 MiB de texto repetido e compare o antes e o depois:

#> yes "Guia Arch: linha repetida de um arquivo de texto" | head -c 100M > /mnt/a8/home/ana/texto-grande.txt
#> sync
#> ls -lh /mnt/a8/home/ana/texto-grande.txt
-rw-r--r-- 1 root root 100M 16 out 13:23 /mnt/a8/home/ana/texto-grande.txt
#> btrfs filesystem df /mnt/a8 | head -1
Data, single: total=328.00MiB, used=53.16MiB     « era 50.03 MiB: 100 MiB viraram ~3 MiB

O ls mostra o tamanho do arquivo (100 MiB); o disco gastou cerca de 3 MiB. Dados aleatórios (fotos, vídeos, arquivos .zst) não comprimem, e o Btrfs percebe isso e grava sem comprimir. Para ver a taxa por arquivo existe o compsize (pacote compsize, repositório extra), que não está instalado na máquina do guia.

Para saber quanto cada pasta ocupa de verdade, contando o que é compartilhado com snapshots, use btrfs filesystem du:

#> btrfs filesystem du /mnt/a8/home/ana
     Total   Exclusive  Set shared  Filename
 908.00KiB   908.00KiB           -  /mnt/a8/home/ana/relatorio.txt
  50.00MiB    50.00MiB           -  /mnt/a8/home/ana/aleatorio.bin
  50.89MiB    50.89MiB       0.00B  /mnt/a8/home/ana

Exclusive é o que só esse arquivo usa; Set shared é o que ele divide com snapshots (aqui, nada ainda). Os tamanhos são os não comprimidos.

Conferir a saúde: btrfs scrub

O scrub (esfregar, faxinar) lê todos os blocos usados e confere cada soma de verificação. Quando há uma segunda cópia (metadados DUP, ou dados em raid1), ele conserta o bloco ruim com a cópia boa. Pode rodar com o sistema montado e em uso.

btrfs scrub start
Começa a verificação.
-B
Fica em primeiro plano (don't Background) e mostra o resumo no fim. Sem ele, o scrub roda escondido e você consulta com btrfs scrub status.
/mnt/a8
Qualquer ponto de montagem do Btrfs: o scrub vale para o sistema de arquivos inteiro.
#> btrfs scrub start -B /mnt/a8
Starting scrub on devid 1
scrub done for 745b2685-6e7d-48ef-af91-5c4e8573d0fd
Scrub started:    Fri Oct 16 13:23:25 2026
Status:           finished
Duration:         0:00:00
Total to scrub:   54.03MiB
Rate:             54.03MiB/s
Error summary:    no errors found        « tudo certo
#> echo $?
0

Um erro de verdade

Para ver o scrub achando um problema, estragamos de propósito um bloco de 4 KiB de um arquivo, escrevendo zeros direto no arquivo-imagem (é o que um setor defeituoso faria). O arquivo importante.bin tinha 1 MiB de dados aleatórios:

#> dd if=/dev/zero of=/var/tmp/a8/disco.img bs=4096 seek=$((978321408/4096)) count=1 conv=notrunc
1+0 registro de entrada
1+0 registros de saída
4096 bytes (4,1 kB, 4,0 KiB) copiados, 7,9655e-05 s, 51,4 MB/s

Na leitura com o sha256sum, o kernel já tinha registrado: BTRFS warning (device loop1): csum failed root 257 ino 267 off 0 csum 0x8941f998 expected csum 0x9653f63a mirror 1. Snapshots ficam no mesmo disco e não substituem backup.

Scrub mensal automático

O btrfs-progs traz o timer btrfs-scrub@.timer. Para a raiz: systemctl enable --now btrfs-scrub@-.timer (o - é o nome "escapado" de /; para /home seria btrfs-scrub@home.timer). Veja Timers e Tarefas.

UUID=745b2685-6e7d-48ef-af91-5c4e8573d0fd	/.snapshots	btrfs     	rw,relatime,compress=zstd:3,ssd,discard=async,space_cache=v2,subvol=/@snapshots	0 0

# /dev/sda2
UUID=02576132-0458-4975-916f-94e08af9a31c	none      	swap      	defaults  	0 0

Três detalhes: o mesmo UUID aparece em todas as linhas (é o mesmo Btrfs); o último campo é 0 (o Btrfs não usa o fsck no boot); e o genfstab incluiu a swap porque ela estava ativa na máquina. Ele tira o subvolid= de propósito: assim, se você restaurar um snapshot no lugar do @, o fstab continua certo.

Experimente

Missão: confirme que a raiz da máquina do guia é ext4 e não Btrfs, usando lsblk -f (ou df -T /).

Quando não funciona

"appears to contain an existing filesystem" 
#> mkfs.btrfs /dev/loop1
ERROR: /dev/loop1 appears to contain an existing filesystem (type=ext4)
ERROR: use the -f option to force overwrite of /dev/loop1
btrfs-progs v7.1
See https://btrfs.readthedocs.io for more information.

O que aconteceu: o dispositivo já tem um sistema de arquivos e o mkfs.btrfs se protege (código de saída 1).

Como confirmar: lsblk -f /dev/loop1 mostra o tipo atual.

Como resolver: se tem certeza de que é o dispositivo certo e que pode apagar, mkfs.btrfs -f /dev/loop1.

mount: fsconfig() falhou: Arquivo ou diretório inexistente 
#> mount -o subvol=@ /dev/loop1 /var/tmp/a8/m
mount: /var/tmp/a8/m: fsconfig() falhou: Arquivo ou diretório inexistente.
       dmesg(1) pode ter mais informação após uma chamada a montar o sistema falhada.
#> echo $?
32

O que aconteceu: o subvolume @ não existe nesse Btrfs (aqui, recém-formatado). A mensagem fala de "arquivo", mas é o subvolume que falta.

Como confirmar: monte o topo (mount /dev/loop1 /mnt, sem subvol=) e rode btrfs subvolume list /mnt.

Como resolver: crie o subvolume ou corrija o nome (@ e @home são só convenções; o seu pode chamar root).

"tipo de sistema de arquivos incorreto, opção inválida…" 
#> mount -o subvol=@,compress=zsdt /dev/loop1 /var/tmp/a8/m
mount: /var/tmp/a8/m: tipo de sistema de arquivos incorreto, opção inválida, superbloco inválido em /dev/loop1, página de código ou programa auxiliar faltando ou outro erro.
       dmesg(1) pode ter mais informação após uma chamada a montar o sistema falhada.
#> journalctl -k -n 1 --no-pager -o short
out 16 13:43:42 notebook kernel: BTRFS error: failed to parse compression option 'zsdt'

O que aconteceu: uma opção digitada errado (zsdt em vez de zstd). A mensagem do mount é genérica; a explicação está no log do kernel, como o próprio mount sugere ("dmesg pode ter mais informação").

Como resolver: leia journalctl -k -n 5 (ou dmesg | tail) e corrija a opção. Se esse erro estiver no /etc/fstab da raiz, o sistema não liga: veja Recuperar o Boot.

"No space left on device" com espaço sobrando no df

O que aconteceu: o Btrfs reserva espaço em chunks separados para dados e metadados. Se todo o espaço foi reservado para dados e os metadados encheram, a gravação falha mesmo com o df mostrando espaço.

Como confirmar: btrfs filesystem usage /: Device unallocated perto de zero e Metadata perto de 100%.

Como resolver: apague snapshots antigos e rode um balance só dos chunks de dados pouco usados, que devolve espaço para o unallocated:

#> btrfs balance start -dusage=50 /var/tmp/a8/m
Done, had to relocate 1 out of 3 chunks

-dusage=50 = só os chunks de dados com até 50% de uso. Um balance sem filtros reescreve o disco inteiro e pode levar horas.

csum failed / Erro de entrada/saída ao ler um arquivo

O que aconteceu: o bloco no disco não bate com a soma de verificação (setor ruim, cabo, memória RAM com defeito).

Como confirmar: journalctl -k | grep -i csum e btrfs device stats /; rode btrfs scrub start -B / para achar todos os arquivos atingidos.

Como resolver: restaure os arquivos citados do backup, zere os contadores com btrfs device stats -z / depois de resolver, e verifique o disco (smartctl, do pacote smartmontools) e a memória. Não rode btrfs check --repair por conta própria: a própria documentação pede para usar só com orientação.

Desfazendo o laboratório

Sempre limpe o que criou: desmonte tudo, solte o loop e apague a imagem.

#> umount -R /mnt/a8
#> losetup -d /dev/loop1
#> rm /var/tmp/a8/disco.img

Resumo

  • Btrfs = cópia na escrita: alterações vão para blocos novos, e isso dá snapshots instantâneos.
  • Subvolumes são árvores independentes no mesmo espaço; o layout do Arch é @, @home, @var_log, @snapshots.
  • Monte cada um com -o subvol=NOME,compress=zstd; o genfstab escreve isso no fstab.
  • Use btrfs filesystem usage para ver o espaço de verdade.
  • btrfs scrub confere tudo; ele detecta corrupção, mas só conserta se houver segunda cópia. Backup continua obrigatório.
