Quando o sistema trava

A tela congelou, o mouse não mexe, nada responde. Antes de apertar o botão de energia, o Linux oferece uma escada de saídas, da mais suave para a mais bruta: trocar para outro terminal (TTY), matar o programa culpado, pedir ajuda direto ao kernel (Magic SysRq) e, só no fim, o botão. Depois do susto, o journalctl mostra o que aconteceu.

Você vai aprender
  • A diferença entre "um programa travou", "a interface gráfica travou" e "o sistema inteiro travou".
  • Usar os consoles de texto (TTY) com Ctrl+Alt+F3 e como o Arch os cria.
  • O que é o Magic SysRq, o que o valor 16 do Arch permite e como habilitar o REISUB.
  • O que o botão de energia faz com um toque e com o dedo segurando.
  • Ler o log do boot anterior com journalctl -b -1.

Três tipos de "travou"

"Travar" não é uma coisa só. Descobrir qual é o seu caso decide a saída:

O que você vêO que provavelmente aconteceuPrimeira tentativa
Uma janela não responde, o resto funcionaUm programa travouFechar pela janela ou matar o processo (Processos e kill)
Nada responde, mas a luz do disco pisca ou a ventoinha aceleraA interface gráfica travou ou a memória acabou e o sistema está "afogado"Esperar 1–2 minutos; depois ir para um TTY
Nem o Caps Lock acende, nenhuma tecla tem efeitoO kernel travou (raro: driver, hardware)Magic SysRq; se nem isso, o botão
Primeiro degrau: esperar

Muitas vezes o sistema está só sem memória, trocando dados com a swap. Isso deixa tudo lentíssimo por um ou dois minutos e depois volta. Antes de qualquer coisa, espere um pouco.

Degrau 2: outro terminal (TTY)

O que é um TTY

Além da tela gráfica, o Linux tem consoles virtuais: telas de texto puro, cada uma com o seu próprio login. O nome TTY vem de teletypewriter (teletipo), as máquinas de escrever ligadas a computadores antigos. Eles ficam de prontidão mesmo quando a interface gráfica trava, porque são desenhados pelo próprio kernel.

Ctrl+Alt+F3
Vai para o console virtual 3 (tty3). Vale de F1 a F6.
Ctrl+Alt+F1 ou F2
Volta para a tela gráfica. Qual dos dois depende do gerenciador de login (GDM costuma usar o tty1 para a tela de login e o tty2 para a sessão; SDDM e LightDM, o tty1 ou o tty7). Experimente.
Alt+F3
Já dentro de um TTY de texto, basta Alt+F-número (ou Alt+←/→) para trocar.

No TTY aparece o pedido de login em texto, igual ao do primeiro boot. Digite o seu usuário e a senha (a senha não aparece enquanto você digita):

No Arch, os TTYs nascem quando você chega neles

Quem desenha o login: é um programa chamado agetty, iniciado pelo serviço getty@ttyN. Na VM do guia, logo depois do boot, só existe um:

$ systemctl list-units 'getty@*'
  UNIT               LOAD   ACTIVE SUB     DESCRIPTION
  getty@tty1.service loaded active running Getty on tty1     « só o tty1 está rodando

Legend: LOAD   → Reflects whether the unit definition was properly loaded.
        ACTIVE → The high-level unit activation state, i.e. generalization of SUB.
        SUB    → The low-level unit activation state, values depend on unit type.

1 loaded units listed. Pass --all to see loaded but inactive units, too.
To show all installed unit files use 'systemctl list-unit-files'.

Então como o Ctrl+Alt+F3 funciona? Quem cria os outros é o systemd-logind, na hora em que você troca para eles. O limite está no /etc/systemd/logind.conf:

$ grep -n 'NAutoVTs\|ReserveVT' /etc/systemd/logind.conf
20:#NAutoVTs=6       « até 6 consoles são criados sob demanda (tty1 a tty6)
21:#ReserveVT=6      « o tty6 fica sempre reservado para um login de texto

As linhas começam com #: são comentários que mostram o valor padrão. Ninguém mudou nada; o padrão já dá seis consoles. O serviço criado sob demanda se chama autovt@ttyN, que no Arch é só outro nome (um alias) do mesmo getty@:

$ systemctl list-unit-files 'getty@*' 'autovt@*'
UNIT FILE       STATE   PRESET
autovt@.service alias   -               « "alias" = apelido de outra unidade
getty@.service  enabled enabled

2 unit files listed.

Detalhes de serviços e unidades estão em systemctl e Serviços. O que importa aqui: o tty3 não aparece na lista até alguém ir para ele, e isso é normal.

No TTY: achar e matar o culpado

Já logado no TTY, a sequência é: listar os processos que mais gastam, achar o nome, matar. Na VM, um sleep faz o papel do "programa travado":

$ pgrep -a sleep
5853 sleep 700          « PID (número do processo) e o comando
$ kill 5853             « pede para ele terminar (sinal TERM)
$ pgrep -a sleep
$ echo $?
1                       « 1 = nenhum processo encontrado: ele morreu

Se o programa ignorar o pedido, kill -9 PID mata à força. A aula Processos e kill explica ps, top, htop, sinais, pkill e killall em detalhes. Um atalho para quem sabe o nome: killall firefox.

Reiniciar só a interface gráfica

Se o que travou foi o ambiente gráfico inteiro (GNOME, KDE…), reinicie o gerenciador de login. Ilustrativo: a VM do guia não tem interface gráfica; o nome do serviço depende do que você instalou em Instalar um Desktop.

$ sudo systemctl restart gdm       « GNOME
$ sudo systemctl restart sddm      « KDE Plasma
$ sudo systemctl restart lightdm   « XFCE e outros
Isso fecha tudo o que estava aberto na sessão gráfica

Reiniciar o gerenciador de login encerra a sessão: documentos não salvos se perdem. É melhor que o botão de energia (o disco é desmontado direito), mas não é "grátis".

Degrau 3: Magic SysRq, falar direto com o kernel

O que é

A Magic SysRq (System Request, "pedido ao sistema") é uma combinação de teclas que vai direto para o kernel, sem passar por interface gráfica, terminal ou programa nenhum. Enquanto o kernel estiver vivo, ela funciona. A combinação é:

Alt
Segure o Alt (o da esquerda).
SysRq
A tecla SysRq é a mesma do Print Screen (PrtSc). Em notebooks pode exigir Fn.
letra
Sem soltar as duas, aperte uma letra: cada letra é um comando (s = gravar no disco, b = reiniciar…).

O que vem ligado no Arch: só o "s"

Por segurança (qualquer pessoa no teclado poderia reiniciar a máquina), o kernel deixa você escolher quais comandos aceitar. A escolha fica em /proc/sys/kernel/sysrq:

$ cat /proc/sys/kernel/sysrq
16
$ sysctl kernel.sysrq
kernel.sysrq = 16

Quem coloca esse 16 é o próprio systemd, num arquivo de configuração do kernel que vem no pacote:

$ sed -n '14,19p' /usr/lib/sysctl.d/50-default.conf
# System Request functionality of the kernel (SYNC)
#
# Use kernel.sysrq = 1 to allow all keys.
# See https://docs.kernel.org/admin-guide/sysrq.html for a list
# of values and keys.
kernel.sysrq = 16
$ pacman -Qo /usr/lib/sysctl.d/50-default.conf
/usr/lib/sysctl.d/50-default.conf pertence a systemd 262-1

O número é uma soma: cada grupo de comandos vale uma potência de 2, e o valor final diz quais grupos estão liberados.

ValorLiberaLetras
0Nada (SysRq desligada)—
1Tudotodas
2Nível das mensagens do kernel no console0–9
4Controle do teclador, k
8Diagnóstico (listar processos, memória…)t, m, w, l…
16Gravar tudo no disco (sync)s
32Remontar os discos só leiturau
64Mandar sinais aos processose, i, f
128Reiniciar e desligarb, o
256Baixar a prioridade de tarefas de tempo realn

Com 16, o Arch aceita do teclado só o Alt+SysRq+s: gravar no disco o que estiver na memória. As outras letras são ignoradas.

REISUB: reiniciar "com educação"

A sequência clássica para reiniciar uma máquina travada sem estragar o disco é R E I S U B, uma letra por vez, com uns 2 segundos entre elas. Um jeito de decorar (em inglês): "Reboot Even If System Utterly Broken", ou ao contrário, "BUSIER".

TeclaNome no kernelO que fazPrecisa do bit
RunrawTira o teclado do controle da interface gráfica4
Eterminate-all-tasksManda o sinal TERM a todos os processos ("feche com calma")64
Ikill-all-tasksManda o sinal KILL a quem sobrou ("morra agora")64
SsyncGrava no disco os dados pendentes16
UunmountRemonta todos os sistemas de arquivos como só leitura32
BrebootReinicia na hora128

Trocando o último B por O (poweroff) você tem o REISUO: a mesma sequência, mas desliga em vez de reiniciar. Somando os bits da tabela, o REISUB precisa de 4 + 64 + 16 + 32 + 128 = 244.

Os nomes da coluna "Nome no kernel" são os que o próprio kernel usa. Como root, você pode pedir a ajuda da SysRq escrevendo h em /proc/sysrq-trigger (é inofensivo: só escreve a lista no log):

#> echo h > /proc/sysrq-trigger
#> journalctl -k -n 1 --no-pager
out 16 13:22:45 notebook kernel: sysrq: HELP : loglevel(0-9) reboot(b) crash(c) terminate-all-tasks(e) memory-full-oom-kill(f) kill-all-tasks(i) thaw-filesystems(j) sak(k) show-backtrace-all-active-cpus(l) show-memory-usage(m) nice-all-RT-tasks(n) poweroff(o) show-registers(p) show-all-timers(q) unraw(r) sync(s) show-task-states(t) unmount(u) force-fb(v) show-blocked-tasks(w) dump-ftrace-buffer(z) dump-sched-ext(D) replay-kernel-logs(R) reset-sched-ext(S)
Não escreva outras letras no /proc/sysrq-trigger

O valor 16 só limita o teclado. O arquivo /proc/sysrq-trigger aceita todas as letras, sempre: echo b ali reinicia a máquina na hora, sem gravar nada; echo c derruba o kernel de propósito. Use só o h para estudar.

A letra F: quando a memória acabou

A letra f (memory-full-oom-kill) chama o "matador por falta de memória" do kernel, que escolhe o processo que mais gasta e o mata. É o resgate ideal para o caso "tudo lento, disco piscando": um só aperto e o navegador com 80 abas some, o resto volta. Também precisa do bit 64. No Arch, nem o systemd-oomd nem o earlyoom (que fazem isso sozinhos) vêm ligados:

#> systemctl is-enabled systemd-oomd
disabled
#> pacman -Q earlyoom
erro: o pacote "earlyoom" não foi encontrado

Habilitar mais letras

Para usar o REISUB e o F, crie um arquivo seu em /etc/sysctl.d/ (o próprio comentário do 50-default.conf manda fazer assim). Ilustrativo: não foi aplicado na VM do guia, que é compartilhada.

# Libera REISUB/REISUO (4+16+32+64+128) para o teclado
kernel.sysrq = 244

$ sudo sysctl --system           « relê todos os arquivos de /etc/sysctl.d e /usr/lib/sysctl.d
* Aplicando /usr/lib/sysctl.d/10-arch.conf ...
* Aplicando /usr/lib/sysctl.d/50-coredump.conf ...
* Aplicando /usr/lib/sysctl.d/50-default.conf ...
* Aplicando /usr/lib/sysctl.d/50-pid-max.conf ...
* Aplicando /etc/sysctl.d/99-sysrq.conf ...        « o seu arquivo, por último
…
kernel.sysrq = 244
$ cat /proc/sys/kernel/sysrq
244

As linhas * Aplicando sem o seu arquivo e a lista de valores são as reais da VM (onde o comando foi rodado sem o 99-sysrq.conf, e o valor continuou 16); a linha do seu arquivo e o 244 são o que você verá depois de criá-lo.

/etc/sysctl.d/
Pasta das suas configurações do kernel. Ela vence a /usr/lib/sysctl.d/, que é do pacote e seria sobrescrita numa atualização.
99-
Os arquivos são lidos em ordem alfabética; o último a definir um valor vence. O 99 garante que o seu vem depois do 50-default.conf.
sysctl --system
Aplica agora, sem reiniciar. No próximo boot, o systemd-sysctl aplica sozinho.

Quer liberar tudo? Use kernel.sysrq = 1. Para mudar só até o próximo boot: sudo sysctl kernel.sysrq=244. Sem sudo, o kernel recusa:

$ sysctl kernel.sysrq=1
sysctl: permissão negada pela chave "kernel.sysrq"
$ echo $?
1

Degrau 4: o botão de energia

Como apertaQuem ageO que acontece
Um toque curtoO systemd-logindDesligamento normal: programas fecham, discos são desmontados. Só funciona se o sistema ainda responde.
Segurar 4–10 segundosO hardware (a placa-mãe)Corta a energia na hora. É como puxar a tomada.

O toque curto é configurado no mesmo logind.conf; o padrão (comentado) é desligar:

$ grep -n 'HandlePowerKey\|HandleLidSwitch' /etc/systemd/logind.conf
28:#HandlePowerKey=poweroff           « toque curto: desliga direito
29:#HandlePowerKeyLongPress=ignore    « segurar: o logind não faz nada (quem age é o hardware)
36:#HandleLidSwitch=suspend           « fechar a tampa do notebook: suspende
37:#HandleLidSwitchExternalPower=suspend
38:#HandleLidSwitchDocked=ignore
Segurar o botão é o último recurso

Os dados que ainda estavam na memória se perdem, e o sistema de arquivos precisa ser consertado no próximo boot. Se der, faça antes pelo menos Alt+SysRq+s (liberado no Arch) e espere uns segundos. E nunca corte a energia durante uma atualização do pacman: veja o que acontece em Atualizar o Sistema.

$ grep -n 'Storage' /etc/systemd/journald.conf

Procurar a causa

Para achar o motivo de um travamento, filtre por prioridade e olhe o final:

$ journalctl -b -1 -p err -n 3 --no-pager
out 16 13:05:01 notebook sudo[413]:      ana : a password is required ; PWD=/home/ana ; USER=root ; COMMAND=/usr/bin/true
out 16 13:06:09 notebook (sd-pam)[674]: pam_systemd(systemd-user:session): Varlink call io.systemd.Login.ReleaseSession failed: io.systemd.Login.NoSuchSession
out 16 13:06:09 notebook dbus-broker-launch[289]: Activation request for 'org.freedesktop.nm_dispatcher' failed.

-p err mostra só erros (e o que for mais grave). Nesse boot não houve nada assustador: um sudo sem senha e avisos normais do desligamento. Num travamento de verdade, procure linhas com Out of memory: Killed process (a memória acabou), BUG:, watchdog, hung_task ou o nome do driver de vídeo (amdgpu, i915, nvidia). Tudo sobre filtros está em Logs (journalctl).

Quando não funciona

Alt+SysRq+R, E, I… não fazem nada

O que aconteceu: no Arch, kernel.sysrq = 16 libera só o s. As outras letras são ignoradas sem aviso.

Como confirmar: cat /proc/sys/kernel/sysrq mostra 16.

Como resolver: crie /etc/sysctl.d/99-sysrq.conf com kernel.sysrq = 244 (ou 1) e rode sudo sysctl --system, antes do próximo travamento. Em alguns notebooks a tecla SysRq exige Fn, ou a combinação é Alt+Fn+PrtSc.

Ctrl+Alt+F3 mostra uma tela preta, sem "login:"

O que aconteceu: o autovt@tty3 não subiu, ou você foi para um console acima do NAutoVTs (por exemplo, F8 com o padrão 6). Também acontece de o driver de vídeo demorar a trocar de modo.

Como confirmar: de outro TTY ou por SSH, systemctl status getty@tty3.

Como resolver: tente Ctrl+Alt+F2 a F6; aperte Enter uma vez (o login: às vezes só aparece depois). Se o computador tem rede e SSH ligado, entrar por outra máquina (SSH) é outra porta de saída.

"Operação não permitida" no kill 
$ kill 1
bash: kill: (1) - Operação não permitida

O que aconteceu: o processo é de outro usuário (aqui, o systemd, do root). Um usuário comum só mata os próprios processos.

Como resolver: confira se é mesmo o processo certo (ps -o user,pid,cmd -p PID) e use sudo kill PID. Veja Processos e kill.

"No journal boot entry found" 
$ journalctl -b -10
No journal boot entry found for the specified boot (-10).
$ echo $?
1

O que aconteceu: o journal não tem esse boot: ele é mais antigo do que os logs guardados (o journal apaga os mais velhos quando enche) ou o journal não é persistente.

Como confirmar: journalctl --list-boots mostra quais existem; ls /var/log/journal mostra se há logs no disco.

Como resolver: use um índice que aparece na lista. Se /var/log/journal não existir (alguém apagou ou mudou Storage=), crie-a com sudo mkdir -p /var/log/journal e reinicie o systemd-journald; os próximos boots passam a ser guardados (veja Logs (journalctl)).

Resumo

  • Suba a escada: esperar → TTY (Ctrl+Alt+F3) → kill → reiniciar o gerenciador de login → SysRq → botão.
  • No Arch só o getty@tty1 roda no boot; os outros TTYs são criados sob demanda (NAutoVTs=6).
  • O Arch vem com kernel.sysrq = 16: só o s. Para o REISUB/REISUO, use 244 (ou 1) em /etc/sysctl.d/.
  • Toque curto no botão = desligamento normal; segurar = corte de energia.
  • O journal do Arch é persistente: journalctl --list-boots e journalctl -b -1 contam o que houve.
