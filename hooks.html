Hooks do pacman

Um hook ("gancho") é uma tarefa que o pacman executa sozinho antes ou depois de instalar, atualizar ou remover pacotes, quando certos pacotes ou arquivos mudam. É por causa deles que, ao atualizar o kernel, a imagem de boot é refeita sem você pedir, e que o systemd "percebe" serviços novos. E você pode escrever os seus.

Você vai aprender
  • Reconhecer os hooks na saída do pacman.
  • Onde eles ficam: /usr/share/libalpm/hooks/ e /etc/pacman.d/hooks/.
  • A sintaxe: [Trigger], [Action], PreTransaction e PostTransaction.
  • Ler os hooks reais do mkinitcpio, do systemd e do openssh.
  • Escrever três hooks seus: grub-mkconfig quando o kernel muda, listar órfãos e limpar o cache com paccache.

Hook do pacman × hook do mkinitcpio

As linhas Running build hook: [base], [systemd]… dentro do item 11 são outra coisa: os "hooks" do mkinitcpio, que decidem o que vai dentro do initramfs. O nome é o mesmo; o mecanismo, não.

O número no começo do nome não é obrigatório: serve para controlar a ordem. Os hooks de um mesmo momento rodam em ordem alfabética do nome do arquivo, então 10-… roda antes de 90-…. O 90-mkinitcpio-install tem 90 para rodar depois de quase tudo (os módulos e o firmware já precisam estar no lugar).

A anatomia de um hook

O mais simples, do systemd:

$ cat /usr/share/libalpm/hooks/30-systemd-daemon-reload-system.hook
[Trigger]
Type = Path
Operation = Install
Operation = Upgrade
Operation = Remove
Target = usr/lib/systemd/system/*

[Action]
Description = Reloading system manager configuration...
When = PostTransaction
Exec = /usr/share/libalpm/scripts/systemd-hook daemon-reload-system
$ pacman -Qo /usr/share/libalpm/hooks/30-systemd-daemon-reload-system.hook
/usr/share/libalpm/hooks/30-systemd-daemon-reload-system.hook pertence a systemd 262-1

Em português: "se a transação instalar, atualizar ou remover algum arquivo em /usr/lib/systemd/system/ (onde ficam os .service), então, no fim, rode o script que faz systemctl daemon-reload". É por isso que você não precisa rodar daemon-reload depois de instalar o nginx (veja systemctl e Serviços).

[Trigger]: quando acordar

ChaveValoresSignificado
TypePackage ou PathOlhar nomes de pacotes ou caminhos de arquivos que estão na transação
OperationInstall, Upgrade, RemoveQue tipo de mudança. Pode repetir a linha para mais de um
TargetNome ou caminho, aceita * e ?O que vigiar. Caminhos sem a barra inicial (usr/lib/…, não /usr/lib/…). Um ! na frente exclui. Pode repetir.

Um hook pode ter vários [Trigger]: basta um deles combinar para o hook rodar (uma vez só).

[Action]: o que fazer

ChaveSignificado
DescriptionO texto que aparece em (n/N) …
WhenPreTransaction (antes de mexer em qualquer arquivo) ou PostTransaction (depois de tudo). Obrigatória.
ExecO comando, com caminho absoluto. Não passa por um shell: |, && e $VAR não funcionam, a não ser com /usr/bin/bash -c "…". Obrigatória.
DependsPacote de que o comando precisa (o hook não roda se ele não estiver instalado)
NeedsTargetsManda para a entrada padrão do comando a lista do que acionou o hook (um por linha)
AbortOnFailSó em PreTransaction: se o comando falhar, cancela a transação inteira

/usr/share/libalpm/hooks/90-mkinitcpio-install.hook pertence a mkinitcpio 42.2-1

Três gatilhos: qualquer coisa que vai dentro do initramfs mudou (firmware, módulos, systemd, cryptsetup, lvm…); um kernel novo chegou; ou o próprio mkinitcpio foi atualizado. O par dele, 60-mkinitcpio-remove.hook, roda antes (When = PreTransaction) quando um kernel é removido, para apagar o initramfs correspondente enquanto o kernel ainda está lá.

Antes e depois trabalhando juntos: o openssh

$ cat /usr/share/libalpm/hooks/10-openssh-mark-sshd-for-restart.hook /usr/share/libalpm/hooks/70-openssh-restart-sshd.hook
[Trigger]
Operation = Upgrade
Type = Package
Target = openssh

[Action]
Depends = systemd
Description = Marking sshd.service for restart...
When = PreTransaction
Exec = /usr/bin/systemctl --runtime set-property sshd.service Markers=needs-restart
[Trigger]
Operation = Upgrade
Type = Package
Target = openssh

[Action]
Description = Restart a running sshd.service
When = PostTransaction
Exec = /usr/share/libalpm/scripts/systemd-hook restart sshd.service

Quando o pacote openssh é atualizado: antes, marca o sshd como "precisa reiniciar"; depois, reinicia o serviço (se estiver rodando), para o servidor SSH passar a usar o programa novo.

Escrevendo os seus

Os três exemplos abaixo foram escritos na VM em /tmp/a5/hooks/, para estudo. Não foram instalados no /etc/pacman.d/hooks/ da VM (um hook errado ali afetaria todos os outros testes); no seu Arch, a instalação é o passo final de cada um.

1. Refazer o menu do GRUB quando o kernel mudar

Um fato que pega muita gente: o pacman não roda o grub-mkconfig sozinho. Quando a VM ganhou o linux-lts, foi preciso rodar à mão para o novo kernel aparecer no menu (veja Bootloader e Kernels):

#> grub-mkconfig -o /boot/grub/grub.cfg
Gerando o arquivo de configuração do grub...
Imagem Linux encontrada: /boot/vmlinuz-linux
Imagem initrd encontrada: /boot/intel-ucode.img /boot/initramfs-linux.img
Imagem Linux encontrada: /boot/vmlinuz-linux-lts
Imagem initrd encontrada: /boot/intel-ucode.img /boot/initramfs-linux-lts.img
…
concluído

Um hook resolve:

[Trigger]
Type = Path
Operation = Install
Operation = Upgrade
Operation = Remove
Target = usr/lib/modules/*/vmlinuz

[Action]
Description = Atualizando o menu do GRUB (grub.cfg)...
When = PostTransaction
Depends = grub
Exec = /usr/bin/grub-mkconfig -o /boot/grub/grub.cfg
Target = usr/lib/modules/*/vmlinuz
Todo pacote de kernel do Arch (linux, linux-lts, linux-zen…) instala o kernel nesse caminho; é o mesmo gatilho que o mkinitcpio usa.
95-
Roda depois do 90-mkinitcpio-install, quando o initramfs novo já existe.
Depends = grub
Se um dia você trocar para o systemd-boot e remover o GRUB, o hook não roda.

Para instalar no seu sistema (ilustrativo):

sudo mkdir -p /etc/pacman.d/hooks
sudo cp 95-grub-mkconfig.hook /etc/pacman.d/hooks/

Na próxima atualização de kernel, a lista do pacman ganha a linha (n/N) Atualizando o menu do GRUB (grub.cfg)... seguida da saída do grub-mkconfig.

2. Avisar sobre órfãos depois de remover

[Trigger]
Type = Package
Operation = Remove
Target = *

[Action]
Description = Procurando pacotes órfãos...
When = PostTransaction
Exec = /usr/bin/bash -c "/usr/bin/pacman -Qdt || /usr/bin/echo '==> Nenhum órfão.'"

Target = * com Operation = Remove: qualquer remoção. Como o Exec não passa por um shell, o || só funciona dentro do bash -c. O pacman -Qdt lista os órfãos (veja Cache e Órfãos) e devolve código 1 quando não há nenhum; aí entra o echo. Dá para testar o comando sozinho, antes de instalar o hook:

$ /usr/bin/bash -c "/usr/bin/pacman -Qdt || /usr/bin/echo '==> Nenhum órfão.'"
==> Nenhum órfão.
Teste sempre o Exec primeiro

Rodar a linha do Exec no terminal (com sudo, se o comando precisar de root, porque os hooks rodam como root) é o jeito mais simples de achar erros antes que eles apareçam no meio de uma atualização.

Missão: crie a pasta ~/hooks e, dentro dela, um orfaos.hook com um [Trigger] para remoção de qualquer pacote e um [Action] que roda depois da transação o comando /usr/bin/pacman -Qdt (use printf com \n; uma configuração por linha, como no exemplo acima). Confira com cat.

3. Limpar o cache com o paccache

O cache do pacman (/var/cache/pacman/pkg) cresce para sempre. O paccache, do pacote pacman-contrib, apaga versões antigas. O pacote traz um timer semanal, mas não traz um hook:

$ pacman -Ql pacman-contrib | grep -E "paccache|hook"
pacman-contrib /usr/bin/paccache
pacman-contrib /usr/lib/systemd/system/paccache.service
pacman-contrib /usr/lib/systemd/system/paccache.timer

Quem prefere limpar a cada transação escreve o seu:

[Trigger]
Type = Package
Operation = Install
Operation = Upgrade
Operation = Remove
Target = *

[Action]
Description = Limpando o cache de pacotes (mantém as 2 últimas versões)...
When = PostTransaction
Depends = pacman-contrib
Exec = /usr/bin/paccache -rk2

O -r remove e o -k2 mantém as duas versões mais recentes de cada pacote (para você poder voltar uma versão). Teste antes com -d (dry run, "ensaio": só mostra o que apagaria):

$ paccache -dk2
==> no candidate packages found for pruning
$ echo $?
0

Na VM, cada pacote tinha uma única versão no cache, então não havia nada para apagar. Hook ou timer? O timer (sudo systemctl enable --now paccache.timer, veja Timers) roda uma vez por semana e não deixa as atualizações mais lentas; o hook mantém o cache sempre enxuto. Os dois juntos não fazem sentido.

Qual usar?

Você quer…Use
Algo que depende do que mudou na transação (kernel novo, pacote X atualizado)Hook PostTransaction
Impedir uma transação perigosa (ex.: sem espaço em /boot)Hook PreTransaction com AbortOnFail
Algo periódico, que não depende de instalar nadaUm timer do systemd
Algo que só um pacote seu precisa ao ser instaladoO script .install do PKGBUILD (veja AUR com Segurança)
Desligar um hook de pacoteUm link com o mesmo nome para /dev/null em /etc/pacman.d/hooks/

Quando não funciona

O hook não roda

Causas comuns: o arquivo não termina em .hook; está em outra pasta; o Target de um Type = Path começa com / (tem que ser usr/…); o Operation não cobre o caso (só Upgrade, e você instalou pela primeira vez); o pacote de Depends não está instalado.

Como confirmar: ls /etc/pacman.d/hooks/, pacman-conf HookDir, e releia o [Trigger] contra o que a transação fez.

O comando do hook falha

O que acontece: o pacman mostra a saída de erro do comando e segue (num PostTransaction, os pacotes já foram instalados). Só um PreTransaction com AbortOnFail cancela a transação.

Como resolver: rode a linha do Exec no terminal, como root, e corrija. Lembre: caminho absoluto (/usr/bin/…) e nada de |, &&, || fora de um bash -c.

A atualização ficou lenta

O que aconteceu: um hook com Target = * roda em toda transação. Se o comando é pesado, você sente a cada pacman -S.

Como resolver: restrinja o Target (pacotes ou caminhos específicos) ou troque o hook por um timer.

Resumo

  • Hooks são tarefas do pacman ligadas a pacotes ou caminhos que mudaram numa transação.
  • Os dos pacotes ficam em /usr/share/libalpm/hooks/; os seus, em /etc/pacman.d/hooks/.
  • [Trigger] (Type, Operation, Target sem /) e [Action] (When, Exec com caminho absoluto e sem shell).
  • PreTransaction roda antes de mexer nos arquivos; PostTransaction, depois.
  • Teste o Exec no terminal antes de instalar o hook.

Na Arch Wiki: a seção pacman § Hooks (em português: pacman (Português) § Hooks) resume o formato, e o manual completo é o alpm-hooks(5) (man 5 alpm-hooks, também em man.archlinux.org). Exemplos prontos aparecem em Pacman/Tips and tricks (como limpar o cache) e em GRUB; o mecanismo do initramfs está em mkinitcpio.
